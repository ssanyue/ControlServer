**做，且按 HudongJingling 的语义做**，但有三处**必须改**（服务版与桌面端形态不同）：

| # | HudongJingling 做法            | 服务版必须改成                            | 为什么                                               |

## 1. 参照对象的授权逻辑（拆解结果）

### 1.1 授权文件

`license.dat`：`JSON → 加 sig 字段 → Base64`。字段表：

| 字段                 | 含义                 | 备注                                  |
| ------------------ | ------------------ | ----------------------------------- |
| `v`                | 版本号                | `1`=授权文件，`2`=时间记录文件                 |
| `mc`               | 绑定机器码              | `XXXX-XXXX-XXXX-XXXX`；**通用授权生成时留空** |
| `lt`               | 类型                 | `full` / `trial` / `temp`           |
| `id`               | 签发日                | `yyyyMMdd`                          |
| `ed`               | 到期日                | `yyyyMMdd`；空 = 永久                   |
| `et`               | **精确到期时刻**         | 毫秒戳；缺失时回退 `ed` 当日 23:59:59          |
| `md`               | 最大天数               | `0` = 永久                            |
| `sn` / `vi` / `hn` | 序列号 / 厂商 ID / 客户备注 | 仅展示                                 |
| `ub`               | 通用授权标记             | `1` = 通用                            |
| `ud`               | **最迟可导入绑定时刻**      | 真实 UTC 毫秒                           |
| `bt`               | 绑定时刻               | 导入后回填                               |
| `ivt`              | **联网校对时间**         | 真实 UTC 毫秒 —— **防篡改核心锚点**            |
| `sig`              | 签名                 | HMAC-SHA256(key, JSON不含sig) 的 hex   |

> 📌 **时间存储约定**：**把北京墙钟当作 UTC 存**（`QDateTime(date, time, utc())`）。读取时也按 UTC 解析 → 直接还原北京时间显示，规避本机时区差异。服务版铁律 #4 是 `BeijingTime`（UTC+8），**语义一致，可直译**。

### 1.2 核心校验流程（`checkAuthorization`）

```
1. 读取 license.dat，验签失败/无文件 → NotAuthorized(0)
2. 机器码绑定校验：mc 必须 == 本机机器码      → 不符 → Error(3)
3. 时间回拨检测（对比 lastrun，容差 48h）      → 命中 → Error(3)
4. ★ ivt 锚点校验：ivt 必须存在，且 now + 2min >= ivt  → 否则 → Error(3)
5. 有效期判定：
   full + md=0 + ed 空             → Authorized(1)  永久
   未到期                          → Authorized(1) / Trial(4)
   已到期                          → Expired(2)
```

**第 4 步是整个防线的关键**：正式/试用授权只能由"联网导入/联网生成"两条路径产生，两条都会写入 `ivt`。手工编辑出来的 `license.dat` 即使签名合法（对称密钥场景下确实可能），也因缺 `ivt` 被拒 —— **堵死"改文件绕过在线校对"**。

### 1.3 时间记录防篡改（`time_record.dat`）

`{v:2, floor, records:[{t,s}]}`，同样签名加密。

- `floor` = **最早一次联网校准时间**（可信起点，只前移不后移）
- `records` = 每次启动的系统时间，**最多 50 条环形缓冲**
- 写入约束：新时间必须 `>= max(floor, 已有记录最大值) - 2min`
- 启动校验返回：`0`=通过 / `1`=回拨 / `2`=记录缺失（需联网校准）

### 1.4 门控分级（QML 侧，值得照抄的分级思路）

| authStatus       | 场景          | 门控行为                    |
| ---------------- | ----------- | ----------------------- |
| `0`              | 无授权文件       | **完整门控**：可「生成试用」或「导入正式」 |
| `2` + `lt=trial` | 试用过期        | 同 `0`（可再生成试用）           |
| `2` + `lt=full`  | 正式过期        | **仅导入**（不可生成试用）         |
| `3`              | 机器码不符 / 被篡改 | **仅导入**（必须导入匹配本机的新授权）   |
| `1` / `4`        | 已授权 / 试用中   | 正常进入，不弹窗                |

倒计时：无授权 60s、时间异常 15s、仅导入 60s。

### 1.5 签发工具（`AuthKeyGen`）

独立 Qt 程序，调用 `LicenseManager::generateLicense()` 静态方法。4 种类型：

```
正式授权（期限）/ 正式授权（永久）/ 通用授权（期限）/ 通用授权（永久）
```

快捷按钮：期限 `1/2/3/6/12` 个月；通用"使用截止" `1/3/7/15/30` 天；通用"到期" `30/60/90/180/365` 天。  
校验：正式必须绑机器码；**永久必须绑机器码**（不绑机器码不允许永久）；通用期限的到期必须晚于使用截止。

### 1.6 踩过的坑（照抄结论、不重蹈）

| 坑                              | 后果                                               | 服务版对策                                               |
| ------------------------------ | ------------------------------------------------ | --------------------------------------------------- |
| `_completeImport` 曾写 `ri >= 1` | **把"已过期(2)/异常(3)"也当成功** → 导入过期授权后门控关闭、直接进主界面且无提示 | 判定**白名单枚举**（只认 `Authorized` / `Trial`），禁止 `>=` 范围比较 |
| 导入不带联网时间                       | 可绕过在线校对                                          | `netVerifiedMs <= 0` **直接拒绝**                       |
| `floor` 可后移                    | 试用期可被重置                                          | `floor` 取 `min(已有, 新值)`，**只前移**                     |

## 3. 数据模型

### 3.1 授权文件（沿用字段名，便于对照）

```jsonc
{
  "v": 1,
  "mc": "A1B2-C3D4-E5F6-7890",   // 空 = 通用授权，导入时绑定
  "lt": "full",                   // full / trial / temp
  "id": "20261008",
  "ed": "20271008",               // 可空
  "et": 1809907199000,            // 精确到期；空/0 = 无
  "md": 0,
  "sn": "SN-001",
  "vi": "VENDOR-001",
  "hn": "XX展厅",
  "ub": 1,                        // 通用授权标记
  "ud": 1809907199000,            // 最迟可导入绑定
  "bt": 1791380000000,            // 绑定时刻（导入后回填）
  "ivt": 1791380000000,           // 联网校对时间 ★
  "sig": "MEUCIQD...base64url"    // ECDSA P-256 + SHA-256（替代 HMAC）
}
```

> **签名口径变更**：`sig` 从 `HMAC-SHA256(key, json) 的 hex` 改为 **`ECDSA-P256-SHA256(私钥, json) 的 base64url`**。  
> 验签时**先移除 `sig` 字段**、按**确定性字段序**重新序列化再验 —— 这是最容易翻车的一步（见 §12 陷阱）。

### 3.2 状态枚举（与参照对象一致，便于对照文档）

```csharp
public enum LicenseStatus { NotAuthorized = 0, Authorized = 1, Expired = 2, Error = 3, Trial = 4 }
```

### 3.3 解析结果

```csharp
public sealed record LicenseState(
    LicenseStatus Status,
    string Kind,              // full / trial / temp / ""
    int RemainingDays,        // -1 = 未知，99999 = 永久
    DateTimeOffset? ExpiresAt,// 北京时间墙钟
    string Info,              // 人类可读摘要
    string LastError);
```

## 4. 密钥模型（**待拍板 ①**）

| 方案                         | 防伪造                    | 实现成本                      | 密钥轮换        | 结论           |
| -------------------------- | ---------------------- | ------------------------- | ----------- | ------------ |
| **A. 沿用 HMAC 对称**          | ❌ 服务端 exe 内嵌密钥，反编译即可伪造 | 低（照抄）                     | 需重编所有客户端    | 不推荐          |
| **B. ECDSA P-256 非对称**（推荐） | ✅ 私钥只在签发工具；服务端只有公钥     | 中（.NET 内置 `ECDsa`，无第三方依赖） | 公钥重编；可支持多公钥 | **推荐**       |
| C. RSA-2048                | ✅                      | 中                         | 同上          | 备选（签名长、性能差些） |

**推荐 B**。理由：

1. 服务版 exe 会交付到客户机房，**能被反编译**。对称密钥内嵌等于把签发权一并交出去。
2. `.NET 8` 内置 `ECDsa.Create(ECCurve.NamedCurves.nistP256)`，**零新增依赖**。
3. `M3-RBAC方案.md §8` 已把"非对称签名"记为待办 —— 本方案正好闭环。

**公钥存放**（**待拍板 ①-b**）：

| 方案                                                | 防替换                 | 换密钥成本  | 结论         |
| ------------------------------------------------- | ------------------- | ------ | ---------- |
| **编译期内嵌**（`Core/Licensing/VendorPublicKey.cs` 常量） | ✅ 最高                | 需重编服务端 | **推荐**     |
| 配置项 `Server:License:PublicKey`                    | ❌ 可被替换成自己的公钥 + 自签授权 | 改配置即可  | 不推荐（安全性归零） |

> ⚠️ **代价必须说清**：内嵌 = 换密钥要重编服务端并重新交付。这是**用"运维便利"换"防伪"**，我认为值得，但请你确认。

## 5. 闸门范围（**待拍板 ② —— 本方案最关键的一项**）

服务版的"中控价值"在于**动作执行 / 对接码监听 / 定时触发**。授权闸门应该卡在这里，而不是"一律 403"。

### 5.1 建议的闸门矩阵

| 能力                               | 未授权 / 已过期                    | 理由                |
| -------------------------------- | ---------------------------- | ----------------- |
| 登录 / 改密 / `/api/auth/me`         | ✅ 放行                         | 不放行就连"导入授权"都做不了   |
| 看板 / 状态 / 日志（只读）                 | ✅ 放行                         | 让现场能看到"为什么不能用"    |
| **导入授权 / 查看机器码**                 | ✅ 放行（AdminOnly）              | 这是**唯一的自救通道**，必须通 |
| 用户管理 / 端口热切换                     | ✅ 放行                         | 运维不该被授权卡住         |
| **执行动作**（`/api/actions/execute`） | ⛔ **403 `license-required`** | 核心价值点             |
| **对接码监听（UDP）**                   | ⛔ **后台自动停摆**                 | 否则绕过 Web 直接靠对接码触发 |
| **定时触发**                         | ⛔ **后台自动停摆**                 | 同上                |
| 配置写入                             | ⚠️ 放行但前端提示                   | 现场可能需要预先配好，待授权后即用 |

> **与强制改密闸门的关系**：两者**独立**、语义不同 —— 改密闸门是**账号级**（这个人必须改密），授权闸门是**设备级**（这台机器没授权）。都拦 `/api`，但白名单不同。

### 5.2 三态开关（**待拍板 ②-b**）

`Server:License:Enforcement`：

| 值          | 行为                  | 适用                 |
| ---------- | ------------------- | ------------------ |
| `Off`      | 完全不校验，仅记录授权状态       | 内部开发 / 不需要授权的场景    |
| **`Warn`** | 校验 + 前端横幅警告 + 后台不停摆 | **默认值**（见 §8 迁移兼容） |
| `Enforce`  | 按 §5.1 矩阵拦截         | 正式交付               |

### 5.3 白名单（`Enforce` 下仍放行）

`/api/auth/*`、`/api/license/*`、`/healthz`、`/readyz`、`/hubs/events`、静态资源。

> 📌 与改密闸门一样**只闸 `/api`**：探活端点被闸会让服务被运维判死；SignalR 被闸会让"授权页"实时日志断掉。

## 6. 时间口径与防篡改

### 6.1 复用既有设施（不新增授时通道）

- **当前时间**：一律 `CorrectedTimeProvider.Instance.GetUtcNow()`（= 系统钟 + NTP 校正量）
- **联网校对时间 `ivt`**：取 `BeijingTime.ClockOffset` 最近一次成功同步的时刻；无同步记录则视为 `0`

### 6.2 校验规则（直译 §1.2 第 4 步）

```
ivt <= 0                          → Error("缺少联网校对记录，可能被篡改")
now + 容差(2min) < ivt             → Error("系统时间早于授权联网校对时间")
```

### 6.3 回拨检测（**待拍板 ③ —— 做多少**）

| 方案          | 内容                                      | 成本 | 结论        |
| ----------- | --------------------------------------- | -- | --------- |
| **精简版（推荐）** | 保留 `ivt` 锚点 + 启动时校验 `now >= ivt - 2min` | 低  | **推荐**    |
| 完整版         | 移植 `time_record.dat` 环形缓冲（50 条 + floor） | 中  | 可选        |
| 不做          | 只按 `CorrectedTimeProvider` 判到期          | 无  | 依赖 NTP 可信 |

**建议精简版**。理由：服务版是服务器，系统时间由运维控制，且有**审计日志**可追溯；50 条环形缓冲在服务端属于过度设计。`ivt` 锚点已能挡住"改系统时间延长授权"这条主要攻击路径。

> ⚠️ **必须如实说明的弱点**：试用记录存在**数据目录**里。删掉数据目录 = 试用重置。参照对象用 `time_record.dat`（exe 同目录）+ `floor` 锚点来缓解，但**本质上单机授权都拦不住"删干净重装"**。若要更强，需引入**服务端/云端激活**（不在本轮范围）。

## 7. 与 RBAC 的关系（**待拍板 ④**）

| 做法                          | 结论                                                         |
| --------------------------- | ---------------------------------------------------------- |
| 保留"超级密码"（授权文件里存 hash 作万能钥匙） | ❌ **取消**。已有 RBAC 三角色，再塞一个绕过角色判定的密码是安全反模式；且它与"谁改了密码"的审计链路冲突 |
| 授权管理端点权限                    | `AdminOnly`（导入授权 = 改变设备级凭证，系统级操作）                          |
| 授权状态可见性                     | 所有已登录角色可见（只读）；否则现场看到"按钮点了没反应"却不知为何                         |

## 8. 迁移兼容（**待拍板 ⑤ —— 关系到现有部署不被锁死**）

**现状**：已有实例正在跑（含用户本机 + 新电脑），**都没有授权文件**。若闸门默认 `Enforce`，升级即全线 403。

**建议**：

1. `Server:License:Enforcement` **默认 `Warn`** —— 升级后照常可用，前端显示"未授权"横幅。
2. **首次启动自动生成试用授权**（照抄参照对象的启动流程），默认 **30 天**（`Server:License:TrialDays`，参照对象是 3 天；展厅项目试装期更长）。生成成功后 `Warn` 自动升为 `Enforce`。
3. 提供 `POST /api/license/trial` 供管理员手动重新生成试用（仅在 `NotAuthorized` / 试用过期时允许，与参照对象 §1.4 分级一致）。

> 这样：**全新安装 → 自动 30 天试用 → 装好就能跑**（与安装包验收标准一致）；**到期 → 拦核心功能 → 引导导入正式授权**。

**试用天数**（**待拍板 ⑤-b**）：`3 天`（照抄参照对象） / **`30 天`（推荐）** / `90 天`。

## 9. API 契约

| 端点                              | 权限          | 说明                                                                                    |
| ------------------------------- | ----------- | ------------------------------------------------------------------------------------- |
| `GET /api/license`              | 所有已登录       | 当前状态：`status / kind / remainingDays / expiresAt / info / machineCode / enforcement`   |
| `GET /api/license/machine-code` | `AdminOnly` | 本机机器码（供复制给销售方）                                                                        |
| `GET /api/license/request`      | `AdminOnly` | 生成"授权申请文本"（机器码 + 申请时间），参照对象 §1 `generateActivationRequest`                            |
| `POST /api/license/import`      | `AdminOnly` | Body: `{ licenseText }`（Base64 文本）。**返回 `LicenseMutationResult`（含服务端全量状态 + 未授权时的原因）** |
| `POST /api/license/trial`       | `AdminOnly` | 生成试用；服务端自行取联网时间，前端不传                                                                  |
| `DELETE /api/license`           | `AdminOnly` | 移除授权（回到 `NotAuthorized`）                                                              |

**状态码映射**（沿用 RBAC 的约定）：

| 场景                                   | 码                               |
| ------------------------------------ | ------------------------------- |
| 文本为空 / Base64 解不开 / 验签失败             | `400` "授权文件格式无效或已被篡改"           |
| 机器码不符                                | `400`（附"文件绑定 X，本机 Y"）           |
| 已过期                                  | `400` "该授权已过期"                  |

**⚠️ 陷阱清单（写代码前必读）**

1. **验签前必须先移除 `sig`**，且序列化必须**确定性**（字段序固定、无缩进）。JSON 字段顺序在不同实现下会变 —— 参照对象用 `QJsonObject`（内部有序）侥幸稳定；.NET 的 `JsonSerializer` 默认按声明序，**要显式锁定**，否则"自己签的自己验不过"。

4. **`floor`/`bt` 只前移不后移**（若采纳完整版回拨检测）。
5. **闸门只拦 `/api`**，白名单见 §5.3。
6. **授权文件不参与配置导入导出**（与指令库同理：授权是设备级凭证，跟着机器走，不该被配置备份带跑）。
7. **别把公钥做成配置项**（§4 表格已说明：等于安全性归零）。
8. **`Enforcement=Warn` 时后台任务不停摆** —— 否则升级当天现场定时任务全停。

### 17.1 S3 授权闸门（已完成）

| 落点 | 说明 |
| --- | --- |
| `src/ControlServer.Server/Security/LicenseGate.cs` | 静态路由分类表：按「HTTP 方法 + 路由模板」判定 `Gated` / `Allowed` |
| `src/ControlServer.Server/Services/LicenseGateState.cs` | 运行时拦截状态 + `BlockedChanged` 事件（后台任务据此起停） |
| `src/ControlServer.Server/Program.cs` | 闸门中间件（排在 `UseAuthorization()` **之后**）、DI 接线、`/readyz` 调整 |
| `tests/.../LicenseGateTests.cs` | 32 个用例：分类表 / 反射守门 / HTTP 矩阵 / 后台停摆 |

**实际被拦的只有 4 个端点**：`POST api/actions/execute`、`POST api/timers/{refId}/fire`、
`POST api/test/udp`、`POST api/test/loopback`。登录 / 只读 / **导入授权** / 用户管理 / 配置写入全部放行 ——
拦掉"导入授权"会变成"没授权 → 不能导入授权"的死锁。

**四个非显然的决策**

1. **按「方法 + 路由模板」分类，而不是路径前缀**：`/api/actions` 下 `execute` 要拦、`preview` 要放；
   `/api/timers` 下 `GET` 要放、`{refId}/fire` 要拦。前缀匹配会把这两组一锅端。
2. **中间件排在 `UseAuthorization()` 之后**：未登录先得 401、角色不足先得 RBAC 403，
   而不是被误报成"没授权"。安全性不受影响 —— 被拦的端点全都要求 `CanOperate`。
3. **后台停摆走两条不同路径**：对接码监听用**事件**起停（UDP 对象天然事件驱动）；
   定时触发用**属性**每拍自查（循环本来就每秒跑）。两者在授权恢复后都**不需要重启服务**。
4. **`/readyz` 把"授权停摆"算作 ready**，另加 `licenseBlocked` 字段。停摆是策略决定而非故障；
   若报 not-ready，容器探针会陷入「重启 → 仍停摆 → 再重启」的死循环。

**过程中揪出的一个真 Bug**：反射守门用例抓到 `GET/DELETE api/config/images/{fileName}` 与
`POST api/timers/{refId}/fire` "未归类"。根因是 `RoutePattern.RawText` **保留声明时的大小写**，
而查表键统一转了小写。**更阴的是同批的 `Value_endpoints_are_gated` 没抓到** ——
fail-closed 让"未归类"也返回 `Gated`，"断言结果是拦"自我欺骗地通过了。
现在两条 `[Theory]` 都先断言 `IsClassified` 再断言结果。

**CLI 形态**

```
LicenseTool new-key [--out 私钥] [--public-out 公钥] [--force]
LicenseTool gen     --type full|trial|temp (--bind <机器码> | --universal)
                    [--expire "2027-10-08 23:59:59" | --days 30] [--deadline ...]
                    [--sn ...] [--vendor ...] [--customer ...]
                    [--key 私钥] [--anchor <北京时间>] [--offline] [--out <文件>] [--force]
LicenseTool inspect <文件.lic> [--key 公钥]
```

**退出码**：`0` 成功 / `1` 用法有误或文件不存在 / `2` 授权不可用或规则不允许 / `3` 未预期错误。

**关键决策**

1. **签发规则放 Core，不放工具里**。这些规则与 `LicenseImportRules`、`LicenseEvaluator` 是一套东西的两面：
   签发侧防"造出收不下的文件"，导入侧防"收下不该收的文件"。放在一起才能共用同一个评估器，
   不可能出现"签发说没问题、导入说有毛病"的分裂。
2. **两道自检，各挡一类失败**：① `SignWithSelfCheck` 挡"签名与载荷不自洽"（代码缺陷）；
   ② `LicenseImportRules.Check` 干跑挡"服务端不愿收"（如签了一份到期时间已经过去的授权）。缺一不可。
3. **自检公钥从私钥现推，不让调用方传公钥文件**。否则自检可能拿的是磁盘上那份已经过期的
   `vendor-public.pem`，结果是"签得没错却报失败"，而真正的错因（公钥与私钥不配对）被完全隐藏。
4. **`new-key` 默认拒绝覆盖私钥**。覆盖不会"更新"任何东西，只会让此前签发的全部授权失效
   （服务端内嵌的还是旧公钥）。必须显式 `--force`。
5. **`--days 0` 在 CLI 层就拦下**。下游把"未指定有效期"理解为**永久** ——
   一个 `0` 换来一份永不过期的授权，属于最不能静默发生的错误。
6. **`gen` 先校验参数、再联网取时**。NTP 最坏要等十几秒；若反过来，
   "网络不通 + 参数也写错"时用户会先折腾网络，修好重跑才发现真正的错在参数上。
7. **本机钟慢于网络时间时，用网络时间当签发时刻**。与服务器的"应用内校正"同口径，
   否则刚签出的文件会被自己的规则判成"时间被回拨"。
8. **`ivt` 必填，取不到网络时间就明确失败**（`--offline` / `--anchor` 是显式降级）。
   若随手用本机钟填 `ivt`，这个字段就从"可信锚点"退化成"又一个可以被改的数"，
   整条防线只剩签名一层。
9. **参数校验与"现在几点"分离**（`GenerateOptions` 中间形态），使两件事各自干净。
10. **输出只用 ASCII 标记**（`[ok]` / `[warn]` / `[fail]` / `[error]`）：签发人常在 `cmd.exe`（CP936）
    里跑，`✓`/`✗`/`⚠` 会变成 `?`；标签列宽按**显示宽度**补空格（CJK 算 2 列），否则中文标签对不齐。

**顺带加固**：`.gitignore` 新增 `*.pem` / `*.lic` / `*.key` ——
私钥入库等于公开签发权，授权文件属客户数据。

**顺带修掉一个真 Bug（跨用例环境变量泄漏）**：全量跑出现 2 个失败
（`TimersApiTests` 期望 200/404 实得 403）。根因是 `ControlServerFactory` 用**进程级环境变量**注入配置，
却对 `Server__License__Enforcement` 采取"传 null 就跳过赋值" —— 闸门矩阵用例把它设成 `Enforce` 后，
该值**永久留在进程环境里**，此后每个宿主都被判成"Enforce + 无授权"，
于是所有要求动作执行的用例集体 403。症状是"换一次运行顺序就换一批红的"，与授权毫无关系。
修法：该键**无条件赋值**（null = 删除变量），并加守门用例
`Enforcement_setting_does_not_leak_from_one_host_to_the_next`。
旁证：修掉后全量集成测试耗时从 **12 分 11 秒降到 2 分 44 秒**
（泄漏的 `Enforce` 让每个宿主都走了一遍"闸门拦截 + 授权刷新"，包括真的去试 NTP）。

**为什么顶栏徽章是个按钮**：未授权时它是**唯一能解决问题的地方**的入口。
现场看到"按钮点了没反应"时，第一反应就是点那个红徽章。

**为什么用 `provide`/`inject` 而不是逐层传 prop**

需要知道"闸门是否停摆"的地方有两处：控制台（App 自己）与编辑页里的「试运行」
（`ActionEditor`，位于 App → EditPanel → ButtonForm → ActionListEditor → ActionEditor 的第 4 层，
子按钮那条要 5 层）。为一个只读布尔量把 `licenseBlocked` 穿过四个与授权毫无关系的组件，
是典型的 prop 钻孔 —— 每个中间组件都被迫认识一个自己根本不用的概念。
`licenseGate.ts` 里同时给出"默认 `false`"的回退，组件被单独挂载也不会炸。

**集合瓦片不置灰，只有按钮瓦片置灰**

集合瓦片点开的是子按钮弹层（只读导航），执行发生在里面的子按钮上。
把集合也禁掉等于"没授权连看都看不了"，而看板本来就是特意放行给现场看"为什么不能用"的。

**置灰的手法与「发送中」刻意区分开**

`.tile.busy`（发送中）用 `saturate(0.6)` + `cursor: progress`；
`.tile.blocked`（未授权）用 `opacity: .45` + `grayscale(.7)` + `cursor: not-allowed`。
两者语义完全不同，若共用一个滤镜，用户会把"没授权"误读成"正在发送"。

**前台只做"提前禁用 + 说明"，判定始终在服务端**（沿用 RBAC §5 的原则）。
点击被拦下的瓦片时走 `blockedByLicense()` 直接给出统一提示，而不是发一个注定 403 的请求。

**过程中揪出并修掉一个真 Bug（试用天数多送一天）**

现象：首次生成 30 天试用后，徽章显示 **「试用 31 天」**。

根因：`GenerateTrialAsync` 里到期日按 **`起算日 + TrialDays`** 算，
而 `ed` 的语义是**当日末刻才到期**（`LicenseEvaluator.ResolveExpiry`，客户直觉里
"11 月 7 日到期"意味着 7 号一整天都还能用）。两条规则叠加：10-09 起算的 30 天试用
到期日落在 11-08，而 10-09 至 11-08 **含首含尾正好 31 个自然日**；
顺带一个更明显的后果 —— **1 天试用会跨到第二天**。

修法：到期日改为 `起算日 + (TrialDays - 1)`，即"N 天试用 = 含起算日在内的 N 个自然日"。
配套守门用例 `Trial_grant_covers_exactly_the_configured_number_of_days`，
断言只**用记录里的两个日期做差**、不掺入"现在是几点"，因此在 23:59 与 00:01 跑结论一致。

**为什么这个场景必须抬到 `Enforce` 并关掉自动试用**

默认档位是 `Warn`（升级不锁死），而首启会自动生成 30 天试用 —— 两者叠加的结果是

**为什么必须真发 UDP，而不只看 `/readyz` 的 `listener` 字段**

`listener=false` 只是"监听服务自称没跑"。真正要证明的是
**"绕开 Web 界面直接往对接码端口发码，也触发不了动作"** —— 这正是当初坚持
要在监听层再设一道闸门、而不是只靠 HTTP 中间件的理由（中间件管不着 UDP）。

为了不让这条断言沦为"配置本来就没写对接码，所以当然没反应"，脚本**先 PUT 一份配置**
（一个带对接码的按钮，动作指向 sink 端口），再发码。这样"收到 / 没收到"才有区分力；
顺带也验证了"未授权时配置写入放行"。

### 17.7 签发自检曾"谎报"（已修 ✅，2026-10-10）

> ❗ **本节的"默认私钥探测"部分已被 §17.9 取代**：那条修复（`LocalPaths.FindDefaultPrivateKey`
> 按指纹筛）所在的 `LocalPaths.cs` 已删除 —— 私钥不再来自文件，也就不存在"挑错文件"这条路。
> 但**根因分析本身仍然有效**，是 §17.9 改造的直接动因。

**现场现象**：用图形界面签发了一份授权，界面报告**两道自检全绿**（"密码学验签：通过"、
"服务端导入规则：通过（服务端会收下这份文件）"），于是把 `.lic` 拿去服务端导入 ——
**HTTP 400 `signatureinvalid`「授权文件签名无效或已被篡改，无法导入。」**

**根因（两层，缺一不可）**：

1. **自检结构上覆盖不到"公钥是不是厂商内嵌的那把"**。
   `LicenseIssuer.DryRunImport` 里 `signatureValid` 传的是 `true`（文档就是本进程刚签的、密码学自洽
   —— 那道检查在 `LicenseSigner.SignWithSelfCheck` 里），`localMachineCode` 传的是文档自己的 `mc`。
   而服务端只认**它自己内嵌**的公钥 ⇒ 这类文件到现场必被拒，自检却永远报通过。
2. **GUI 默认私钥探测会静默改用非厂商私钥**。
   `LocalPaths.FindDefaultPrivateKey()` 原按"文件存不存在"挑，候选①是 **exe 同目录**；
   而「生成密钥对」页的默认输出位置**恰好就是 exe 同目录** ⇒ 用户一旦生成过一对新密钥，
   **下次启动**就会静默选中那把新私钥，界面上完全看不出换了钥匙。
   实际发生的就是这条：用户 21:02 启动 GUI → 21:10 生成密钥对（落在 `dist\license-tool-gui\`）
   → 21:12 用它签发 → 导入失败。

**复现**（`.tools/lic-repro/repro.py`，起真服务端、走 HTTP 接口）：

| 场景 | 签发 | 导入 |
| --- | --- | --- |
| A 厂商私钥 + 正确机器码 | ok | **HTTP 200** 授权导入成功 |
| B 新生成私钥 | 旧版报"服务端会收下这份文件" | **HTTP 400 `signatureinvalid`** |
| C 厂商私钥 + 别台机器码 | ok | HTTP 400 `machinemismatch` |
| D 篡改授权文本 | — | HTTP 400 `malformed` |

B 就是事故本身：**签发说没问题，导入说签名无效**。

**修复**：

1. **Core —— 把"服务端认不认"变成签发结果的一部分**
   `LicenseIssuanceResult` 新增 `MatchesVendorPublicKey`（= `PublicKeyFingerprint` 与
   `VendorPublicKey.Fingerprint` 的比对）。这是签发侧唯一能判定"服务端收不收"的信号。
   另公开 `LicenseSigner.DescribeKeyPair(privateKeyPem)`（从私钥现推公钥指纹），
   供界面**在选定私钥的那一刻**就比对。
2. **CLI / GUI —— 报告与横幅如实交代**
   自检段第三条：一致 → `[ok] 签名公钥：与服务端内嵌公钥一致 —— 服务端会收下这份文件`；
   不一致 → `[error] 签名公钥与服务端内嵌公钥不一致 —— 这份文件服务端会判「签名无效」，无法导入！`
   并给出两条处置路径（拿错私钥 / 确要换密钥须先替换 `VendorPublicKey.cs` 并重编交付）。
   **GUI 横幅升级为 Error 级**：文件是签出来了，但用错钥匙时它到现场一定被拒 ——
   那比"签发失败"更坏（失败至少不会把文件发出去）。
3. **GUI —— 私钥预检**：签发页私钥框下新增一行，选定/输入私钥后**立即**显示
   "该私钥对应公钥指纹 XXXX"并与服务端内嵌公钥比对（一致=绿、不一致=红并说明后果）。
   误操作在点「签发」之前就可见。
4. **GUI —— 默认私钥按指纹选优**：`FindDefaultPrivateKey()` 改为
   **先按"指纹是否等于服务端内嵌公钥"筛，再按"存不存在"筛**。只要厂商私钥还在任一候选位置，
   选中的永远是对的；都不匹配时才退回原行为（并交给预检去提醒）。

**教训（写给下一个改授权的人）**：
- **"签名自洽"与"服务端认不认"是两件事**。自检里凡把某个输入**写死为期望值**
  （这里是 `signatureValid: true`），就等于宣布"这类失败我不管" —— 必须在注释**和用户可见的输出**
  里把这条缺口交代清楚，否则它就是在谎报。
- 工具的**默认值**与另一个功能的**默认输出位置**撞在一起时，会制造**必然的误操作**：
  「生成密钥对」默认写到 exe 同目录 × 「签发」默认从 exe 同目录读 = 生成即污染。
- ⚠️ 发布脚本 `build-license-tool-gui.ps1` 会 `Remove-Item -Recurse` **清空输出目录**。
  把私钥放在 `dist\` 下，重新发布时会被**一并删掉** —— 厂商私钥应放在
  `.tools/license-keys/`（或交付物之外的自有目录），不要放交付目录。

### 17.8 授权逻辑核查 + 操作手册（2026-10-10）

用户要求交代两件事：**"签发器不校验机器码是否目标机器的"这个缺口的后果**，以及**完整的授权操作方法**。

**新增核查脚本** `.tools/lic-repro/check-license-logic.py`（起真服务端 + 真签发工具，走 HTTP；
报告落 `.tools/lic-repro/logic-report.txt`）。**新增文档 `docs/授权操作手册.md`**。

**实测结论（全部实跑）**：

| 项 | 结论 |
|---|---|
| 缺口 ① —— 签发器能否发现"机器码不是目标机器的" | **发现不了**。用厂商私钥 + 错误机器码 `DEAD-BEEF-DEAD-BEEF` 签发：退出码 **0**，工具全绿（含"签名公钥与服务端内嵌公钥一致 —— 服务端会收下这份文件"） |
| 缺口 ② —— 后果 | **白跑一趟，不是安全漏洞**。服务端导入该文件 → **HTTP 400 `machinemismatch`**。服务端才是判定权威；缺口只影响"厂商侧自检"。放大因素：机器码是 SHA256 前 16 位、**无校验位**，抄错一位照样签得出去且不报警 |
| 要求 (1) 首次试用 + 必须联网校时 | ⚠️ **部分成立**。首启自动 30 天试用 ✅，本次起点来源实测 = `ntp` ✅；但 `RequireNetworkTime` **默认 false** ⇒ 取不到网络时间会退回本机钟并照样放行。要强制须设 `Server:License:RequireNetworkTime=true` |
| 要求 (2a) 试用结束不得再试 | ❌ **不成立（新发现真 bug，未修）**。见下 |
| 要求 (2b) 重装也不行 | ✅ **成立**。`uninstall-service.ps1` **刻意保留** `%ProgramData%\ControlServer`，试用记录随之保留；自动试用只在"记录不存在"时触发 |
| 要求 (3) 改系统时间不得影响 | ⚠️ **视部署而定**。判定走 `CorrectedTimeProvider`（系统钟 + NTP 偏移）：能上网 ⇒ 改钟会在下次校准（≤30 min）被抵回；**离线 / `AutoSync=false` ⇒ `ClockOffset` 恒 0**，判定完全等于系统钟 ⇒ 回调即可延长。见 `REF-M3-授权.md` 陷阱 21 |
| 移除授权是否重置试用 | ✅ 不重置（再证，与既有设计一致） |

**新增缺陷（待修）—— 试用可"无限续杯"**：

`LicenseService.GenerateTrialAsync` 的守卫写成

```csharp
if (existingTrial is not null && _state.Status == LicenseStatus.Trial) { return ...trial-active...; }
```

**只判"试用是否仍在有效期内"**。试用**过期后** `Status == Expired` ⇒ 守卫落空 ⇒
直接写一份新记录。实测：把 `license.trial.json` 改为已过期 → 状态 `Expired` →
再点「生成 30 天试用」→ **HTTP 200，又发一份新的 30 天**（前端 `v-if="!d.isUsable"`，过期时按钮正好可见）。

这与两处自述**自相矛盾**（本类注释"试用仍在有效期内时不允许重刷 —— 否则'重新生成'就成了
永久免费的按钮"；前端 tooltip"仅在既无授权、也无有效试用时可用"）⇒ **是 bug 不是设计**。

修法（一处判定）：判据从"试用是否仍有效"改为"**试用记录是否存在**" ——
与 `EffectiveEnforcement` 同口径。守门用例待补：
`Trial_cannot_be_regenerated_after_it_expires`（预置已过期记录 → `POST /api/license/trial` → 期望 409）。

**环境坑（新增）**：本机可能跑着用户的实例，单实例守卫用**全局互斥量**
`Local\ControlServer.Server.SingleInstance`，**不区分端口/数据目录** ⇒ 测试实例会被直接劝退。
**不必杀用户进程**：加 `--Server:Startup:SingleInstance=false` + 独立 `DataDir` + 独立端口即可共存。

"使用截止必须早于授权到期时间"拒签 —— 这是设计，界面上没有复制这两条规则（多写一份早晚会跟 Core 打架），
预览层只判"是不是一个时刻、离现在还有多久"。

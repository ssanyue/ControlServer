# M6.4 升级 / 回滚

> 交付物：一条**可执行的**回滚路径 + 一份真机演练数据 + 两个新工具（`--dbinfo`、`upgrade/rollback` 脚本）。
> 上游依赖：`docs/M6.1`（备份）。**没有备份就没有回滚**，这两块必须一起用。
> 演练脚本：`deploy/upgrade/rehearse-upgrade.py`（数据链路，见 §2 / §3）＋ `deploy/upgrade/rehearse-scripts.ps1`（脚本逻辑，`-ProcessMode` 真跑，见 §7.5）。

---

## 0. 一句话结论

**升级是"覆盖安装 + 数据库自动迁移"，回滚是"卸新版 → 恢复升级前备份 → 装旧版" —— 中间没有第三条路。**
本轮在真实现场形态的库上把这两条路都走了一遍：**升级后 9 项数据一项不少，回滚后 10 项快照与升级前完全一致**，
代价是**回滚会丢掉"升级之后、回滚之前"产生的所有数据**（这是设计如此，不是缺陷）。

---

## 1. 为什么回滚不能"只把 exe 换回旧版"

EF 的迁移**只向前，不回退**。旧版程序读一个已经被新版升过结构的库，会遇到：

| 情况 | 后果 |
|---|---|
| 新版加了表 | 旧版不认识，通常无害，但它写回配置时可能丢掉那些表里的关系 |
| 新版加了列（NOT NULL） | 旧版 INSERT 不带这一列 ⇒ **运行期报错** |
| 新版改了列名（本仓真发生过：`IsRevoked` → `IsBlocked`） | 旧版的 SQL 直接查不到列 ⇒ **启动即崩** |
| `__EFMigrationsHistory` 里多了一条旧版没有的记录 | 旧版不会回退它，只是"看见一条不认识的记录"，行为未定 |

所以正确的回滚是**两件事一起做**：

```
停服 → 用升级前的备份把数据退回那个版本该有的形状 → 把程序换成那个版本
```

这也是为什么 `deploy/upgrade/upgrade.ps1` 的第 2 步是**强制备份**，并且**备份失败就中止升级**：
不是"顺手备一下"，是"没有它就没有回滚"。

## 2. 升级：真机演练做了什么

演练脚本 `deploy/upgrade/rehearse-upgrade.py` 不是拿空库跑的。它的做法是：

1. 把**现场数据目录整份复制**一份（`C:\ProgramData\ControlServer`，5 MB 库 + 1026.9 MB 文件仓库）；
2. 把这份副本**往回倒一版**：撤掉最后一条迁移（`M4_12_AgentBlock`，一次纯粹的列重命名
   `IsBlocked` → `IsRevoked`），连同它在 `__EFMigrationsHistory` 里的记录一起删；
3. 此时它就是一个**货真价实的"上一版现场库"**（12 条迁移，状态列叫 `IsRevoked`）；
4. 然后启动新程序，让它自己 `Migrate()` 把库升上来。

> **为什么不用空库**：空库上跑迁移证明不了任何事。迁移在"5 MB、13 条迁移历史、3 台真实 Agent、
> 4787 行遥测、1 GB 文件仓库"的库上和在空库上，风险完全不同。

### 2.1 实测数字

| 项 | 值 |
|---|---|
| 升级前后**数据**（9 项：用户 / 配置文档+版本 / 审计 / Agent 台数 / Agent 业务摘要 / 遥测行数 / 文件仓库摘要 / license 哈希 / 迁移条数） | **全部一致** |
| 结构变化 | 状态列 `IsRevoked` → `IsBlocked`；迁移历史 **12 → 13** |
| 服务启动 → `/healthz` 200 | **3.1 – 4.4 s**（多次运行） |
| 日志「启动中 → 数据库就绪」 | **1.2 – 1.5 s** |
| 升级前跑的版本 | `0.1.0+build.20261017-2240`（构建标识，见 §5） |

**「数据库就绪」那 1.2–1.5 s 的口径**：它包含 `Migrate()` + `PRAGMA journal_mode=WAL` + 种子账号检查 +
清理历史遗留的"必须先改密"标记，**不是纯 EF 迁移的时间**。要单量 Migrate 得改代码，本轮没做。

### 2.2 升级窗口

把 §2.1 和 M6.3 的断线数字接起来，一次现场升级的"用户感知不可用"大约是：

```
停服 → 备份（1 GB 现场约 9–10 s）→ 装新版（Inno 静默安装，含注册服务与自检）
     → 起服 ≈ 4 s → 客户端最坏 30 s 察觉到断线 → 30 s 内全部回位
```

⇒ **升级期间屏幕上"按了没反应"大约 1–2 分钟**，具体取决于备份体积与安装包大小。
**别在演出中升级**（这条在 M6.3 报告 §5 已经量过：停服后客户端最坏 30 s 才察觉，中心起来后 20 s 内 100 台全回）。

## 3. 回滚：真机演练做了什么

在 §2 升级完成、并且**往库里写了一条"升级之后才有的"审计记录**之后：

```
停服 → --restore 升级前备份 --force → 起服
```

### 3.1 实测数字

| 项 | 值 |
|---|---|
| 恢复耗时 | **7.8 – 12.0 s**（6 个文件 / 1026.9 MB） |
| 回滚后 10 项快照 vs 升级前 | **完全一致**（含 `IsBlocked` 退回 `IsRevoked`、迁移历史 13 退回 12） |
| 升级后写入的那 1 条审计 | **消失了**（这就是代价，见 §4） |
| 回滚后能不能起 | 能，**3.76 – 4.14 s** 到 `/healthz` 200 |

### 3.2 恢复之前必须停服的证据

`--restore` **自己不检查服务是否在跑** —— 它只要求 `--force` 这个覆盖确认开关。
服务在跑的时候恢复，内存里的旧数据会在恢复之后写回去，症状是"恢复成功但数据还是旧的"。
所以 `rollback.ps1` / `rollback.sh` 的第一件事是停服 + 确认进程真的退出（端口不再接受连接），
不是"顺手 sc stop 一下"。

## 4. 回滚的代价（必须让运维知道）

**备份只包含升级前那一刻的状态，恢复就是回到那一刻。**

```
升级之后、回滚之前产生的所有数据都会没有：
    配置改动、审计记录、遥测明细、上传的文件、新注册的 Agent
```

§3.1 里那条"消失的审计记录"就是这个代价的实测样本。

⇒ 因此升级手册里必须写明：**升级后如果有业务改动，回滚前先单独导一份当前数据**（或至少导出配置），
否则"退回去"等于"这几天的改动白做"。

## 5. 版本可辨识（这一块的前置修复）

在此之前，**升级完和回滚完，日志里那一行完全一样**，无法证明动作生效：

| 问题 | 原状 |
|---|---|
| 程序集版本 | `Directory.Build.props` 写死 `<Version>0.1.0</Version>`，从不递增 |
| 安装包版本 | `ControlServer.iss` 默认 `1.0.0` —— 与程序集**对不上**（两处各自写死） |
| 构建脚本 | `build-installer.ps1` 默认又一个 `1.0.0`（第三处） |
| 启动自述 | 只打「════ 中控服务版 启动中 ════」，**没有版本号** |
| `ResolveVersion()` | 主动把 `+abc123` 这类构建标识**剥掉** |

**改成**：

1. **版本号只留一处真源**：`Directory.Build.props` 的 `<Version>`。`build-installer.ps1` 从这个文件读，
   `.iss` 的默认值改成 `0.1.0` 并注明"别在这里写死"。
2. **构建标识**：构建脚本按时间生成 `build.yyyyMMdd-HHmm`，通过 `-p:SourceRevisionId=...` 注入
   （SDK 会自动拼成 `InformationalVersion = 0.1.0+build.20261017-2240`）。
3. **启动自述加一行**：
   ```
   2026-10-17 22:31:22.057 +08:00 [INF] 程序版本：0.1.0+build.20261017-2240
   ```
   没注入构建标识时明确写 `0.1.0(未注入构建标识)`，不伪装成正常。
4. **安装包落一个 `dist/installer/BUILD-STAMP.txt`**：安装包文件名只有三段版本号（Inno 的
   `VersionInfoVersion` 必须是数字点，塞不进 `+build.xxx`），两次构建会重名；这个文件就是
   "手里这个 setup.exe 是哪一次构建"的凭证。

> ⚠️ 不用程序集文件的 `LastWriteTime` 兜底：解压/复制会改它，那会造出"看起来有标识但其实是拷贝时间"的假证据。

## 6. 数据目录权限（审计清单 #40，真机验证）

审计清单把这一条挂成"只能在真机装一遍才能验证"。本轮在 `C:\ProgramData` 下做了实测（用测试目录，没动现场数据）。

### 6.1 默认继承下来的是什么（实测）

```
C:\ProgramData\ControlServer
    NT AUTHORITY\SYSTEM:(I)(OI)(CI)(F)
    BUILTIN\Administrators:(I)(OI)(CI)(F)
    DESKTOP-xxxx\<当前用户>:(I)(F)
    CREATOR OWNER:(I)(OI)(CI)(IO)(F)
    BUILTIN\Users:(I)(OI)(CI)(RX)          ← 本机任何普通用户可读
    BUILTIN\Users:(I)(CI)(WD,AD,WEA,WA)    ← 还能在子目录里创建文件/目录
```

🔴 **第二条比审计清单原来写的更严重**：原文只说"读+执行"。实测 `Users` 还有
`WD,AD,WEA,WA`（写数据 / 追加数据 / 写扩展属性 / 写属性）—— 也就是说普通用户**能往 `files/`、`downloads/`
里塞文件**，不只是偷看私钥。

### 6.2 收紧命令有效（实测）

```powershell
icacls "<数据目录>" /inheritance:r /grant:r "*S-1-5-18:(OI)(CI)(F)" /grant:r "*S-1-5-32-544:(OI)(CI)(F)"
```

执行后只剩 `NT AUTHORITY\SYSTEM` 与 `BUILTIN\Administrators`（均 `inh=False`），`Users` 全部消失。

### 6.3 现在的做法（已接线）

- `deploy/windows/install-service.ps1`：在**建完数据目录、写任何文件之前**执行上面这条命令
  （参数 `-HardenDataDir`，默认**开**；失败只警告，不中止安装 —— 装不上服务比权限没收紧严重得多）。
- `deploy/linux/install.sh`：`chown` 之后加 `chmod`，目录 `750`、文件 `640`。

**为什么必须"目录还空着的时候收紧"**：`icacls` 先切断父目录继承、再去打开子对象时，
会被刚设上去的 ACL 挡住 —— 实测 `icacls ... /T`（对已有子对象）报"拒绝访问"、**退出码 5**。
在空目录上做，之后写进去的东西自动继承。

### 6.4 🔴 收紧的副作用（踩过，必须写进运维文档）

收紧之后，**未提升的管理员也会被挡在外面**：

| 动作 | 未提升窗口（UAC 中等完整性） | 提升窗口 / 服务（LocalSystem） |
|---|---|---|
| 列目录 | **拒绝访问**（实测） | 正常 |
| `--backup` / `--restore` / `--dbinfo` | **读不了** | 正常 |
| `deploy\backup\backup.ps1` | **读不了** | 正常 |

而且——"账号在管理员组"**不等于**"进程有管理员权限"：UAC 下未提升的令牌里，
Administrators 是 deny-only，`IsInRole(Administrator)` 返回 `False`。

⇒ **从 M6.4 起，所有维护命令与备份脚本都必须"以管理员身份运行"**。
`backup.ps1` / `backup.sh` 已经加了前置检查，提前拦住并给出提示，不会跑到一半才报错。

> ⚠️ **未实测的一项**：服务以 LocalSystem 运行时能否正常读写收紧后的目录。
> 从 ACL 上看 `NT AUTHORITY\SYSTEM:(OI)(CI)(F)` 明确在列，逻辑上必然可访问；但本轮**没有**
> 以 SYSTEM 身份起过进程来证明它 —— 记为挂账，不许写成"已验证"。

## 7. 怎么用

### 7.1 升级前先演练（**强烈建议，一条命令**）

```bash
# 用现场数据的一份副本来跑，源目录只读
python deploy/upgrade/rehearse-upgrade.py "C:\ProgramData\ControlServer"
```

它会做：复制 → 倒回一版 → 备份 → 升级 → 9 项比对 → 写增量 → 回滚 → 10 项比对 → 起服。
全通过退出码 0，产物自动清理；不通过保留在 `.tools/upgrade-rehearsal/` 供排查。

### 7.2 正式升级

```powershell
# 必须：以管理员身份运行；把旧版安装包留在手边（自动回滚要用它）
powershell -NoProfile -ExecutionPolicy Bypass -File deploy\upgrade\upgrade.ps1 `
    -Installer \\share\ControlServer-Setup-0.2.0.exe `
    -PreviousInstaller C:\ControlServer-Backups\ControlServer-Setup-0.1.0.exe
```

八步：前置检查（**磁盘余量 ≥ 数据目录 × 1.2**）→ 停服 → `--dbinfo` 基线 → **强制备份（失败即中止）**
→ 静默安装 → 起服 → 验收 → 不过则自动回滚。

`-PreviousInstaller` **不给的话，自动回滚只能恢复数据、换不回程序** —— 脚本会明确喊出来。

### 7.3 手工回滚

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File deploy\upgrade\rollback.ps1 `
    -BackupDir C:\ControlServer-Backups\pre-upgrade-20261017-223000 `
    -Installer C:\ControlServer-Backups\ControlServer-Setup-0.1.0.exe
```

### 7.4 `--dbinfo`：验收与巡检的抓手（本轮新增）

```bash
ControlServer.Server.exe --dbinfo
```

```
db=5120000
migrations=13
migrations.latest=20261014171130_M4_12_AgentBlock
table.agent_hosts=3
table.agent_metrics=4787
...
files.count=1
files.bytes=1071700351
```

- **只读**（`Mode=ReadOnly`），服务在跑时也能跑；
- 键名**一律 ASCII** —— 同一个 exe 要在中文 Windows 控制台（GBK）、Git Bash（UTF-8）、Linux（UTF-8）
  三种终端里被脚本 grep，只有 ASCII 键在三处都稳；
- 升级脚本用它做"升级前 / 升级后"逐行比对；M6.5 的周巡检也用它（**每周记一次，磁盘占用与行数走势就有据可查**）。

### 7.5 两种部署形态与退出码契约（10-18 补）

脚本不是只有"服务"一种跑法 —— 否则它只会在真升级那天第一次执行，任何拼写错误都留到现场。

| 形态 | 开关 | 前提 | 谁在用 |
|---|---|---|---|
| 服务（默认） | 无 | 管理员；`Program Files`＋`sc.exe` | 现场升级/回滚 |
| 进程 | `-ProcessMode -ProcessPort <空闲端口>` | **免提权** | `dist\win-x64` 单文件控制台 exe；演练 |

- `-ProcessMode` **不是测试开关**：单文件控制台 exe 本身就是真实交付形态（`build-portable-exe.ps1` 的产物）。
- ⚠️ 进程模式的端口**别用 8080**：开发机上若有自启的 Agent/服务在听，演练会以最迷惑的方式失败。
- `-AllowSameVersion`：同版本号默认**判失败**（升完级日志一模一样＝等于没升），豁免时才放行。

**退出码**（`upgrade.ps1` / `rollback.ps1` 一致）：

| 码 | 含义 | 该做什么 |
|---|---|---|
| 0 | 升级成功 | 无 |
| 1 | **没开始就中止**（前置检查不过，备份没动） | 看原因，数据与程序都还是旧的 |
| 2 | 需要人工介入（无备份、回滚也失败） | 按日志手工处置，别重跑 |
| 3 | **升级失败，但已干净回滚** | 查到失败原因再升；**绝不能当成成功** |

> 🔴 3 这个码是必须的：`rollback.ps1` 成功也返回 0，若原样透传，"升级失败、已回退"在任何 CI/RMM 眼里都是绿的。

演练（免提权、沙盒空目录起家、13 项判据）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File deploy\upgrade\rehearse-scripts.ps1
```

### 7.6 两份演练各管一半

| 脚本 | 验什么 | 用不用现场数据 |
|---|---|---|
| `rehearse-upgrade.py` | **数据链路**（备份/恢复/迁移/`--dbinfo` 逐项比） | 用，拿现场数据的副本 |
| `rehearse-scripts.ps1` | **脚本逻辑**（分支、退出码、自动回滚、拒绝执行） | 不用，沙盒空目录 |

两份都绿，也只说明"除了安装包那一步，链路上的事都跑过了"。

## 8. 这份报告**不能**说明什么

| # | 局限 | 后果 |
|---|---|---|
| 1 | 演练用的是 `bin\Debug` 的 exe，**不是安装包** | "Inno 覆盖安装"这一环没被端到端跑过；`-SkipInstaller` 模式验的是数据链路 |
| 2 | 只造了"往回一版"的场景（撤掉最后一条迁移） | 跨多个大版本的升级没验；跨版本更要先演练 |
| 3 | `upgrade.ps1` / `rollback.ps1` 的**安装包那一步**（`/VERYSILENT` 装到 `Program Files`＋注册服务）仍未在提权真机上跑过 | 脚本逻辑已由 `rehearse-scripts.ps1` 在 `-ProcessMode` 下真跑（13/13）；只剩"装包＋注册服务"这一环没跑 |
| 4 | `upgrade.sh` / `rollback.sh` 只在 Git Bash 下用 `--no-service` 跑通了判定逻辑 | 真实 systemd 环境未验（M6 的 Linux 侧一贯挂账） |
| 5 | 服务以 LocalSystem 读写收紧后的目录**未实测** | 见 §6.4 的告警 |
| 6 | 备份是**全量**的 | 现场 1 GB 文件仓库 ⇒ 每次升级前备份再花 1 GB 与约 10 s；磁盘余量检查就是为它 |
| 7 | 迁移耗时只证明了这个 5 MB 的库 | 现场库到几百 MB 时 `Migrate()` 会变慢，`Migrate` 本身没有超时保护 |

## 9. 挂账（本轮新增）

- `install-service.ps1` 的 `-HardenDataDir` **未在真机装一遍验证**（会把 Program Files 与 `%ProgramData%` 都改一遍）；
- `backup.ps1` 的提权检查同样只做了逻辑与语法验证；
- **安装包那一步**（静默装到 `Program Files`＋注册服务）仍未提权真机跑过（脚本其余逻辑已 13/13 真跑）；
- `Migrate()` 在几百 MB 现场库上的耗时未量；
- Linux 侧升级/回滚整套未验。
- ⚠️ 演练**替代不了**安装包：`rehearse-scripts.ps1` 用的是 `dist\win-x64` 的 exe，不是 Inno 产物。

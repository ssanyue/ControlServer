> 面向：**厂商（签发方）** 与 **现场管理员**
> 配套：`docs/M3-授权方案.md`（设计与实施全文，§17 是实施记录）、`.workbuddy/memory/REF-M3-授权.md`（改代码前必读）

## 0. 一页速览

```
客户现场                                    厂商（你）
────────────────────────────────          ────────────────────────────────
① 部署服务端，首次启动自动拿 30 天试用
② 打开「授权」页，复制【机器码】
③ 把机器码发给厂商  ─────────────────────▶  ④ 双击打开签发工具，填表 → 点「签发」
                                               （密钥已内置，不需要任何密钥文件；
                                                默认到期日 3 天，要更久就点「快捷到期日」）
⑤ 导入 .lic        ◀─────────────────────   把 .lic 发回客户
   → 立即生效，无需重启
```

**三个物件，先分清：**

| 物件 | 在谁手里 | 作用 |
|---|---|---|
| **厂商私钥**（已**内嵌**进签发工具） | **只在厂商手里** —— 就是那两个 exe | 给授权「盖章」（签名）。**不落成任何密钥文件**；正因如此，那两个 exe 本身就是机密 |
| **厂商公钥** `VendorPublicKey.cs` | 编进服务端（编译期常量） | 验章。只能验、不能签，所以可以随服务端交付 |
| **授权文件** `*.lic` | 交付给客户 | 一纸「被私钥盖过章的声明」：绑哪台机器、何时到期。里面**没有任何密钥** |

> **操作者不需要理解"密钥"这件事。**
> 私钥已编译进 `ControlServer.LicenseTool.Gui.exe` / `ControlServer.LicenseTool.exe`，
> 两者都**不读取、也不需要任何 `.pem` 文件**。你要做的就是「双击 → 填表 → 点签发」。
>
> **代价（必须知情）**：签发工具 exe **本身就是钥匙** —— 拿到它的人可以签出任意机器、
> 任意期限的授权。所以它必须始终当作厂商机密：**不随服务端交付、不进共享目录、不发客户**。

## 1. 密钥：日常不用管，只有"换钥"时才要动

### 1.0 当前模型（一句话读懂）

厂商私钥被**编译进签发工具**：构建时把 `<仓库>\.tools\license-keys\vendor-private.pem`
作为内嵌资源打进 `dist\license-tool-gui\ControlServer.LicenseTool.Gui.exe` 与
`dist\license-tool\ControlServer.LicenseTool.exe`（实现见 `tools/LicenseToolKey.cs`）。
于是**日常签发不需要任何密钥文件** —— 打开工具就能签。

- 服务端只保留**配对的那把公钥**（`src/ControlServer.Core/Licensing/VendorPublicKey.cs`，
  编译期常量，随服务端交付）。
- 签发工具 exe **本身就是钥匙**（拿到它 = 拿到签发权）⇒ 必须当厂商机密保管。
- 内嵌密钥的**源文件** `.tools\license-keys\vendor-private.pem`（已在 `.gitignore`）是
  换钥与灾备的唯一备份；**它丢了就只能换钥**（见 §1.5）。

> **为什么不能真的"取消公钥"**：验签必须有公钥。去掉它，服务端就只能无条件相信送进来的
> `.lic` —— 任何人自己编一份就能生效，授权体系等于没有。能"简化掉"的是**人的操作**
> （保管密钥文件、选钥、比指纹），而不是**密码学本身**；后者只留在这一处常量里，你见不到它。

### 1.1 更换厂商密钥对（日常用不到，只在换钥时做）

```bash
dist\license-tool\ControlServer.LicenseTool.exe new-key --out .tools\license-keys\vendor-private.pem
```

**私钥放哪**：必须落在 `<仓库>\.tools\license-keys\vendor-private.pem`（已在 `.gitignore`）——
两个签发工具的 csproj 就按这个路径把它内嵌（`LogicalName` 固定为 `vendor-private.pem`）；
放到别处，工具签出来的东西就与服务端对不上。

> GUI 已**不再提供**"生成密钥对"页：日常签发不需要它，换钥属于厂商侧一次性维护。

记下工具打印的**公钥指纹**（当前为 `D14EE793C89328E7`）。

### 1.2 把公钥写进服务端

把工具给出的公钥 PEM 与指纹写进：

```
src/ControlServer.Core/Licensing/VendorPublicKey.cs
```

**必须是编译期常量** —— 这是刻意的：一旦做成配置项，任何能改配置文件的人都能塞进自己的公钥、自签一份永久授权，而日志里看不出异常。

### 1.3 重建并重新交付（**全部形态**，缺一不可）

公钥是**编译期内嵌**的 ⇒ 只要有一份产物没重编，那份产物就还在用旧公钥，新授权在它上面一律验不过。

**换钥时，签发工具也必须重编**：新私钥要重新内嵌进那两个 exe。
只换 `.tools\license-keys\vendor-private.pem` 而不重编工具，工具里装的仍是旧私钥 ——
于是"刚换完钥，签出来的文件却还是旧的"，现象与没换一样。

```bash
# ① 服务端 —— 绿色版 + 服务版（同一次发布产出两套目录）
powershell -NoProfile -ExecutionPolicy Bypass -File deploy/windows/build-portable-exe.ps1

# ② 服务端 —— Windows 安装包（依赖 ① 产出的 dist\win-x64-service payload）
powershell -NoProfile -ExecutionPolicy Bypass -File deploy/windows/build-installer.ps1

# ③ 服务端 —— Linux（交叉发布）
bash deploy/linux/build-linux.sh

# ④ 签发工具（**换钥后必须重编**：新私钥要重新内嵌进两个 exe；否则工具里装的还是旧私钥）
powershell -NoProfile -ExecutionPolicy Bypass -File deploy/windows/build-license-tool.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File deploy/windows/build-license-tool-gui.ps1

# ⑤ 冒烟（含 license 场景）
python deploy/smoke/run-all.py
```

**重建清单对照**：`dist\` 下六个目录都要刷新 —— `win-x64`（绿色版）、`win-x64-service`（服务版）、
`installer`（安装包）、`linux-x64`（Linux 包）、`license-tool`（CLI）、`license-tool-gui`（GUI）。

### 1.4 换密钥的连带后果（务必知情）

**旧私钥签出的所有授权全部作废** —— 服务端只认内嵌的那把公钥。换密钥 = 主动作废全部存量授权，必须重新签发。

### 1.5 私钥丢失后如何换密钥

**先说一条能让人松口气的**：换密钥**不需要旧私钥** —— `new-key` 是凭空生成一对全新的
（实测：在一个空目录里生成，退出码 **0**）。所以"私钥丢失"只是一个**触发原因**，
操作流程与主动轮换**完全一样**，不会因为丢了而变难。

**但铁律不变**：换了公钥，**旧私钥签出的所有授权当场作废**（服务端只认新公钥）。

**五步**（前缀与 §1.3 相同）：

```bash
# ① 生成新密钥对
#    旧私钥已丢失 ⇒ 目标文件不存在，不会被"拒绝覆盖"拦住，直接生成即可
dist\license-tool\ControlServer.LicenseTool.exe new-key --out .tools\license-keys\vendor-private.pem
#    → 记下新指纹；把打印出来的 Fingerprint + Pem 整段替换进 VendorPublicKey.cs（见 §1.2）

# ② 重编并重发**全部**服务端形态（§1.3 的 ①②③）
# ③ 重编两个签发工具（§1.3 的 ④）—— 新私钥就是在这里被重新内嵌进 exe 的，**不能漏**
# ④ 冒烟（§1.3 的 ⑤）
# ⑤ 用新密钥重签**全部**客户授权，连同新服务端一起交付
```

**⚠️ 三个坑（都会让人白跑一趟）**：

1. **新私钥必须落在 `.tools\license-keys\vendor-private.pem`（默认路径）** ——
   两个签发工具的**构建**就按这个路径把它内嵌进 exe；放到别处 ⇒ 工具里装的还是旧钥，
   签出来的东西服务端一律不认。（`license-smoke.py` 也按此路径作参考；
   但它 C 段实际走的是**工具内嵌密钥**，可用 `--key` / `CONTROL_SERVER_VENDOR_KEY` 覆盖。）
2. **切换是原子的、全量的**：新服务端**拒**旧授权，旧服务端**拒**新授权。
   ⇒ 给客户交付时，**新服务端与新的 `.lic` 必须成对**，绝不能交叉（老程序配新授权 = 403）。
3. **记下上一版公钥指纹留档**（本次换钥前为 `7B521A193C143289`）—— 否则现场无法判断
   "这台机器上装的到底是哪一版"，排错时会绕远路。

**过渡期可选（当前未实现）**：让服务端**同时认新旧两把公钥**（把 `VendorPublicKey.Pem` 改成字符串数组），
客户就能慢慢换、不必同一步完成。代价是"当前生效的到底是哪把钥匙"变得含糊，因此当初没做。

**实测记录（2026-10-10 → 10-11）**：`new-key` 生成新对 → 退出码 **0**，打印新指纹与可整段粘贴的
`VendorPublicKey.cs` 代码块；对**已存在**的私钥文件 → **拒绝覆盖**，退出码 **1**（需 `--force`）。
本次由此得到正式厂商密钥 **`D14EE793C89328E7`**，并完成"私钥内嵌进签发工具"的改造。

## 2. 常规发放流程（每台设备）

### 2.1 客户侧：取机器码

1. 部署服务端，浏览器打开 `http://<机器IP>:8899`
2. 用管理员登录
3. 进入「**授权**」页
4. 复制【**机器码**】（形如 `084C-98CF-BE5A-9AEC`）
   - 或点「加载申请」再「复制申请文本」，把整段发过来（信息更全，便于留档）

### 2.2 厂商侧：签发

**GUI**（推荐，双击即用）

> **界面上没有的东西**（2026-10-11 起，别去找）：没有「授权类型」下拉（一律按正式授权签发）、
> 没有「自签发起 N 天」、没有「解读授权」页、也不显示任何**公钥指纹**。
> 要核对一份 `.lic` 请用命令行版的 `inspect`（见 §2.5）。

| 字段 | 填什么 |
|---|---|
| 授权对象 | 选「绑定机器码」，粘贴客户给的机器码（发长期授权时也可选「通用授权」） |
| 使用截止 | **仅通用授权用**：最迟可被导入绑定的时刻。默认只到**当天 23:59:59**（日期下面是它的实时余量），要更长的导入窗口就自己把日期往后改 |
| 有效期 | 永久 / 到期日 / 精确到期时刻（三选一）。**默认到期日是 3 天后** |
| 快捷到期日 | 懒得算日期就点：**3 天 / 1 个月 / 2 个月 / 3 个月 / 6 个月 / 1 年**（从今天起算，并自动切到「到期日」模式） |
| 签发密钥 | **已内置，无需填写**（状态行只说"能用/不能用"，不显示指纹） |
| 输出文件 | 生成的 `.lic` 路径（留空则按客户备注自动命名） |
| 取时方式 | 「联网取时」（默认）；离线时才勾「允许用本机时钟」 |

> 若状态行显示**「不是一对」**，说明工具内嵌的私钥与服务端内嵌的公钥不匹配（换钥时只更新了一边），
> 此时**不要签发** —— 先按 §1.3 重编服务端与工具。

**CLI 等价**（同样**不需要** `--key`：密钥已内嵌）

```bash
# 绑机器 + 到期日
ControlServer.LicenseTool.exe gen --type full ^
  --bind 084C-98CF-BE5A-9AEC --expire 2027-10-08 ^
  --customer "XX展厅" --sn "SN-001" ^
  --out 授权_XX展厅.lic

# 绑机器 + 精确到秒
... gen --type full --bind 084C-98CF-BE5A-9AEC --expire "2027-10-08 23:59:59" ...
# 绑机器 + 天数（自签发起算）—— GUI 上没有这个选项，只有命令行版支持
... gen --type temp --bind 084C-98CF-BE5A-9AEC --days 30 ...
# 永久（必须绑机器码，不允许"通用 + 无期限"）
... gen --type full --bind 084C-98CF-BE5A-9AEC ...
```

**签发后必须看这一行**（GUI 与 CLI 都有，文案略有差异）：

```
[ok]  签名公钥：与服务端内嵌公钥一致 —— 服务端会收下这份文件。
```

> CLI 的输出里还带着公钥指纹（`…（指纹 D14EE793C89328E7）`），那是给**换钥**时核对用的；
> **GUI 上有意不显示指纹**（用户要求），只给「一致 / 不是一对」这个结论。

**若不是「一致」，这份文件发出去必然被拒**（`signatureinvalid`）——
说明**工具里内嵌的私钥与服务端内嵌的公钥不是一对**（多半是换钥时只更新了一边，见 §1.3）。

### 2.3 客户侧：导入

1. 「授权」页 → 「导入授权文件」
2. 粘贴整段内容，或点「选择文件」/ 直接**把 `.lic` 拖到虚线框**
3. 点「导入授权」

**导入是覆盖式的**：续期直接导入新文件即可，**不需要先移除旧的**。导入成功后**无需重启**，后台任务自动恢复。

### 2.4 验证

页面应显示：

```
正式授权有效，剩余 N 天（至 YYYY-MM-DD 23:59:59）
```

顶栏徽章同步变化；未授权时被拦的功能（动作执行 / 对接码监听 / 定时触发）自动恢复。

## 3. 通用授权（不绑机器码）

**用途**：先发货后绑定；或一批同型设备统一发一份。

```bash
ControlServer.LicenseTool.exe gen --type full --universal ^
  --deadline 2026-12-31 --expire 2027-10-08 --customer "某批次"
```

- `--universal` **必须**同时给 `--deadline`（= 最迟可导入绑定的日期，写进 `ud`）
- 客户**首次导入**时，服务端把本机机器码写进 `license.binding.json` 完成绑定
- 绑定后再拿到另一台机器导入 → 被拒（`machinemismatch`）

> 通用授权**不可**配「永久」：那等于一份可以无限复制的永久授权。

**GUI 里的默认值（2026-10-18 起）**：「使用截止」默认是**今天**、时间 23:59:59，也就是
**只到当天结束** —— 签完当天客户就得导入，过了零点这份通用授权就绑不上了（服务端回 `deadlineexceeded`）。
默认取最短是刻意的：通用授权是"任何机器都能绑"的文件，默认给一个月的导入窗口，
等于每次签发都顺手把这份权限的可用期延长了一个月。**要给客户留更多时间，就把日期往后改**，
改多少自己清楚；改完日期下面那行会实时写出"使用截止 = …，距今约 …"。

> 签发时 Core 还会再判两条：截止**必须晚于签发时刻**、且**必须早于授权到期时间**。
> 所以「到期日」不能早于或等于使用截止那一天 —— 否则自检就会拦下（这是设计，不是 bug）。

## 4. 试用机制（含**实测结论**）

### 4.1 机制

| 项 | 值 |
|---|---|
| 首次启动自动试用 | **是**（`Server:License:AutoTrial` 默认 `true`）；只在「既无授权文件、也无试用记录」时生成 |
| 天数 | **30 天**（`Server:License:TrialDays`） |
| 到期日算法 | `起算日 + (天数 − 1)`，即"含起算日在内的 N 个自然日"，末刻为第 N 天 23:59:59 |
| 起算时间来源 | 优先**联网校时**（记为 `ntp`）；取不到时退回本机时钟（记为 `local`） |
| 落盘 | `%ProgramData%\ControlServer\license.trial.json`（**不带签名**：服务端只有公钥，签不出东西；它是"本地策略状态"而非凭证） |
| 到期后 | 生效档位升为 `Enforce` → 动作执行 / 对接码监听 / 定时触发 被拦（`403 license-required`） |

### 4.2 三项要求的核查结果（**2026-10-10 实跑**）

| # | 要求 | 结论 | 证据 |
|---|---|---|---|
| 1 | 首次使用可试用，且必须联网校对正确时间 | ⚠️ **部分成立** | 首启自动生成 30 天试用，本次起点来源实测 = `ntp`（联网校时成功）。但 `RequireNetworkTime` 默认 **false** ⇒ 取不到网络时间时**会退回本机时钟并照样放行**。要强制"必须联网"，需设 `Server:License:RequireNetworkTime=true` |
| 2a | 试用结束后不得再次试用 | ❌ **不成立** | 实测：试用有效期内再次生成 → `409 trial-active`（正确）；把试用记录改为**已过期**后，状态 = `Expired`，此时点「生成 30 天试用」→ **HTTP 200，又发了一份新的 30 天** |
| 2b | 重装也不行 | ✅ **成立** | 卸载脚本**刻意保留** `%ProgramData%\ControlServer`；试用记录在数据目录里，与 exe 无关 ⇒ 重装后不会重新生成。且自动试用只在"记录不存在"时触发 |
| 3 | 不得通过修改系统时间影响试用时间 | ⚠️ **视部署而定** | 到期判定用 `CorrectedTimeProvider.GetUtcNow() = 系统UTC + BeijingTime.ClockOffset`；`ClockOffset` 由 NTP 校准写入。**能上网**：改钟会在下次校准（最多 30 分钟内）被抵回来。**上不了网 / `AutoSync=false`**：`ClockOffset` 恒为 0，判定完全等于系统时间 ⇒ 把系统钟往回调即可延长有效期 |

### 4.3 2a 的性质：这是 **bug**，不是设计

代码注释写的是「试用仍在有效期内时不允许重刷 —— 否则'重新生成'就成了永久免费的按钮」，
前端按钮的 tooltip 也写「仅在既无授权、也无有效试用时可用」——

但实现里的守卫是：

```csharp
if (existingTrial is not null && _state.Status == LicenseStatus.Trial)   // ← 只看"仍在有效期内"
{
    return ...trial-active...;
}
// 落空 ⇒ 走到下面写一份新的
```

**过期后 `Status == Expired`（不是 `Trial`），守卫落空 ⇒ 直接把新记录写盘**。
所以「生成 30 天试用」这个按钮在**试用到期后**变成了"无限续杯"开关。

**修法（一处判定）**：把守卫从"试用是否仍有效"改成"**试用记录是否存在**" ——
即 `if (existingTrial is not null) return ...trial-used...;`（与 `EffectiveEnforcement` 的判据保持一致：
那里判断的正是"记录是否存在"，而不是"试用是否有效"）。

> 新增守门用例建议：`Trial_cannot_be_regenerated_after_it_expires`（预置一份已过期记录 → POST `/api/license/trial` → 期望 409）。

### 4.4 试用的固有上限（如实说明）

单机离线授权的天花板就在这里：试用记录是一份**本地明文 JSON**，能改它的人同样能删掉整个数据目录。
给它套一层假签名不增加任何防护，只会让人误以为拦得住。**厂商签发的 `.lic` 才是完整签名凭证**（ECDSA 验签 + 机器码绑定 + 联网锚点）。

## 5. 续期 / 换机 / 移除

| 场景 | 操作 |
|---|---|
| **续期** | 直接签发一份新 `.lic`（同机器码、新的到期日）→ 客户导入覆盖。**不需要先移除** |
| **换机** | 索取绑定**新机器码**的授权。原授权绑定的是旧机器，换机后必然 `machinemismatch` |
| **硬件变更** | 机器码由 `CPU ProcessorId \| 主板 SerialNumber \| 产品 UUID` 经 SHA256 得出。**换主板 / 换 CPU 会改变机器码** ⇒ 既有授权失效，需重签。<br>（WMI 全部取不到时会回退到数据目录里的持久化 `install-id` —— 此时**清空数据目录也会改变机器码**） |
| **移除授权** | 「授权」页 →「移除授权」→ 5 秒内再点一次确认。<br>**不会重置试用**（否则"移除 → 重启 → 又白拿 30 天"就是免费通道） |
| **临时调试** | 用 `--type temp` 签发 30 天内的临时授权，或 `--days N` |

## 7. 排错表

| 现象 / 返回 | 含义 | 处置 |
|---|---|---|
| `signatureinvalid` | 签名与内嵌厂商公钥不符 | 多半是**工具内嵌的私钥与服务端内嵌的公钥不是一对**（换钥时只更新了一边）⇒ 按 §1.3 重编服务端与工具；若刚重编过，则这份 `.lic` 可能被改动过 |
| `machinemismatch` | 授权绑的是别的机器 | 核对机器码（**注意大小写不敏感、但要逐位对**）；换过主板/CPU 需重签 |
| `expired` | 导入时已过期 | 重签一份新的 |
| `missingnetworkanchor` | 文件缺 `ivt`，多为手工拼装 | 不要手工改 `.lic`；用工具重签 |
| `clockunusable` | 本机时间早于授权里的联网校对时间 | 先校正本机时间（「设置」页有手动校时）再导入 |
| `unsupportedversion` / `unknownkind` | 文件版本或类型不认识 | 用与当前服务端配套的工具重签 |
| `deadlineexceeded` | 通用授权超过了可导入截止时间 `ud` | 重签（或改用绑机器的授权） |
| 导入成功但功能仍被拦 | 看「授权」页的**生效档位**与状态 | 生效档位可能是 `Enforce` + 状态非可用；导入后后台任务会自动恢复，稍等或刷新页面 |
| 反复导入失败 | 每次失败都会写审计 `license-import-rejected:<原因>` | 「日志」页可按该前缀查，用于还原"到底拿错了什么" |

## 8. 已知边界与缺口（如实告知）

1. **签发工具不校验"机器码是否真是目标机器的"**
   自检干跑用的是**文档自己的机器码**，所以它对"绑给谁"结构上无法判定 —— 签给别台机器的授权天然"自洽"。
   **后果**：不是安全漏洞（服务端导入时会以 `machinemismatch` 拦下），而是**白跑一趟**：文件发到现场才发现用不了。
   更麻烦的是机器码是 16 位十六进制、**没有校验位**，抄错一位照样能签出去、且不报任何警。
   报告里已写明这一条；详见 §9。

2. **换密钥 = 作废全部存量授权**（见 §1.4）。

3. **试用到期的无限续杯**（见 §4.3）——待修。

4. **离线部署下"改系统时间"拦不住**（见 §4.2 第 3 条）——这是单机离线授权的固有上限。

5. **授权文件不参与配置导入导出**：它是设备级凭证，跟着机器走。若能被配置备份带跑，"把 A 的配置恢复到 B"就会顺带把授权带过去，得到一片"已授权但功能全不可用"的混乱。

6. **PBKDF2 升级未做**：口令哈希当前仍是 SHA-256 + salt（与本手册的授权体系无关，一并挂账）。

## 9. 关于"机器码无法校验"这个缺口 —— 后果与可选加固

### 9.1 后果（按严重度排序）

| # | 后果 | 说明 |
|---|---|---|
| 1 | **没有安全后果** | 服务端是唯一的判定权威：导入时逐项校验签名、版本、类型、`ivt` 锚点、机器码绑定、有效期。绑错机器的文件**进不去**。缺口只存在于"厂商侧的自检"，不影响防线 |
| 2 | **白跑一趟（主要成本）** | 授权发到现场 → 导入被拒 → 回厂重签。若现场无网络/需上门，成本显著 |
| 3 | **抄写错误静默通过** | 机器码 = SHA256 前 16 位，**无校验位**。错一位仍是"合法格式"，签发器不会察觉；直到客户导入才暴露 |
| 4 | **硬件变更导致的静默失效** | 换主板/CPU 后机器码改变，既有授权失效 —— 签发时同样无从预见 |

### 9.2 可选加固（按性价比排序）

| 方案 | 效果 | 代价 |
|---|---|---|
| **A. 用「申请文本」代替裸机器码** | 签发页改为粘贴客户整段申请文本、由工具解析出机器码。消除"贴错字段"这一类 | **低**（只改工具输入与解析） |
| **B. 签发前回读确认** | 把规范化后的机器码大字号回显，要求操作者逐位核对再签 | **低** |
| **C. 机器码加校验位** | 从 16 hex 里留 4 位做 CRC ⇒ 抄错一位当场被拒 | **高**：机器码格式变更 ⇒ **全部存量授权与算法作废**，需版本化迁移 |
| **D. 维持现状** | 依赖服务端那道 `machinemismatch`（权威判定），配合报告里的明文提示 | 零 |

**当前采取 D**，并把本条写进签发报告（"不保证客户机器上一定可用 —— 那还取决于机器码与客户机器是否一致"）。
若要进一步收敛现场返工率，建议做 **A + B**（低代价、能消掉大部分人为错误）。

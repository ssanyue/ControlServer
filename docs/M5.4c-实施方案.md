### 🔥 一个必须点名的用词陷阱：「分片」≠「分块」

- **分片（chunking）**：**一帧已编好的字节**装不进一条消息 ⇒ 拆成 N 条**传输消息**，到对面拼回来。
  码流本身**一字未变**，解码器不知道这件事。→ **M5.4-c**。
- **分块编码（tile）**：把**一幅图**切成几块，每块**独立编码**（各有一个 SPS/PPS 与参考链）。
  码流**变了**，前端要拼接。→ **M5.5**。

中文里这两个词只差一个字，而它们改的是完全不同的两层（传输层 vs 编码层）。
本方案此后**一律写「分片（chunking）」**，并在 M5.5 的文档里写「分块编码（tile）」，**不许简称**。

## 2. 开工前实况核查（读出来的，不是推出来的）

### 2.1 帧路径六跳，与「一条消息 = 一帧」这个**隐含假设**

| # | 跳 | 实现 | 「一条消息 = 一帧」 | 上限 / 备注 |
|---|---|---|---|---|
| 1 | 抓屏 + 编码 | `WindowsGpuFrameEncoder` | 一帧一帧产出 ✅ | 编码器自己不知道"消息"这回事 |
| 2 | 托盘 → 服务（**本地命名管道**） | `RemoteStreamProtocol.WriteFrameAsync` / `ReadFrameAsync` | ✅（`[头长度][码流长度][头][体]`） | `MaxPayloadBytes` ≈ **5.75 MiB** |
| 3 | 服务 → 中心（**SignalR**，客户端→服务端） | `AgentConnection.PushRemoteFrameAsync` → `AgentHub.PushRemoteFrame` | ✅ | 🔴 **中心的 `MaximumReceiveMessageSize` = 8 MiB** —— **越限的后果是掐断整条 Hub 连接**（心跳/遥测/配置/音频全在它上面）。**这就是那堵墙** |
| 4 | 中心接收 → 每会话转发队列 | `RemoteSessionRegistry.Entry.Observe` → `Fanout` | ✅（队列项 = 一帧） | 容量 **1**，`DropOldest`（**忙就丢，且不回报**） |
| 5 | 中心 → 浏览器（**SignalR**，服务端→客户端） | `SendToGroupAsync` → `RemoteHubMethods.Frame` | ✅ | JS 客户端 **8.0.29 无收包上限**（`maximumReceiveMessageSize` 只存在于服务端/.NET 客户端）⇒ **这条路上没有同一堵墙** |
| 6 | 浏览器 `push` → 解码 | `remotePlayback.push` → `h264Decoder` | ✅（队列项 = 一帧） | `VIDEO_QUEUE_LIMIT = 12`，满则**丢最旧** + `breakChain()` |

**结论（这一节的全部价值）**：**「一条消息 = 一帧」被六跳里的每一跳默默依赖，而只有第 3 跳真的挡不住 8K。**
⇒ 设计目标就一句话：**只破坏第 3 跳的那个假设，并在中心把它恢复回来。**

### 2.2 尺寸上限：现在是**一个数**，而它其实在守**两道不同的墙**

| 常量 | 值 | 它守哪道墙 | 谁引用 |
|---|---|---|---|
| `RemoteStreamLimits.SignalRMessageBytes` | 8 MiB | 中心**单条消息**（`Program.cs` 直接引用，不抄副本） | `Program.cs` |
| `RemoteStreamLimits.MaxFramePayloadBytes` | 8 MiB ÷ 4 × 3 − 8 MiB ÷ 32 = **6,029,312**（≈5.75 MiB） | **单帧裸码流**上限（被控端写管道前判，超了丢帧） | `RemoteStreamProtocol.MaxPayloadBytes` / `FitsInPipe` |

⚠️ `MaxFramePayloadBytes` 的**存在理由**（写在它自己的注释里）正是「**别让帧大到撞穿第 3 跳那道墙**」。
分片做完之后，这个理由**消失**了 —— 但它**不能就此删掉**：它要**改换身份**（见 §3.3）。

## 3. 关键设计 A：分片（chunking）—— M5.4-c①

### 3.1 分片点与重组点：为什么**终止在中心**

| 方案 | 做法 | 判 |
|---|---|---|
| **甲 · 端到端** | 被控端分片 → 中心**透传**每一片 → 浏览器拼回 | ❌ **否**。中心的 `Fanout` 是容量 1 + `DropOldest` ⇒ 它丢掉的是**"一条消息"**，也就是**同一帧的中间一片** ⇒ 前端会拼出一帧**长度对、内容错**的码流 ⇒ 花屏（甚至解码器 `error`），而**中心与前端都不会报错**。要救它就得把队列的**丢弃单位**从"消息"改成"帧" —— 而那**等于中心已经在重组了**（只是把重组放到了队列入口） |
| **乙 · 终止在中心** | 被控端分片 → **中心拼回整帧** → 中心按**整帧**入队、透传 | ✅ **推荐**。跳 4/5/6 **零改动**；前端**零改动**（除 §3.6 那条自愈）；`Latest` 语义不变；中心的重组发生在 `AcceptFrame` **之前** |
| **丙 · 只抬上限** | 把 `MaximumReceiveMessageSize` 抬到 64 MiB，不分片 | ❌ **否**。它是**整条连接**的上限：一帧畸形就能让连接（心跳/遥测/配置/音频都在上面）吃 64 MB 内存，且 base64 后是 85 MB 的字符串。**分片的全部意义就是把压力摊平成多条小消息** |

**取方案乙。**

### 3.2 协议形状

```
// 契约（新增，不动 RemoteStreamFrame）
public sealed record RemoteStreamFrameChunk(
    RemoteStreamFrameHeader Header,   // 每一片都带完整帧头
    int ChunkIndex,
    int ChunkCount,
    byte[] Data);

// SignalR（新增方法；PushRemoteFrame 的签名一个字不动）
PushRemoteFrameChunk(RemoteStreamFrameChunk? chunk) → AgentIngestAckDto
```

- 🔥 **只有"装不下"的帧才分片**。`ChunkCount == 1` 的帧**仍走老路 `PushRemoteFrame`**
  ⇒ **2160×1440 与 4K 的行为一个字都不变**（改动对现有场景是**惰性**的，这是它敢进的底气）。
- **每一片都带完整帧头**（约 200 字节 JSON，占单片上限的 **0.003%**）⇒ 每一片**自描述**，
  中心不必记住「第 0 片长什么样」，也**不必**假定片是按序到的（虽然它们确实有序，见 §3.5）。
- ⚠️ **必须新增方法，不许给 `PushRemoteFrame` 加参数**：`HubContractArityTests` 用反射把 Hub 方法的
  **实参个数**钉死了（`AgentHubClientMethods.Heartbeat` 的注释记着实测结论：SignalR 的实参个数必须与签名**严格一致**，
  C# 的默认值参数在这里毫无作用）。加参数 = 让**旧中心**上所有新客户端的**每一帧**调用失败。

### 3.3 三个尺寸常量，与它们各自守的那道墙

| 常量 | 值 | 守哪道墙 | 变化 |
|---|---|---|---|
| `SignalRMessageBytes` | **8 MiB** | 中心单条消息 | 不变 |
| `MaxChunkPayloadBytes` | **6,029,312**（≈5.75 MiB，**沿用原 `MaxFramePayloadBytes` 的推导式**） | **单片**上限 —— 保证 base64 后的单片仍塞得进一条消息 | **改名**（原 `MaxFramePayloadBytes`），值不变 |
| `MaxFrameBytes`（新增） | **64 MiB** | **防呆**：单帧上限，抗"畸形/异常大帧" | 新增 |

- 🔥 **为什么"改名"而不是"再加一个"**：原名 `MaxFramePayloadBytes` 在分片之后是**错的名字** ——
  它现在管的是**一片**，不是**一帧**。名字错了比数字错了更难查（下一个人会拿它去当帧上限）。
- 🔥 **64 MiB 是怎么来的**：8K（7680×4320）的 IDR 量级，按 M5.4-a 实测的 2160×1440 IDR 306.9 KB
  与像素数比例外推，再留一个数量级的余量 ⇒ 单帧 64 MiB 是"够用且绝不会误伤"的防呆值。
  按 5.75 MiB 一片折算：**最坏 12 片**。
- ⚠️ **三个数仍然只有一个根**（8 MiB 那条）—— 这正是原注释要守的东西。原注释写的是
  「两个数绝不能各写一份」，现在要改成「**三个数、三道墙、但同一个根**」，并把每道墙**分别写清**。

### 3.4 中心的离锁重组（不能把 15 MB 的拷贝压在 `_gate` 里）

`RemoteSessionRegistry` 的既有并发假设是：**`Entry` 的字段一律在 `_gate` 内改动**
（`AcceptFrame` → `entry.Observe(frame)` 就在锁内；`Sweep` / 快照也在锁内读）。

⚠️ 分片重组要**拷贝几 MB 到十几 MB 字节**。把它放进 `_gate`，等于让**所有会话的所有帧**
去等那一次拷贝（拿账本的锁去做大内存操作）。

⇒ 做法：

1. **归属与会话校验在锁内**（一次字典查找，与 `AcceptFrame` 完全一致，**每一片都做**，不是只在第 0 片做）；
2. **拼字节在锁外**：每会话一份**单槽**重组缓冲（§3.5），自带一把**小锁**（只保护它自己）；
3. 拼齐之后，**再**调既有的 `AcceptFrame(agentId, frame)` ⇒ `Observe` / `Latest` / `Fanout`
   的并发假设**一行都不用改**。

### 3.5 🔥 单槽重组：**不需要定时器、不需要超时、不需要后台清扫**

**可以论证「同一时刻至多只有一帧不完整」**：

- 第 3 跳是**单条顺序连接上的一段顺序流**；
- 被控端的 `PumpAsync` 是 `await sink(frame)` **之后**才读下一帧（`FrameSink` 在泵循环里被 await）；
- 分片的各片**在同一帧内**也是顺序 `await` 的（见 §3.6 的 ack 策略）。

⇒ **当下一个帧 id 出现时，上一帧要么已经拼齐、要么已经永久丢了。**

于是重组器的规则只有三条：

1. 收到**新 `Sequence`** 而槽里还有未完成的帧 ⇒ **判定那一帧已丢**（计数 + 置「请补关键帧」，见 §3.6）、清槽、开新槽；
2. 收到**同一 `Sequence`** ⇒ 校验 `ChunkCount` 一致、`ChunkIndex` 未重复，存片；累计字节 > `MaxFrameBytes` 或 `ChunkCount` 越界 ⇒ **丢这一帧**（清槽 + 计数）；
3. `received == expected` ⇒ 拼成 `RemoteStreamFrame`，**离开重组器**（交给 `AcceptFrame`）。

⚠️ **防御性上限（全部按"丢帧 + 计数"处理，绝不当异常抛）**：`2 ≤ ChunkCount ≤ 1024`、
`0 ≤ ChunkIndex < ChunkCount`、累计字节 ≤ `MaxFrameBytes`。
🔴 **不许把这些判成异常**：`AcceptFrame` 那条路径上"抛"的后果是**掐整条连接**，
而这里最坏的后果应该只是**丢一帧** —— 这与 `FrameTooLargeException` 当初被从
`InvalidOperationException` 里摘出来是**同一条纪律**。

### 3.6 失败语义：丢一帧 → **在参考链上戳了个洞**，必须补关键帧

`FrameTooLargeException` 的注释早就写清楚了：**H.264 丢一帧，从那一刻起观看端解出来的每一帧都是花的，
而解码器不会报错**。被控端**自己**丢帧时会置 `wantKeyframe`（下一帧编成 IDR）。分片引入了**新的丢帧来源**，
而它在**中心**——被控端不知道。⇒ 必须补一条**回传**：

| 谁丢的 | 现状 | 本批 |
|---|---|---|
| 被控端（`OversizeGiveUp`） | ✅ 已置 `wantKeyframe` | 不变（阈值改由 `MaxFrameBytes` 判） |
| **中心（重组失败）** | ❌ **无任何回传** | 🆕 `AgentIngestAckDto` 增 `NeedKeyframe`；中心在**下一次 ack** 上带出去；被控端置 `wantKeyframe` |
| **中心（`Fanout` 队列 `DropOldest`）** | ❌ **无任何回传，且前端也不自愈** | 🆕 见下面那条**更基础的洞** |

**🆕 前端还有一个更基础的洞（本轮新发现）**：`remotePlayback.push` 只丢「序号 ≤ 已画」的**旧**帧
（`if (header.sequence <= this.lastPaintedSeq) return`），**不检测序号跳变**。
⇒ 中心丢掉一帧（`Fanout` 的 `DropOldest` **今天就会发生**），前端会**缺一个参考帧继续解**、
一路花到下一个关键帧，而**没有任何一层知道这件事**（不报错、不计日志、不重建解码器）。

⇒ 本批补上：`sequence > lastSeq + 1` ⇒ 走**既有的** `breakChain()`（重建解码器 + 等下一个关键帧）。
**这条不只是为分片** —— 它把「中心队列丢帧」这个**既有**故障一起治了。

> ⚠️ **两条一起做的理由**：只有前端自愈，「恢复代价」是**最多一个 GOP**
> （`gopSize = 60`、默认 12 fps ⇒ **5 秒花屏**）；加上中心的「请补关键帧」回传，
> 才压到「**下一帧**」。所以：
> - **必做**：前端序号跳变 ⇒ `breakChain`（小、覆盖**全部**丢帧来源、是"能自愈"的地基）；
> - **建议做**：中心 → 被控端的「请补关键帧」（把恢复从 5 秒压到 40 毫秒）。
>
> ⚠️ 代价诚实说明：「请补关键帧」是本批**第二个跨层信号**
> （`AgentConnection` → `RemoteSessionCoordinator` → `RemoteStreamHost`，跨三层）。
> 必须有**去重/节流**：不许"每帧都请求关键帧"（那会把一个丢帧放大成**一路 IDR**，
> 而 8K 的 IDR 正是最贵的东西）。

### 3.7 兼容性

| 组合 | 行为 |
|---|---|
| **新中心 + 新客户端** | 超大帧走分片；其余一切照旧 |
| **旧中心 + 新客户端** | `PushRemoteFrameChunk` 调用**抛** ⇒ 客户端按既有纪律**就地把这路流停掉**（与 `PushRemoteAudio` 同一条：**不许静默忽略**，否则"编一帧、丢一帧"空烧 CPU）。✅ **但**：小帧仍走老路 ⇒ **旧中心上 4K 及以下照常工作**，只有真出现超大帧时才停 —— 这正是 §3.2「惰性」的价值 |
| **新中心 + 旧客户端** | 旧客户端永远只发单条消息；超限 ⇒ 被控端自己丢帧（现有 `OversizeGiveUp`）。中心**不需要任何特判** |

### 3.8 不变量清单（改完之后，这几条**仍然**成立）

1. 「**一条消息 = 一帧**」在**跳 4 / 5 / 6** 继续成立（中心的重组发生在入队**之前**）⇒ `Fanout`、前端**零改动**；
2. `Latest` 仍然是**完整的一帧**（新观众进来补一帧，语义不变）；
3. `Dropped`（帧头里那个）仍然是**只有被控端本地丢的帧**才计 —— 🔴 **中心丢的帧另有一个计数，绝不合并**
   （合并了「它编不动」与「链路上掉了」就再也分不开，而那正是这两个数并排存在的全部意义）；
4. **序号仍然连续**，仍然**不被丢帧撑出空洞**（M5.4-b 实测钉过的一条）；
5. **归属校验仍然在中心做**，而且**每一片都做**；
6. `PushRemoteFrame` 的**实参个数不变**（`HubContractArityTests` 钉住）。

## 4. 关键设计 B：静止降帧 ＋ 上报「桌面静止中」—— M5.4-c②

### 4.1 🔸 更正：手段 7（静态场景跳过整帧编码）**其实已经天然实现**

方案 §1.6 写的是「DDA dirty rect 为空 ⇒ 不编、复用上一帧」，代价栏写着「**要维护「上一帧」与脏区状态机**」。
**实测后的更正**：DDA 是**增量投递**的 —— 桌面没变就不给新帧
（`WindowsDxgiScreenCapturer` 用 `AccumulatedFrames` 判，`LastPresentTime` 也在那里读出来）
⇒ **编码器根本收不到那一帧**（被控端日志自己写着「抓屏连续 N 次没有新帧……这是正常现象，**没有丢帧**」）。

⇒ **手段 7 不需要额外实现**，本批只**把这件事写清楚**（否则下一个人会去"实现"一个已经存在的东西）。

⚠️ 附带的**反向提醒**：`CapturedSurface.DirtyRects` **确实**抓回来了（`MaxDirtyRects = 64`），
**但本批不去消费它**。它的用处是 M5.5 的 ROI / tile；现在去用等于**在没有需求的地方动热路径**。

### 4.2 手段 8：静止时把轮询**退避**下来

**现状**：`idleTicks` 只做两件事 —— **记日志**（按 300 次节流）与**重置启动预算**
（`pumpStartedAt = Stopwatch.GetTimestamp()`）。轮询周期**恒为** `targetPeriod = 1 / TargetFps`。

**改**：`idleTicks` 超过阈值（≈2 秒，即连续 ~2×TargetFps 次没新帧）⇒ 把**抓屏轮询周期**按退避放大，
下限约 **2 fps** 的周期；一旦抓到新帧，**立刻**回到目标帧率。

⚠️ **两条纪律（都来自已经翻过的车）**：

1. 🔴 **不许把「降帧」做成「停止」**。`REF-M5 §14.14` 刚刚因为「静止画面被 Sweep 判死」翻过车 ——
   展厅里定格在一张图上的机器**就是**本批要救的那台。降帧的下限必须**仍然定期有上行**。
   好在 §14.14 之后中心已经认**「状态上报」**为活性（`Entry.LastAgentAt`）⇒ **两道保险**：
   ①降帧下限（保证抓屏轮询还在跑）、②每秒一次的计数上报（`#41` 刚加的，保证中心一直听得见）。
   **这两条要在同一个注释里一起说清楚**，否则下一个人优化掉任何一条都会让局面退回去。
2. ⚠️ **退避参数不许写死成"2 fps"就完事**：它要与 `TargetFps` 成比例（目标 60 fps 的机器上退到 2 fps
   比目标 12 fps 的机器上退到 2 fps 激进得多），且**上限**要能被将来 ③ 的自适应覆盖。

### 4.3 🆕 新增状态上报「桌面静止中」—— 顺手关掉一条挂账

**挂账原文**（`REF-M5 §14.14`）：修完活性判据之后，**「桌面静止」与「托盘卡住」在协议层上长得一模一样**
（都是"没帧、状态照报"）⇒ 中心只能靠猜。而**被控端早就知道**（`idleTicks`），它只是**不说**。

**落地**：

- `AgentRemoteSessionStateDto` **增一个字段**：`long? DesktopIdleMs`（"静止了多久"，毫秒）。
  🔥 **用"多久"而不是 `bool Static`**：`null` 与 `0` 与 `12000` 是三件不同的事
  （「旧客户端不认识」/「刚动过」/「已静止 12 秒」），而一个 bool 把它们压成两件 ——
  这与 `AgentInputStates` / `AgentAudioStates`「**不许压成布尔**」是同一条纪律。
- ⚠️ 这是**扩展字段**，不是**改签名**：Hub 方法的**实参个数不变** ✅（加字段只是 JSON 里多一个成员，
  旧客户端反序列化时忽略它）。
- **中心的用量**：本批**只用于显示与提示**（页面能写「被控端桌面静止中」而不是「画面卡住」），
  🔴 **不并入 `Sweep` 的生死判据** —— 同一批里既改协议又改生死，出问题就分不清是谁干的。
  真要让它参与判据，是**下一批的独立决定**（那时它已经有真机数据了）。

## 4.4 🔥 落地时补的一段：那句话**怎么**从托盘走到页面（七跳）

§4.3 只说了"被控端早就知道、它只是不说"，**没说它怎么说**。落地时必须先把这条链路定死 ——
少任何一跳都**不会报错**，页面只是永远显示 `—`，而 `—` 在契约里恰好又是一个合法取值
（"旧客户端"）⇒ 这种"少了一跳"会伪装成"版本较旧"，是本批最容易漏的一处。

| # | 跳 | 做了什么 | 为什么这么选 |
|---|---|---|---|
| 1 | 抓屏器 | `CaptureSurfaceAsync` 回 `null`（DDA 的"没有新帧"） | 这是"桌面没变"的**唯一**权威答案 |
| 2 | 托盘泵 | 把"最后一次抓到新画面"的时刻记在会话上（`_lastNewFrameAt`，QPC） | 用**时刻**而不是 `idleTicks`：退避之后每 tick 的时长会变，"第几次"会跟着漂 |
| 3 | 托盘泵 | `Session.DesktopIdleMs` = 现在 − 那个时刻 | `null` = 还没有起点（没 Prepare），**不是 0** |
| 4 | 托盘 `Handle` | 新动作 `desktop-idle` ⇒ `DescribeDesktopIdle()`，把数放进 `SessionCommandResult.DesktopIdleMs` | **结构化字段**，不并进 `Message`：靠解析人话抠数字，文案一改就静默变成 0/null |
| 5 | 服务 | 每秒**问一次**（与那条周期计数上报同一拍，问完再报） | 见下面三条"为什么" |
| 6 | 服务 | `Active.DesktopIdleMs` ⇒ `NewState(...)` ⇒ `AgentRemoteSessionStateDto.DesktopIdleMs` | **只改 `NewState` 一处**：那十几个位置参数少传一个会整体错位，编译器不报 |
| 7 | 中心 → 页面 | `Entry._desktopIdleMs` ⇒ `RemoteSessionDto.DesktopIdleMs` ⇒ 那一格 + 那句提示 | 见 §4.4 末尾"为什么不放 AgentStats" |

**为什么是"服务每秒问一次"，而不是别的三种做法**

| 备选 | 否决理由 |
|---|---|
| 走**码流管道**（塞一条"状态帧"） | 那是热路径，而"帧数"这个判据与"帧"这个语义会当场分叉；**它是本仓最不该出错的一处** |
| 让托盘**主动推**给服务 | 托盘不持有凭据（M4 的设计），而且**方向反了**：托盘是服务端、服务是客户端 |
| 服务自己数"多久没收到帧" | 🔴 **这正是本步要消掉的那个"猜"**：编不出来 / 链路丢了 / 桌面没动，计数上一模一样 |

**三个必须写死的细节**

1. **超时 1 秒**（不是管道自带的 5 秒）：这条查询与"每秒一次的计数上报"同一拍，
   而后者是"这路还活着"的**唯一正证据**（中心 20 秒收不到就判死）——
   用 5 秒等一格**显示**，等于为了装饰品牺牲生命体征。
2. **问失败时保留上一次的值**，不 `null` 掉：一次超时不等于"这台机器突然不认识这个字段了"。
   而失败本身**只在状态翻转时记一行**（一秒一条会把真问题刷没）。
3. **每片都写清楚 `null` / `0`**：`0` 是"刚动过"（**一个答案**），`null` 是"这台机器不提这件事"。
   链路两端各有一条用例钉住这一侧（服务 3 条、中心 4 条、前端 6 条）。

**为什么 `DesktopIdleMs` 放在 `RemoteSessionDto` 上、不进 `AgentStats`**

`AgentStats` 有一条为 `null` 的判据（"一帧都没发过就还不报数"），而
**"从开流第一秒桌面就没动过"的机器恰恰一帧都发不出去** —— 塞进去的话，
最该被解释的那一台在页面上反而什么都没有。所以这条信息走**会话级字段**，与计数彻底解耦
（用例 `The_idle_time_survives_when_no_frame_has_ever_been_sent` 钉住这一点）。

## 5. 关键设计 C：运行时自适应 —— M5.4-c③（建议另开一批）

### 5.1 闭环的两个方向（能分开，就必须分开）

| 方向 | 判据落在哪 | 本批 |
|---|---|---|
| **本地可判** | 被控端自己量得到：`ActualFps` vs `TargetFps`、编码耗时 vs 帧间隔、`idleTicks` | ② 已覆盖"静止"；「**编不动就降目标帧率**」放这里 |
| **需要跨机反馈** | 观看端才知道：前端 `overflow` 次数、解码器重建次数、将来可能的带宽估计 | ③ |

### 5.2 反馈通路（新增一条**下行指令**）

中心已有 `RemoteSessionCommandDto`（`action`: `start` / `stop` / `grayscale` / …）⇒
新增一个 `tune`，带 `MaxFps` / `BitrateBps`。

⚠️ **`RemoteStreamRequest.MaxFps` 已经存在，但它只在开会话时被读一次**（`RemoteStreamHost` 里
`Math.Clamp(command.MaxFps ?? DefaultMaxFps, MinFps, MaxFps)` 之后写进 session 对象）
⇒ 要把它变成**运行时可改**：一个 `volatile` 字段 + 泵循环每轮读。

⚠️ **码率的运行时可改性要实测**：MF 的码率是编码器属性。**改属性通常要重建编码器**
（`CODECAPI_AVEncCommonMeanBitRate` 支持运行中设，但**在 MF 硬编上是否立即生效、会不会打断 GOP**，
本仓**没有实测过**）⇒ 这一条**先做实验再定设计**，不许在方案里当成已知可用。

> ✅ **已实测（10-17）—— 见 §5.4：运行中改不动，只能重建（≈0.3 s 空窗）。本节这条 ⚠️ 已兑现。**

### 5.3 与 §1.5 降级链对齐

`§1.5` 写的是「带宽不足 ⇒ 降码率 → 降帧率 → 降分辨率」。**本批只做前两级**；
**降分辨率不做**（要重建整条 GPU 管线，且与「1:1 要保细节」矛盾）⇒ 明确留在链上、留后。

### 5.4 🔴 前置实验（10-17 实测）——**`tune` 的码率那一半不成立**

> 原文写的是「新增一个 `tune` 下行指令，带 `MaxFps` / `BitrateBps`」。**实验把后半截否掉了，**
> 前半截（帧率）恰好是唯一成立的那个 —— 见本节末尾的表。
> 这一段是**量的**，不是推的：临时探针（已删）在真机上直接对运行中的 MF 硬编码器
> 调 `ICodecAPI::SetValue`，同时用 `GetValue` 回读、并用字节数/秒交叉验证。

**环境**：Intel® Quick Sync Video H.264 Encoder MFT｜1280×720@30｜
内容＝**逐帧全帧噪声**（不可压缩，所以字节数完全由码控决定，旋钮有没有用一眼能看出来）。

| 码控 | 旋钮 | `SetValue` 返回 | `GetValue` 回读 | 实测码率 | 判读 |
|---|---|---|---|---|---|
| **Quality（生产就是它）** | `Quality` 70 → 20 | `0x00000001`（**S_FALSE**） | **仍是 70** | 85.48 → 85.24 Mbps（**-0.3%**） | 没接受 |
| Quality | `Quality` 20 → 70 | `0x00000000`（S_OK） | 70 | 85.47 Mbps | 只在"设成它已经是的那个值"时 S_OK |
| **CBR** | `MeanBitRate` 8 → 2 Mbps | `0x00000001`（**S_FALSE**） | **仍是 8000000** | 8.63 → 8.40 Mbps（**-3%**） | 没接受 |
| CBR | `MeanBitRate` 2 → 8 Mbps | `0x00000000`（S_OK） | 8000000 | 8.34 Mbps | 同上 |

三条**必须一起读**的结论：

1. **运行中改不动**：这台 MFT 在已经 `StartStreaming` 之后拒绝改这两个属性
   （回 S_FALSE、回读不变、字节数不变）。**S_OK 只出现在"设成当前值"时** ——
   谁只看返回值谁就会以为成功了。
2. **Quality 模式下 `MeanBitRate` 连"上界"都不是**：8 Mbps 的提示喂噪声跑出 **85 Mbps**（差 10 倍）。
   所以生产（默认 `Quality`）**根本没有码率这个量可调**；要限码率必须换码控模式。
3. **两种改法都没有换关键帧**（关键帧计数 0）—— 因为压根没生效，所以"会不会打断 GOP"
   这个问题的答案是"轮不到它发生"。

**既然只能重建**，那就得先量重建的价：

| 量 | 实测（720p） |
|---|---|
| `TryCreate`（建编码器） | **137 / 141 / 212 ms** |
| 建好后到"第一帧真的出来" | **147–166 ms**（喂 3 次） |
| 合起来：观众看到的空窗 | **≈ 0.3 秒** |
| 重建后第一帧 | **必为关键帧**，噪声内容 691 KB（真实桌面小得多） |

⇒ **③ 的正确切法（据此改写）**：

| 项 | 原设计 | 实测后 |
|---|---|---|
| 帧率 | `tune` 下行改 `MaxFps` | ✅ **成立**：帧率是**本机 pacing**，不碰编码器，零代价（② 已实现退避，只差"从中心改"） |
| 码率 / 质量 | `tune` 下行改 `BitrateBps` | 🔴 **不成立**：只能**重建编码器**，一次 ≈0.3 s 空窗＋一张关键帧 ⇒ 必须有**冷却＋迟滞**，否则来回重建＝一直在黑 |
| 分辨率 | 不做 | 不变（也是重建，且与 1:1 矛盾） |
| 中心侧反馈源 | 「前端 `overflow` / 解码重建次数」 | 不变，但**现在没有**；没有它，码率就无从判起 |

⚠️ **两条诚实的边界**：

- 这只是一台机器上的**一个** MFT（Intel QSV H.264）。NVIDIA NVENC / AMD 未必一样，
  **不许**把这条结论写成"MF 硬编都不支持运行时改码率"。它证明的是
  **"不能假设它行"**，而不是"它一律不行"。
- 720p 的重建价不等于 4K 的重建价（**4K 真机本机不可得**，见 §6.1）。

## 6. 验收判据

### 6.1 🔴 先说清本机**做不到**的那条

**本机显示器只有 2160×1440**（M5.4-a §5.1 第 1 条）⇒ **8K 真机端到端在本机物理上不可得**。
⇒ 「**8K 真机达标**」仍然是一条**挂账**（与 HEVC 端到端同一条），本批**不假装**它被验过。
本批能证的，是**分片机制本身**与**量级的算术**，分两层（下一节）。

### 6.2 分片怎么验（三层，各证各的）

| 层 | 怎么证 | 证的是什么 |
|---|---|---|
| **单测（中心）** | 直接对重组器灌片：① 3 片拼回**逐字节相等**；② **缺一片** ⇒ 丢帧 + 计数 + `NeedKeyframe`；③ **新序号打断** ⇒ 丢旧帧 + 计数；④ `ChunkCount`/`ChunkIndex` 越界、同片重复、`ChunkCount` 不一致 ⇒ 一律丢帧、**不抛** | 重组器的**正确性与防御性** |
| **单测（被控端）** | 用假 hub：① 小帧 ⇒ **仍是一条 `PushRemoteFrame`**（老路不变）；② 正好等于单片上限 ⇒ 单片；③ 上限 + 1 字节 ⇒ 2 片；④ 6 MiB 假帧 ⇒ 片数 = `ceil(len / 上限)` 且**拼接逐字节相等**；⑤ ack 带 `NeedKeyframe` ⇒ `RequestKeyframe()` 被调用 | 分片点的**切片正确性**与**惰性** |
| **端到端（冒烟）** | 加一个**临时**参数（如 `--chunk-threshold 65536`）把分片阈值**降到 64 KB**，跑一次完整的真机冒烟 ⇒ **正常帧也走分片路径** | 「分片这条路**端到端是通的**」（抓屏 → 浏览器画面） |

> 🔴 **必须写清楚的一句**：**「降阈值跑通」≠「8K 跑通」**。
> 它证明的是「分片机制没有 bug」；而「8K 会不会撞」是**算术**（`ceil(帧字节 / 片上限)`），
> 由单测覆盖。**把这两件事说成一件，就是编数字。**

### 6.3 ② 的验收

### 7.1 🔴 **本批新增的一条写法纪律：「用例造的数据，必须由生产那一份代码造出来」**

分片这条路上有两端（被控端切 / 中心拼），而**用例自己再写一份切片**是最容易发生、
也最不容易被发现的一种假绿：那样一来，"3 片拼回来逐字节相等"证明的是
**「用例切的片能被拼回来」**，而生产切片器把最后一片多切一个字节时，用例**全绿**。

⇒ 落地方式只有一条：**切片这件事在 `RemoteFrameChunker` 里只有一处实现**，
被控端与用例都调它（`Slice` 允许传一个小的片上限，那只是为了免得用例去分配 6 MB 的假码流
—— 走的是同一条代码路径）。

⚠️ 但它有一条**边界**：`ChunkCount` 荒唐 / 下标越界 / 片数为 1 / 同序号片数不一致 /
累计字节超单帧上限 —— 这五种片**生产代码永远造不出来**（那正是它们要防的东西），
所以它们**必须**在用例里手搓。判据是「**生产代码造得出这种形状吗**」，
而不是"能不能偷懒用现成的切片器"。

> 🔥 **写法纪律（`#42` 的教训）**：凡是「**先写用例再改代码**」的，**第一版用例必须是红的**。
> `RemoteSessionSweepTests` 第一版**修完仍然红 —— 红的是用例不是代码**（把两个事件时刻**一起**推旧了）。
> ⇒ 分片这批的用例，**先把红的跑出来贴进文档**，再动生产代码（本轮的两条红记录见 §9.4）。

### 9.1 步 2 的落地：单槽重组器

`RemoteFrameReassembler`（中心，每会话一个实例）——**离锁拼字节**、
**防御性上限一律"丢帧 + 计数"绝不抛**、**按下标拼而不按到达顺序拼**。

🔴 **一处"读完文档才看得见"的关键判据**：拼齐的判据是 `_received < _chunkCount ⇒ 返回 null`（半帧不是帧）。
它一旦被删掉，`pieces[index]` 会直接抛 `KeyNotFoundException` ——
而这条路上"抛"的后果是**掐断整条 Hub 连接**。
本轮的用例组**真的抓到过一次**（见 §9.4 的"红"记录）。

### 9.2 🔥 步 3 的落地：**只有一处切片实现**

- 新文件 `src/ControlServer.Contracts/RemoteFrameChunker.cs`：
  `CountFor` / `NeedsChunking` / `Slice` 三个方法，**不写任何字面量尺寸**
  （三个数仍然只有 `RemoteStreamLimits.SignalRMessageBytes` 一个根）。
- 🔥 **它同时被两端调用**：被控端真正切片时用它，
  **用例造片时也用它**（`RemoteFrameReassemblyTests` 里**没有**任何自己的切片代码）。
  这一条不是洁癖 —— 见 §7 那条新纪律。
- 被控端那条路拆成两层：`PushRemoteFrameAsync`（生产唯一入口）→
  `internal static PushFrameAsync(invoke, frame, ct)`（**全部逻辑**）。
  后者收一个"发射器"委托，于是用例能拿一个**假 hub** 看见
  "到底发出去了几条什么消息" —— 而 `HubConnection` 是个具体类、方法不可替，不抽这一刀就没法验。

### 9.3 ✅ 步 5 已做 ⇒ 这个标志**有人接了**（本节保留"没做时是什么样"的历史）

中心在重组失败时会把 `AgentIngestAckDto.NeedKeyframe = true` 带回去。
**步 5 之前**：被控端没有任何一行读它（`PushFrameAsync` 只看 `Ok`）——
那是这一批里**唯一一处"协议已经通了、行为还没通"**。**步 5 已把它接上**（见 §9.6）。

⚠️ **步 4/步 5 之前与之后的差别，必须分清**（否则会把三件不同的事混成一件）：

| | 丢一帧之后的表现 | 有谁"知道" |
|---|---|---|
| **步 4 之前** | **花屏**到下一个关键帧 | **没有任何一层** —— 那正是这条洞最坏的地方 |
| **步 4 之后** | **冻结**到下一个关键帧（队列里那些非关键帧被丢掉，不再上屏） | **前端**知道（`gaps` 与 `resets` 都涨了） |
| **步 5 之后** | 恢复到**下一帧** | **被控端**也知道（它收到 `NeedKeyframe` 就去编一个 IDR） |

⇒ 「**最长约 5 秒**」这个时长三行都一样（`gopSize = 60` ÷ 12 fps）；变的是**它的样子**与**有没有人知道**。
把「花屏」写成「冻结」不是措辞问题：花屏看起来像**编码器坏了**（于是人去查编码参数，
而真因是"参考帧压根没到"），冻结是一个**明确可知的状态**，而且页面上有计数。

> 🔥 **两个观察点，不许合成一个**：中心的 `ReassemblyDroppedFrames` 是"**中心自己丢了**"，
> 前端的 `gaps` 是"**我根本没收到**"。它们是同一条纪律的又一次应用
> （同 `frameDiagnosis` 里"被控端发 N / 中心收 M"）：**两边各自记一次，对不上就说明中间那一段在说谎**。
> ⚠️ 而"两个数都对得上、却仍有缺口"的那种情况（前端 `gaps` 涨、中心 `ReassemblyDroppedFrames` 不涨）
> 指向的是**中心→浏览器那一段**（第 ⑤/⑥ 跳），**不是分片**。

### 9.5 🔥 步 4 的落地：序号体检（`RemoteVideoBuffer.checkSequence`）

改动集中在 `web/src/remotePlayback.ts`：新增私有字段 `lastReceivedSeq`、私有方法
`checkSequence`（`push()` 里在**入队之前**调一次），`VideoBufferStats` 新增 `gaps`，
面板那格读数从 4 个数变 5 个（`排队 / 挤出 / 过期 / 未上屏 / 未收到`）。

**为什么是"入队之前"**：断链时要丢的是"队列里那些**还没解的旧帧**"，
而**刚到的这一帧是要留下的** —— 它恰好是关键帧的话，画面就是从它接上的。
这与队列溢出那条路（`push` 里的 `while`）是同一条纪律，两条路共用同一个 `breakChain()`。

#### 🔴 新发现 1：缺口判据指向得**很准** —— 被控端丢帧**不占序号**

`RemoteStreamHost.OversizeGiveUp` 那段注释里记着一条**实测**结论（逐字）：

> 这一帧**不占序号**（序号是在下面构造帧头时才取的，而丢帧根本走不到那儿）…
> 曾经想当然地以为"丢帧会在序号上留一个洞"，实测 `Sequence` 是连续的。

⇒ 被控端本地的丢帧由帧头里的 `dropped` 回答，**序号是连续的**。
于是"序号不连续"这件事只可能意味着**帧在离开被控端之后丢了** ——
而整条链路上能"悄悄丢一帧"的只有中心那个**容量 1 ＋ `DropOldest`、且不回报**的 `Fanout`（§2.1 第 ④ 跳）。

🔥 **这就是那条洞唯一的窗口**：中心不回报自己丢了帧，前端的 `gaps` 是链路上**第一个**能看见它的数。

#### 🔴 新发现 2：缺口检测的基线必须是「**收到的号**」，不是「**画过的号**」

这是本步最容易踩、踩了之后症状又离真因最远的一个坑：

- `lastPaintedSeq` **只在"上屏"时才前进**（`doPaint`），而队列最多能积 `VIDEO_QUEUE_LIMIT = 12` 帧；
- 拿它当基线 ⇒ 队列里积了 5 帧，第 6 帧一到就被读成"**跳了 5 个号**" ⇒ **每一帧都重建解码器**；
- 症状：**画面永远停在关键帧上**（一直在等下一个关键帧才有图），**没有任何报错**，
  而 `resets` 一路涨 —— 看起来像"中心一直在丢帧"，于是人跑去查中心。

⇒ 新增一个只由 `push()` 维护的 `lastReceivedSeq`（`clear()` 里一并归零）。
**用例里专门有一条钉它**（"队列积压时**不许**误报"：先让一帧真的上屏，再连灌 10 帧、一次都不 tick）。

| 刀 1 | `const previous = this.lastReceivedSeq` → `…lastPaintedSeq`（"顺手复用现成字段"的写法） | **6 红**（含那条"积压不许误报"） |

### 9.6 🔥 步 5 的落地：四跳链路 ＋ 两处"明确写出来的例外"

**链路形状（一条反向信号，横跨两个进程）**

```
中心 RemoteFrameReassembler 拼不起来
   └─ ack: AgentIngestAckDto.NeedKeyframe = true      ← 步 2 就做了
        └─ AgentConnection.PushFrameAsync 读它          ← 第 1 跳（发帧路径上）
             └─ RemoteSessionCoordinator.RequestKeyframe（**1 秒节流**）  ← 第 2 跳
                  └─ 会话指令管道 SessionCommandMethods.RemoteStream
                       └─ RemoteStreamHost.RequestKeyframe → Session.RequestKeyframe（Interlocked 标志）  ← 第 3 跳
                            └─ 推流泵下一轮 wantKeyframe = true ⇒ 编码器出 IDR    ← 第 4 跳
```

**为什么非绕这么一圈**：丢帧发生在**中心**。托盘那边"我只是把每一片都发出去了"——
它**无从知道**对面拼不拼得起来。这个信号只能由中心往回带，而托盘与发帧那条路
**不在同一个进程**（`Agent.Tray` / `Agent.Service`）⇒ 必须经会话指令管道。

**为什么节流放在服务侧（收到的那一侧）**：中心只知道"我这帧拼不起来了"，
它**不知道对面多久能补上一个**——让它去重，等于让它猜。
服务侧是"知道托盘有一路流正在跑"的那一侧，它才该决定要不要麻烦托盘。
窗口 **1 秒 ≈ 12 帧一个 IDR**：既是"恢复得快"与"不把码率打爆"之间的一格，
也是中心持续丢帧时能长期承受的上限。

**为什么按「帧」去重、而不是按「片」**：一帧十几片，中心在同一个故障下会**每片都回**这个标志
（它每次都判"这一帧拼不起来"）。照着每片各要一次 ⇒ 把**一次丢帧放大成一路 IDR**
（8K 的 IDR 正是整条链路上最贵的东西）。所以 `PushFrameAsync` 里用 `needKeyframe |= ack.NeedKeyframe`
累积、**循环外只问一次**。

**⚠️ 为什么没用 `IVideoEncoder.RequestKeyframe()`（那个方法本来就在）**

`RemoteDesktop.cs` 里确实有 `IVideoEncoder.RequestKeyframe()`，但这里走的是**泵里的 `wantKeyframe`**：

1. `wantKeyframe` 是**既有且已被用例钉住**的机制（`RemoteStreamOversizeTests` 断言 `ForceKeyframeFlags` 的形状），
   而"丢帧后补关键帧"本来就是它；再来一条平行的路，就会出现"两种补关键帧的方式，谁生效取决于调了哪个"。
2. `Session` 只持公共底座 `IFrameEncoder`（见 `Session.Grayscale` 那段注释：**这里看不到更强的类型**），
   拿不到 `IVideoEncoder`。
3. `forceKeyframe` 参数是**同步**传到"这一帧的编码调用"上的，没有"请求了但下一帧没用上"的窗口。

**两处例外（必须写出来，否则下一个人会"顺手改回去"）**
| 例外 | 在哪 | 为什么 |
|---|---|---|
| `Active` 的字段**不在 `_gate` 内改** | `_lastKeyframeRequestTicks`（`Interlocked` + CAS） | `RequestKeyframe` 的调用点在**发帧路径**上，每帧都可能来一次；为一个时间戳去抢账本锁，等于让它和建会话/状态上报互相排队。**第 2 个例外**（第 1 个是中心的 `_reassemblyDropped`） |
| **同步 `void` ＋ fire-and-forget** | `RequestKeyframe` → `_ = SendKeyframeRequestAsync(...)` | 同上：不许让发一帧去等一次 IPC 往返。⚠️ 于是 `void asyncFn()` 那条纪律必须**显式兑现** —— 被调的那个方法**从第一行到最后一行都在 `try` 里**，异常落 `Warn` 日志，绝不外泄到 SignalR 调用栈 |

**顺带修掉的一个静默洞**：泵里原来是 `wantKeyframe = false;`（**无条件**清）。
而 `forceKeyframe: true` 只是**请求**不是**命令** —— 编码器可能这一帧给不出 IDR
（忙 / GPU 重建 / 参数集没就绪）。无条件清 = 请求永久消失在空气里，
而两边日志都写着"请求已送出、帧也发出去了"。改成 `if (payload.IsKeyframe)`，
与同段代码里 `_oversizeKeyframeStreak` 只在关键帧上清零是同一条纪律。

**"先红后绿"四处实测（不是推的）**

### 9.7 🔥 步 6 的落地：**把"死代码"逼到端到端**

步 6 要回答的问题与前面五步不同：前五步都能用单测证明，**而"被控端真的切了 / 中心真的拼了 /
浏览器真的画了"只能靠一台跑起来的机器**。而这里卡着一个物理事实：

> **本机显示器只有 1920×1280**（实测），一条消息装得下 8 MB ⇒ **分片那条路平时是死代码**。
> 要碰到它，就得把"一片能装多少"降下来。

#### ① 诊断旋钮：环境变量（不是配置项、不是命令行）

`AgentConnection.ChunkThresholdBytes`（默认 = 协议上限）＋ `ResolveChunkThreshold()` 解析
`CONTROLSERVER_CHUNK_THRESHOLD_BYTES`，由 `AgentRuntime.AttachRemoteSession` 读一次。

| 决定 | 理由 |
|---|---|
| **走环境变量**，不进 `appsettings` / 命令行 | 它**不该**看起来像一个可配置的产品能力（否则会有人设成 1 MB 再抱怨 CPU 高）。环境变量不进配置快照、不进客户机 UI、**随进程结束自动消失** —— 与"这次诊断"对齐 |
| **只许调小**，非法值一律回落 + **警告** | 调大不会更省：它会让中心那条 SignalR 消息超出 8 MiB ⇒ **掐断整条连接**（心跳 / 遥测 / 配置 / 音频全在上面）。而回落**必须留痕** —— 静默回落等于"跑了一整轮老路却以为在验分片" |
| **不在发帧路径上二次校验** | 那是每秒几十次的热路径，而输入只在启动那一刻来一次。已有的 `Slice` 会在片数荒唐时抛（那是"我们自己的参数错"，该炸） |

⚠️ 一个必须算清的边界：`64 KiB × MaxChunkCount(1024) = 64 MiB = MaxFrameBytes` —— **刚好闭合**。
再往下（16 KB）理论上会让 64 MiB 的帧算出 4096 片 ⇒ `Slice` 抛。冒烟脚本对 `< 64 KB` 会明确提示。

#### ② 可断言性：中心新增 `ReassembledFrames`

🔴 **这一步不是"顺手加个指标"，它是整条端到端判据的地基**：
旋钮没接线 / 环境变量名打错一个字 ⇒ 冒烟会**安安静静跑完一整轮老路、画面一切正常、然后报绿**。
那是一张**假 PASS**，比不跑更坏。

所以加 `RemoteSessionStatsDto.ReassembledFrames`（中心把多片拼成的帧数），判据是它 `> 0`。
它**与 `FramesReceived` 并排、绝不合并**：

| 读数 | 含义 |
|---|---|
| `FramesReceived > 0 && ReassembledFrames == 0` | 这一路**从没走过分片**（2160×1440 / 4K 的正常状态） |
| 两者都在涨 | **分片路真的在工作** |
| `ReassembledFrames == 0 && ReassemblyDroppedFrames > 0` | 走了但**一帧都没拼成** —— 画面会一路花，合起来才指向真因 |

🔴 **它刻意不进观看页**（与 `ReassemblyDroppedFrames` 同一条纪律）：分片是**传输层**的事，
前端看到的是已拼好的整帧。把"重组帧数"画到页面上，等于告诉前端"这帧是几片拼的"——
而那正是**方案乙（终止在中心）**立身之处：跳 4/5/6 与前端一律零改动。
它只出现在 `/api/remote/sessions` 与冒烟判据里。

#### ③ 两轮冒烟（都在本机、都走系统 Edge 155）

| 轮次 | 命令 | 结果 |
|---|---|---|
| 默认（验**惰性**） | `remote-e2e.py --no-pointer` | **13/13 PASS**｜1920×1280｜解码器重建 0、解不出 0｜帧时延 117~135 ms |
| 降阈值（验**分片**） | `… --no-pointer --chunk-threshold 64` | **16/16 PASS**｜**收到帧 74 / 拼出来的帧 74 / 重组丢弃 0**｜帧时延 123~135 ms |

🔥 **第二轮那三个数是本批最强的一条证据**：74 帧**全部**由多片拼成（64 KB 阈值下 1920×1280 的帧约 5 片），
而帧时延与默认路径基本一致（123~135 vs 117~135 ms）⇒ **分片没有引入可见延迟**。

⚠️ 那两个数**每次跑都不一样**（70 / 74 都出现过 —— 取决于采样窗口里落了多少帧）。
判据是**它们相等**（每一帧都走了分片路），**不是等于某个具体数字**。

#### ④ 🔴 顺带修掉一个"看不见异常"的洞（验证工具自身，代价 3 轮）

`remote-e2e.py` 的 `finally` 里那句 `sys.exit(...)` 在 `finally` 里 ⇒
**它抛出的 `SystemExit` 会把正在传播的那个异常整个盖掉**（Python 不打印被 finally 覆盖的异常）。
现场表现 = **"只跑了 4 项就正常退出 0，没有任何报错"**，而真因
（`ModuleNotFoundError: No module named 'playwright'`）一个字都看不见。

修法：`sys.exc_info()` + `traceback.print_exception(..., file=sys.stdout)`，并让异常也计入失败退出码。
⚠️ **必须 `file=sys.stdout`**：默认写 stderr，而重定向到文件时两个流各自缓冲 ⇒
traceback 会跑到**文件最前面**，把"下面才是真因"这句提示指到空处（实测踩过）。

同时记两条**环境事实**（它们各自都能白烧一轮）：
1. 冒烟必须用 **`C:\Users\IYLONG\.workbuddy\binaries\python\envs\default\Scripts\python.exe`**
   —— `PATH` 上那个受管的 3.13.12 **没装 playwright**（冒烟会静默走到浏览器半边才炸）；
2. `run_browser(...)` 是**独立函数**，不是 `main` 的闭包 ⇒ 在它里面写 `args.xxx` 是
   **`NameError`，而 `py_compile` 查不出来**（只能靠跑）。新参数必须从 `main` 显式传进去。

| 中心 | `Expected … DesktopIdleMs to be 4200L … but found <null>` ×4 | `ApplyState` 还没赋值 |
| 前端 | 模块不存在（vitest 直接报解析失败） | 文件还没写 |

> 🔸 顺带一条纪律：**"守卫类"用例在骨架期本来就是绿的**（"答不出 ⇒ null"、"从没报过 ⇒ null"）。
> 那不代表它们没用 —— 它们守的是**将来有人把 `null` 改成 `0`** 的那一刻。

#### ③ 步 8：静止退避

| 件 | 内容 |
|---|---|
| `RemoteStreamPacing`（新） | `PollPeriod(targetFps, idleFor)` / `BackoffFps(targetFps)`；常量 `IdleBackoffAfter = 2s`、`IdleBackoffRatio = 6`、`MinIdleFps = 2`、`MaxIdlePeriod = 1s` |
| 泵 | 空闲分支按 `PollPeriod` 决定这一轮的睡眠；进/出退避各打一句（`退避到 N fps` / `恢复目标帧率`） |
| 日志节流 | 从"每 300 次"改成"**每 10 秒**"：退避之后每 tick 从 16 ms 变成 100 ms，同一个 300 次会从 10 秒变成两分半 |

**退避曲线**（`BackoffFps = Min(target, Max(2, target/6))`）：

| 目标 | 退避后 | 周期 |
|---|---|---|
| 12 fps | 2 fps | 500 ms |
| 30 fps | 5 fps | 200 ms |
| 60 fps | 10 fps | 100 ms |
| 1 fps | 1 fps（**不许比目标更快**） | 1 s |

#### ④ 两条用例自身的错（**红的是用例，不是代码**，都已就地修掉）

1. **"两处读数必须逐毫秒相等"是错的**：`DesktopIdleMs` 是"到此刻为止"的时长，
   两次读之间本来就隔着几毫秒 —— 第一版红在 `1211 vs 1214`。
   改成"两处差值 ≤ 500 ms"（真正该钉的不变式是"**同一个起点**"，不是"两次读数一样"）。
2. **没接接收端 ⇒ 推流循环根本没开始抓屏**：推流循环要等 `RemoteStreamProtocol.ConnectTimeoutMs`
   那一段先连上。不接的话，量到的"静止时长"只是"从建会话到现在过了多久" ——
   一条**看起来对、其实什么都没证**的绿（第一版红在 `416 ms` 与 `1211 ms` 两个数上同时露馅）。

#### ⑤ 灵敏度检查（两刀，都已回滚）

| 刀 | 期望 | 实际 |
|---|---|---|
| `BackoffFps` 去掉 `Math.Min(targetFps, …)` | 只有"不许比目标更快"那条红 | ✅ 恰好 1 红 |
| 去掉 GPU 路径上的 `ResumeTargetPacing()` | 只有"立刻恢复"那条红 | ✅ 恰好 1 红 |

#### ⑥ 🔴 三条**诚实的边界**（不许算成"已验"）

1. **`MaxIdlePeriod` 当前是一条"安全带"，不是一个生效的分支**：
   现有参数下 `BackoffFps ≥ Min(target, 2)` ⇒ 周期永远 ≤ 1 秒，**上限从来不会被触发**。
   它防的是"将来有人把 `MinIdleFps` 或比例调小" —— 所以**拆掉它不会有任何用例变红**，
   这一点必须写明，别让下一个人以为它被测过。
2. **内存（MJPEG）路径没有"桌面静止"这个概念**：那条路每轮必出一帧（GDI 抓的是整屏，
   不检测变化）⇒ 它的 `DesktopIdleMs` 恒接近 0，页面显示"画面在变"。
   那不是 bug，是这条路的性质 —— 已在 `RemoteStreamStatus.DesktopIdleMs` 与
   `Session.DesktopIdleMs` 两处注释里写明。
3. ~~🔴 **退避行为端到端（真机冒烟）没有被覆盖过**~~ —— **已在 §9.9 补上**
   （`--idle SEC`：盖住桌面 10 秒 ⇒ 退避 2.1 秒时触发、撤布立刻恢复，26/26）。
   补的过程本身是个坑：**第一版盖布自己没有光标**，于是抓屏器每帧都报"指针动了"，
   屏幕上明明 0 像素变化，却永远"有新帧" —— 详见 §9.9 ③④。
   **教训留在这里**：那一轮冒烟的三条红（静止时长不涨 / 无退避 / 无恢复）
   看起来完全像产品 bug，而真因在工具里。**"造环境"的工具必须和被测代码一样被怀疑。**

### 9.9 端到端补验：让桌面**真的**静止（`--idle SEC`）

> 起因：§9.8 ⑥.3 那条边界 ——「退避只被单测验过」。补它的过程本身比结论更值钱：
> **第一版工具是错的，而且它错得和产品 bug 一模一样。**

#### ① 加了什么

| 件 | 内容 |
|---|---|
| `SolidOverlay`（`deploy/smoke/remote-e2e.py`） | 一个**置顶纯色全屏** Win32 窗口（`WS_POPUP｜WS_EX_TOPMOST｜WS_EX_TOOLWINDOW｜WS_EX_NOACTIVATE`，类过程直接用 `DefWindowProcW` + 纯色画刷），独立线程跑消息泵 |
| `verify_idle_backoff()` | 盖住 `SEC` 秒期间每秒读一格「桌面静止」+ 会话状态，撤布后等恢复；**5 条判据** |
| `--idle SEC` | 默认 0＝跳过（与 `--backdrops` / `--shapes` / `--chunk-threshold` 同类） |

为什么必须"盖住"而不能"人别动鼠标"：观看页播的**就是这块屏**，屏幕上任何东西在动
（任务栏、别的窗口、本脚本自己的日志窗口）`DesktopIdleMs` 都不会涨。

#### ② 第一轮：3 条红，而且红得"很有道理"

```
· t=9.1s  画面在变｜会话 streaming｜帧 155          ← 盖布**挂着**，10 秒里一帧都没停
[FAIL] 静止时长真的涨起来了（≥ 2 秒）   最长读到 None 秒
[FAIL] 托盘进了静止退避（日志有「退避到 N fps」）
[FAIL] 撤掉盖布后立刻恢复（日志有「恢复变化」）
```

同时独立测了一次**像素**：盖布期间连拍 5 张，**任意两张之间最大像素差 0、变化像素 0**
（中心像素恒为 `(38,38,38)`）；撤布后立刻恢复成 `(255,255,255)`。
⇒ 屏幕**确实完全静止**，而抓屏器**仍然每 tick 都认为"有新帧"**。

#### ③ 一次**错误的根因假设**（记下来，因为它的证据也很像真的）

第一反应是"DWM 在无脑 present"：只要有任何被遮挡的程序在自绘，`AccumulatedFrames != 0`
就一直成立，而"present 过"≠"像素变了"。为了坐实，用一个**临时探针**（已删）直接读
`WindowsDxgiScreenCapturer.Diagnostics`：

```
第 1 次 → NoDesktopUpdate  accum=0   meta=0     shape=4096  present=0
第 2 次 → TimedOut         accum=0   meta=0     shape=4096  present=0
第 3 次 → DesktopUpdated   accum=1   meta=16    shape=4096  present=1665917373726
第 4..24 次 → PointerUpdated  accum=0   meta=0     shape=4096  present=0
=== accum!=0 且 meta==0 → 0 次；accum==0 → 23 次 ===
```

**假设当场被推翻**：`AccumulatedFrames` 几乎恒为 0（DWM **没有**在乱 present）。
真正每 tick 都在变的是 **`PointerUpdated`（22/24）** —— 而它成立的判据是
`LastMouseUpdateTime` 一直在变，`PointerShapeBufferSize` **每帧都是 4096**（整个光标形状每帧重发一遍）。
光标明明一动不动。

#### ④ 真因：**盖布自己没有光标**

`WNDCLASSW.hCursor = NULL` ⇒ 光标到了这块窗上"没人负责它" ⇒ 系统反复重设它
⇒ DDA 每帧都报一次"指针更新" ⇒ 抓屏器 `pointerMoved = true` ⇒ `changed = true`
⇒ **静止计时永远归零**。

一行修掉（`wc.hCursor = LoadCursorW(NULL, IDC_ARROW)`），同一探针立刻变：

```
第 2 次 → DesktopUpdated   accum=1   meta=16    shape=0    ← 形状不再重发
第 3..24 次 → TimedOut      accum=1   meta=16    shape=0    ← 22/24 都是"没有新帧"
=== accum!=0 且 meta==0 → 0 次；PointerUpdated → **0 次** ===
```

> 🔴 **这一条的教训比整节都重要**：`DesktopIdleMs` 的判据是
> 「**抓屏器没报新帧**」，而"抓屏器报新帧"里有一条**与画面完全无关**的来源 ——
> **指针**。所以任何"让桌面静止"的工具，都必须先把自己那只手指安顿好。
> 而**像素级探针（截图连拍）对这条完全瞎**：它看到的是 0 变化，于是会把人
> 引向"产品没退避"这个错误结论（这次就被引了半个多小时）。

#### ⑤ 绿了（26/26）

```
· t= 8.1s  已静止 7 秒｜会话 streaming｜帧 107
[PASS] 静止时长真的涨起来了（≥ 2 秒）   最长读到 8 秒
[PASS] 托盘进了静止退避（日志有「退避到 N fps」）
· 退避：… 桌面已静止 2.1 秒，抓屏轮询从 12 fps 退避到 2 fps（这只是省 CPU，**不是停止**：…）
[PASS] 静止期间中心没把它判成死机器（会话始终 streaming）  全程 streaming
[PASS] 撤掉盖布后立刻恢复（日志有「恢复变化」）
· 恢复：… 桌面恢复变化，抓屏轮询立刻回到目标帧率 12 fps（此前退避了 8.4 秒）。
[PASS] 那一格回到「画面在变」
[PASS] 画面真的又活了（framesReceived 继续涨）   110 → 119
合计 26 项：通过 26，失败 0
```

两个数值得记住：**退避发生在静止 2.1 秒**（阈值 2 秒，1 秒粒度读数 ⇒ 符合）、
**恢复是"立刻"**（撤布那一刻，不是等 500 ms 的退避周期跑完）。

#### ⑥ 灵敏度（sabotage，已回滚）

| 刀 | 期望 | 实际 |
|---|---|---|
| `IdleBackoffAfter` 改 1 小时（退避永不触发） | 只有「退避」「恢复」两条红 | ✅ **恰好 2 红**（24/26），其余 24 条照旧绿 |

⇒ 这两条断言的**唯一**判据就是退避本身，不是"跑完了没报错"。

#### ⑦ 边界（仍然不许算成"验过了"）

- 本轮的"静止"是**工具造出来的**（纯色盖布），不是"人离开工位"。真实的展厅定格画面
  还多一个变量：**光标悬停在画面上**——本轮已证明它会持续产生"指针更新"，
  而产品侧在"光标不动"时并不因此退避，这一条**只在盖布上验证过**（盖布给了光标一个固定形状）。
  ⇒ 是否需要"光标静止也算静止"是**产品决策**，不在本批。
- `MaxIdlePeriod` 那条安全带**仍未生效**（§9.8 ⑥.1），只是现在多了一个"真机也没触发它"的注脚。

### ③ 运行时自适应 —— **前置实验已完成，结论见 §5.4（范围要缩）**

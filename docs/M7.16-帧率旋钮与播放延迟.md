# M7.16 · 帧率旋钮修复 ＋ 播放延迟按帧率算（第一阶段：1080p / 60 fps）

> 一句话结论：**「帧率」这个旋钮以前是坏的**（选了 20/30 还是 12，没有任何一层报错），
> 修好之后 60 帧才真的下得去；同时把播放缓冲从固定的 60 ms 改成"按帧率买两帧"
> （60 fps ⇒ 33 ms），砍掉约 27 ms 的端到端延迟。
> ⚠️ 本轮的**现场帧率实测没做成**（被控端客户端的长连接掉了，见 §7）——
> 代码、用例、构建都过了，但"1080p 真的跑出 60"这句话**还不能打勾**。

## 0. 为什么先修这三个 bug，再谈优化

做"60 帧"之前先把现状量了一遍，发现**60 帧这条路在代码里根本走不通**，
而且是三处彼此独立的断点：

| # | 现象（现场的话） | 真因 |
| --- | --- | --- |
| 1 | "帧率选 30 没用，画面还是那个样" | 服务端把请求帧率与档位推荐值**取更小**，而默认档位 `auto` 解析成 12 fps ⇒ `min(30, 12) = 12`。页面上没有任何一处说这件事 |
| 2 | "选了流畅也还是 12 帧" | 建会话时**根本不上报档位**，每一路新会话都从 `auto`（12 fps / 6 Mbps）起步，"流畅"要等连上之后再点一次才生效 |
| 3 | "点了流畅看着 60，一重建又回到 12" | 「按当前设置重建会话」不带档位 ⇒ 重建出来的会话是 `auto`；而重连用的 `lastConnectParams` 里也没有这个字段 |

三条合起来的效果是：**页面上有五个档位、六个帧率，实际能真正影响的组合只有"连上之后再点档位"**。

> 🔴 这三条都属于本仓记过很多次的那一类：**没有任何一层会报错**。
> 旋钮转了、请求发出去了、页面也没有红字 —— 只是效果没发生。

## 1. 改了什么

### 1.1 服务端：帧率以请求为准（`RemoteQualityProfiles.FoldTargetFps`）

```csharp
// 之前（两个调用点各写一遍）
targetFps = Math.Min(maxFps ?? profileFps, profileFps);

// 现在
public static int FoldTargetFps(int? requestedMaxFps, int profileFps)
    => Math.Clamp(requestedMaxFps ?? profileFps, MinFps /*1*/, MaxFps /*60*/);
```

- **请求值优先**，档位只在"没指定"时提供默认值；
- 夹到 1–60（面板就是 60 Hz，更高没有意义，也没有一层能验证）；
- 两个调用点（建会话的 `RemoteSessionRegistry.Open`、运行中切档的 `SetQualityAsync`）用**同一个函数**。

⚠️ **码率仍然只由档位决定**。所以「均衡（6 Mbps）＋ 60 fps」是能选出来的组合，
每帧只有 100 kbps，画面会糊 —— 那是用户明确选的，页面上靠「生效 N fps · 档位 X」两个读数让他看见。
`Sixty_fps_survives_the_low_bitrate_profile` 这条用例**故意钉住**它：谁想"顺手帮他降回 12"，立刻红。

### 1.2 页面：`帧率上限` → `帧率`，新增 45 / 60，并把生效值摆出来

```
改前： 帧率上限 [默认（12）| 5 | 12 | 20 | 30]      ← 与档位取小 ⇒ 20/30 是死选项
改后： 帧率      [默认（跟档位）| 5 | 12 | 20 | 30 | 45 | 60]
       生效 60 fps · 档位「流畅」
       （只在"你选的 ≠ 实际下发的"时补一句：被控端按自己的能力夹过 —— 软件 JPEG 上限 20 fps）
```

另有两处**只在条件成立时出现**的提示（无条件横幅必被当噪声，铁律 35）：

- `maxFps >= 60` 时说明 60 帧的**两个前提**（硬编 ＋ 25 Mbps 档位）；
- `maxFps !== targetFps` 时说明"你选的和实际的不同，是被控端夹的"。

### 1.3 建会话 / 重建 / 重连都带上档位

`chosenQuality` 是"用户选的档"，三处入口都写它：

| 入口 | 之前 | 现在 |
| --- | --- | --- |
| 建会话 `POST /api/remote/sessions` | 不带 `quality` | 带 |
| 「按当前设置重建会话」 | 丢掉档位（退回 auto） | 带上 |
| 自动重连 / 重连 | `lastConnectParams` 里没有档位 | 记进去并恢复 |

「接着看」入组别人开的会话时，面板也会**跟着那一路的实际参数走**
（档位、帧率都从会话 DTO 读回来），否则"看着 60 帧、点一下重建变 12 帧"。

## 2. 延迟：把固定的 60 ms 缓冲按帧率算

### 2.1 原来的 60 ms 是什么

`RemoteVideoBuffer` 按 `playhead = 本机对端时刻 − 60ms` 决定"该显示哪一帧"，
`RemoteAudioPlayer` 把每一段排在 `采集时刻 + 60ms`。
**两条流用同一个值**——这是 A/V 对齐的唯一依据，这个设计保留。

问题是 60 ms 与帧率无关：

| 目标帧率 | 60 ms 相当于 | 缓冲真正需要 |
| --- | --- | --- |
| 60 fps | **3.6 帧** | 2 帧（吃掉一个完整周期的乱序） |
| 12 fps | 0.7 帧 | 不到一帧，多给也没用 |

⇒ 60 fps 下多出来的 1.6 帧（≈27 ms）是**每一帧都白付的延迟**。

### 2.2 现在的算法（`web/src/playbackLatency.ts`）

```ts
latency = clamp(2 × (1000 / targetFps), 20, 60)
```

| 目标帧率 | 改前 | 改后 |
| --- | --- | --- |
| 60 | 60 ms | **33 ms** |
| 45 | 60 ms | **44 ms** |
| 30 及以下 | 60 ms | 60 ms（两帧已超上限 ⇒ 不变） |
| 帧率未知 | 60 ms | 60 ms（不知道路况不赌） |

- **低帧率一个都不降**：12 fps 的帧间隔是 83 ms，给 20 ms 等于"一帧都不缓冲"。
  只有高帧率才有"多余的缓冲"可省。
- 值放在**进程级单值**里，音频与视频每一段/每一帧**现读**，不各存副本 ——
  存副本就会出现"一个改了、另一个没改"，而那正是 A/V 慢慢错开的起点。
- 会话结束 / 换会话时 `resetPlaybackLatency()` 回上限（否则下一路 12 fps 会沿用 33 ms）。

### 2.3 它为什么值得单独成一个模块

这个数**没有任何界面证据**：调大了是"有点慢"，调小了是"有点卡"，两端日志都干净。
所以判据写在 `playbackLatency.test.ts`（7 条），而不是散在组件里的一个常量上 ——
M7.16 之前它就是一个 `const TARGET_LATENCY_MS = 60`，谁也不知道为什么是 60。

## 3. 怎么验"1080p 60 帧"

### 3.1 在 2160×1440 的机器上量 1080p 的办法

抓屏器的区域编码是 **1:1** 的，所以给一个 1920×1080 的视口（M5.5 的 ROI）得到的就是
**一块 1920×1080 的编码** —— 与"那台机器本来就是 1080p 屏"在编码器看来是同一件事。

🔴 **但这条路在本轮之前根本不存在** —— 见 §3.3。修掉之后才有下面这两条命令。

`deploy/smoke/remote-fps.py` 本轮加了 `--viewport`：

```bash
# 2160×1440 全屏，60 档
python deploy/smoke/remote-fps.py --quality smooth --seconds 8 --warmup 6

# 只编左上角 1920×1080 = 「1080p 情况下」
python deploy/smoke/remote-fps.py --quality smooth --viewport 1920x1080 --seconds 8 --warmup 6
```

⚠️ 它**不造画面变化**。DXGI 是增量投递，桌面不动就没有新帧 ——
测上限时另开一个持续重绘的窗口（本轮用 `.build/motion.html`，Edge `--app` 打开）。

### 3.2 判据（比读 fps 更硬）

M7.4 定下的那条仍然有效：探针行里 **`出帧` ≈ `抓屏 ×N` 的 N**，且 **`轮 − 出帧` ≈ 0**。
`--show-probe` 打开后能看到（需要被控端跑的是含探针的构建）。

### 3.3 🔴 顺带修掉的真 BUG：ROI 从来没接过线

准备实测时发现 `--viewport` **必然失败**，一路查下去是"实现写好了但没接线"：

```
RemoteStreamHost.SetViewport:
    if (encoder is not IRegionSurfaceEncoder region)      ← 恒为 true
        return Failure("这一路用的编码器不支持只编视口（当前是 MJPEG/内存路径）");

WindowsGpuFrameEncoder : ISurfaceFrameEncoder             ← 只挂了这一个
    public IReadOnlyList<EncodeRegion> Regions     ✓ 实现了
    public bool SetViewport(EncodeRegion?)         ✓ 实现了
    public bool TryEncodeSurfaceRegions(...)       ✓ 实现了
```

**三个成员全在，唯独类声明漏了 `IRegionSurfaceEncoder`。** 于是：

| 后果 | 说明 |
| --- | --- |
| M5.5 的视口（ROI） | 一次都没生效过。改声明后编译 `<see cref>` 齐全 ⇒ 一行就通 |
| M5.5 的分块编码 | 死码。三屏拼接永远落到 MJPEG 缩略图（与 M7.10 的"只能是缩略图"互为因果） |
| 帧头坐标系 | `keepsNativeSize = surfaceEncoder is IRegionSurfaceEncoder` ⇒ 恒 false ⇒ 按 payload 尺寸算，与接口契约（1:1、不缩放）不符 |
| 本轮验收 | **"在 4K 屏上量 1080p"这条路不存在**（`--viewport` 是本轮才加进脚本的） |

修法与防回归：

```csharp
// ControlServer.Platform.Windows/WindowsGpuFrameEncoder.cs
public sealed class WindowsGpuFrameEncoder : IRegionSurfaceEncoder   // ← 接上

// 编译期钉子：删掉上面的接口，这一行就编不过（CS0266/CS0029）
private static IRegionSurfaceEncoder ContractPin(WindowsGpuFrameEncoder encoder) => encoder;
```

钉子**已实测会咬人**：临时把声明改回 `ISurfaceFrameEncoder` 后编译报
`error CS0029: 无法将类型 WindowsGpuFrameEncoder 隐式转换为 IRegionSurfaceEncoder`。

⚠️ 这类 bug 没有日志、没有告警，症状只是"某个功能看起来就是不生效" ——
所以判据必须是**类型层面**的（`is` / 编译期转换），不能靠"用一下看看"。

### 4.1 唯一拿到的现场证据：**60 真的下去了**

会话能建起来之后（03:20 客户端短暂恢复 `online`），用
`smooth` ＋ `maxFps=60` 建会话，读回：

```
quality           = smooth          ← 旧行为会是 auto
targetFps         = 60              ← 旧行为是 Min(60, 12) = 12
targetBitrateKbps = 25000           ← smooth 档
```

被控端日志同一时刻：

```
[Remote] 会话 032119-adf88d30 已开始：已开始抓屏推流：主显示器 \\.\DISPLAY1
        （2160×1440 @ 0,0）（2160×1440），目标 60 fps（mjpeg 软编）。
```

⇒ **`目标 60 fps` 这一格就是本轮修复的判据**。旧代码这里必然是 `目标 12 fps`，
而且中心侧也一样：`Min(请求, 档位)` 把旋钮整个压平，页面上选 20/30/60 全变 12。

⚠️ 但这一次**只证明了"60 送到了"**，没证明"跑出了 60" —— 被控端实际只发出
**9 帧 / 13.9 秒**，原因见 §7.2（硬编不可用）与 §7.3（旧构建）。

## 5. 与既有文档的关系

- **`M7.4` 的结论不变**：2160×1440 上 `smooth` 实测 57.1 fps，瓶颈是"等桌面更新"（抓屏 11.2 ms、
  编码 4.9 ms）。本轮的改的是**能不能把 60 这个目标下得去**，不是编码器。
- **`M7.10` 的分辨率结论不变**：合并显示只能是缩略图（MJPEG 软编）。

## 6. 风险与不改的东西

| 项 | 说明 |
| --- | --- |
| 60 fps ＋ 低码率档 | 会糊。**这是允许的组合**（用户明确选的），页面把两个读数摆出来 |
| 播放延迟降到 33 ms | 抖动大于 ~33 ms 时会退化成"某帧晚一拍上屏"（不是花屏、不是断流）。低帧率不受影响 |
| 软件 JPEG 这条路 | 仍然被如实夹到 20 fps（`RemoteStreamPacing.SoftJpegMaxFps`），前端会显示"被控端夹过" |
| 不动编码器 / 不动抓屏 | 本轮零被控端改动 |

## 7. 🔴 现场实测没做成（三个独立阻塞，都要管理员）

打算在本机（i5-8265U / UHD 620，2160×1440）上量 `smooth` 与 `--viewport 1920x1080`。
**没做成，而且不是一个原因。**

### 7.1 客户端长连接半开：心跳在，连接没了

```
GET  /api/agents            → 12 DESKTOP-9VFHRMA unstable
POST /api/remote/sessions   → 409 {"code":"remote-agent-offline",
                                   "message":"机器「DESKTOP-9VFHRMA」此刻没有长连接"}
```

| 看哪一侧 | 读数 |
| --- | --- |
| 中心 | `ConnectionIdOf(12) == null`（内存连接表里没有） |
| 客户端 `status.json` | `"Connected": true`（它**以为**自己连着） |
| 中心 `lastSeenAt` | **每 10 秒还在刷新** |
| 客户端日志 | `03:01:09` 之后**一条都没有** ⇒ 它不再尝试重连 |

⚠️ 这比"半开连接"更具体：**心跳走的是另一条通道，它成功了** —— 于是客户端把
"心跳通"当成了"我连着"的证据，永远不重连；而指令走的是长连接，永远发不出去。
两者指向同一个词（"连接"），却不是同一条连接。

退避重连本身是好的：02:59 被 401（凭据被实验客户端轮换掉了）、03:00:04 重新注册连上。
坏的是上面那个判据 **"心跳成功 ⇒ 已连接"**。

### 7.2 硬编在托盘进程里耗尽了

同一个托盘进程（PID 20344，**10-19 20:27 启动、至今未重启**）内：

| 时刻 | 这一路的编码 |
| --- | --- |
| 01:49 / 01:54 / 01:55 / 01:59 / 02:15 | `h264 硬编` |
| **02:22 之后，每一次** | `mjpeg 软编` |

同进程、无重启、无换构建 ⇒ 是**运行期环境**从"能用"变成"不能用"（不是代码差异）。
最先怀疑的是"反复开关会话把 MF 硬编会话数用完了"，但**这条没能证实** ——
因为那版托盘的日志里没有失败层级（见 7.3）。

替代证据是**抓屏也几乎不出帧**：桌面被确认在动的情况下（见下），
03:25 那次会话只有 **9 帧 / 13.9 秒（0.6 fps）**，而 MJPEG 这条路的设计上限是 20 fps。

> 桌面"在动"是**先验证过**的，不是假设：用 `.build/anim.py` 建了一个自己重绘的
> 顶层窗口（30 ms 定时 `InvalidateRect`，实测 161 帧 / 5 秒 ≈ 32 fps），
> 再用 `.build/shot.py` 隔 1 秒截两次全屏比对 —— **字节差异 0.0348%**（之前是 0.0%）。
> ⇒ 桌面确实在变，而推流仍然 0.6 fps。

⇒ 更像是**托盘那侧的 GPU 管线整体失效**（DDA 与硬编同源），只剩 GDI 兜底且节奏错乱。
这正是"必须重启那个进程"的典型形态。

### 7.3 第三件事：托盘是 10-19 15:29 的旧构建（这条最硬）

```
C:\Program Files\ControlServer Agent\ControlServer.Agent.Tray.exe   → 10-19 15:29
```

判据不是看时间，是**看它少了哪两条日志**（当前源码里这两条都必打，它一次都没打过）：

| 当前源码必定输出的日志 | 该托盘 |
| --- | --- |
| `⚠️ GPU 硬编不可用，已回退 MJPEG（… 停在哪一级：…）`（`Tray/Program.cs:373`） | **从未出现** |
| `[Stream] 目标帧率 60 → 20 fps：…`（`RemoteStreamHost.cs:946`，`ApplyEncoderCap` 夹过就必打） | **从未出现** |

第二条尤其说明问题：`GdiJpegFrameEncoder` 只实现 `IFrameEncoder, IScalableFrameEncoder`，
`encoder is ISurfaceFrameEncoder` 必为 false ⇒ 当前源码必然把 60 夹到 20 并留下这行日志。
它没打 ⇒ **那版构建里根本没有这段夹取逻辑**，60 被原样拿去驱动 MJPEG 循环。

两个后果：

- 硬编死在哪一级**无法判断**（7.2 因此无法定论）；
- 那个构建的硬编路径**没有 ROI**：01:49 那批会话 `--viewport` 被拒
  （`不支持只编视口`）⇒ 即使长连接与硬编都恢复，`--viewport 1920x1080`
  也要等**新客户端装上去**才能跑。

### 7.4 恢复步骤（都要管理员；本轮会话 `IsAdmin=False`）

```powershell
# 1) 长连接
Restart-Service ControlServerAgent
# 2) 把新构建换上去（关键：单纯 Stop-Process 只会把同一个旧 exe 再拉起来）
#    deploy/build-agent*.ps1 产出的安装包/绿色目录覆盖 C:\Program Files\ControlServer Agent\
# 3) 换掉托盘进程 —— 杀了之后由登录启动项拉起，或重新登录一次
Stop-Process -Name ControlServer.Agent.Tray -Force
```

本轮试过 `Stop-Process -Id 20344`，返回 **拒绝访问**（托盘是提权进程）。

### 7.5 待补的验收（恢复后直接跑，不改代码）

**先确认新客户端真的上去了**（两条日志必须出现，否则下面测的仍是旧的）：

```
⚠️ GPU 硬编不可用，已回退 MJPEG（… 停在哪一级：…）    ← §7.3
[Stream] 目标帧率 60 → 20 fps：…                      ← §7.3（MJPEG 机器上必有）
```

而 `h264` 起来了的话，第二条不该出现，第一条也不该出现 —— 那时才是真正的 60 帧场。

```bash
python deploy/smoke/remote-fps.py --quality smooth --seconds 8 --warmup 6
python deploy/smoke/remote-fps.py --quality smooth --viewport 1920x1080 --seconds 8 --warmup 6
```

达标线：`smooth` 两行都要 **≥ 57 fps**（M7.4 在 2160×1440 上就是 57.1；
1080p 只会更快，因为瓶颈是桌面更新节拍不是像素）。

⚠️ 跑之前先让桌面动起来，否则测到的是"静止退避"而不是上限：
本轮已经踩过这个坑（`KB/帧 0.0`、`实测 0.0 fps`）。

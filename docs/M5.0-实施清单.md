## 1. 🔥 必须先定的架构问题：码流怎么回到中心

### 1.1 为什么现有管道**不能**直接送视频

`SessionPipeProtocol` 的形状是**刻意为低频动作设计的**，三条特征都与视频流冲突：

| 特征 | 出处 | 对视频流的影响 |
|---|---|---|
| **一请求一连接**，用完 `Disconnect()` | `SessionPipeServer` 内层循环 | 60 fps ⇒ **每秒 60 次连接**，开销爆炸 |
| **单实例**（`maxNumberOfServerInstances: 1`） | 同上 | 视频流会**独占**管道，`launch`/`volume` 全部排队 |
| **5 秒请求超时** + 一行文本响应 | `RequestTimeoutMs` | 二进制大块、长连接语义全不适用 |

⇒ **视频流必须另开一条通道。** 这是 M5.0 必须解决的设计问题，不是实现细节。

### 1.2 关键约束：编码**只能**在托盘进程里做

| 事 | Session 0（服务，SYSTEM） | 用户会话（托盘） |
|---|---|---|
| **抓屏**（DXGI Desktop Duplication） | ❌ **做不到** —— 没有桌面 | ✅ |
| **GPU 编码**（MF / NVENC） | ⚠️ 技术上可建 D3D 设备，但**拿不到要编的帧** | ✅ |
| **输入注入**（SendInput） | ❌ 注入到 Session 0，用户看不见 | ✅ |
| **枚举适配器 / 判引擎数** | ✅ **可以**（`GpuAdapterNames` 的 D3DKMT 路径就是为 Session 0 准备的） | ✅ |

⇒ **抓屏 + 编码 + 注入三件事全部在托盘**；只有**能力探测**可以留在服务侧。

⇒ 而**原始帧绝不可能过管道**：4K60 的 BGRA 是 **1.99 GB/s**（§1.4）。**能过管道的只有「编码后的码流」**（几十 Mbps，本地管道毫无压力）。

### 1.3 三个候选路径

| 方案 | 做法 | 评价 |
|---|---|---|
| **A** | 托盘**自己连中心**（SignalR 客户端）推流 | ❌ 托盘目前**刻意不持有任何凭据**（`status.json` 里明确没有 `agentKey`）。给它发凭据 = 推翻 M4 的安全设计，且要新增一条对外连接 |
| **B** ✅ **建议** | 托盘抓屏+编码 → **新开一条二进制长连接管道** → **服务** → 复用**已有的 SignalR 连接**转发 | ✅ 托盘仍然零凭据；复用 `AgentConnection`（已存在）；本地管道只搬几十 Mbps；服务侧天然获得码流的背压/审计位置 |
| **C** | 原始帧过管道、服务侧编码 | ❌ 1.99 GB/s **过不去**；且服务在 Session 0，抓不到桌面，帧还得先从托盘搬过去 —— 正是要避免的那次拷贝 |

**建议 B**。代价只有一跳**本地命名管道**（亚毫秒），换来的是「托盘不见凭据」这条安全设计不被破坏。

> ✅ **已拍板：走 B**（2026-10-15）。第三批按此落地，见 §3.3。
>
> 落地时的两条关键推论（都来自"管道默认 DACL"这一条事实）：
> 1. 🔥 **管道必须由托盘创建、服务去连**。命名管道的默认 DACL 是 `SYSTEM + 管理员 + 创建者` ——
>    若倒过来（服务创建、托盘连），普通用户身份的托盘根本连不上，而失败形态是
>    `UnauthorizedAccessException`，看起来像"权限没配好"，其实是**方向错了**。
>    这与 M4.5 的 `SessionPipeServer`（托盘侧）是同一个方向。
> 2. 🔥 **新开一条管道，不要复用 `SessionPipe*`**。那条协议是"一请求一连接"的短连接，
>    而码流是一条要持续几十秒到几小时的长连接 —— 塞进去会让"超时"的语义彻底变味
>    （短连接的超时 = 没响应；长连接的超时 = 流还在不在）。

## 2. 能力探测：一个比硬编码 DeviceId 表可靠得多的做法

方案 §16.1 ④ 给的是**芯片代号速查**（`AD102 / AD103 / AD104-400 = 2`，`AD107 / AD106 / AD104-250 = 1`）。

⚠️ **但同一颗芯片的不同 SKU 引擎数并不相同** —— 最典型的是 AD104：`RTX 4070` 被禁掉一个 NVENC（**1 个**），而 `RTX 4070 Ti / 4070 Super` 是 **2 个**。也就是说**「查芯片代号」在 AD104 上会直接把结果猜错一半**。

### 2.1 探测分三层，每条结论都必须能说清"是测的还是猜的"

| 层 | 查什么 | 手段 | 可靠性 |
|---|---|---|---|
| **① 事实** | 有哪些适配器、`VendorId` / `DeviceId`、显存、是否软件光栅器 | **DXGI 枚举** | ✅ 确定性事实，不含推断 |
| **② 有没有硬编** | 这台机器**确实注册了**哪些硬件编码器（**含厂商**） | **Media Foundation `MFTEnumEx(HARDWARE)`** | ✅ **可靠** —— 查注册表，与当前有无编码活动无关 |
| **③ 有几个引擎** | 编码引擎数（决定 8K60 能否走双引擎 SFE） | **PDH `\GPU Engine(*)\engtype_VideoEncode`** | ⚠️ **只是下界**，见 §2.3 |

### 2.2 🔥 第二批实测：原来那条"PDH 数引擎"的路**不能单独下结论**

**先写结论：`MFTEnumEx` 是"有没有"的可靠依据；PDH 只能给"有几个"的下界。**

`MFTEnumEx` 之所以可靠，是因为它问的是驱动**注册**了什么。而 PDH 那条路在本机实测暴露了致命性质：

| 实测项 | 结果 |
|---|---|
| `\GPU Engine(*)\Utilization Percentage` 的实例数 | **231 条，全部带 `pid_` 前缀** |
| 出现的 `engtype` | `3d` / `compute_0` / `compute_1` / `copy` / `cuda` / `gdi render` / `graphics_1` / `legacyoverlay` / `security` / `videodecode` / `videoprocessing` |
| `VideoEncode` | **0 条** |

⇒ **该计数器是按"哪个进程用过哪个引擎"创建实例的**。**没有编码活动 ⇒ 一条 `VideoEncode` 都没有。**
⇒ **一台空转的 4090 与一台 MX250 在这上面长得一模一样。** 拿它下"这台机器没有硬编"的结论，
就是本方案最不能犯的那个错（把"没用过"说成"没有"）。

**因此第二批的判定顺序是**：

| 优先 | 条件 | `EncodeEngines` | 依据文案要点 |
|---|---|---|---|
| ① | PDH **观测到** ≥1 个编码引擎（同一块卡的多个节点取 **max**，不求和） | 观测值 | 「PDH 实测：这一刻有 N 个编码引擎在被使用」**并注明这是下界** |
| ② | MFT **枚举成功**且该厂商一条硬编都没有 | **`0`** | 「Media Foundation 枚举成功且未发现该厂商硬件编码器」← **它与"没查出来"不同** |
| ③ | MFT 有硬编，但引擎数拿不到 | **`null`** | 「已确认有硬编（列出 MFT 名），但引擎数未能实测」 |

**四个概念必须一直分清**（第二批把它们都编进了类型与用例）：
`null`（未知）≠ `0`（明确无硬编）≠ 空表（枚举成功但没发现）≠ 枚举失败（查不了）。

### 2.3 ⚠️ 顺带实测出来的两个坑

1. **MFT 返回的条目数不是引擎数。** 本机实测 H.264 / HEVC 各返回 **2 条同名**记录
   （驱动按多种设备型态各注册一份）。把 2 当"双引擎"会得出"这机器能 8K60"的假结论。
2. **DXGI 的适配器节点数 ≠ 显卡块数。** 本机实测 DXGI 枚举出 **4** 个适配器，而
   "Intel UHD Graphics 620" 出现**两次且 LUID 各不相同**（`0xE577` / `0x19C01`，DeviceId 相同）
   ⇒ 同一块物理显卡可以有**多个适配器节点**。报告因此**按型号归并**
   （引擎数取各节点 **max**，不求和 —— 那是同一块卡，求和会把 2 报成 4）。
   ⚠️ 由此给 M5.1 的约束：**这份报告不是"抓屏设备清单"**，选 D3D 设备必须自己重枚举 DXGI 凭 LUID 挑。

### 2.2 铁律：判不出来就报 `null`，**不许用 0 代替**

`0 引擎` 与 `引擎数未知` 是**两件完全不同的事**：
- `0` = 明确无硬编（如本机 MX250，`GP108` 官方矩阵注明不支持）；
- `null` = 还没测出来。

把后者写成前者，会**在能力探测这个最关键的地方说谎**（§1.6 手段 1 是 8K 目标的地基）。因此：

```csharp
int?    EncodeEngines      // null = 未知；0 = 明确无硬编
bool?   SupportsTenBit     // 未知同样给 null
bool?   SupportsSplitEncode
string? EngineBasis        // 这个结论是怎么来的（"PDH 实测" / "官方矩阵" / "未知"）
```

`EngineBasis` 是刻意加的：**现场能一眼看出这条结论有多可信**，而不是拿到一个不知道从哪来的数字。

### 3.5 第五批 ✅ 已交付（M5.2 收尾：**归属校验** + 多人同看的语义）

> 起因是 §5.4.3 第 6 条（"陈旧页面也能翻控制开关"）。用户拍板**补校验**，
> 并明确 **"支持多人同时看一路即可"** —— 合起来给出了一句判据：
> **"你正在看这一路"是唯一的资格条件**，判据里不许出现"别人"。

**① 语义（本轮唯一需要复核的东西）**

| 问题 | 答案 |
|---|---|
| 谁有资格操作这一路？ | **任何一个此刻正在看这一路的人**。不是"第一个打开的"，也不是"抢到控制权的" |
| 多人同时看一路会怎样？ | 都能操作 ⇒ 会互相抢鼠标。**这是刻意的**（§5.4 取舍③：开关是会话级的）。页面上一句话点明（见 ② 第 5 行） |
| 为什么**不做**"当前 N 人在看"？ | 那要中心维护一张"谁在看哪一路"的表，而有表就有漏水路径 —— 漏掉的后果是**计数漂高**：页面上永远显示"还有别人在看"，于是**没人敢操作**。比没有计数更坏。会话级语义 + 一句提示已经够用（人多时现场自己约定） |
| 陈旧页面（刷新过 / 切走过）还能操作吗？ | **不能**。两个输入端点都过同一道归属关卡 |
| 观众全走光会停流吗？ | **不会**（M5.1 起就这么定的）：它支撑"刷新页面不掉流"，停流由空闲超时与"结束会话"兜底 |

**③ 顺带修掉的两处（同一类病，一并清掉）**

- `Join` 原来**不清上一路**（依赖客户端先调 `Leave`）。客户端会忘（刷新 / 切标签 / 那次调用在路上丢了），
  而"忘了"是**双向**代价：那条连接一直收着上一路的高频帧，**且**还能往上一路送输入。
  现在"一条连接同时只看一路"是**服务端强制**的不变量。
- `Leave` 原来**无条件摘登记**。前端切会话是"先 Leave 旧的、再 Join 新的"，
  而重发 / 重复调用会让 `Leave` 带着一个**已经不是当前那一路**的 Id 到 —— 无条件摘会把**新**的登记误摘掉，
  症状是"刚切过去，点第一下就被拒"。

### 3.6 第六批 ✅ 已交付（**M5.3：声音回传 + 通道三态 + 网页安全上下文**）

> 这一批实际交付了**两件事**，而且第二件是被第一件**逼出来的**：
> 音频要用浏览器的 `AudioDecoder` + `AudioWorklet`，而这两样东西
> **只在安全上下文里存在** —— 局域网里按 `http://192.168.x.x` 打开页面时，
> `window.AudioDecoder` 不是"报错"，是 **`undefined`**。
> 所以"做声音"这件事顺带要求"让页面跑在 https 上"。

**① 端到端链路（一句话）**

被控端**托盘**（Session 0 没有音频端点，这一点与 M4 的结论一致）
→ WASAPI loopback 采集 → **Opus 20 ms/帧** → **第二条管道**（托盘写、服务读）
→ 服务经 SignalR `PushRemoteAudio` → 中心 `AcceptAudio` → **独立的转发队列**
→ Hub 广播 `Audio` → 浏览器 `AudioDecoder` → AudioWorklet 环形缓冲 → 扬声器。

画面那一侧同时从"收到就画"改成**抖动缓冲 + 按目标延迟排期显示** ——
不这么做，画面就**没有"我现在显示的是哪一刻"这个量**，音画对齐无从谈起。

**② 本批的八个取舍（供复核）**

| # | 取舍 | 定为 | 代价 / 何时反过来 |
|---|---|---|---|
| ① | 音频要不要也配"两道闸门" | **不配**。音频**没有中心侧的会话级开关**，所以 `AgentAudioStates` 比输入少一态 | 与 M5.2 刻意不对称，理由：**有声音是这路会话的默认行为**，不像"动别人鼠标"必须逐次授权。要加就得先回答"谁在什么情况下会想关掉别人的声音" |
| ② | 管道复用还是新开 | **新开第二条**（与 M5.2 输入那条同形、方向相反） | 与 M5.2 取舍①同一个坑：同流双向写会读到**另一方向的半句话** |
| ③ | 转发队列与视频共用吗 | **不共用**（音频 **1** 包、视频 **50** 帧） | 合并的话被控端每推一段音频就会把待发的视频帧顶掉，症状是**"一有声音画面就掉到 1 fps"**，而两边日志都正常 |
| ④ | 目标播放延迟 | **两条流共用同一个值（60 ms）** | 各定各的 = "对齐"变成"两套估计碰巧差不多"。60 的依据：局域网抖动是个位数 ms，再小会"一抖就补静音"（听感是噼啪） |
| ⑤ | 音画偏差怎么算 | **测**（实际上屏的那一帧 vs 实际正在响的那一段，各自外推到同一时刻再相减），**不是按公式算** | 多一层外推数学；换来的是一句**能自证**的读数 —— 恒等于 0 说明测量写错了，不是说明做得好 |
| ⑥ | 网页安全上下文怎么办 | **中心自己建一个本地根 CA + 第二个 https 监听器**，并给出根证书下载 | 现场多一步"装根证书"。反过来（不改中心）就只能告诉用户"去配 nginx" |
| ⑦ | 根证书走哪条路下载 | **明文 http、匿名、且在 `/api` 之外** | 见下面 ③ —— 两个"看起来更规整"的选项都会把用户逼成"看见警告就点继续" |
| ⑧ | 被控机的音量 / 静音要不要做 | **不做**。页面上的"静音"**只切本机**，不通知任何人 | 少一块功能；换来的是"看的人静音不会影响别人、也不会动被控机的音量" |

**③ 三个"看起来更规整、实际会坏事"的选择（都已避开）**

- 🔥 **无声时不发 DTX**（方案 §9.1 原来推荐的就是它，本批改成"极小但连续"）：
  DTX 的做法是"一段时间内**根本不发包**"，那会让接收端的时间轴**凭空少掉一段时间** ——
  而"时间轴上少一段"正是 AV 同步最怕的错（前端只能靠补静音去猜缺了多久，猜错就是持续漂移）。
  Opus 默认就是变码率，静音段编出来只有十几字节（≈ 每秒 < 1 KB）—— **已经足够"不占带宽"**，
  而时间轴是完整的。⇒ 用"极小但连续"换"完全不发"。**方案 §9.1 已同步改正（v3.5）。**
- **根证书不走 https 端口发**：观看端第一次访问时**还没信任那张证书**，
  从 https 去下载，浏览器会先拦一道"此连接不安全"，用户点"继续"才拿得到 ——
  这一点次数一多，大家的习惯就变成"看见警告点继续"，
  **正好把这一整套信任机制想教的那件事抵消掉**。根证书里只有公钥，明文发没有机密性损失。
- **`/trust/*` 不放在 `/api` 之下**：那条路的可用性必须**早于**"这台机器已授权"这个前提
  （没导授权的机器照样得能把根证书装到观看端上）。顺带也避开了
  "每个新 `/api` 端点都要进 `LicenseGate` 分类表"那条纪律 —— 少一处将来会漂的东西。

### 3.7 ✅ 已交付（**M5.1 遗留缺陷修复**：会话活性判据把「画面静止」判成「断线」）

> **它是怎么被翻出来的**：M5.4-b 收官后按例做"下一批开工前核查"，
> 读 `RemoteSessionRegistry.Sweep` 的**判据来源**时发现的 —— 不是复现出来的，是**读出来的**。
> 会话生命周期是 M5.1 建的，所以补在这里，不另开批次。

#### (a) 缺陷：说明写着「帧 **或** 状态上报」，代码只看「帧」

三处说明写的是同一句话，**三处都对**：
`IdleTimeout`（「不再收到帧、**也没有状态上报**时，多久判成"断了"」）、
`RequestedTimeout`（「多久还没等到被控端的**任何**状态上报就判成"没起来"」）、
`Sweep` 自己的文档（「清掉已经断掉的会话（**帧停了、状态也不再上报**）」）。

而实现只看**帧的时间戳**与**建会话那一刻**：

| 说明写的 | 代码做的 | 后果 |
|---|---|---|
| 「不再收到帧、**也没有状态上报**时判成断了」 | `last = LastFrameAt ?? StartedAt ?? RequestedAt` | 被控端**一直在回话也救不了它** |
| 「多久还没等到被控端的**任何**状态上报就判成没起来」 | `now - RequestedAt > 20 秒` | **接到了、正在建编码器/切分辨率**被当成"没接到" |

**触发路径**（产品主线场景，**必现**）：DXGI Desktop Duplication 是**增量投递**的 ——
桌面没变、指针也没动时它按约定返回"没有新帧"，于是被控端**一帧都不产**
（它自己的日志就写着「这是正常现象，**没有丢帧**」）。
⇒ 中心侧 `LastFrameAt` 停住 ⇒ **15 秒后被判死**；`Close` 之后被控端下一次推帧收到
`Rejected`，**整路会话结束**。观众重开，15 秒后再死一次 —— **远程看一台定格画面的机器等于不可用**。

> 🔥 **为什么它一直没被发现**：M5.1 起的每一次真机冒烟，屏幕上**都有东西在动**
> （编辑器光标在闪、鼠标在动、任务栏时钟在跳）⇒ 总有帧 ⇒ 判据永远不触发。
> **"展厅里定格在一张图上的机器"正是没有东西在动的那一台**，
> 而它恰好是这套系统最典型的使用场景。

#### (b) 修法：判据收成**一个字段**，并要求每处新上行**表态**

新增 `Entry.LastAgentAt` =「最近一次收到这个被控端的**任何上行**」，
由 `Observe`（帧）与 `ApplyState`（状态上报）各刷新一处；`Sweep` 的两个分支都改用它
（`requested` 分支的计时起点从 `RequestedAt` 改成"最后一次回话"）。

> 🔥 **为什么不"各处补一个 `if`"**：这条链路上还有**第三条上行** —— 音频
> （`ObserveAudio`），而它**刻意不算**活性：一台没有声卡的机器照样在正常推画面；
> 反过来「只有声音在走」也不该让一路死会话赖着不走。
> 做成一个字段、并**要求每处新上行都明确表态**，比散落三处 `if` 多一层保障：
> 下一个加上行的人会**看见**这个字段，而不会只看见自己要改的那个方法。
> （音频那处因此写了一整段"为什么不算"的注释，并有用例 `E` 钉住。）

⚠️ **取舍（必须写明）**：修完之后，**"被控端服务活着在回话、但托盘那条流真的卡住"**
不再被自动清掉。这是**故意**换的 —— 因为在协议层上
**"桌面静止"与"托盘卡住"长得一模一样**（两者都是"没有帧、状态照报"），
而前者每 15 秒毁一次会话、后者只是画面冻住（且页面读数会明说 0 fps，
用户还能自己点「结束会话」）。真要分开，得让被控端**上报「本机桌面静止中」**
（它已经知道这件事 —— `idleTicks`）⇒ 见 §6 待确认。

⚠️ **另一处顺带发现、但本批不动的**：`RequestedTimeout`（20 秒）与被控端自己的
`StartupFrameBudget`（30 秒）**不一致** —— 中心可能在被控端认为"还在预算内"时先把会话清掉。
修法很简单（两边对齐或让被控端在上报里带进度），但它要在"什么算启动太慢"这件事上有统一口径，
所以**只记录，不改**。

## 4. LicenseGate 分类（判据沿用该文件自己的规矩：**会不会真的作用到别的机器上**）

| 端点 | 分类 | 理由 |
|---|---|---|
| `GET api/remote/capabilities/{agentId:int}` | **Allowed** | 纯读取，与 `GET api/agents/{id}/inventory` 同类 |
| `GET api/remote/sessions` | **Allowed** | 只读列表 |
| `GET api/remote/sessions/{sessionId}` | **Allowed** | 只读详情 |
| `POST api/remote/sessions` | 🔥 **Gated** | **让一台机器开始抓屏推流** —— 与「建立分发任务」「远程重启」同类 |
| `POST api/remote/sessions/{sessionId}/grayscale` | 🔥 **Gated** | 改变被控端编码参数（决策 14） |
| `POST api/remote/sessions/{sessionId}/input` | 🔥 **Gated** | **直接操作别人的键鼠**，本档风险最高的一类 |
| `POST api/remote/sessions/{sessionId}/input/enabled` | 🔥 **Gated** | 打开它就是**解除了那道默认关着的闸门**，等价于"允许有人操作这台机器" |
| `DELETE api/remote/sessions/{sessionId}` | **Allowed** | **只做减法**：结束会话 = 让被控端**停止**工作。拦它会导致「未授权时中断不了正在进行的远控」 |

> ⚠️ 最后一条是刻意的：**「停止」不该被授权拦住**。这与 `POST api/agents/{id}/unblock`（同样是"只做减法"）被归在 Allowed 是同一条判据。

**这三行数字把 M5.1 的两条设计约束从"推断"变成了"实测"：**

| 结论 | 依据 |
|---|---|
| 🔥 **原始帧绝不可能过管道** | 单帧 12 MB × 12 fps ≈ **145 MB/s**；4K 是它的 2.4 倍 ⇒ 约 **350 MB/s**。这正是路径 B 存在的理由（能过管道的只有码流） |

| 12 fps 的带宽代价 | 17 Mbps（M5.4 换 H.264 后应降到 1–3 Mbps 量级） |

> ⚠️ **本批做到与没做到（诚实记录）**：
> - ✅ **做到**：链路的每一跳都通了，且服务端这一半有真宿主用例守着；
>   抓屏 / 编码这一段是**真机实测**的。
> - ❌ **没做到**：**跨两台机器的端到端**（中心 → 客户机 → 画面）没有自动化验证 ——
>   它需要在一台客户机上真的装服务与托盘，而那是"验收"而不是"用例"的事。
>   本批只保证"每一跳的接口都对得上、服务端半条链子是活的"。
> - ❌ **没做到**：4K 及以上的 MJPEG 会被 512 KB 上限挡住（见上表）。这不是 bug，是**已知的阶段性边界**。
> - ⚠️ **已知缺口**：中心侧的转发队列（容量 1、丢旧留新）丢掉的帧**没有被计数**，
>   所以 `droppedFrames` 只反映被控端丢的帧，不含"观看端跟不上被中心丢掉的帧"。
>   留到 M5.4 与真实带宽压力一起处理。

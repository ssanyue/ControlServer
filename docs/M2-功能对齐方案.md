# M2 功能对齐方案（Web 服务版）

> 目标：把**旧版**（.NET 8 MAUI 单机桌面中控，**已废弃**）的**全部业务能力**在服务版上实现，做到"功能齐全、行为一致、可校验"。
>
> 本文件是**设计稿**。截至本稿完成，**未新增/修改任何业务代码**（M1 骨架保持原样）。
>
> 前置文档：`docs/中控Web服务版-落地方案.md`（总方案）、`docs/M1-骨架设计-dotnet8.md`（骨架与实测）。
>
> ⚠️ **生效范围（2026-10-07 追加）**：本文档的功能清单来自**旧版**（已废弃的单机桌面程序）的逐项拆解；
> **实现方式以本文档与服务版源码为准**。本项目与旧版**无依赖、无联动**，旧版的实现**不是**正确性判据，
> 其缺陷**不照抄**。术语见 `docs/项目边界与术语.md`。

## 0. 本轮定位与边界

### 0.1 一句话

M2 = **把桌面版"按钮 / 动作 / 子按钮集 / 对接码三级匹配 / 定时器 / 指令库 / 配置导入导出 / 日志"这套业务内核，在 `ControlServer.Core` 里重新实现一遍，并通过 REST + SignalR 暴露给 Web 前端。**

### 0.2 明确的边界

| 项 | M2 做 | M2 **不做**（谁做） |
|---|---|---|
| 按钮/动作/子按钮集 CRUD | ✅ | — |
| 对接码三级匹配 + 自动执行 | ✅ | — |
| 定时器（每日/指定星期/月度计划多时间点） | ✅ | — |
| 指令库 | ✅ | — |
| 配置导入/导出（含图片内嵌） | ✅ | — |
| 收发日志（最近 + 历史 + 实时推送） | ✅ | — |
| 时间校准（NTP） | ✅（简版） | 多源回退 + 偏差告警细化 → M2.5 |
| 前端**基础**管理界面（列表/编辑/执行/点选排序） | ✅ | — |
| 前端**拖拽自由排布 / 批量对齐分布 / 拖拽排序** | ❌ | **M2.5** |
| 多角色 RBAC、密码策略 | ❌ | **M3**（M2 沿用 M1 单管理员 Cookie） |
| 授权（License）/ 加密 `.dat` 迁移 | ❌ | **M4**（与机器码/授权一起做） |
| 文件分发 / 远程桌面 | ❌ | **M5 / M6** |

> **为什么要留 M2.5**：拖拽布局、批量对齐、Alt+拖拽复制这类交互，本质是**前端工程**而非业务能力，且对后端零影响。把它们与业务对齐捆绑，会让 M2 的"功能对齐"验收被 UI 细节拖住。**先把能力做对，再把交互做顺。**

### 0.3 M2 的验收口径

以"**行为等价**"为准，不以"代码相同"为准。等价性用**同一批测试向量**在两个实现上跑出相同结果来证明（见 §11.3）。

### 1.2 关键行为（**必须逐条对齐**）

**A. 对接码三级匹配（顺序敏感）**

```
收到 UDP 数据报
  ├─ ① 按钮级：第一个 PairingCode 命中的按钮 → 执行该按钮「全部动作」
  ├─ ② 子按钮级：第一个命中的子按钮 → 执行该子按钮「全部动作」，IP/端口用所属集覆盖
  └─ ③ 动作级：先扫按钮内动作，再扫子按钮内动作，取第一个命中 → 仅执行「该单条动作」
       （子按钮内动作命中时，IP/端口同样由所属集覆盖）
未命中 → 记一条"接收数据 N 字符"，不执行
```

- **比较用的文本 = UTF-8 解码后 `Trim()`**（⚠️ 见 §10.1，M1 用的是 ASCII，必须改）
- `Hex` 类型：**原始字节**转大写十六进制（去 `-`）与对接码（去空白、转大写）比较
- `String`/`UTF-8`：`OrdinalIgnoreCase` 文本比较
- 按钮级与子按钮级的**优先级高于**动作级；即一条数据只要命中按钮级，就不再往下找

**B. 动作执行（顺序 + 延迟）**

```
for i in 0..n-1:
    if i>0 && actions[i].DelayMs>0: await Delay(DelayMs)   // 第 0 条不等待
    send(actions[i])
```

- 子按钮场景：`overrideIp/overridePort` 覆盖每条的 IP/端口，且 `Protocol=="WoL"` **强制改为 UDP**
- 单条失败**不中断**后续动作，逐条汇总结果

**C. 编码分支**

| DataType | 编码 |
|---|---|
| `String` / `UTF-8` | UTF-8 |
| `ANSI` | **GBK(936)**（中文 Windows ANSI 代码页），取不到回退系统默认 |
| `ASCII` | ASCII（>127 变 `?`） |
| `Hex` | 去空格/换行/`0x` → 字节；**奇数长度报错** |
| `指令库` | 先按 `DataContent` 查指令库，用指令的 `Protocol/DataType/Data` 替换后再走上面的分支 |

**D. WoL（网络唤醒）**

魔术包 = 6×`0xFF` + 16×MAC。MAC 支持 `AA:BB:CC:DD:EE:FF` / `AABBCCDDEEFF` / `-` / `.` 分隔；长度必须 12 位十六进制。端口默认 9；IP 为空或 `0.0.0.0` → `255.255.255.255`；需 `EnableBroadcast`。

**E. 定时器**

- 每秒轮询 `BeijingTime.Now`（UTC+8，与系统时区解耦），比较 `HH:mm:ss`
- 任务定时：`TimerTimes` 命中 → `Daily` 直接触发；`SpecificDays` 再校验 `TimerDays`
- 月度计划：遍历 `Enabled` 计划 → `Times` 命中 → 校验 `MonthDays[当月].Days` 含当日
- **幂等**：进程内记录 `(buttonId[:planId]:time)` 上次触发时间，2 秒内不重复
- 触发即执行该按钮**全部动作**

**F. 配置导入导出**

- 导出：深拷贝配置 → 把所有**真实存在的图片**读出 base64，路径改写为 `imgN.ext` → 产出 `ConfigBackup`
- 导入：把 `imgN.ext` 还原为本地文件 + 绝对路径 → 整体写盘
- 恢复出厂：删图片文件 + 裁剪缓存 + 写回默认 `AppSettings`

**G. 排序归一化**

按钮与子按钮集放入同一列表按 `Order` 排序；`Order` 相同时**按钮优先于集合**；随后从 0 重新编号（`0..N-1`）。

**H. 兼容性清洗**

加载时对所有可空字段做 `??=` 兜底；`TimerTime→TimerTimes`、`Time→Times`、`Months+Days→MonthDays` 三个**旧格式迁移**；子按钮动作强制去 WoL；`ListenPort/TargetPort` 越界回默认。

**I. 日志**

收发日志字段：`Time` / `Direction`("发送"|"接收") / `Protocol` / `TargetIp` / `Port` / `Data`(>200 截断) / `Success` / `Message` / `ButtonName` / `ActionName`。
- 内存环形缓冲 400 条（供"最近日志"）+ 异步批量落盘（500ms）+ 单文件上限 5000 条
- 实时事件推给 UI

**J. 主界面交互（M2.5 范围）**

编辑模式、多选批量删除、批量对齐/分布、统一样式应用、拖拽排序（Alt=复制）、自由排布拖拽、右键菜单（复制/删除）、子按钮集点击弹窗。

## 3. 领域模型落地（Core 层）

原则沿用 M1 的硬规则：**`Core` 不引用 ASP.NET Core / EF Core / 平台 API**。因此：

- 模型放在 `ControlServer.Core/Models/`，为**纯 POCO + 可变属性**（因为要支持"编辑-保存"与旧格式迁移）
- 序列化契约放在 `ControlServer.Contracts`（DTO），Core 模型**不直接对外**（避免前端绑死内部字段）
- 命名与 JSON 风格**对齐桌面版**（`camelCase`），使旧 `control_config.json` 能**近乎直读**

### 3.1 新增文件清单（Core）

```
Core/Models/ButtonAction.cs        // 含 PairingCode/Type、DelayMs、DataType 常量
Core/Models/ButtonConfig.cs
Core/Models/SubButton.cs           // SubButton + SubButtonSet
Core/Models/MonthlyPlan.cs         // MonthlyPlan + MonthDaySchedule
Core/Models/ControlSettings.cs     // 对应 AppSettings（Web 版裁剪桌面专有项）
Core/Models/CommandItem.cs
Core/Models/ConfigBackup.cs
Core/Models/TrafficLogEntry.cs     // 收发日志
```

### 3.2 AppSettings → ControlSettings 的取舍

桌面版 `AppSettings` 里有 4 个**纯桌面**字段，服务版无意义，需显式决定：

| 桌面字段 | 服务版处理 | 理由 |
|---|---|---|
| `WindowWidth` / `WindowHeight` / `WindowLocked` | **丢弃** | 浏览器窗口无法由服务端控制 |
| `MinimizeOnClose` | **丢弃** | 无托盘概念（服务常驻） |
| `AutoStart` | **语义转换** → 服务自启（Windows SCM `auto` / systemd `enable`） | 由部署脚本管理，不入配置 |
| `UserPasswordHash` | **迁移**到 `users` 表（M1 已有 AppUser） | 认证已由 Cookie + 用户表承担 |
| `FreeLayoutEnabled` / `BackgroundImagePath` / `DefaultButtonImage` / `AppName` / `ListenPort` | **保留** | Web 端同样需要 |

> ⚠️ 这意味着导入旧配置时，桌面字段**静默丢弃**——方案建议：导入结果里返回一个"被忽略字段"清单，让用户知道丢了什么。**不做静默吞掉。**

## 4. 持久化设计（关键决策）

### 4.1 三个候选

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 关系表** | 6+ 张表（buttons/actions/sets/subbuttons/plans/monthdays）+ 外键 | 可 SQL 查询、可增量更新 | 表多、映射复杂、排序维护累、导入导出要拆装、字段变更要迁移 |
| **B 单 JSON 文档** | 整份配置存 1 行（`config_documents`） | 与桌面版同构、导入导出零转换、结构演进不改 schema | 全量覆盖写、无法按按钮查询 |
| **C 混合** ✅ | 配置走 B（带版本号乐观锁），用户/审计走关系表（M1 已是） | 兼顾 | 需实现乐观并发 |

### 4.2 推荐：C 混合

```
config_documents(
  key        TEXT PK,      -- 'settings' | 'commands' | 'layout'
  value      TEXT,         -- JSON
  version    INTEGER,      -- 乐观锁版本，每次写入 +1
  updated_at TEXT,
  updated_by TEXT
)
```

**理由（三条硬论据）**

1. **本项目配置是"整体语义"**：写入永远是"读全量→改→写全量"，不存在"只更新某个动作的某个字段"的真实需求。关系表的增量能力**用不上**。
2. **导入导出是一等公民**：`ConfigBackup` 本就是 JSON 结构。用 JSON 文档存 = 导出即读、导入即写，**零映射代码**。
3. **嵌套深度大**：按钮→动作→（指令库引用）；按钮→月度计划→每月日期列表。关系化会让 EF 配置与迁移成本翻数倍，而收益为零。

**指令库单独一个 key**（`commands`），与桌面版 `commands.json` 独立于配置的语义一致——**不参与配置导入导出**。

### 4.3 并发与一致性（服务版必须解决，桌面版不需要）

桌面版是单进程单窗口，**不存在并发写**。服务版多浏览器同时编辑，会丢更新。

设计：

1. **乐观锁**：`GET /api/config` 返回 `version`；`PUT /api/config` 带 `If-Match: <version>` 或 body 内 `version`。版本不匹配 → **409 Conflict** + 返回服务端最新版本，前端提示"配置已被他人修改"。
2. **单写者串行化**：`ConfigStore` 内部用 `SemaphoreSlim(1,1)`，保证"读-改-写"原子。
3. **变更广播**：写入成功后向所有客户端广播 `ConfigChanged(version, changedBy)`；其他端提示刷新（或自动拉取）。
4. **原子落盘**：写 `config_documents` 走事务；JSON 序列化失败不落盘（避免写坏）。
5. **审计**：每次配置写入记一条 `audit_logs`（谁、何时、改了什么类型）。M1 已有该表。

### 4.4 基线迁移（M1 遗留项必须在本轮清掉）

M1 用 `EnsureCreated()`（无迁移）。M2 加表后若继续 `EnsureCreated`，老库（已建）不会新增表 → **运行期报错**。

处置：M2 第一步引入 **EF Core Migrations**，做一次 **基线迁移**：
- 全新库：`Migrate()` 一次建全。
- 已存在的 M1 库：先比对（`users/settings/audit_logs` 已在），采用"**基线快照 + 增量迁移**"（把 M1 结构记为 `InitialCreate` 快照，M2 新表为独立迁移），避免对老库重复建表。

## 5. 服务层设计（Core）

### 5.1 组件总览

```
Core/Services/
  ├─ ControlSettingsService   配置读写 + 兼容清洗 + 排序归一化 + 版本控制
  ├─ PairingMatchService      三级匹配（纯函数，可单测）
  ├─ ActionExecutionService   多动作顺序执行 + 延迟 + 编码 + 指令库解析
  ├─ DataEncoder              5 种编码 + Hex 解析 + MAC 解析（纯函数）
  ├─ TimerSchedulerService    定时轮询 + 触发记录（可注入时钟）
  ├─ CommandLibraryService    指令库 CRUD + Resolve
  ├─ ConfigBackupService      导出（图片内嵌）/ 导入（图片落盘）
  ├─ TrafficLogService        收发日志环形缓冲 + NDJSON + 事件
  └─ TimeSyncService          NTP 校准（简版）
```

**关键工程原则**：`PairingMatchService` 与 `DataEncoder` 是**纯函数**（输入→输出，无 IO），因为它们是"行为等价性"的核心，必须能被测试向量直接验证。

### 5.2 PairingMatchService（三级匹配）

```
MatchResult Match(byte[] payload, string utf8Text, IReadOnlyList<ButtonConfig> buttons,
                  IReadOnlyList<(SubButton sub, SubButtonSet set)> subs)

MatchResult:
  Kind      = None | Button | SubButton | Action
  Button    : ButtonConfig?
  SubButton : (SubButton, SubButtonSet)?
  Action    : (ButtonAction, ownerLabel, overrideIp?, overridePort?)?
```

- 内部顺序：按钮级 → 子按钮级 → 动作级（按钮内动作 → 子按钮内动作）
- `Hex` 比较用**原始字节**；文本比较用**UTF-8 Trim 后**文本
- 与桌面版 `ListenerService` 的 `TryMatchAction` + `IsPairingCodeMatch` 逐行等价

### 5.3 ActionExecutionService

- 输入：`IReadOnlyList<ButtonAction>` + `buttonLabel` + 可选 `overrideIp/Port`
- 逐条：延迟（第 0 条跳过）→ 指令库解析 → 编码 → 发送 → 记日志 → 汇总
- 返回 `ActionExecutionResult`（每条的成功/失败/消息 + 总耗时）
- **行为对齐点**：失败不中断；WoL 在 override 下强制 UDP；`指令库` 未找到记失败但继续

### 5.4 TimerSchedulerService（服务化增强）

在桌面版逻辑之上，**必须补三件事**（否则服务版会出问题）：

| 问题 | 桌面版 | 服务版 | 处置 |
|---|---|---|---|
| 进程重启丢去重状态 | 进程常驻，几乎不重启 | 服务会重启/升级 | **触发记录持久化**到 SQLite，`(refId, date, time)` 唯一约束，重启后不重复触发 |
| 服务停机期间漏触发 | 无此场景 | 存在 | 默认**不补执行**（避免重启后集中爆发），记录"错过 N 个触发点"告警；可选配置开启补执行 |
| 时间漂移 | 依赖系统时间 | 无人值守服务器易漂移 | 接 `TimeSyncService`，偏差超阈值（如 3s）告警并可选拒绝触发 |

触发记录表：

```
timer_fires(
  ref_id     TEXT,   -- buttonId 或 buttonId:planId
  fire_date  TEXT,   -- yyyy-MM-dd（北京时间）
  fire_time  TEXT,   -- HH:mm:ss
  fired_at   TEXT,
  PRIMARY KEY(ref_id, fire_date, fire_time)
)
```

### 5.5 DataEncoder（编码）

- `Encode(DataType, content) → byte[]`：**与桌面版分支一一对应**
- ⚠️ **ANSI 跨平台**：Windows = GBK(936)；**Linux 上 GBK 需 `Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)`**，否则 `GetEncoding("GBK")` 抛异常。方案：启动时注册；Linux 缺码页时回退 UTF-8 并在 UI 明示。**这是必须写进代码的坑**（见 §10.4）。

### 5.6 TimeSyncService（简版）

- 复用 M1 已配置的 NTP 服务器列表（`aliyun` / `tencent` / `cn.pool`）
- SNTP 客户端：取偏移量 → 提供 `BeijingTime` 校正值（**不改系统时钟**，只做应用内校正）
- 定时器与日志时间戳统一走校正后的 `BeijingTime`
- 多源投票/回退细化 → M2.5

## 9. 并发 / 一致性 / 稳定性

| 场景 | 处置 |
|---|---|
| 多浏览器同时编辑 | 乐观锁 409 + `ConfigChanged` 广播 |
| 配置写入中断电 | SQLite 事务 + WAL（M1 已启） |
| 监听端口被占用 | M1 已有：记录错误不裸崩；M2 加"端口占用 → UI 明确提示 + 重试" |
| 定时器与手动执行并发 | 执行入口统一排队（`ActionExecutionService` 内信号量），避免同按钮重入 |
| 日志暴涨 | 环形缓冲 400 + NDJSON 按日分文件 + 保留天数上限（建议 31 天，可配） |

| 重复触发 | 持久化触发记录唯一约束（§5.4） |

## 10. 与桌面版的差异清单（诚实项）

### 10.1 ⚠️ M1 的解码就是错的（必须改）

M1 `PairingListenerService` 用 **`Encoding.ASCII`** 解码，桌面版用 **`Encoding.UTF8`**。
- 影响：非 ASCII 对接码（中文、UTF-8 特殊字符）在 M1 下会变 `?`，**永远匹配不上**
- 处置：M2 改为 UTF-8 解码；`PairingDatagram` 的 `AsciiText` 字段改名为 `Text`
- 这是**行为不等价**，不是风格问题

### 10.2 日志模型必须分家

M1 的 `LogEntry`（`Level/Category/Message`）是**运维日志**，与桌面版的**收发日志**（`Direction/Protocol/TargetIp/Port/Data/Success/ButtonName/ActionName`）**不是一回事**。

- 处置：**保留** M1 的运维日志（Serilog 文件 + 现有 `/api/logs`）；**新增** `TrafficLogEntry` 与 `TrafficLogService` 承载收发日志
- 前端"最近日志"面板绑 `TrafficLog`；`LogViewPage` 等价页绑历史 `TrafficLog`

### 10.3 端口与监听地址

桌面版监听 `9999`（UDP）；服务版同端口即可。**但**：服务版 HTTP 也是对外端口（8080）。安全上建议 M2 保留 `Server:Security:AllowedCidrs`（M1 已留位）——**内网默认不限制，需在文档明示风险**。

### 10.4 ANSI 在 Linux 需要注册代码页

`Encoding.GetEncoding("GBK")` 在 .NET 跨平台下**默认不可用**（需 `System.Text.Encoding.CodePages` + 运行时注册）。

- Windows：可直接用（.NET 已内置）
- Linux：必须 `Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)`
- 处置：在 `DataEncoder` 静态构造中**无条件注册**；注册失败或码页缺失 → 回退 UTF-8 + 记警告（不抛异常）

### 10.5 遗漏触发点的语义（新增，无桌面对应）

服务版新增"停机期间漏触发"概念。默认不补执行，但**必须让用户知道漏了**（状态栏/日志告警）。这是一个**桌面版不存在的决策**，需用户确认（§12）。

### 10.6 无托盘 / 无窗口尺寸 / 无注册表自启

这三项在服务版不存在对应物，已在 §3.2 与 §7.3 明确丢弃或转换。

### 10.7 ⚠️ 桌面版 `TimerTime → TimerTimes` 迁移是**死代码**（服务版有意修正）

**这是实施 M2-A 时实测发现的、桌面版的一个隐性缺陷。**

桌面版 `ButtonConfig` 的属性初始化器是：

```csharp
public List<string> TimerTimes { get; set; } = new() { "08:00" };   // ← 默认值写在这里
```

于是当旧配置**只有 `timerTime`、没有 `timerTimes` 字段**时，反序列化后集合已被初始化器填成 `["08:00"]`，紧接着的迁移判断：

```csharp
if (btn.TimerTimes.Count == 0 && !string.IsNullOrWhiteSpace(btn.TimerTime))
    btn.TimerTimes.Add(btn.TimerTime);   // 永远不会执行
```

`Count == 0` 恒为假 —— **那条迁移永远不会触发**。后果：用户当年设的 `timerTime = "07:45"` 被**静默替换**成 08:00。`MonthlyPlan.Time → Times` 同理。

**服务版的处置（有意偏离，非疏漏）**：把默认值**从属性初始化器下移到清洗器**，即模型默认 `new()`，由 `ControlSettingsNormalizer` 负责补 `"08:00"`。效果：

| 输入 | 桌面版 | 服务版 |
|---|---|---|
| 只有 `timerTime="07:45"` | `["08:00"]`（旧值**丢失**） | `["07:45"]`（旧值**保留**） |
| 有 `timerTimes=["12:00"]` + `timerTime="07:45"` | `["12:00"]` | `["12:00"]`（一致） |
| 两者都没有 | `["08:00"]` | `["08:00"]`（一致） |
| `timerTimes=[]` + `timerTime="07:45"` | `["07:45"]` | `["07:45"]`（一致） |

差异**只出现在桌面版本来就出错的场景**。守门用例：`Legacy_TimerTime_is_honored_even_when_the_new_field_is_never_mentioned`、`Legacy_plan_Time_is_honored_when_Times_is_never_mentioned`。

> 如需**逐字节 bug 兼容**，把两处默认值改回 `new() { "08:00" }` 即可 —— 但有旧配置的用户会继续丢时间点。**建议保留修正**。

### 11.3 行为等价性测试向量（核心验收手段）

**这是 M2 最重要的一项工程产出**：把桌面版行为抽成"输入→期望输出"的表，两个实现都跑。

| 类别 | 向量示例 |
|---|---|
| 编码 | `("Hex","0x41 42")→[0x41,0x42]`；`("Hex","ABC")→异常`；`("ASCII","中")→[0x3F]`；`("ANSI","中")→[0xD6,0xD0]`(GBK)；`("UTF-8","中")→[0xE4,0xB8,0xAD]` |
| MAC | `AA:BB:CC:DD:EE:FF`/`AABBCCDDEEFF`/`aa-bb-cc-dd-ee-ff` 均 → 6 字节；12 位以下 → null |
| 延迟 | 3 条动作 `[0,100,50]` → 仅第 2、3 条等待；总耗时 ≈150ms（±容差） |
| 匹配-按钮级 | 命中 → Kind=Button，执行全部动作 |
| 匹配-子按钮级 | 命中 → Kind=SubButton，IP/Port = 集合值 |
| 匹配-动作级 | 命中 → 仅执行 1 条；子按钮内命中时用集合 IP/Port |
| **优先级** | 同一码同时命中"动作级"与"按钮级" → **按钮级胜出** |
| Hex 匹配 | 对接码 `"41 42"` + 收到 `0x41 0x42` → 命中 |
| 大小写 | `"LIGHT_ON"` vs `"light_on"` → 命中（String/UTF-8） |
| 定时 | `TimerTimes=["08:00"]` + 08:00:00 → 触发 1 次，重复轮询不重复触发 |
| 月度 | `MonthDays=[{Month:10,Days:[7]}]` + 10-07 → 触发；10-08 → 不触发 |
| 排序 | 按钮 Order=0、集合 Order=0 → 按钮在前；重编号 0..N-1 |
| 迁移 | 旧 `TimerTime="08:00"` → `TimerTimes=["08:00"]`；`Months+Days` → `MonthDays` |
| 往返 | 配置 → BuildBackup → ApplyBackup → 与原配置逐字段相等（图片路径除外） |

### 14.5 本轮发现并修正的缺陷

1. **桌面版 `TimerTime → TimerTimes` 是死代码**（详见 **§10.7**）。桌面版把 `TimerTimes` 默认值写在属性初始化器里，导致"旧配置只有 `timerTime`"时集合已被填成 `["08:00"]`，迁移条件 `Count == 0` 恒假 —— 用户设的时间点被静默丢弃。服务版把默认值下移到清洗器，使旧值真正迁移过来。**这是有意偏离，已用两个专门用例守门。**
2. **排序说明被无条件追加**，会破坏"清洗幂等"这一不变量。已改为"顺序真的变了才记说明"。这个问题是**写测试时暴露的** —— 正是"行为等价性测试向量"的价值所在。

### 14.6 M2-A 遗留 / 下一步

- **`/api/config` 系列端点尚未暴露**（属 §11.1 的 M2-F「API 收口」）。当前 `ControlSettingsService` 只能被进程内调用 —— 集成测试就是直接 resolve 服务来验的。
- **`timer_fires` 表**未建（属 M2-D）。到时**新开一个迁移**，不要动 `InitialCreate`（见 14.3）。

### 16.2 关键实现决策（与设计稿的差异）

1. **匹配做成纯静态函数**（设计稿写的是 `PairingMatchService` 服务）。
   理由：它无 IO、无状态、无依赖，静态化之后测试向量可以**直接对输入输出断言**，不必装配 DI。
   与之相对，**派发**（要配置 / 执行 / 日志）落成 `PairingDispatchService` 服务并注册进 DI。
2. **监听循环 `await` 处理器**（设计稿写的是"事件"）。
   事件是"发完即忘"的，两个对接码在 5ms 内到达就会**并发执行**，日志与动作顺序出现歧义。
   桌面版是在收包循环里 `await` 执行的 —— 改成 `Func<..., Task>` 才真正等价，且顺带让 `HandlerError`
   有地方落（单条失败不终止监听）。这条在 `Handler_is_awaited_so_datagrams_are_processed_serially`
   里用"最大并发数必须为 1"守门。
3. **`PairingDatagram` 携带原始字节 `Payload`**（设计稿没提）。
   文本解码是**有损**的（非法 UTF-8 字节被替换为 U+FFFD，`0x0A` 还会被 `Trim` 掉），
   而 Hex 对接码必须按字节比较 —— 不能拿解码结果反推字节。见
   `Hex_pairing_code_matches_on_raw_bytes_not_on_decoded_text` 与
   `Hex_text_is_uppercase_and_separator_free`。
4. **派发每次都读最新配置**（不走 `CachedSettings` 快照）。
   编辑页刚保存的对接码必须"下一包就生效"。`ControlSettingsService.GetAsync` 内部按版本号判断，
   未变更时不重新反序列化，开销可接受。`Latest_config_edit_takes_effect_on_the_next_datagram` 守门。
5. **`Actions` 空序列视为成功**（沿用 M2-B 语义，不额外造"没有动作可执行"的失败态）。

### 16.4 本轮**新发现**的桌面版既有行为（两处 quirk，已用测试锁定）

实施时发现两处"看起来该通、实际不通"的规则不一致。**服务版选择逐字节复刻**，并各写一条守门用例 ——
否则将来有人"顺手修好"，两个实现就又不等价了。

| # | 现象 | 成因 | 守门用例 |
|---|---|---|---|
| 1 | **文本为空时，动作级不匹配，但按钮级 / 子按钮级仍会匹配** | 桌面版 `TryMatchAction` 开头即 `if (string.IsNullOrEmpty(code)) return false;`，而按钮级 / 子按钮级没有这个早退。后果：Hex 对接码 `"00"` 收到单字节 `0x00` 时，文本被 `Trim` 成空串 → 在按钮级能命中、在动作级不能 | `Empty_text_skips_action_level_matching_but_not_button_level` |
| 2 | **Hex 对接码既不剥离 `0x` 前缀，也不兼容 `:` / `-` 分隔** | 桌面版 `NormalizeHex` **只去空白 + 转大写**；而同一程序里 WoL 的 `ParseMacAddress` 是兼容 `:` `-` `.` 空格的。两处规则不同，用户按 MAC 习惯写 `AA-BB-CC-DD-EE-FF` 或 `0x4142` 都永远匹配不上 | `Hex_pairing_code_with_0x_prefix_does_not_match`、`Hex_pairing_code_does_not_strip_colon_or_dash_separators` |

> 如果希望**服务版比桌面版更宽容**（自动剥离 `0x` 与 `-`/`:`），改动点只有 `PairingMatchService.IsPairingCodeMatch`
> 一处，但同时会引入"同一份配置在两个实现上行为不同"。**建议维持逐字节等价**，把宽容化留给"对接码输入框的即时校验提示"（前端增强阶段）去做。

### 17.2 与设计稿的**有意偏离**（6 条）

1. **契约层不复制配置 DTO**。`ConfigViewDto.Settings` 用 `JsonElement` 透传 ——
   `Contracts` 在 `Core` 之下不能反向引用 `Core.Models`，而在契约层把
   `ControlSettings` 再抄一份会造成**两处真相**（改一处忘另一处 → 字段静默丢失）。
   配置的形状只有一份真相（`Core.Models`），HTTP 层只做序列化 / 反序列化。
   前端 TS 类型与其 camelCase 一一对应。
2. **不开 `/api/buttons/{id}/execute` 与 `/api/subbuttons/{id}/execute`**。
   方案 §6.1 列了这两个端点，但 `POST /api/actions/execute` 用 `buttonId` / `subButtonId`
   已经覆盖同一语义；再加一层薄壳就是**两个入口做同一件事**，前端会分裂成两种调用方式。
   因此**统一走 `/api/actions/execute`**，前端也只调它。
3. **新增图片端点 `GET /api/config/images/{fileName}`**（方案中没有）。
   原因：配置里的图片字段存的是**服务端绝对路径**，浏览器加载不到 ——
   不加这个端点，"导入桌面配置"之后所有按钮图都会是空的，用户会以为图片丢了。
   安全上双闸：文件名过 `IsSafeImageKey` 白名单，且解析后的绝对路径必须仍位于 `ImagesDirectory` 内。
4. **新增「空配置保护」**（方案中没有）。导入是整体覆盖；若解析结果里一个按钮 / 子按钮集都没有
   而现有配置非空，则**拒绝**并指向「恢复出厂设置」。
   同时 `Parse` 对"裸 JSON"路径要求**至少认得一个已知字段** ——
   否则任意 JSON 对象（如 `{"version":"1.0"}`）都会被宽松反序列化成"全默认空配置"，一次点击清空全部数据。
   这是本轮实做时发现的**静默数据丢失路径**，两处都补了守门用例。
5. **`RestoredImages` 按去重张数计**，而不是"还原操作次数"。同一张图被
   「默认按钮图 + 多个按钮」引用时是**一张**图，报成 N 会让用户以为备份里凭空多了图（导出侧本就是去重计数）。
6. **子按钮集弹层用居中模态**（桌面版是悬浮弹窗）；**自由排布**按模型文档语义实现 ——
   `LayoutX/LayoutY` 非 0 的瓦片绝对定位、为 0 的仍走流式布局，两层并存。

### 17.3 实时通道（前端依赖的两条新线）

```
TrafficLogService.TrafficLogAdded ─┐
                                   ├─→ RealtimeRelayHostedService ─→ INotifier ─→ SignalR
ControlSettingsService.Changed ────┘
```

- `TrafficLogAdded` 推**完整记录**（体量小）→ 前端直接追加到列表尾部（上限 400，与服务端环形一致）。
- `ConfigChanged` **只推版本号**，客户端自行 `GET /api/config`。
  把整份配置塞进推送会在配置较大（含图片 base64 时可达数 MB）时撑爆实时通道。
- 前端重连（`onreconnected`）后会补拉配置与收发日志，避免断线期间的缺口。

### 17.5 遗留与已知局限

1. **编辑页尚未实现**（按钮 / 子按钮集 / 子按钮 / 指令库），属 **M2-G2**。
   因此本轮界面上**只能看与执行，不能改配置** —— 配置的来源是「导入桌面版备份」或后续的编辑页。
   `/api/config` 的 PUT 与配置服务的细粒度操作（`AddButtonAsync` 等）**已就绪**，M2-G2 直接接。
2. **图片按文件名匹配有歧义**：前端只把路径的最后一段发给服务端。
   若配置里引用的是图片目录之外的路径，且那里恰好有同名文件，可能串图。
   这是在"不暴露服务端任意路径"（安全）与"路径映射精确"之间的取舍，极端场景下表现为显示错图而非报错。
3. **`LayoutX/LayoutY` 的单位是桌面像素**，Web 端直接用 CSS px，不同分辨率下比例可能与桌面版不完全一致。
4. **`ListenPort` 仍是双真相源**（配置字段 vs `Server:Listener:PairingPort`），待方案 §12 决策 #8 拍板。
5. **EF Core 的 SQL 日志仍未压级**（M2-C 记录，见 §16.6）：本轮的 `GET /api/config`
   与 `ConfigChanged` 自动重拉会进一步放大 `server-*.log` 体积。
   一行修法已备好（`Program.cs` 补 `.MinimumLevel.Override("Microsoft.EntityFrameworkCore", LogEventLevel.Warning)`），**等用户确认**。
6. **XMP / 合规水印**等与 AI 换脸相关的合规能力不属 M2 范围。

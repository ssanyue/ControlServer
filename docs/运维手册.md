## 1. 一分钟体检：一条命令

```powershell
# 🔴 必须"以管理员身份运行"：M6.4 起数据目录 ACL 只给 SYSTEM 与 Administrators，
#    UAC 下未提升的窗口连目录都列不出来（详见 §1.3）。
ControlServer.Server.exe --health
```

输出是 **一行一项 `键=值`**，最后一行是 `health=ok|warn|fail`，**退出码 0/1/2**（下面是**节选**，
真实输出还有 `data.root`、`data.bytes`、`files.*`（见 §1.1）、`cert.*.subject`、`license.kind/machinecode`、
`service.port/version` 等行 —— 别拿这份节选去写解析脚本，以实际输出为准）：

```
data.exists=1
db.bytes=5120000
db.wal.bytes=0
logs.bytes=1697548
logs.files=17
files.bytes=1071700351
files.db.count=1
files.disk.count=1
files.orphans=0
files.lost=0
disk.free=123155611648
disk.needed=5368709120
cert.server.daysleft=1094
license.present=1
license.status=Authorized
license.daysleft=24
trial.daysleft=21
service.healthz=unreachable
warn.1=授权还有 24 天到期（2027-06-30）—— 现在就该续期
warn.count=1
fail.count=0
health=warn
```

### 1.1 每个键是什么意思、什么时候该动手

| 键 | 正常 | 该动手的阈值 | 怎么处理 |
|---|---|---|---|
| `data.exists` | `1` | `0` | 数据目录没建或指错了 → §3.1 |
| `db.bytes` | 有值（空部署也有几 MB） | `0` = **失败**；> 4 GB | `0` → §3.1；>4 GB → §4.4 |
| `db.wal.bytes` | 0 – 几十 MB | > 256 MB | 重启一次服务回收（库本体没这么大，这是没 checkpoint） |
| `logs.bytes` | < 策略上限 | 超过 `logs.retention.mb` | 保留策略没生效 → §3.4 |
| `files.bytes` / `files.db.count` | 业务量 | 关注**增速**，不设绝对值 | §4.2 |
| `files.orphans` | `0` | > 0 且**一周不降** | 后台每 30 分钟自动回收；不降＝删不掉（被占用 / 权限）→ 看 `server-*.log` 的 `Files` |
| `files.lost` | `0` | **> 0 就当天处理** | 库里有记录、磁盘上没有文件 ⇒ 这些文件**下载会失败**。对账不替你删记录，去备份里找 → §4.5 |
| `logs.retention.enabled` | `1` | `0` | 有人在配置里关掉了 → 打开 |
| `disk.free` vs `disk.needed` | `free ≥ needed` | `free < needed` | 清盘或扩盘。**`needed` 是"够下一次全量备份"，不够就升级/备份必失败** |
| `cert.server.daysleft` | > 30 | ≤ 30 或为负 | 服务器证书 3 年一签，到期前换 → §3.2 |
| `cert.ca.daysleft` | > 90 | ≤ 90 | 根 CA 20 年；真到这天要换密钥并重新分发根证书 |
| `license.status` | `Authorized` / `Trial` | `Expired` / `Error` | 见 `docs/授权操作手册.md` |
| `license.daysleft` | > 30 | ≤ 30 | 正式授权续期要客户配合，**提前一个月开始** |
| `trial.daysleft` | > 7 | ≤ 7 | 到期前必须导入正式授权，否则 Enforce 下 `/api` 全线 403 |
| `license.signature` | `ok` | `bad` | 文件被改过、或用的不是厂商公钥签的 → 重新签发 |
| `service.healthz` | `200` | `unreachable` | 服务没在跑 → §3.1（维护窗口里是正常的） |
| `logSink.healthy`（`/healthz` 里） | `true` | `false` | 日志写不进去 → §3.4 |

> ⚠️ `service.healthz=unreachable` 只证明"**本机这个端口上没人应答**"，
> 它区分不了"服务没启动"和"服务启动在别的端口"。端口是 `service.port`，与 `Server:Http:Port` 同源。

> 🔴 **试用 7 天报警、正式授权 30 天报警 —— 这两个阈值刻意不同。**
> 试用续命只是"导一个文件"，一小时能搞定；按 30 天报的话，**一台刚从箱子里拆出来装好的机器第一天就带告警**，
> 值班很快就会对"巡检有告警"脱敏，等真出事时就不看了。正式授权要客户配合（报价、付款、签发），30 天是必须的。

### 1.2 退出码（给定时任务用）

| 退出码 | 含义 | 定时任务该怎么反应 |
|---|---|---|
| `0` | `health=ok`，全绿 | 什么都不做 |
| `1` | `health=warn`，有告警 | 把 `warn.N` 那几行原样发出来（别只发"有告警"） |
| `2` | `health=fail`，有失败项 | 值班应该被叫起来 |

```powershell
# 每天 08:00 跑一次，只在有告警时留证据（Windows 任务计划程序里当"操作"）
$out = & "C:\Program Files\ControlServer\ControlServer.Server.exe" --health
$code = $LASTEXITCODE
if ($code -ne 0) { $out | Out-File "$env:ProgramData\ControlServer\health-$(Get-Date -f yyyyMMdd).txt" }
```

### 1.3 🔴 为什么必须提权跑

M6.4 把数据目录的 ACL 收紧成 **只有 `NT AUTHORITY\SYSTEM` 与 `BUILTIN\Administrators`**。
在这之前 `BUILTIN\Users` 不但能读，还能往 `files/`、`downloads/` 里**塞文件**。

副作用（知情同意）：**"账号在管理员组"不等于"这个窗口有管理员权限"**。
UAC 下未提升的令牌里 Administrators 是 deny-only，`--health` 会读不到目录、报一堆 `?`。
⇒ 从 M6.4 起，`--backup` / `--restore` / `--dbinfo` / `--health` 与 `deploy/backup/*` **一律要提权**。

## 2. 巡检：每周做什么、每月做什么

### 2.1 每周（5 分钟）

1. `--health`，退出码必须是 0 或 1（`2` 当天就要处理）；
2. 逐条看 `warn.N`，按 §1.1 处理；
3. 把输出**存档**（一行命令就能存）：这是"这个月磁盘怎么涨的""授权还剩几天"的唯一依据。

```powershell
& "...\ControlServer.Server.exe" --health |
    Out-File "$env:ProgramData\ControlServer\health-$(Get-Date -f yyyyMMdd).txt" -Encoding utf8
```

> 为什么强调"存档"：`--health` 是**当时**的快照，它不记历史。
> 想知道"库一个月长了多少"，只能靠自己每周存的这几份文件比。

### 2.2 每月

| 动作 | 判据 | 说明 |
|---|---|---|
| 比 `db.bytes` 走势 | 是否与 §4.3 的规划相符 | 超预期 ⇒ 要么台数涨了，要么保留策略没在裁 |
| 比 `files.bytes` 与 `files.db.count` 的走势 | **有库记录的文件永不自动删**（那是用户的东西） | 只增不减，见过期的分发文件由管理员在页面上删；孤儿由后台自动回收，不用人管 |
| 抽查一次备份**能不能恢复** | 见 §5 | 没恢复过的备份不算备份 |
| 看一眼授权/证书的 `daysleft` | 见 §1.1 | 这两件事都要**外部配合**（客户续费 / 分发证书），不能等到当天 |

### 2.3 巡检**不**包括什么（别以为它看过就没事了）

- 它**不测**业务功能：点一个按钮、看一台客户端在不在线，`--health` 都不管；
- 它**不测**远控画面质量（M5 侧的事）；
- 它**不联网**：唯一的外呼是 `127.0.0.1`。NTP 是否校准成功要另看 `server-*.log`；
- 它读的是**磁盘上的文件**，不读内存。所以"服务在跑但状态是错的"它看不出来 ——
  那类问题看 `/healthz` 与 `/readyz`。

## 3. 故障树

> 用法：从"你看到的症状"往下找，每一步都给了**能判死的证据**，不要凭感觉跳步。

### 3.1 服务起不来 / 起了一下就没了

**先确认"到底有没有起来"**：`--health` 的 `service.healthz`，或

```powershell
curl.exe -s -o NUL -w "%{http_code}" http://127.0.0.1:8899/healthz
```

拿到 200 才算起来了。**"进程在"不等于"服务可用"**（绑不上端口时会立刻退出）。

| 判据（`server-*.log` 里的关键字） | 原因 | 处置 |
|---|---|---|
| `Address already in use` / `http://0.0.0.0:8899` 失败 | 端口被占（常见：上一个实例没退干净、或别的软件占了 8899） | `netstat -ano \| findstr :8899` 找到 PID；是残留的**自己**的进程就结束它，是别人的就改 `Server:Http:Port` |
| `UnauthorizedAccessException` / `拒绝访问` | 数据目录 ACL（M6.4 收紧之后，未提权的进程写不进去） | 以管理员身份运行服务（服务本身是 LocalSystem，正常情况下不该出现；手工用命令行起就要提权） |
| `SQLite Error 11: database disk image is malformed` | 库损坏（断电 / 磁盘坏道） | **不要删库**，按 §5 用最近一次备份恢复；恢复不了再想别的 |
| `Security:AllowedCidrs` 相关的启动失败 | 白名单配错，服务**故意**拒绝启动（M6.2 的 fail-closed） | 修 `Server:Security:AllowedCidrs` 的 CIDR 写法；这是设计如此，不是 bug |
| `口令文件 … 里没有有效的口令行` | `https/pfx.password` 被清空 / 被改坏 | 从备份里找回该文件；找不回就删掉整个 `https/` 让它重签（**观看端要重新导根证书**） |
| 日志里什么都没有 | 服根本没执行到这里（路径错 / 权限错 / 被安全软件拦） | 看 Windows 事件日志；确认 `ControlServer.Server.exe` 能被手工执行 |

`--health` 里对应的信号：

```
data.exists=0        → 数据目录根本不存在（路径错，或从没初始化过）
db.bytes=0 + fail    → 目录在但没有 control.db
```

### 3.2 能起，但浏览器打不开

| 症状 | 判据 | 处置 |
|---|---|---|
| 本机能开、别的机器不能 | `--health` 的 `service.healthz=200` 但别的机器超时 | Windows 防火墙入站规则：`8899`（HTTP）、`8443`（HTTPS，如果开了）、`9999`（对码）、`9998`（发现） |
| 打开是"证书错误" | `cert.server.daysleft` 为负，或换了 IP | 服务器证书按本机地址签发，**换网段/换 IP 会自动重签**（重启一次）；观看端不认是因为根证书没装 |
| 打开是一片空白 / 一直在转 | 前端资源 404（`wwwroot` 没打进包）或反代把 `/api` 拦了 | 用绿色版验证同一台机器是否正常；看 `server-*.log` 里有没有 404 记录 |
| `403` 且页面提示"未授权" | `license.status=Expired` | 见 `docs/授权操作手册.md` |

> **首次信任的唯一正确做法**：在**观看端**访问 `http://<中心IP>:8899/trust/controlserver-ca.crt` 下载根证书并导入"受信任的根证书颁发机构"。
> 这个地址是**匿名**的（不需要登录、不受授权闸门限制），因为"要有授权才能让浏览器信任"是个死循环。

### 3.3 能打开，但点按钮没反应 ← 现场问得最多的一条

按**发生概率**排，不要按"你觉得可疑的"排：

| # | 判据 | 原因 | 处置 |
|---|---|---|---|
| 1 | `--health` 的 `license.daysleft` 为负 / `trial.daysleft` 为负 | 授权过期。Enforce 档位下 `/api` **全线 403**，但页面照样能打开 —— 看起来像"功能坏了" | 导授权 / 续期 |
| 2 | 在线表里那台机器是**灰点** | 客户端离线。判离线是"最后心跳 + 75 秒"（`Server:Agent:OfflineAfterSeconds`） | 到那台机器上看客户端进程在不在；网络通不通 |
| 3 | 按钮绑的是 UDP，且 `ExecuteUdpCommands=false` | 客户端处于**演练模式**。这个开关**连远控一起挡** | 改客户端配置；这是防"点一下把展厅灯全关了"的保险 |
| 4 | 中心和被控不在同一网段 / 组播被隔离 | 发现的 UDP 广播过不去 | 改用安装时填固定地址；或按 §3.2 查防火墙 |
| 5 | 目标机 9999 端口没监听 | 对码监听没起来（客户端没启动 / 端口被占） | 那台机器上 `netstat -ano \| findstr :9999` |
| 6 | 页面显示下发成功，但设备没动 | 中心只是把指令**交给长连接**，回 200 不代表设备收到 | 看数据面板的流量记录与那台机器的日志 |

> 🔴 **"命令回执"这个词在本协议里不存在**：`Command` 是单向推送。
> 验收/排查要看的是 **中心下发条数 vs 客户端实收条数**，不是某个"回执成功率"。

### 3.4 日志断了 / 磁盘满

**症状**：页面上"最近日志"还在滚动更新，但 `logs/log-YYYY-MM-DD.ndjson` 不再变长。

**为什么难查**：`LogService` 的落盘失败是**静默丢弃**的（写日志失败决不能拖垮业务）。
所以在 M6.5 之前，这件事**在系统里没有任何信号**。

**现在的信号（M6.5 新增）**：

1. `server-*.log` 里有一条 `[ERR] 业务日志落盘失败（…）…`（连续失败只在第一次报）；
2. `http://127.0.0.1:8899/healthz` 的 `logSink.healthy = false`，带 `lastError`；
3. `--health` 会把它转成一条 `warn.N`。

**处置顺序**：

```powershell
# 1. 看是谁在占（--health 已经给了分项）
ControlServer.Server.exe --health | Select-String "bytes"

# 2. 清盘：先搬走备份与安装包（downloads/ 里的旧版安装包是最安全的下手处）
# 3. 永远不要"删 logs/ 来解决问题" —— 那是排查唯一的证据。
#    保留策略已经会按 Server:Logging 自动裁，手工删只会删掉现场证据。
```

**日志保留策略（M6.5）**：`Server:Logging:RetentionDays`（默认 30 天）、
`Server:Logging:RetentionMaxMegabytes`（默认 200 MB），每天首次落盘时清理一次；
**今天的文件永不删**；只碰 `log-*.ndjson`（`server-*.log` 归 Serilog 自己滚 31 天）。

> ⚠️ 反过来说：**日志保留只保护 logs/**。`files/`（文件仓库）与 `downloads/`（安装包）
> **没有任何自动清理**，它们涨起来只能人工处理。这是 M6 之后仍存在的最大磁盘风险。

### 3.5 远控相关

远控的"手"在客户端托盘进程（不是服务）：**只起 Service 不起 Tray = 石沉大海**。
黑屏 / 卡 / 无法操作那一整套判据在 `docs/M5-局域网远程桌面实时方案.md` 与 `deploy/smoke/remote-e2e.py`，本手册不复述。

### 3.6 升级之后"数据看起来少了"

先确认**升级到底有没有成功**，再怀疑数据：

```powershell
# ① 跑的是哪个包（启动自述第一屏就有，M6.4 起）
Select-String "程序版本" "$env:ProgramData\ControlServer\logs\server-*.log" | Select-Object -Last 3

# ② 数据对不对（升级前后各跑一次，逐行比）
ControlServer.Server.exe --dbinfo
```

`--dbinfo` 的 `migrations` 应该比升级前**多**；`table.*` 的行数一条都不该少。
真少了 ⇒ 走回滚（`docs/M6.4-升级回滚.md` §3），**别手工改库**。

## 4. 容量

### 4.1 实测基线（这台机器比现场工控机弱，所以结论偏保守）

| 项 | 实测值 | 来源 |
|---|---|---|
| 100 台在线 30 分钟：CPU 均 / 峰 | **1.2% / 10.3%** | M6.3 |
| 100 台在线 30 分钟：内存末段 | **151 MB**（峰值 312 MB 在头 90 秒） | M6.3 |
| 每台每分钟遥测行数 | **12 行**（5 s 采样） | M6.3 |
| 每行落库体积（含索引） | **约 54 B** | M6.3 |
| 每台每天 | **17 280 行 ≈ 0.93 MB** | 由上面两个数算出 |
| **100 台 / 30 天明细** | **约 2.8 GB** | M6.3 |
| 业务日志（安静的一天） | **约 100 KB** | M6.5（17 个文件共 1.7 MB） |
| 一次全量备份耗时 | **9 – 10 s**（1 GB 现场） | M6.4 |
| 升级时「启动中 → 数据库就绪」 | **1.2 – 1.5 s**（5 MB 库） | M6.4 |

### 4.2 换算公式（拿这个去报价 / 选盘）

```
数据库 ≈ 台数 × 保留天数 × 0.93 MB

  10 台 × 30 天  ≈ 0.28 GB
  50 台 × 30 天  ≈ 1.4 GB
 100 台 × 30 天  ≈ 2.8 GB
 300 台 × 30 天  ≈ 8.4 GB
```

**但数据库从来不是占盘最多的那个。** 真正吃掉磁盘的是：

```
数据目录 ≈ 数据库 + 文件仓库(files/) + 客户端安装包(downloads/) + 图片(images/) + 日志(logs/)
现场实测：5 MB + 1.02 GB + 65 MB + 少量 + 1.7 MB  ≈ 1.1 GB   ← 文件仓库占了 93%
```

> 🔎 **`downloads/` 与 `files/repo/` 会增长的原因完全不同**，别混着看：
> `downloads/` 放的是**人工投放**的客户端安装包（全仓代码里没有任何地方往这个目录写），
> 大小由人控制，`--health` 的 `downloads.bytes` 只用来核对"是不是放错了版本"。
> 真正会自己长的是 `files/repo/`。
>
> ⚠️ 而 `files/repo/` 里**有库记录的文件永远不会被自动删** —— 删除是"用户的东西没了"，
> 必须是人的决定（管理员在文件仓库页面删）。自动回收只处理**孤儿**（盘上有、库里没有），
> 见 §4.5。

⇒ **磁盘规划按"数据目录 × 2.2 + 20 GB"给**：

| 规模 | 数据目录估算 | 建议磁盘 |
|---|---|---|
| 10 台，不传文件 | 0.5 GB | 30 GB |
| 50 台，少量分发 | 2 GB | 40 GB |
| 100 台，1 GB 文件仓库 | 4 GB | 50 GB |
| 300 台，长期累积 | 15 GB+ | 120 GB |

**× 2.2 的理由**：升级前必须做一次**全量**备份（M6.4 §7.2 的强制步骤），备份占 1 份，
加上数据目录本身 1 份，再留 20% 写入余量。**余量不足时升级会中途失败** ——
`--health` 的 `disk.needed` 就是这条判据。

### 4.3 三个旋钮（改配置，不用改代码）

| 旋钮 | 默认 | 影响 |
|---|---|---|
| `Server:Agent:Telemetry:MetricsSeconds` | 5 s | **最有效的一个**。调到 30 s ⇒ 行数降到 1/6，100 台 30 天从 2.8 GB 降到 **约 470 MB** |
| `Server:Agent:Telemetry:DetailRetentionDays` | 30 | 明细保留天数。调小立即见效，但历史曲线就没了 |
| `Server:Logging:RetentionDays` / `RetentionMaxMegabytes` | 30 天 / 200 MB | 只影响 `logs/` |

> 🔴 **采样率是"精度"与"体积"的兑换**：30 s 采样意味着一次 10 秒的卡顿**看不见**。
> 排查期临时调回 5 s、查完调回去，是正常的用法；一直开着 5 s 又要省盘，是不可能的。

### 4.4 什么时候该动手（`--health` 已经替你判了）

- `db.bytes > 4 GB` → 先确认台数与保留天数，再决定调采样率还是调保留天数；
- `db.wal.bytes > 256 MB` → 重启一次（长时间没 checkpoint）；
- `disk.free < disk.needed` → **当天处理**，否则下一次备份/升级会失败；
- `files.orphans > 0` 且一周不降 → 后台已经在回收，不降说明删不掉（被占用 / 权限），看 `server-*.log` 的 `Files` 告警；
- `files.lost > 0` → **当天处理**：那些文件下载会失败，去备份里找回 `files/repo/` 下的同名文件（§4.5）；
- `files.db.count` 月度增幅超出预期 → 由管理员在文件仓库页面删过期分发文件。**有库记录的文件永不自动删**，这是刻意的。

### 4.5 文件仓库对账（库 ↔ 盘）

`files/repo/` 与数据库是**两套存储**：字节在磁盘上，元数据在 `file_repo_items` 表里。
它们会不同步，而且不同步时**不报错**：

| 现象 | 含义 | 谁负责 |
|---|---|---|
| **孤儿**：盘上有、库里没有 | 删元数据成功但删文件失败（被占用）、落库失败回滚也失败、或有人手工往目录里拷了文件 | **后台任务自动回收**（宽限期 24 小时，每 30 分钟一轮） |
| **断链**：库里有、盘上没有 | 恢复备份时只带了库没带 `files/`；或磁盘文件被人删了 | **不是自动能修的** —— 去备份里找回来 |

```
files.db.count=1       ← 库里几条记录
files.disk.count=1     ← repo/ 下几个文件
files.orphans=0        ← 盘有库无（可回收）
files.orphan.bytes=0
files.lost=0           ← 库有盘无（要人管）
files.parts=0          ← uploads/ 下几个 .part（含正在传的）
files.stale.parts=0    ← 无主 .part（可回收）
files.grace.hours=24   ← 宽限期，来自 Server:Files:OrphanGraceHours
```

三条必须知道的事：

1. **宽限期不是保守值，是在防一个具体竞态**。完成上传的顺序是「`File.Move(.part → repo)`」
   然后「落库」。两步之间文件**已经在 repo 里、库里还没有记录**，与孤儿长得一模一样。
   按"不在库里就删"去清理，会删掉一个刚刚上传成功的文件 —— 用户看到"上传成功但文件没了"。
   所以判据是**文件年龄**，不是"这次扫描没对上"。
2. **`files.lost` 不会被自动修**。删掉那条记录能让"断链"这个数字变好看，但那等于替用户
   决定"这个文件不要了"，而且让"文件丢了"这件事从此看不见。正确动作是去备份里找。
3. **有库记录的孤儿永远不会被删**。你删的不是"垃圾"，是用户的文件 —— 这个决定只能人做。

> 完整的判据与实现见 `docs/M7.1-文件仓库对账.md`。

## 5. 变更窗口（升级 / 回滚）

完整步骤见 `docs/M6.4-升级回滚.md`，这里只讲**窗口有多大**：

```
停服 → 备份（1 GB 现场约 9–10 s）→ 装新版 → 起服约 4 s
     → 客户端最坏 30 s 察觉断线 → 30 s 内全部回位
```

⇒ **屏幕上"按了没反应"大约 1–2 分钟**。**别在演出中升级。**

三条铁律：

1. **升级前必须备份，且备份要能恢复**（没恢复过的备份不算备份，见 §2.2）；
2. **回滚 = 卸新版 → 恢复升级前备份 → 装旧版**，三件事缺一不可。
   只把 exe 换回旧版是**半回滚**，旧版读新库的行为未定（本仓真发生过 `IsRevoked → IsBlocked` 的列重命名）；
3. **回滚会丢掉"升级之后、回滚之前"的所有数据**（设计如此）。升级后现场改过东西，
   回滚前先单独导一份配置。

## 6. 这份手册**不能**替你做的事

| # | 局限 | 后果 |
|---|---|---|
| 1 | `--health` 只看**磁盘上的文件 + 本机探活** | 服务"活着但业务是错的"它看不出来；那类问题看 `/healthz`、`/readyz` 与页面 |
| 2 | 容量数字来自**协议级压测**（100 台假 Agent），不是 100 台真机 | 不能承诺"100 台真机 + 4K 远控"；被控端的抓屏/硬编不在压测范围内 |
| 3 | 内存只证明 30 分钟不涨 | 8 h / 24 h 的缓慢泄漏未排除 |
| 4 | Linux 侧一贯未上真机 | `deploy/linux/*` 与 systemd 行为未验证 |
| 5 | `files/repo/` 里**有库记录**的文件永不自动删（只回收孤儿） | 这是刻意的 —— 删用户文件必须是人的决定。所以"仓库该不该瘦身"仍然是人工动作 |
| 6 | 服务以 LocalSystem 读写"ACL 收紧后"的目录**未实测** | 逻辑上必然可以（`SYSTEM:(OI)(CI)(F)` 在列），但没起过 SYSTEM 进程证明它 |

# M7.10 合并显示（全部屏幕）的全屏清晰度

> 现场反馈：**"全部显示屏幕状态下的全屏效果，未达到单屏幕状态下的全屏那样的效果。"**
>
> 结论：这不是显示器的问题，也不是前端放大的问题 —— 是**编码前就把画面压扁了**，
> 而且压的比例**随屏数变差**（单屏 1:1、双屏 1:2、三屏 1:3）。

---

## 1. 根因：降采样长边被钉死在一个与屏数无关的数上

`GdiJpegFrameEncoder.DefaultMaxLongEdge = 1920`，一直如此。它的注释写着
"1080p 级画面够用"—— 那句话对**单屏**成立，对**拼接**不成立：

| 场景 | 抓到的整幅 | 压到长边 1920 之后 | 每块屏实际像素 |
|---|---|---|---|
| 单屏 1080p | 1920×1080 | 1920×1080（不压） | 1920×1080 |
| 单屏 4K | 3840×2160 | 1920×1080 | 1920×1080（**1/2**） |
| 双屏 1080p 横排 | 3840×1080 | 1920×540 | **960×540**（1/2） |
| 三屏 1080p 横排 | 5760×2160 | 1920×720 | **640×720**（1/3） |

缩略图状态下（面板里那一小块）看不出来 —— 640 宽塞进 600 px 的框里正好。
一旦点 **全屏**，浏览器把 640 宽拉到 1920 宽，**每 1 个像素被摊成 3 个**，
满屏都是糊的。而同一台机器的单屏走硬编（H.264/HEVC，原生分辨率），
两相对比就是"合并显示的全屏没法看"。

⚠️ 这是 **M7.8 那个"画面只占左上 1/9"** 的同一个根，但**两件事**：
M7.8 修的是"画面画在哪个位置、占多大"，这里修的是"画面本身有多少像素"。
前者修完不再错位，后者不修就一直是糊的。

---

## 2. 为什么敢往上提：瓶颈不在输出尺寸

现场直觉是"提分辨率 = 更卡"。实测（5760×2160 源，合成界面图，q70，中位值）：

| 长边 | 目标尺寸 | 缩放 | JPEG | 合计 | 等效帧率 |
|---|---|---|---|---|---|
| 1920 | 1920×720 | 95.6 ms | 20.0 ms | **115.6 ms** | 8.7 fps |
| 2560 | 2560×960 | 126.3 ms | 39.2 ms | **165.4 ms** | 6.0 fps |
| 3840 | 3840×1440 | 121.5 ms | 60.2 ms | **181.7 ms** | 5.5 fps |
| 5760 | 5760×2160 | 33.9 ms | 127.6 ms | **161.5 ms** | 6.2 fps |

两张表里最反直觉的两行：

1. **缩放耗时几乎与目标尺寸无关**（95–135 ms 一档）。贵的是"把 12.4 MPix 的源
   读一遍再重采样"，不是"写多大"。
2. **不缩放反而更快**（33.9 ms）—— GDI+ 有 1:1 的快速路径。

⇒ 从 1920 提到 3840，每帧只多 **66 ms**（≈ 8.7 → 5.5 fps），
换来的是**每块屏 640 → 1280 宽，线性翻倍**。这笔账是划算的。

⚠️ 同一次实测里 `HighQualityBicubic` 是 **320–450 ms**（3–5 倍），
所以插值算法**没有**动 —— 清晰度靠像素，不靠重采样滤镜。

## 3. 改了什么

### 3.1 判据：`RemoteFrameExtent.ResolveMaxLongEdge(double)` → `int`

```csharp
public static int ResolveMaxLongEdge(int screenWidth, int screenHeight)
{
    if (screenWidth <= 0 || screenHeight <= 0) return MinMaxLongEdge;   // 部分已知 = 未知
    return Math.Clamp(Math.Max(screenWidth, screenHeight), 1920, 3840);
}
```

| 输入 | 结果 | 理由 |
|---|---|---|
| 1920×1080（单屏） | 1920 | 与历史一致，不降 |
| 3840×1080（双屏） | 3840 | 每块屏 **原生 1920**，不降采样 |
| 5760×2160（三屏） | 3840 | 每块屏 1280（旧值 640） |
| 3840×2160（单屏 4K） | 3840 | 顺带修好"单屏 4K 被压成 1/2" |
| 15360×4320（4×4K） | **3840（封顶）** | 再往上就该切单屏，不是继续加 MJPEG |
| 0 / 负值 | 1920 | 尺寸未知时退回历史默认 |

### 3.2 能力：`IScalableFrameEncoder`

编码器**必须在挑屏之前建好**（GPU 路径要求它自己持有抓屏器），
那一刻还不知道这一路要编多大 ⇒ 长边只能**建完再设**。

```csharp
public interface IScalableFrameEncoder
{
    int MaxLongEdge { get; set; }   // 0 = 不降采样
}
```

`GdiJpegFrameEncoder` 实现它，字段用 `Volatile` 读写成对
（写的是开流那条命令线程，读的是推流循环线程）。
`RemoteStreamHost.Start` 在 `Prepare` 成功之后、`Begin` 之前调
`ApplyScalableLongEdge(...)`，所以**第一帧就按新尺寸编**。

⚠️ 改它**不改变码流坐标系**：帧头里的"整幅"仍等于实际编出来的尺寸
（M7.8 那条纪律），否则画面又会缩回左上角。

### 3.3 🔴 预算必须跟着像素走，否则白改

`DefaultMaxFrameBytes = 380 KB` 是按 1080p 定的。提到 3840×1440（5.53 MPix，
是 1080p 的 2.67 倍）之后，同样画质的字节数也涨到 2.67 倍 ——
**预算不动的话，第一帧就被判"超限"，然后降质量重编到 q20**：

> 分辨率提上去了，画面反而更糊，而且这件事**不报错**。

所以 `ComputeFrameBudget(基准, 宽, 高)`：`基准 × max(1, 像素/1080p)`，封顶 4 MiB。

| 输出 | 倍数 | 实际预算 |
|---|---|---|
| 1920×1080 | 1.00 | 380 KB |
| 3840×1440 | 2.67 | 1013 KB |
| 3840×2160 | 4.00 | 1520 KB |
| 15360×4320 | — | 4 MiB（封顶） |

⚠️ `0` 仍然是"不限制"（历史约定），不是"预算为 0"。

### 3.4 日志

开流时多一行，让现场能直接对上算式：

```
[Stream] 编码长边=3840（画面 5760×2160，按它等比降采样）；
         这是**整幅**的长边 —— 拼接时每块屏只有它的 1/N，要看细节请切到单屏（硬编 + 原生分辨率）。
```

## 4. 现场会看到什么变化

| 项 | 改前 | 改后 |
|---|---|---|
| 三屏拼接编码尺寸 | 1920×720 | **3840×1440** |
| 每块屏的有效像素 | 640×720 | **1280×1440** |
| 帧率（参考） | 8.7 fps | **5.5 fps** |
| 单帧字节（界面类画面） | ~330 KB | ~600–1000 KB |
| 带宽（@5.5fps，含 base64） | ~19 Mbps | ~45–75 Mbps |

⚠️ **帧率会降**，这是换清晰度的代价，不是 bug。想看流畅就把画面切回缩略图状态
（那时其实也吃同样的编码开销 —— 长边是按"这一路"定的，不按窗口大小），
或者说：**合并显示这条路本来的定位就是"看全局"，看细节请切单屏**。

⚠️ **单屏（硬编）完全不受影响**：`IScalableFrameEncoder` 只有 MJPEG 实现，
硬编走 `ISurfaceFrameEncoder` 的 1:1 路径，尺寸从来没被降过。

---

## 5. 一条没做的事，说清楚

**没有"每屏至少 1920（也就是完全不降采样）"这个选项。**
三屏时那等于长边 5760（12.4 MPix），实测 JPEG 单帧 2.6 MB、@6 fps ≈ 125 Mbps
（还没算 base64 的 +33%）。局域网扛得住一时，但中心要转发三份，且被控机的
JPEG 编码从 60 ms 涨到 128 ms。**不如切单屏** —— 那条路是硬编 + 原生分辨率，
单帧只有几十 KB。

如果现场确实需要"合并且每屏原生"，正确的做法不是继续调这个数，
而是给拼接做 GPU 合成（多 output 各建一个 DDA、GPU 上拼、一次硬编）——
那是另一件事，没在本轮做。

## 6. 验证

| 项 | 结果 |
|---|---|
| 编译 | 0 警告 0 错误 |
| Agent 单测 | **374 / 374**（+8，`RemoteFrameExtentTests` 里新增长边判据 8 条） |
| 集成测试 | **620 / 620**（+7，新增 `ScalableEncoderTests`） |
| Core | 933 / 933（未触及） |
| 前端 | 未改（`describeEncodingScale` 会自动按新的编码尺寸算比例） |

`ScalableEncoderTests` 钉住的两条可证伪性质：

1. **构造后改 `MaxLongEdge`，下一帧就生效**（5760×2160 源：1920×720 → 3840×1440）；
2. **小帧不放大**（1280×720 在长边 3840 下仍是 1280×720）。

以及预算的四条：1080p 基准不放大、按像素放大、封顶 4 MiB、`0` 仍是"不限制"。

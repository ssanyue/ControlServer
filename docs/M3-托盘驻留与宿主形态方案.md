## 0. 结论先行（TL;DR）

1. 需求拆成三条（R1 托盘图标 / R2 关控制台不停服务 / R3 只能从托盘停），**R2 才是难点**。
2. **"关掉控制台不停服务"不是代码写没写对，是 Win32 子系统语义问题。** 当前 exe 是**控制台子系统**程序，
   进程**拥有**那个控制台；Windows 关闭控制台时发的是 `CTRL_CLOSE_EVENT`，**应用无法否决**（只能延迟约 5 秒）。
   ⇒ 必须改**子系统**（`WinExe`），而不是"在代码里拦住关闭"。
3. **托盘图标不等于服务能停。** Windows 服务跑在 **Session 0**（无交互桌面），通知区域不存在 ⇒
   **服务形态下托盘图标不可能出现**（与已知的 M5 远程桌面 Session 0 约束同源）。
   ⇒ 托盘是"绿色版 / 双击启动"的体验，**不是**服务形态的体验。
4. 推荐 **方案 A**：`OutputType=WinExe` + 在 `Platform.Windows`（**保持 `net8.0`**）里用
   **P/Invoke `Shell_NotifyIcon`** 自研托盘。
   （**方案 B 用 WinForms `NotifyIcon` 会直接违反铁律 #3**，见 §4。）
5. **你已拍板同时做方案 D**（服务形态也要托盘 ⇒ 额外一个托盘助手 exe）。设计见 **§11**，
   其中**两条关键结论**：① 控制通道推荐 **D1（SCM + 安装期 `sc sdset` 授权）——零 IPC、零凭据**；
   ② **绿色版仍是单文件**（托盘内建在 server 里），只有**服务版**多一个文件。
6. 有 **2 项子决策待你确认**（§11.6）+ **1 项阻塞**（`.ico` 需你提供）。
   另有 **1 处必须实测的风险**（§6.3 冒烟 stdout）。

## 3. 先回答三个"为什么"

### 3.1 为什么"关控制台"会停服务

控制台窗口的关闭**不是**给应用发 `WM_CLOSE`，而是 `GenerateConsoleCtrlEvent(CTRL_CLOSE_EVENT)`：

- 系统给该控制台的**每个持有者**约 **5 秒**处理时间；
- **没有"否决"通道** —— `SetConsoleCtrlHandler` 只能**延长**，不能取消；
- 超时后进程被强杀（`TerminateProcess`），`ApplicationStopping` / Serilog flush / `NIM_DELETE` 全部来不及跑。

⇒ **只要进程拥有控制台，就拦不住。** 这条不是"没实现好"，是 API 语义。

### 3.2 为什么不能"保留控制台但脱离所有权"

Windows 控制台是**进程组共享**对象：进程要么**拥有/共享**它（会被一起关），要么**没有**。
唯一的"两者兼得"是让子进程 `DETACHED_PROCESS` 启动 —— 那就是**没有控制台**。
⇒ 想让"关窗口不停服务"，本质上就是**不要那个窗口**。

### 3.3 为什么 Windows 服务形态**不可能**有托盘

托盘图标是往 `explorer.exe` 的通知区域发 `Shell_NotifyIcon`，那是**会话内**（per-session）对象。
服务运行在 **Session 0 / 服务窗口站**，那里**没有 explorer、没有通知区域** ⇒ 图标无处可去。

> 这与项目已知的 M5 约束同源：Windows 服务在 Session 0 无法捕获桌面，所以远程桌面必须
> "中心服务 + 用户会话内 Agent" 双层。

⇒ **托盘只能在"用户会话 + 交互式桌面"出现**。装成服务后要停服务，只能用 `services.msc` / `sc stop`
（或另做一个**独立的托盘助手 exe**，见 §4 方案 D）。

## 4. 方案对比

| # | 方案 | 保持 `net8.0`/可跨平台编译 | 关窗口不停服务 | 有托盘 | 服务形态也能托盘 | 第三方依赖 | 代码量 | 判定 |
|---|---|---|---|---|---|---|---|---|
| **A** | `WinExe` + **自研 P/Invoke `Shell_NotifyIcon`**（放 `Platform.Windows`） | ✅ | ✅ | ✅ | ❌ | 无 | 中（约 400–600 行） | **推荐** |
| **B** | `WinExe` + **WinForms `NotifyIcon`** | ❌ **违反铁律 #3** | ✅ | ✅ | ❌ | `UseWindowsForms` | 小（约 80 行） | **排除** |
| **C** | 保留控制台 + `ShowWindow(SW_HIDE)` 藏窗口 | ✅ | ❌ **不解决** | ✅ | ❌ | 无 | 很小 | **排除** |
| **D** | Windows 服务 + **独立托盘助手 exe** | ✅ | ✅ | ✅ | ✅ | 无 | 大 | 后续可选 |

### B 为什么排除（**关键**）

`System.Windows.Forms.NotifyIcon` 要求 `TargetFramework=net8.0-windows` + `<UseWindowsForms>true</UseWindowsForms>`。

但：

1. `Directory.Build.props` 把 TFM **统一**为 `net8.0`；
2. **铁律 #3**：`Platform.*` 必须是 `net8.0` —— `net8.0` 项目**无法引用** `net8.0-windows`（`NU1201`）；
3. 若把 `Platform.Windows` 改成 `net8.0-windows`，则引用它的 `Server` 也只能在 Windows 编译
   ⇒ **Linux 交付（M3 目标之一）当场失败**。

⇒ B 的"省事"（80 行 vs 500 行）换来的是**架构破口 + 跨平台交付失败**，不划算。

### C 为什么排除

`ShowWindow(GetConsoleWindow(), SW_HIDE)` 只是**藏**起窗口，**所有权还在**：

- `conhost.exe` 照旧被拉起、照旧占资源；"双击闪黑框"的观感问题依旧；
- 任何作用于该控制台的关闭（`taskkill` 控制台、`Ctrl+Break`）**照样杀进程**。

⇒ 解决的是"看不见"，不是"关不掉"。**排除。**

### D 的价值与代价

唯一能让**服务形态**也有托盘的方案（助手 exe 与主服务走本地 HTTP/IPC + 鉴权）。
代价：两个可执行文件、IPC 与鉴权、安装/卸载/升级都变复杂。
⇒ **列为后续可选，不在本轮。**

## 5. 推荐方案 A · 设计

### 5.1 输出子系统（`WinExe`）与开发期取舍

`ControlServer.Server.csproj` 加 `<OutputType>WinExe</OutputType>`。

副作用：`dotnet run` 将**没有任何控制台输出**（日志仍落 `logs/server-*.log`）。三种处理方式：

| 选项 | 行为 | 优点 | 缺点 |
|---|---|---|---|
| **A1** | 始终 `WinExe` + 启动时 `AttachConsole(ATTACH_PARENT_PROCESS)` | 终端启动→日志照常打到该终端；双击→无窗口 | **终端启动时关终端仍会杀进程**（附着进程同样收 `CTRL_CLOSE_EVENT`）⇒ R2 只在"双击"路径成立 |
| **A2** | 始终 `WinExe`，默认**不**附着，`--console` 显式开启 | **R2 全场景成立** | dev 必须记着加 `--console`，否则"什么都看不到" |
| **A3** | 仅**发布产物** `WinExe`（`-p:OutputType=WinExe` 或 Release 条件） | dev 零影响 | **R2 在 dev 构建上不成立**；"两种行为"靠构建配置区分，易误判 |

**已拍板选 A1**（见 §7）：交付形态（双击）天然满足 R2；开发/排障不受影响；
把"在终端里启动、又关掉终端会停"视为**开发/运维语义**（本来就坐在终端里，kill 的手段多的是）。

> ⚠️ A1 的实现细节：`AttachConsole(ATTACH_PARENT_PROCESS)` 成功后需**重定向**
> `Console.SetOut/SetError`（否则 .NET 已缓存过无效句柄）；附着失败**不报错**，静默继续（双击路径）。
> 另：附着后 `Console.IsOutputRedirected` 语义会变，`Program.cs:715` 那段设 `Console.Title` 的逻辑要相应调整。

### 5.2 托盘实现（`Platform.Windows`，**保持 `net8.0`**）

**抽象**（追加到 `Platform.Abstractions/HostIntegration.cs`，与既有 `IFirewallRuleManager` 并列）：

```csharp
/// 通知区域（托盘）图标。仅在"用户交互式会话"可用；
/// Windows 服务(Session 0)与 Linux 注册 Noop 实现（IsAvailable=false）。
public interface ITrayIconHost : IAsyncDisposable
{
    bool IsAvailable { get; }
    Task<bool> ShowAsync(TrayIconOptions options, CancellationToken ct = default);
    event Action<string>? CommandInvoked;   // 菜单项 id
}
```

**Windows 实现的 P/Invoke 清单与易错点**：

| API | 用途 | ⚠️ 易错点 |
|---|---|---|
| `RegisterClassExW` + `CreateWindowExW` | 建**隐藏**窗口接收托盘回调 | 用 `HWND_MESSAGE`（消息窗口）最省资源；类注册失败要报错而不是静默 |
| `Shell_NotifyIconW` `NIM_ADD/NIM_MODIFY/NIM_DELETE` | 增删改图标 | **退出时必须 `NIM_DELETE`**，否则图标残留在通知区域（鼠标划过才消失） |
| `NOTIFYICONDATAW` | 图标数据结构 | **`cbSize` 必须按当前结构版本设定**；x86/x64 大小不同，写死会**静默失败** ⇒ 需单测断言结构体大小 |
| `CreatePopupMenu`/`AppendMenuW`/`TrackPopupMenu` | 右键菜单 | **`TrackPopupMenu` 前必须 `SetForegroundWindow(hWnd)`，之后 `PostMessage(hWnd, WM_NULL, 0, 0)`** —— 否则菜单点了不消失（微软文档明写的经典坑） |
| `LoadImageW` / `CreateIconFromResourceEx` | 加载图标 | 仓库**无 `.ico`** ⇒ 需新增资源（拍板点 3） |
| `Shell_NotifyIconW` + `NIF_INFO` | 气泡提示 | 启动完成 / 端口冲突提示用 |
| 注册 `TaskbarCreated` 消息 | **explorer 重启后重新 `NIM_ADD`** | 不处理 ⇒ explorer 一崩，托盘图标**永久消失**，只能重启应用 |

**消息循环**：在**专用 STA 线程**跑 `GetMessageW`/`TranslateMessage`/`DispatchMessageW`；
退出时 `PostThreadMessage(WM_QUIT)` 收线程。
**绝不在 Kestrel 线程上跑消息循环**（会把请求处理堵死）。

### 5.3 托盘右键菜单（建议清单）

```
打开管理界面            ← 默认项（双击图标同效）
复制访问地址
──────────────
打开数据目录
打开日志目录
查看运行状态…            ← 小窗/气泡：监听地址、收发条数、数据目录
──────────────
退出服务                ← 优雅停机
```

**"退出服务"走 `IHostApplicationLifetime.StopApplication()`（不是 `Environment.Exit`）**，
让 Serilog flush、SQLite 收摊、`NIM_DELETE` 都走完。

> 日志并没有因此难找：Web 界面本来就有「系统日志」tab，文件在 `<数据目录>/logs/`。

### 5.4 生命周期接线（`Program.cs`）

```
ApplicationStarted:
    if (OperatingSystem.IsWindows() && Environment.UserInteractive && !isServiceHost)
        await tray.ShowAsync(...)          // 仅用户会话
ApplicationStopping:
    await tray.DisposeAsync()              // NIM_DELETE + WM_QUIT
```

- `Environment.UserInteractive` 在服务下为 **false** ⇒ 天然守卫。
  但**仍要**显式判 `isServiceHost`（"以服务身份但挂调试器启动"时它可能为 true）。
- Linux 注册 `NoopTrayIconHost`（`IsAvailable=false`）⇒ 调用处**不需要**任何 `if (Linux)` 分支。

### 5.5 ⚠️ 启动失败必须可见（`WinExe` 的直接副作用）

改成 `WinExe` 后，`Program.cs:759` 那段"端口被占用"的 `Console.Error` **没人看得见** ——
用户双击第二个实例会"闪一下、什么都没发生"。必须补：

- 端口占用 → `MessageBoxW`（`MB_ICONERROR`）弹出可读说明 + 提示"可能已有一个中控服务在运行"；
- 其它致命异常 → 同样兜底 `MessageBoxW`（**仅限 `Environment.UserInteractive` 为真时**）；
- 可选：`CreateMutexW` **单实例互斥** → 第二个实例**直接打开浏览器**并退出（见拍板点 4）。

### 6.3 ⚠️ 必须**实测**的一处风险

`OutputType=WinExe` 后，`deploy/smoke/run-all.py` 的 `Popen(argv, stdout=log, stderr=STDOUT)`
还能不能把 Serilog 的**控制台 sink**写进那个日志文件？

- **好消息**：就绪判定是**轮询 HTTP**（`run-all.py:64`），不依赖 stdout
  ⇒ **不会**因此把"服务已就绪"误判成"没起来"。
- **但**"失败时把启动日志打出来"这个**诊断能力**依赖它。GUI 子系统进程预期仍能拿到父进程给的
  `STARTF_USESTDHANDLES` 句柄并写入 —— **但这是预期，不是结论。**
- ⇒ 落地时**先做一次实测**（起打包 exe，看 log 文件是否有内容）；若拿不到，退路是
  冒烟只依赖 `<数据目录>/logs/server-*.log` 文件日志。

### 6.4 其它风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **explorer 重启后托盘丢失** | 通知区域重建，旧图标句柄失效 | 处理 `TaskbarCreated` 消息重新 `NIM_ADD`（§5.2 已列） |
| **`NOTIFYICONDATA` 结构体大小随位数变化** | 写死 `cbSize` 会静默失败 | 单测断言结构体大小；本轮只交付 `win-x64` |
| **进程被强杀（任务管理器）后图标残留** | 鼠标划过才消失 | 无法根治；`NIM_DELETE` 只覆盖正常退出 |
| **高 DPI 下图标模糊** | 需多尺寸 `.ico` | 提供 16/20/24/32/48/256 |
| **首次双击 3–8 秒无反馈**（单文件解压） | 用户可能重复双击 → 第二个实例端口冲突 | 与单实例逻辑（拍板点 4）联动；可加"启动中"气泡 |
| **杀软/EDR 敏感** | "无窗口 + 监听端口 + 自启动"特征 | 交付说明里写清楚；不申请开机自启（除非拍板要） |

## 11. 方案 D 详细设计（服务形态 + 独立托盘助手）

### 11.1 两个进程、两个会话

| | `ControlServer.Server.exe` | `ControlServer.TrayAgent.exe`（新） |
|---|---|---|
| 运行会话 | **Session 0**（服务窗口站） | **登录用户的交互会话** |
| 谁启动 | SCM（`sc create` 装的服务） | 用户登录时（见 §11.4） |
| 有无桌面 | **无** ⇒ 托盘代码**必须完全不启动** | 有 ⇒ 托盘在这里 |
| 需要管理员 | 服务本身需要（安装时） | **不需要**（见 §11.3 的授权设计） |

> ⚠️ **服务进程里的托盘代码必须被彻底禁用**（`Environment.UserInteractive == false` 守卫，
> 且**再显式判一次** `isServiceHost`）—— 在 Session 0 建窗口/加托盘是"无声失败"，
> 排障时极难定位。

### 11.2 职责边界（刻意做小，换取长期兼容）

托盘助手**只做 4 件事**，不做任何深度耦合：

1. 显示图标（含"服务未运行"的灰态）
2. 打开管理界面 —— 打开 `http://localhost:<port>`（**零权限、零凭据**）
3. **启动 / 停止服务** —— 走 SCM（§11.3）
4. 探活 —— `GET /healthz`（**匿名端点，已有**）

**刻意不做**：不读配置、不读日志内容、不调管理 API、不传凭据。
这样 **agent 与 server 版本不一致也不会坏**（协议面只有一个 `/healthz`），
避免每次 server 升级都要同步升级托盘助手。

### 11.3 控制通道：三条路对比（**这是 D 的核心决策**）

| # | 通道 | 机制 | 普通用户能否停服务 | 安装期改动 | 安全面 |
|---|---|---|---|---|---|
| **D1** | **SCM + 服务 ACL**（推荐） | agent 用 `OpenSCManager`/`OpenService` + `ControlService(SERVICE_CONTROL_STOP\|START)` | **能** —— 安装时 `sc.exe sdset` 给 `SERVICE_STOP`+`SERVICE_START`+`SERVICE_QUERY_STATUS` 授给指定组（如 `IU` 交互用户） | **仅一条 `sc sdset`** | 本机交互用户可停/启服务。对受控局域网中控设备可接受；可收窄到指定组 |
| **D2** | 命名管道 + 安装期令牌 | 服务开 `NamedPipeServerStream`（ACL 限本机）；agent 持安装期生成的随机令牌 | 能 | 生成并保护令牌文件（DPAPI / ACL） | 中等：需自研 IPC 协议、超时、并发；令牌是新增泄露面 |
| **D3** | 复用 HTTP API（新增 `POST /api/system/shutdown`，AdminOnly） | agent 先登录拿 Cookie 再调 | 需要管理员口令 | 需要凭据托管 | **最差** —— 等于把管理员口令放进托盘进程 |

**推荐 D1**：**零 IPC、零凭据、零自研协议**，复用 Windows 自带 SCM，安装期一条 `sc sdset` 搞定。
它同时天然解决了"启动服务"（`SERVICE_START`），而 D2 还要额外设计启动路径。

> ⚠️ D1 的失败模式要处理：用户**没装服务**时 `OpenService` 返回
> `ERROR_SERVICE_DOES_NOT_EXIST` ⇒ 托盘显示灰态 + 菜单只留"打开管理界面 / 如何安装服务"。

### 11.4 托盘助手怎么启动（**已拍板 D-a**）

| # | 方式 | 说明 | 评价 |
|---|---|---|---|
| **D-a** | **安装时为"当前登录用户"注册启动项**（`HKCU\…\Run` 或 `shell:startup` 快捷方式） | 用户登录即起，无需提权、无需会话枚举 | **推荐**：简单可预期。代价：要用托盘的**每个账号**都得装一次（多用户机器上是"每人一次"） |
| **D-b** | 服务用 `CreateProcessAsUser` 拉起到交互会话 | 需 `WTSQueryUserToken` + `DuplicateTokenEx` + `CreateProcessAsUser` + 监听登录/注销事件 + 崩溃重启 | 与 **M5"用户会话内 Agent"同源**，将来 M5 直接复用这套能力；但**本轮复杂度大**（会话枚举、多用户、会话切换） |
| **D-c** | 手动双击 | 最简单 | **不满足 R1**（"运行服务时就该有图标"） |

**推荐 D-a**；D-b 建议**推迟到 M5**，届时把它做成 `Platform.Windows` 的
`IUserSessionLauncher`，M5 的远程桌面 Agent 直接复用，一笔投入两处收益。

### 11.5 ⚠️ 对"单文件"承诺的影响（**必须知情**）

| 形态 | 之前 | 之后 |
|---|---|---|
| **绿色版**（双击） | 1 个文件 | **仍是 1 个文件** ✅（托盘内建在 server 里） |
| **服务版**（`sc` 安装） | 1 个文件 | **2 个文件**：`ControlServer.Server.exe` + `ControlServer.TrayAgent.exe` |

⇒ `build-portable-exe.ps1` 的"发布目录必须只有 1 个文件"校验**逻辑要区分两种产物**，
`REF-M2-模块细节.md` §10 里"单文件模式正常"的判据也要相应补一句。
**绿色版用户的体验完全不变**（这很重要：绿色版是本项目的主交付形态）。

### 11.6 2 项子决策（**已拍板，2026-10-08**）

| # | 问题 | 决定 |
|---|---|---|
| **D-1** | **控制通道** | **D1（SCM + `sc sdset`）** —— 零 IPC、零凭据；代价是"本机交互用户可停/启服务" |
| **D-2** | **托盘助手启动方式** | **D-a（安装时注册当前用户启动项）**；`CreateProcessAsUser` 推迟到 M5 一起做 |

### 11.7 服务形态下的连带收益

现在服务形态（Session 0）**没有浏览器、也没有桌面** ⇒ `Startup:AutoOpenBrowser` 无效
（`BrowserLauncher` 已按 `isServiceHost` 跳过）。
托盘助手正好补上这个缺口：**"打开管理界面"由它承担** —— 服务形态的用户第一次也有了"点一下就能进界面"的入口。

## 12. 实施回填（2026-10-08，**已完成**）

> 本节记录"实际做成了什么"，与上面的设计对照。**与设计有出入的地方都在这里说明原因**。

### 12.1 验收标准逐条核对

| # | 需求 | 结果 | 证据 |
|---|---|---|---|
| R1 | 运行时在右下角通知区域显示服务图标 | ✅ | 绿色版由 Server 自持；服务版由 TrayAgent。日志 `托盘图标：已显示（右键可退出服务）` |
| R2 | 关闭控制台**不能**停止服务 | ✅ | `OutputType=WinExe`；窗口枚举确认新实例**只有隐藏窗口，无 `ConsoleWindowClass`**，PE `Subsystem=2 (WINDOWS_GUI)` |
| R3 | 停服务必须在托盘图标右键菜单里操作 | ✅ | 绿色版菜单「退出服务」；服务版菜单「停止服务」（走 SCM） |

### 12.2 与设计的差异（3 处）

1. **`ITrayIconHost` 的 `CommandInvoked` 在 Linux Noop 上用 `add{} remove{}` 空访问器**，
   而不是"注册了但永不触发" —— 让"永远不会发生"在**类型层面**就写清楚，上层代码无需任何 `if (Linux)` 分支。
2. **`WindowsServiceController` 刻意不抽 `IServiceController` 接口**：它唯一的消费者
   `ControlServer.TrayAgent` 本身就是 Windows 专属程序，抽接口只会增加一层无收益的间接。
3. **`build-portable-exe.ps1` 的两种产物放在两个目录**（`dist\win-x64` / `dist\win-x64-service`），
   而不是在同一目录里区分 —— 因为"绿色版目录必须恰好 1 个文件"这个校验是**资产**（它守住了单文件承诺），
   混在一起就没法自动校验了。

### 12.3 实现中发现的**设计缺陷**（已修，值得记住）

- **托盘隐藏窗口被外部 `WM_CLOSE` 时不能交给 `DefWindowProc`**：
  WinExe 没有控制台、托盘图标又被销毁 ⇒ 进程变成**"没有任何控制面的孤儿"**，只能去任务管理器杀。
  改成把 `WM_CLOSE` 翻译成 `TrayCommands.Exit` 走优雅停机 —— 顺带让 `taskkill`（不带 `/F`）
  与托盘「退出服务」**走同一条路径**，实测日志一致：`收到「退出服务」请求（托盘菜单或外部关闭信号）`。
- **`Shell_NotifyIconW` 的 DLL 写错**（`user32.dll` → 应为 `shell32.dll`）：
  编译期**完全正常**，只在真跑时抛 `EntryPointNotFoundException`。这正是本方案坚持写
  "真建图标再优雅摘掉"那条集成用例的理由（`TrayIconTests` 第 8 条，**别删**）。
- **单实例互斥体与集成测试冲突**：互斥体是**进程级**资源，而 `Config_survives_host_restart`
  等用例在**同一进程内**新建第二个宿主 ⇒ 被误判为"已有实例"⇒ `Program` 提前 return ⇒
  报 `The entry point exited without ever building an IHost`。
  加 `Server:Startup:SingleInstance` 开关，测试宿主设 `false`。

### 12.4 安装脚本的取舍（3 处必须知情）

1. **`sc sdset` 是"补权"而不是"重设"**：读现有 SDDL → 只给 IU 的 ACE 追加 `RP`+`WP` → 按规范顺序
   重建权限串 → 写回。**不动** SY/BA/SU 的 ACE，也不扩大 IU 的其它权限。
   带 `S:(SACL)` 段时若因缺乏 `SeSecurityPrivilege` 失败，**自动退化为只设 DACL 重试**。
2. **托盘助手是"每用户"部署**（HKCU 启动项），不是"每机器"。装了服务之后，
   **每个想看到托盘的账号都要装一次**。脚本会检测"当前身份 ≠ 控制台登录用户"并给出警告。
3. **安装时立即拉起托盘助手用的是 `Start-Process`（= 管理员身份）**，图标照样出现；
   下次登录时 HKCU 启动项以**普通权限**再启一个，靠"每会话单实例互斥"自动去重。
   想要纯普通权限的图标，注销/重登即可。

### 12.5 顺带修掉的两个既有坑（与需求无关但同一批文件）

- **`✓`/`✗`/`⚠` 不在 GBK 里**：真实控制台显示成 `?`；Python 脚本里 `print()` 带这些字符时，
  一旦输出被重定向/管道就退化成 cp936 ⇒ **`UnicodeEncodeError` 崩在"报错"那一步**。
  已把用户可见输出统一换成 ASCII 标记（`[OK]` / `[!!]` / `[X]` / `[!]`）。
- **`run-all.py` 必须关掉托盘与单实例**（理由见 §12.3 与 REF §25.7），否则冒烟会出现
  "桌面闪图标" 与 "未能在超时内就绪"这种假故障。

### 12.6 ⚠️ 后续修正：A1 的"已知代价"被第二轮需求推翻（同日）

**用户在验收后又报了一条**：「关闭CMD窗口不能直接关闭服务，这个功能未实现」。

**现象属实**：§7 拍板 A1 时记的代价是"终端启动时关终端仍会杀进程"，当时判定为"运维语义，可接受"。
但用户实际就是走 `run.cmd`（从 CMD 启动）这条路 —— 于是"关掉那个 CMD 窗口 = 服务没了"，
**直接违背 R2**。而 `run.cmd` 自己第 8 行还写着「关闭窗口 = 停止服务」，等于把缺陷写在了脸上。

**真机复现**（起 cmd 跑服务 → `AttachConsole(cmd_pid)` 拿到那扇窗 → `WM_CLOSE`）：

| | 服务进程挂在控制台上 | 关窗后 |
|---|---|---|
| 修复前 | **True** | **1 秒内消失** |
| 修复后 | **False** | 12 秒仍存活 |

**结论：R2 不能只在"双击"路径成立 —— 那不算实现。**
`WinExe` 只保证"双击时没有控制台"；"从 cmd 启动时**继承**控制台"是另一件事，
而后者才是用户实际的用法。§3.2「不能保留控制台但脱离所有权」那段分析本身是对的，
A1 却偏偏选了"保留控制台"这条路。

**最终选型 = A1 与 A2 的合体**（覆盖 §7 表格第 1 项）：

| | 原 A1（§11.3） | 现方案 |
|---|---|---|
| 默认 | 附着父控制台 | **`FreeConsole()` 主动脱离** —— 关窗不停服务，R2 在**所有**启动路径上成立 |
| 开发期日志 | 自动可见 | `--Server:Startup:AttachConsole=true` 显式开口（代价：关终端会停服务） |
| 输出被重定向 | 不附着 | **什么都不做**（`FreeConsole` 不碰文件/管道句柄 ⇒ 日志与测试都不受影响） |

即：**默认站 A2（安全），A1 降级为显式开关**。§11.3 里"附着进程同样收 `CTRL_CLOSE_EVENT`"
这句判断没错，只是当时把它当成"可接受的代价"，现在改成"必须消除"。

细则与踩坑：`REF-M2-模块细节.md` §25.8 / §25.9。

# M7.3 · Linux 音量：会话侧执行（**已实施**）

> **状态**：路线 A 已落地（2026-10-18）。Windows 侧一行未改；Linux 侧新增会话定位与降权执行。
> **上游**：`docs/M7-真机验证清单.md` §5.1（那里记的是"为什么以前没通"），本文记"怎么通的"。
> **约束**：Windows 侧一行不动；不给 Linux 加托盘；不为一个能力造一个常驻进程（除非另有理由）。

---

## 0. 一句话结论

Linux 音量以前缺的不是"接线"，是**执行身份**：`wpctl` / `pactl` / `amixer` 都必须以**登录用户**
的身份、在**那个用户的 `XDG_RUNTIME_DIR`** 下跑。服务是 root、跑在系统会话里，直接调必然
"返回成功、桌面没动静"。

现在的实现：**服务侧解析活动图形会话 → `runuser` / `sudo -n` 降权执行 → 探测延迟到首次使用**。
不加常驻进程、不动 Windows，约 300 行 ＋ 18 条单测。

**而且它比原计划多走了一步**：`AgentCommandExecutor` 在"会话侧通道结构上不可用"时回落到本机
`IAudioController`，所以**中心的音量按钮在 Linux 上真的能生效**（原方案 §3.3 曾把这条划在范围外，
实施时发现回落只需 20 行，不做反而是留一个假的缺口）。

## 2. 三条路线

| | A. 服务侧降权执行（**推荐**） | B. 造 Linux 会话伴侣 | C. 明确不做 |
|---|---|---|---|
| **做法** | 服务解析活动图形会话 → `runuser -u <user> -- env XDG_RUNTIME_DIR=... <cmd>`；探测延迟到首次使用 | 新增 `ControlServer.Agent.Session` 常驻进程（用户登录后启动），复刻命名管道协议到 Unix domain socket | 页面/文档写明"Linux 不支持音量"，`M7` 清单改成设计结论 |
| **代码量** | ~300 行 ＋ 单测 | ~1200 行 ＋ 新部署物 ＋ 协议分叉 | 0 |
| **新增进程** | 无 | 有（还要 systemd --user 单元 / autostart） | 无 |
| **以后要加"启动程序"** | 同一条路复用（解析器已就位） | 直接可用 | 仍不可用 |
| **以后要加 Linux 远控** | 仍不可用（抓屏得另做） | 有宿主可用 | 仍不可用 |
| **风险** | root 降权执行外部命令（敏感面）；SELinux/AppArmor 可能拦 `/run/user/<uid>` | 多一个要维护的部署物；协议分叉（命名管道 vs Unix socket） | 与"把所有挂账都解决"的历史指令相冲 |
| **本机可验** | 解析/前缀/缓存/文案（纯函数）；**真机连通性不可验** | 同样只有逻辑可验 | 无需验 |

**为什么不选 B**：它要解决的问题（会话内执行）在 Windows 上由托盘承担，而 Linux 上
"托盘"根本不存在 —— 造出来的进程只为一个音量动作存在，却要背上安装、自启、退出、
权限、崩溃重启五件事。**等 Linux 真的要做远控时再造，那时它有第二个消费者。**

**为什么不选 C**：Linux 侧已经写好了三个后端探测与解析（38 条单测），
差的是执行身份这一层。C 等于把已经付出的成本扔掉，而且"Linux 能管电源但不能调音量"
在现场是个说不圆的缺口。

## 3. 路线 A 的设计

### 3.1 新增：会话定位器

```csharp
// src/ControlServer.Platform.Linux/LinuxLoginSession.cs
public sealed record LinuxLoginSession(
    string UserName, int Uid, string SessionId, string Type, string RuntimeDir);

// src/ControlServer.Platform.Linux/LinuxSessionLocator.cs
public static class LinuxSessionLocator
{
    // 纯函数：解析 loginctl 的两段输出，单测直接喂文本
    internal static LinuxLoginSession? PickActiveGraphical(string listOutput, Func<string, string> showSession);

    // 真实探测：loginctl list-sessions --no-legend → 逐个 show-session -p Active -p Type -p Remote
    public static (LinuxLoginSession? Session, string Note) Locate();
}
```

**选取规则**（按优先级，全部写进日志）：

1. `Active=yes` 且 `Type ∈ {x11, wayland}` 且 `Remote=no` ⇒ 图形会话；
2. 多个命中 ⇒ 取 **SessionId 最大**（`loginctl` 的会话号单调递增 ⇒ 最新登录的那个）；
3. 一个都没有 ⇒ `(null, "这台机器当前没有图形会话登录……音量无处可调。")`。

🔴 **实施时砍掉了原方案的"扫 `/run/user` 兜底"**：无人登录时就算某个 uid 下还留着
`pipewire-0`（用户级服务的 linger），那台机器上也**没有人能听见任何声音**。
挑一个 uid 去调音量是"猜"，而猜错的表现是一次成功且毫无意义的操作 ——
本仓的纪律是"未知一律 null"，不是"尽量给个值"。

### 3.2 改造：`LinuxAudioController`

| 改动 | 为什么 |
|---|---|
| 构造函数**不再探测**，改成 `EnsureBackend()` 懒探测 | 服务启动那一刻还没有图形会话（开机自启早于登录），构造时探测会把"暂时没有"固化成"永远没有" |
| 探测失败**缓存 5 秒** | 用户连续点音量不该每次都跑三条命令；5 秒足以吸收连点，又不会让"刚登录"等太久 |
| `Run()` 拆成 `BuildInvocation(exe, args, session)` ＋ `Run(prefix, exe, args)` | 前缀构造是纯函数 ⇒ 单测钉住三种形态 |
| `AvailabilityNote` 分三态 | ①没有图形会话 ②有会话但三个后端都探不到 ③选中某后端（带用户名）。**现场排障全靠这一行** |

前缀构造（纯函数，单测直接断言字符串）：

```
当前进程 uid == 会话 uid        → 不加前缀（Agent 以用户身份跑的部署）
否则 runuser 存在               → runuser -u <user> -- env XDG_RUNTIME_DIR=<dir> <exe> <args>
否则 sudo -n -u <user> 存在     → sudo -n -u <user> -- env XDG_RUNTIME_DIR=<dir> <exe> <args>
都没有                          → 失败 + "找不到 runuser / sudo，无法以 <user> 身份执行"
```

⚠️ **三个不能省的细节**：

1. `XDG_RUNTIME_DIR` **必须显式设**。`runuser` 不会替你带上用户的环境（它继承的是 root 的），
   而 `wpctl` / `pactl` 就是靠这个变量找 socket。
2. `pactl` 还需要 `PULSE_SERVER` 或 `DBUS_SESSION_BUS_ADDRESS` 时的回退：先只设
   `XDG_RUNTIME_DIR`（PipeWire 与默认 pactl 都够），失败时把 stderr 原文带回去 ——
   **不猜**（铁律：未知一律 null / 不编原因）。
3. **`sudo -n`** 的 `-n` 不能省：没有它，`sudo` 会在无人值守的服务进程里等密码，
   表现是"点一下音量卡 3 秒然后超时"。

### 3.3 接线：`Agent.Service` ＋ `AgentCommandExecutor`

**第一处：注册端口**（`agents/ControlServer.Agent.Service/Program.cs`）

```csharp
builder.Services.AddSingleton<IAudioController>(sp => OperatingSystem.IsWindows()
    ? new UnsupportedAudioController(
        "Windows 上音量由托盘进程持有（服务在 Session 0 里没有音频端点），服务侧不直接控制。")
    : new LinuxAudioController(message => sp.GetRequiredService<LogService>().Info("Agent", message)));
```

**第二处：让它真的被消费**（`agents/ControlServer.Agent/Tasks/AgentCommandExecutor.cs`）

原来的音量分支只走 `_session.SendAsync(...)`。非 Windows 上那是
`UnavailableSessionCommandChannel`（`IsSupported` 恒 false），于是中心的音量按钮
在 Linux 上永远只回一句"尚未提供会话内的托盘伴侣"。现在加一层回落：

```csharp
// 判据是 IsSupported（这平台上有没有这条通道），不是"这一次发送失败了"。
if (!_session.IsSupported && _audio is not null)
{
    return ExecuteVolumeLocally(action!, logCategory);
}
```

🔴 **判据必须是 `IsSupported` 而不是"发送失败"**：用后者的话，Windows 上"托盘没起"会被误报成
"本平台不支持音量"，现场会去查一个根本不存在的能力缺失 —— 而真正该做的只是把托盘拉起来。

⇒ 于是中心（SignalR）与 UDP 两条通道的音量指令，在 Linux 上都落到
`LinuxAudioController.Apply()`，由它降权执行。**Windows 上 `IsSupported` 恒 true，一个字节的行为都没变。**

## 6. 明确不做（本文范围外）

- ❌ Linux 会话伴侣进程（路线 B）—— 等有第二个消费者（远控 / 启动程序）再开；
- ❌ Linux 抓屏 / 输入注入 / 剪贴板 —— 平台层整块没有，属另一个里程碑；
- ❌ Linux Agent 的部署物（systemd 单元 ＋ install.sh）—— **这是另一个独立缺口**
  （`deploy/linux/` 只有中心 Server 的），建议单独排一轮。

## 7. 拍板记录与一处边界修正

**用户拍板走 A**（而不是 B 造常驻进程 / C 明确不做）。

**修正了什么**：拍板时我给 A 划的边界是「服务进程内可用 ＋ 可诊断，但中心按钮仍不生效」。
实施到接线那一步发现这个边界**没有必要** —— `AgentCommandExecutor` 里加一层
"`!IsSupported` 时回落本机实现"只要 20 行，而它让中心与 UDP 两条通道的音量指令
在 Linux 上真的生效。留着那一层不写，等于人为制造一个假的缺口。

⇒ 所以现在的实际能力**大于**拍板时描述的范围：**中心音量按钮在 Linux 上可用**。
代价是 `AgentCommandExecutor` 多了一个可选构造参数（Windows 上传的是
`UnsupportedAudioController`，`IsSupported` 恒 true ⇒ 行为零变化）。

# M8.1 · 远控悬浮面板中的文件传输（可行性 + 方案）

> 状态：**方案，未改任何代码**（本轮只做分析）。
> 目标问题：在远控窗口的悬浮面板里加"文件传输"，并回答一个具体场景 ——
> **一台既没装服务端、也没装客户端的电脑，能不能与一台装了客户端的电脑双向传文件？**

---

## 1. 结论

**能，但它不是"两台电脑直传"，而是"两台电脑各连中心的一侧"。**

一句话判据：

> 只要那台"裸机"能用浏览器打开中心服务端（默认 `8899`）并以**管理员**登录，
> 就能与任意一台装客户端（Agent）的机器双向传文件 —— **裸机上什么都不用装**。
> 反过来，**整个场景里没有中心服务端，就一定不行**，装不装客户端都不行。

| 现场形态 | 双向传输 | 说明 |
|---|---|---|
| 裸机浏览器 ↔ **同一台机器**（既跑 Server 又跑 Agent） | ✅ 可行 | 单机部署形态，裸机连它的 8899 |
| 裸机浏览器 ↔ Agent 机，**中心在第三台** | ✅ 可行 | 裸机必须能路由到中心；Agent 只需能出站到中心 |
| 裸机 ↔ Agent 机，**只有这两台、没有中心** | ❌ 不可行 | Agent 不提供入站 HTTP，也没有横向通道；见 §3.3 |
| 两台都装 Agent、仍无中心 | ❌ 仍不可行 | Agent 之间没有互相寻址的路径，装客户端解决不了"没有中心" |
| 裸机想**被自动推送**到指定目录（无人值守） | ❌ 不行 | 浏览器只能"手动下载"；要自动接收必须在那台机器装 Agent |

---

## 2. 先澄清一件事：这是三端，不是两端

项目里"一台电脑上的程序"其实是两个独立角色（`docs/M5-局域网远程桌面实时方案.md`、`RemoteHub` 类注释）：

| 角色 | 程序 | 谁连谁 | 身份 |
|---|---|---|---|
| **中心** | `ControlServer.Server`（Kestrel `0.0.0.0:8899`） | 等两边连进来 | —— |
| **被控端** | `ControlServer.Agent`（含托盘） | **主动出站**连中心 `/hubs/agent`，并用 HTTP 拉/推字节 | `AgentKey`（认机器） |
| **观看/操作端** | 浏览器 | 连中心 `/hubs/remote` 与 `/api/*` | Cookie（认人、认角色） |

所以"裸机"在这个系统里的唯一合法身份就是**第三端（浏览器）**。
它一旦是浏览器，文件传输就退化成一件很平常的事：

```
裸机浏览器 ──HTTP(上传/下载)──> 中心 ──SignalR 信令 + HTTP(Range/分块)──> Agent
```

**裸机与 Agent 之间不需要任何直连** —— 这正是"裸机什么都不装也能传"的原因。
`FileTransferClient` 里客户机全程**主动出站**（下载用 `Range`、上传用分块 `PUT`），
所以 `M4.1` "客户端不开入站端口"的承诺在这里没有被破坏。

## 3. 可行性判据（五道门槛，缺一即不可行）

### 3.1 网络可达

裸机的浏览器必须能访问中心的 `8899`（HTTP）。这一条最容易被忽略：

- 中心在另一个网段 / 只监听内网 / 防火墙只放行了几台机器 ⇒ 裸机连页面都打不开，后面全免谈。
- 现场已经踩过同类的坑：`M7.12` 把默认端口从 8080 改成 8899 之后，**防火墙规则还放着 8080**。

### 3.2 账号与角色

文件传输用的是远控页同一套身份，**而远控页本身是 `AdminOnly`**：

- `RemoteHub` 整个 Hub 要求 `Policies.AdminOnly`（连"只读观看"都不放宽）；
- 建单要管理员：`POST api/distributions` 与 `POST api/distributions/collect` 都是 `[Authorize(Policy = Policies.AdminOnly)]`。

⇒ 结论：**能打开远控页的人，天然就有传文件的权限；普通角色（`CanOperate`）连面板都进不去。**
这条不是新增的权限面，所以不需要为文件传输另做一套授权。

### 3.3 反例：没有中心就一定不行（这条要写进现场话术）

- Agent **没有** HTTP 服务。它唯一开着的入站口是 `UdpCommandListener` 的 **UDP 8090**，
  而那条通道是**纯明文、无验签、无重放防护**的（2026-10-13 起有意如此），
  只用来说四个词：`DOWN` / `RESTART` / `+/-` / `0/1`。
  **绝不能把它扩成文件通道** —— 那等于"同网段任意主机都能往这台机器里塞任意字节"，
  而它现在的安全边界已经只剩"网络可达性"了。
- 别指望"两台都装 Agent 就能互传"：Agent 只会往中心连，没有 Agent↔Agent 的寻址与鉴权模型。

### 3.4 客户机的开关

- `Agent:Transfer:Enabled = false` ⇒ 浏览直接回 `disabled`，下发也会被拒。
- 下发落地有**可写白名单**（默认 `{状态目录}\inbox`），越界由客户机拒绝**这一台**，
  服务端无权也无从代它校验（它不知道对方磁盘长什么样）。

### 3.5 授权闸门（授权过期时的真实行为，和直觉不一样）

按 `LicenseGate.cs` 现有分类：

| 动作 | 归类 | 授权过期时 |
|---|---|---|
| `POST api/distributions`（下发建单） | **Gated** | 被拒 |
| `POST api/distributions/collect`（回传建单） | **Gated** | 被拒 |
| `POST/PUT api/files/uploads/*`（上传字节） | Allowed | **仍然可用** |
| `GET api/files/{id}/download`（下载） | Allowed | **仍然可用** |
| `GET api/agents/{id}/browse`（浏览目录） | Allowed | **仍然可用** |

⇒ 现场表现是"文件明明传上去了/看得见文件列表，却发不出去"。
**面板必须把"是哪一步被拒"说出来**，否则运维只会看到一句"失败了"。
（这条与 `M6.2` 审计里"未授权时看得见、但取不回来"的取舍一致，不是 bug。）

## 4. 现有能力盘点：双向其实已经通了

文件传输**不需要新协议**。中心侧已经有一套完整的"仓库 + 分发"底座（M4.4）：

| 能力 | 端点 / 组件 | 谁在用 |
|---|---|---|
| 分块上传（断点续传） | `POST api/files/uploads` → `PUT ?offset` → `POST complete` | 网页（Cookie）/ 客户机（AgentKey） |
| 下载（`Range`） | `GET api/files/{id}/download`（`enableRangeProcessing`） | 网页 / 客户机拉取 |
| 下发 | `POST api/distributions`（`direction=push`） | 管理员 |
| 回传 | `POST api/distributions/collect`（`direction=collect`） | 管理员 |
| 目录浏览 | `GET api/agents/{id}/browse`（中心经 SignalR `InvokeAsync` 问 Agent） | `CanOperate` |
| 进度推送 | `/hubs/events` 的 `TransferProgress` | 网页 |
| 客户机落地 | `FileTransferClient.DownloadAsync`：自算 SHA256 → `.cs-part` → 原子 `Move` | Agent |
| 客户机上传 | `FileTransferClient.UploadAsync`：先建会话，`409` 纠正偏移后续传 | Agent |
| 前端分块上传 | `api.ts` 的 `uploadFileChunked`（`File.slice`，不占内存） | 网页 |
| 速率估算 | `web/src/transferRate.ts`（`RateTracker`，20 s 滑窗） | 网页 |
| 目录选择器 | `AgentPathPicker.vue` | 网页 |
| 任务/进度 UI | `DistributionPanel.vue`（1492 行，页面级） | 网页 |

**所以这个需求的真实性质是"把已有能力接进远控窗口"，不是"新建一条传输链路"。**
这一点决定了工作量与风险量级（见 §9）。

## 5. 双向映射：两个方向的完整时序

### 5.1 裸机 → 客户机（push）

1. 裸机浏览器 `POST api/files/uploads`（Cookie，`FileIngest`）→ 中心建上传会话，**带 `size` 做磁盘余量预检**；
2. 浏览器按 8 MB 分块 `PUT ?offset=`（`File.slice`，不整份进内存）；
3. `POST .../complete` → 中心**自算** SHA256 → 原子移入仓库；
4. `POST api/distributions`，`targets=[{agentId, targetDir}]` → 中心为这台机器建明细（**离线也建**）；
5. 中心经 `/hubs/agent` 推 `PushTransferTask`（离线则等它上线**补领**）；
6. Agent `GET api/files/{id}/download`（`Range` 续传）→ 自算 SHA256 比对 → `.cs-part` → `File.Move(overwrite: true)`；
7. Agent 回报 `progress` / `complete` → 中心 → `/hubs/events` → 面板进度条动起来。

### 5.2 客户机 → 裸机（collect）

1. 面板里 `GET api/agents/{id}/browse?path=` 逐级点进去（中心等 Agent 回话，有超时）；
2. `POST api/distributions/collect`，`sourcePath` 为**绝对路径**；
3. Agent 建会话（AgentKey）→ 4 MB 分块 `PUT`（被 `409` 纠正偏移会自动对齐）；
4. 中心落仓库，`kind=collected`（服务端强制，客户机不能自称别的 kind）；
5. 面板 `GET api/files/{id}/download`（`Range`）→ 浏览器流式落盘；
6. Agent 回报完成 → 面板刷新为"已取回"。

### 5.3 两条链路共同的两个好性质

- **客户机离线也能建单**：`AgentTransfersController.Pending` 会把 `pending` 一次拉走，
  所以"给一台当时关着的机器传文件"是成立的，上线自动开始。
- **远控断线不影响传输**：字节走 HTTP、执行在 Agent 侧；浏览器只是"看进度"。
  远控 WebSocket 断了，面板重连后刷新一下进度即可，**不会让已传的部分从头再来**。

## 6. 必须向现场讲清的七条限制

这几条决定了"能不能当同步工具用"，写在文档里比写在代码注释里更重要（铁律 35：解释性文案也要能被断言）。

| # | 限制 | 后果 | 处置 |
|---|---|---|---|
| 1 | **裸机只能"手动下载"**，不能指定落盘路径（http 下），默认落浏览器下载目录 | 无法自动化、无法放回指定目录 | 面板写明"接收 = 下载到你浏览器的下载目录" |
| 2 | 想**自动接收**必须装 Agent | 浏览器拿不到目录访问权 | 长期需求就装 Agent（见 §8 方案 D） |
| 3 | 下发落地**同名直接覆盖**（`File.Move(overwrite: true)` 是刻意的） | 覆盖客户机旧文件，不可恢复 | 选中目标目录后若同名，面板要给**明确的红色警告**（不能在传完才说） |
| 4 | 下发只能落**白名单目录**（默认 `inbox`） | 想放桌面会失败 | 浏览能看整盘但写不了 ⇒ 面板要把"可写/只读"标在目录行上 |
| 5 | **单文件任务模型**，不支持目录/多选 | 传文件夹要打包 | 一期说清；二期做 zip 或批量建单 |
| 6 | 单文件上限 **4 GB**，分块 8 MB，会话 **24 h** 过期 | 超限直接 413 | 面板先做本地预检，别传到 99% 才报 |
| 7 | **两跳中转**：中心要占一份磁盘，带宽 ×2，且"传完才发"（串行） | 4 GB 体感 = 上传 + 下发 | 面板显示两段进度（"上传到中心" / "已发到机器"），别合成一个假的总进度 |

> 第 7 条的体感参考（理想值，未计磁盘与防病毒拖累）：
> 千兆 ≈ 110 MB/s、百兆 ≈ 11 MB/s、5G Wi-Fi ≈ 30 MB/s、2.4G Wi-Fi ≈ 5 MB/s。
> 1 GB 两跳 ≈ 千兆 20 s / 百兆 3.5 min / 5G 1 min / 2.4G 7 min。
> 4K60 远控的 H.264 码率约 10–30 Mbps，千兆下影响可忽略；**百兆下会明显抢带宽**。

## 7. 方案设计（一期）

### 7.1 形态：面板新增第 6 个标签「文件」

`RemoteDesktopPanel.vue` 现在是 5 个标签（`SHEET_TABS`：连接 / 画面 / 控制 / 声音 / 诊断），
插在「控制」之后即可 —— 它属于"对这台机器做事"，不属于诊断读数。

面板内两块，**方向用词与既有的"下发/回传"保持一致**，不要另起一套说法：

```
┌ 文件 ──────────────────────────────────┐
│ 发给这台机器                             │
│  [选择文件]  report.zip  12.4 MB         │
│  存放目录  [D:\inbox          ▾] 可写    │
│  [开始发送]                              │
│  ── 上传到中心 ████████░░ 78%  6.1 MB/s  │
│  ── 已发到机器 ███░░░░░░░ 31%  待开始…   │
├─────────────────────────────────────────┤
│ 从这台机器取回                           │
│  [D:\logs ▾]  ⇧上一级   [刷新]           │
│  ☐ app-20261020.log        82.3 MB  [取回]│
│  ── 机器 → 中心 ██████░░░░ 62%           │
│  ── 下载到本机 [下载]（落到浏览器下载目录）│
└─────────────────────────────────────────┘
```

复用与新建的边界：

| 复用（不要再写一份） | 说明 |
|---|---|
| `api.uploadFileChunked` | 已经会按 `File.slice` 分块并处理 `offset` |
| `api.createPushDistribution` / `api.collectFiles` | 建单 |
| `AgentPathPicker.vue` | 目录选择（可裁剪成"目录行"而不是弹层） |
| `transferRate.ts` 的 `RateTracker` | 速率（服务端**不推速率**，只能前端派生） |
| `DistributionPanel` 的进度订阅方式 | `/hubs/events` 按 `itemId` 原地更新 |

### 7.2 必须抽成纯函数的规则（可断言）

按项目既有做法（`reconnect.ts` / `transferRate.ts` / `codecFallback.ts`），
**下面这些"规则"不放组件里**，否则只能靠人读代码：

1. `transferFlow.ts` —— 两段状态机：`idle → uploading → uploadFailed | publishing → delivering → done | failed`。
   关键是**"上传成功但建单失败"必须是一个独立状态**（`publishing` 失败），
   不能笼统报"传输失败"：文件其实已经在仓库里了，重试应该**从建单开始**，不是重新上传。
2. `transferPrecheck.ts` —— 本地预检：`size > 4 GB` ⇒ 直接拒；`size === 0` ⇒ 直接拒（客户机侧会判"源文件为空"）。
3. `transferLabels.ts` —— **三句"不能传"必须分开**：
   - 机器离线（"上线后会自动开始"，这是正常态，不是错误）
   - 授权未生效（"建单被拒，上传与浏览仍可用"）
   - 目录不可写（"这台机器只允许写 `D:\inbox`"）

> 铁律 35 的教训：一句无条件的"当前不可用"横幅会一直挂到它变成假话为止。这三句都必须是**条件成立才出现**。

### 7.3 缺口清单（按风险排序）

| # | 缺口 | 现状 | 建议 |
|---|---|---|---|
| 1 | 面板只看"这一台"，但任务列表是**全量**的 | `GET api/distributions?limit=50` 无机器过滤 | 加 `?agentId=` 过滤参数（后端小改），否则前端过滤会漏掉老任务 |
| 2 | 上传成功后建单失败 ⇒ 仓库留一份孤儿 | 仓库没有"面板临时文件"概念，删除要手动 | 面板内给"删除仓库副本"按钮；若要自动回收则需新增 `kind`（会牵动 `FileKinds` 白名单和仓库页过滤，一期先不做） |
| 3 | 刷新/切标签丢掉 `uploadId` | `uploadFileChunked` 的会话只活在内存 | 把 `uploadId + offset + fileId` 存 `sessionStorage`，重开可续（**注意**：`File` 对象刷新后拿不到，只能重新选同一个文件，靠"文件名 + size"匹配） |
| 4 | 同名覆盖无提示 | 客户机 `overwrite: true` | 建单前用 browse 查一次目标目录，命中同名则显式确认 |
| 5 | 目标目录默认值不明确 | 留空 = 那台机器的默认目录（通常是 `inbox`） | 面板首次打开时 browse 到默认目录并显示绝对路径，别只写"默认" |
| 6 | 大文件与远控抢带宽 | 无任何限速 | 一期不做限速，但在"诊断"里显示传输占用；二期给"低速模式" |
| 7 | 审计可读性 | 日志有 `Files` 分类，但面板不显示发起人 | 用 `DistributionTaskDto.CreatedBy` 显示"谁传的"；日志保持可 grep |
| 8 | 目录/多文件 | 单文件模型 | 一期禁用多选（明确说"一次一个"），二期再谈 |

### 7.4 实施注意（本项目特有的坑）

- **改前端必须再 `dotnet build Server`**：`dist/`、冒烟、绿色版读的是**内嵌那份**（铁律 11）。
  面板改动属于"前端改了"，只重启服务不重编，现场看到的还是旧面板。
- 内嵌产物被运行中的服务锁着 ⇒ **先停服再 build**（`M7.13` 已踩）。
- 面板内容切换用 `v-show`，不要 `v-if` —— 「刷新不能让正文卸载重建」（铁律 8）。
  已选的本地文件、已输入的目录不能因为切了一次标签就没了。
- 机器归属一律用 `windowAgentId`（铁律 37）：会话断了、`activeSession` 没了，
  文件面板仍要能对"这台机器"发东西；**不许 `?? 0` 兜底**（会画出"机器 #0"）。
- `void asyncFn()` 会连异常一起吞（铁律 10）⇒ "点了发送没反应"。

## 8. 明确不做的四条路（以及为什么）

| 方案 | 结论 | 理由 |
|---|---|---|
| **A. 两跳中转（推荐，= §7）** | 做 | 0 新协议，复用 `push/collect`，天然支持断点续传与离线补领 |
| **B. 边收边转的流式直通** | 一期不做 | 要新增流式协议；一旦不落仓库，就**失去离线补领与续传**，还得自己做背压。收益只是"省一次落盘 + 少等一段"，不值 |
| **C. WebRTC DataChannel 让裸机与 Agent 直连** | 不做 | ① Agent 要内嵌 WebRTC 栈（C# 侧没有成熟官方实现）；② 要 STUN/TURN 与 ICE，客户机因此要开 UDP 候选端口，破坏"客户端不开入站"的模型；③ 鉴权/审计要从中心挪到对端，等于**新造一套信任模型**；④ 收益仅是"局域网内省一跳" |
| **D. 让裸机装 Agent（10 秒安装包）** | **如果这是长期需求，这才是最便宜的方案** | 装上之后它立刻获得"被推送 / 被浏览 / 任意白名单目录"三件事，且无需任何新代码。代价是它被纳管（可被远控、关机），对"临时访客机"不合适 —— **这正是"不装"的合理场景，也就是本方案存在的意义** |

> 一句话取舍：**偶发传文件 ⇒ 浏览器；长期收发 ⇒ 装 Agent；两者都不要 ⇒ 做不出直连。**

## 11. 需要拍板的三件事

1. **面板里传完的文件，仓库副本留不留？** 留（可复用、可再发）会让仓库越来越大；删（一键清理）会让"想再发一次"要重新上传。建议：**默认保留 7 天**，面板上给"删除副本"，用一个新 `kind`（`transient`）在仓库页默认折叠 —— 但这会动 `FileKinds` 白名单，需要确认是否愿意为此改公共契约。
2. **要不要在一期做"同名覆盖确认"？** 不做的话，第一次现场就会有人覆盖掉客户机上的同名文件（`overwrite: true` 是既有的、刻意的行为）。
3. **裸机（浏览器）这一侧的"接收"要不要做成"另存为"？** 需要中心启用 HTTPS（安全上下文）才能用 `showSaveFilePicker`；HTTP 下只能落下载目录。若现场本来就是 HTTP，这条只能如实说明，不要承诺"可选路径"。

## 12. 附：为什么"裸机能传"这件事不需要新代码做协议

把两条链路摊开看，裸机侧只用了三个 HTTP 端点：

```
POST api/files/uploads          ← 建会话（Cookie）
PUT  api/files/uploads/{id}     ← 追加分块（Cookie）
POST api/distributions|collect  ← 建单（Cookie, AdminOnly + Gated）
GET  api/files/{id}/download    ← 收文件（Cookie, Range）
```

这四个端点**今天就在用**（文件仓库页 / 分发页），只是没有人把它们串成"面板里的两步动作"。
所以本需求的技术风险集中在**UI 编排与文案**，不在传输可靠性 ——
后者已经被 `M4.4`（分块续传）、`M4.4+`（目录浏览）、`M7.1`（仓库对账）打磨过。

### 13.4 三条实现上的坑（下次别再踩）

1. 🔴 **`Path.GetFileName` 在 Linux 上不认 `\`**：回传的 `SourcePath` 是 Windows 路径，
   服务端若跑在 Linux，取末段会拿回整串 ⇒ 匹配永远失败 ⇒ **"回传成功了但下载按钮永不出现"**。
   已收进 `DistributionsController.LeafNameOf`（同时认 `\` 与 `/`），并有前端同名实现（`fileBrowser.leafOf`）。
2. 🔴 **分块上传带 `application/x-www-form-urlencoded` 会被 MVC 当表单读掉**：
   服务端返回 `ok:true, receivedBytes:0` —— **看起来成功，其实一个字节都没写**。
   浏览器 XHR 发 Blob 不会踩（type 不是表单），脚本/命令行客户端会。
3. 🔴 **同一台物理机的第二个 Agent 会复用同一个 machineKey/Id**：
   用"在线列表里多了一台"来判断"测试实例起来了"是**假阴性**（实测直接复用 #12）。
   判据应从该实例自己的日志读 `已确认连接：AgentId=…`。

### 13.5 已知限制（现场要知道）

- **收起参数面板会卸载组件** ⇒ 正在"上传到中心"的那一段会中断；已经在客户机侧拉取的那一段不受影响。
  页面底部有常驻提示。彻底解决要把传输队列提升到窗口级（不在本轮）。
- **本机侧没有"此电脑"**：浏览器不允许枚举盘符，只能先选一个根目录，再在其内逐级进出。
- **同名覆盖**：两侧都会先弹确认；确认之后客户机侧是 `File.Move(overwrite: true)`（真覆盖，不可恢复）。
- **不支持目录递归**：单文件任务模型，文件夹要自己压缩。
- 🔴 **客户机写不再有白名单**：拿到管理员 Cookie 即可往被控机任意绝对路径写文件，
  而 Agent 常以 LocalSystem 运行 ⇒ 等价于"可在被控机上落任意内容"。安全边界只剩
  "管理员账号 + 授权闸门"。部署方必须知道这一条（已同步写进 `TransferOptions` 的类注释）。

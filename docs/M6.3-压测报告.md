## 1. 这份报告测的是什么，不是什么

**测**（全部是中心的活）：

- `/hubs/agent` 的建连、鉴权、Welcome 下发；
- 心跳与遥测的**入库**（`agent_metrics` 真的按采样率落行，不是空转）；
- 命令下发（`POST /api/agents/{id}/reboot` → Hub 单向推送）；
- 远控帧转发（建会话 → 假观看端 `/hubs/remote` 收帧）。

**不测**（也**不许**拿这份报告去承诺）：

| 不测的 | 为什么 |
|---|---|
| 被控端的抓屏 + 硬编 | 假 Agent 不抓屏、不编码。100 台真机还要各自跑 MF/DXGI（`M5.4c` §6.1），本机物理不可得 |
| 真 4K 码流 | 帧是 `Random.Shared.NextBytes` 的随机字节，中心不解码只转发 —— 对中心的压力真实，但对**浏览器解码**的测量是 0 |
| Linux / Docker | 沿用既有挂账，本轮没碰 |
| GC 次数 / 暂停 / 线程池队列 | 要 `dotnet-counters` 挂上去，本工具不带 |
| 真实网卡的吞吐 | 全程 `127.0.0.1`，没有经过物理网卡与交换机 |

## 3. 三档曲线怎么读

| 看什么 | 读数 | 解读 |
|---|---|---|
| 规模翻倍，CPU 涨了吗？ | 20 台 1.1% → 50 台 0.9% → 100 台 1.6%（均值） | **基本不涨**：本负载是"每 10 s 一次心跳 + 每 5 s 一次遥测"的**极稀疏**形态，CPU 大头是固定开销（Kestrel + 日志），不是每台成本 |

## 5. 断线恢复专项（100 台 · 中途停服 26 秒）

之所以单独跑这一轮：方案 §1 的验收目标里有"**掉线重连成功率**"，而基线那轮 0 次重连
只说明**没制造断网**，不构成证据 —— **"没测"和"稳"是两件事**。

做法：100 台稳定在线后，**直接把中心进程杀掉**（模拟升级停服 / 崩溃），停 **26 秒**，原端口原数据目录重启。

| t(s) | 在线（窗口峰值） | 心跳 ok | 心跳 fail | 重连（**累计**） | 发生了什么 |
|---:|---:|---:|---:|---:|---|
| 70 | 100 | 89 | 11 | 0 | 中心被杀，第一批心跳失败 |
| 80 | 100 | 0 | 100 | 0 | 全部打不通，但**还没有一台判定断线**（连败不足 3 次） |
| 90 | 100 | 0 | 100 | 11 | 攒够 3 次连败的 11 台开始重建连接 |
| 100 | 75 | 0 | 89 | 89 | 累计 89 台判定断线（在线数开始真实下降） |
| 110 | **0** | 15 | 0 | 100 | 100 台全部判定断线并在退避；少数机器的残留调用还在返回 ack |
| 120 | **100** | 100 | 0 | 100 | **全部 100 台回来了** |

> ⚠️ **读这张表的两个坑**（写进工具文档了，这里再说一次）：
> ① 报告 csv 里"重连"这一列是**每 10 秒窗口内**的次数（11 / 89 / 0），本表已**累加**成 100；
> ② "在线"是窗口**峰值**、且是**假机器自报**。100 台同时重连的那十几秒里，两个计数器会有相位差
> （t=110 那格：`重连` 已经 100、`在线` 却是 0、还夹着 15 次成功心跳）——
> **不要用单行读数下结论，看整条曲线**。

**结论（两个可以直接写进升级手册的数字）**：

1. **客户端察觉断线最长要约 30 秒** —— 判定口径是"心跳连败 3 次"
   （`AgentWorker.PumpAsync` 的 `failStreak >= 3`，与真 Agent 退避口径一致），
   心跳 10 s 一次 ⇒ 最多 30 s。停服 26 秒期间累计 **300 次失败 = 100 台 × 3 次**，正好对上；
2. **中心起来后约 20 秒内 100 台全部回位**（退避 1→2→4→8→10 s，100 台同时退避也不挤爆中心，
   注册/鉴权/握手零失败）。

> ⇒ **升级窗口内的"指令不可达"最坏 ≈ 停服时长 + 30 秒（察觉）+ 20 秒（回位）**。
> 这条要写进 M6.4 的升级步骤说明里：**别在演出中升级**，且升级后至少要等 1 分钟再验收"全部在线"。

另：这一轮"内存上涨 15.9%"是**短轮次的假读数** —— 3 分钟的窗口里前 20% 热身段只有 36 秒，
而本机预热要 60–90 秒。同配置跑满 30 分钟是 **−5.8%**。工具的 §6 已把这条写进报告模板。

## 6. 门槛（回填方案 §7②）

**实测值不等于门槛**：门槛是"过 = 可交付"的判定线，必须给现场更弱的机器、更大的库、真实 Agent 的抖动留余量。
下面每个数都标了"为什么是这个数"。

| # | 指标 | 100 台 30 min 实测 | **建议门槛** | 为什么是这个数 |
|---|---|---|---|---|
| 1 | 注册成功率 | 100 / 100（0 失败） | **100%**（允许 0 失败） | 注册是一次性动作，失败即漏一台机器，没有"可接受失败率" |
| 2 | 心跳失败率 | **0.00%** | **≤ 0.1%** | 30 分钟 18000 次心跳，0.1% = 18 次；局域网抖动不该超过这个量级。超过就要查是不是 SQLite 写锁或 GC 停顿 |
| 3 | 心跳 RTT P95 | **1.4 ms** | **≤ 50 ms** | 实测的 **35 倍**余量。50 ms 仍远低于"人感觉不到"的门槛，而现场可能跑在 VM/低配工控机上 |
| 4 | 心跳 RTT P99 | **4.2 ms** | **≤ 150 ms** | 实测的 35 倍。P99 用来兜 GC / 首次迁移这类长尾 |
| 5 | 中心 CPU 均值 | **1.2%**（占整机） | **≤ 20%** | 本负载极稀疏，留 16 倍余量给"现场采样率更高 + Release/Debug 差异 + 同机还跑着前端/托盘" |
| 6 | 中心 CPU 峰值 | **10.3%** | **≤ 50%** | 峰值出现在 100 台同时握手那 30 秒；50% 保证那一刻还有一半算力留给 HTTP 与远控 |
| 7 | 内存稳态（30 min 末段） | **151 MB** | **≤ 512 MB** | 实测 3.4 倍。按每台约 0.5 MB 粗估，512 MB 的余量大致对应 500–800 台同口径（**粗估，不是实测拐点**） |
| 8 | 内存漂移（跳过热身段） | **−5.8 MB（−3.3%）** | **≤ +20%** | 只判"涨"，不判"必须持平"；+20% 是给"库变大后缓存增长"留的口子，超过就要查泄漏 |
| 9 | 命令到达率（假机器实收 / 中心下发） | **100%**（17784 / 17784） | **差 ≤ 0.1%** | `Command` 是单向推送，中心无法保证送达；0.1% = 每 1000 条允许丢 1 条，超过就是连接层有问题 |
| 10 | 命令下发 HTTP P95 | **7.3 ms** | **≤ 100 ms** | 实测 13 倍。这是**中心处理耗时**，不是回执（见下方⚠️） |
| 11 | 推流到达率（1 路） | **100%**（53403 / 53403） | **≥ 99%** | 队列容量 1 + 丢最旧是**设计**，所以不要求 100%；99% 已经是"几乎不丢" |
| 12 | 推流端到端 P95 | **3.0 ms** | **≤ 150 ms** | 实测 50 倍。150 ms 是"操作跟手"的上限，留足现场网络与真实编码的余量 |
| 13 | 掉线重连成功率 | **100 / 100**（停服 26 s） | **100%**（≤ 60 s 内全部回位） | 回不来就是那台机器失联，运维必须知道；60 s 是实测 20 s 的 3 倍余量 |
| 14 | 服务端 ERR / FTL | **0 条** | **0 条** | 没有可接受的数量 |
| 15 | 库体积（30 天、5 s 采样、100 台） | 折合 **≈ 2.8 GB** | **≤ 5 GB** | 给现场采样率与行宽差异留一倍。超了就必须调采样率或缩短 `DetailRetentionDays` |

> ## ⚠️ 原验收口径里有两处必须改
>
> **① "命令回执 p95" 这个词在本协议里没有对应物。**
> `Command` 是单向推送、无回执，中心回 200 只代表"已交给长连接"。
> 本轮把它拆成两个**能量**的事实：#9 到达率（假机器实收）+ #10 下发 HTTP P95。
> 验收表里继续写"回执 p95"会变成一条**永远无法证伪的指标**。
>
> **② "掉线重连成功率"原来无法验证，现在有了（#13）。**
> 但这轮的断网是**杀进程**造的，不是拔网线/交换机重启 ——
> 真机还要验"半开连接"（心跳走通但 TCP 已死）的恢复，见 §8。

**判定方式**：门槛是**逐条**判的，没有"综合评分"。
任何一条不达标 ⇒ 该配置不可交付，先定位再谈。

## 7. 怎么复现

前置：**必须用临时数据目录起的实例**（否则 100 台假机器会留在现场库里）。

```powershell
# Windows：一条命令跑完挑端口、起临时实例、压测、停服、删目录
deploy\loadtest\run-loadtest.ps1 -Agents 100 -Minutes 30 -CommandsPerMin 600 -Streams 1 -Tag 100-baseline
```

```bash
# Linux / macOS / Git Bash
deploy/loadtest/run-loadtest.sh 100 30
```

手动分步（调试时更清楚）：

```bash
# 1) 挑一个当时空闲的端口（不要写死）
# 2) 用临时数据目录起实例，并注入这些开关：
#    Server__Storage__DataDir=<临时目录>  Server__Http__Urls=http://127.0.0.1:<port>
#    Server__Https__Enabled=false  Server__Startup__AutoOpenBrowser=false
#    Server__Tray__Enabled=false   Server__Startup__SingleInstance=false
#    Server__Time__AutoSync=false  Server__Timer__Enabled=false
#    Server__Discovery__Port=0     Server__Auth__LoginRateLimit__PermitLimit=1000
# 3) 等 /healthz 返回 200
# 4) 跑工具（--server 没默认值，逼你写清楚打谁）
ControlServer.LoadTest.exe --server http://127.0.0.1:<port> \
    --agents 100 --minutes 30 --ramp 10 \
    --commands-per-min 600 --streams 1 --stream-frame-kb 32 --stream-fps 30 \
    --server-pid <服务PID> --tag 100-baseline
# 5) 报告默认落在 deploy/loadtest/reports/（与 cwd 无关），逐秒数据在同名 .csv
```

断线恢复那一轮（§5）没有专用开关，是手工做的：

1. 起 100 台、`--commands-per-min 0 --streams 0`（**只测 L1**，避免服务重启后 Cookie 失效污染 L2 数据）；
2. 盯着进度行到"在线 100/100"后，**杀掉中心进程**，等 25–30 秒；
3. 用**同端口同数据目录**重启；
4. 报告里看 `重连` 累计数与在线数的时间序列。

## 8. 挂账与已知限制

| # | 限制 | 影响 | 什么时候回访 |
|---|---|---|---|
| 1 | `run-loadtest.ps1` **未在本机端到端跑通** | Windows 一键脚本未验 | 本机 PowerShell 环境禁止直接起原生 exe；.sh 与分步命令都验过。**必须在能跑 PS 的机器上补一次** |
| 2 | 压测工具**不模拟拔网线 / 交换机重启** | 半开连接（心跳能通、TCP 已死）的恢复未验 | 现场首次部署时手工验一次 |
| 3 | 未采 GC 次数 / 暂停 / 线程池队列 | 不知道为什么 P99 会到 4.2 ms | 需要 `dotnet-counters` 挂到中心进程上 |
| 4 | 假帧是随机字节 | 测不到浏览器解码、测不到 H.264 码流特性 | 只能真机 |
| 5 | Linux / Docker 未覆盖 | Linux 交付说明仍未验证 | 沿既有挂账 |
| 6 | `agent_metrics_daily` 在 30 分钟内是 0 行 | 日汇总表 365 天的增长**没量到** | 需要 24 h 长跑一轮 |
| 7 | 内存漂移只证明 30 分钟 | 8 小时 / 24 小时的缓慢泄漏没排除 | 与"8K 未验"那批挂账一起做长跑 |
| 8 | 断网测试是**杀进程**，不是优雅停服 | 优雅停服**理论上**会发 WebSocket close，客户端应**立即**察觉（不用等 30 s）—— **但没实测** | 本轮按"崩溃恢复"这个更差的情况测，结论偏保守，可接受；优雅停服的数字等 M6.4 升级演练时一并量 |
| 9 | 只有 1 路推流 | 10 路 / 100 路推流的带宽与队列压力未测 | 方案 §7④ 已明确"不做 100 路"，不列为缺口 |
| 10 | 100 台是**协议级**模拟 | 不能承诺"100 台 4K 远控" | 见 §1，永久限制 |

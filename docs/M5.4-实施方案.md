> **状态**：方案已立档，实施中。
> **上游**：`docs/M5-局域网远程桌面实时方案.md` v3.5 §4（零拷贝管线）/ §5（抓屏）/ §6（编码）/ §16.1（能力标定）。
> **承接**：`docs/M5.0-实施清单.md`（M5.0–M5.3 合并档）。
>
> 🔥 **本批是「垂直切片」，不是「接管线」** —— 这是方案 §14 风险登记自己写下的顺序：
> 「先写最小垂直切片（抓屏→编码→落文件）再接管线」，理由是
> **「MF 异步 MFT + D3D11 互操作工作量大」**。

## 0. 本批的四个已拍板决策

| # | 分叉 | 定成了什么 | 为什么 |
|---|---|---|---|
| ① | **本批范围** | **垂直切片**：DXGI 抓屏 → D3D11 转 NV12 → MF 硬编 → **落 `.h264`/`.hevc` 文件 + 解回验证**。**不碰推流链路与前端。** | 「异步 MFT + `IMFDXGIDeviceManager`」是本批最大未知。先用最小面积证明它能出**正确的**码流；一旦同时改了四层，"是编码器错了还是链路错了"分不开 |
| ② | **互操作写法** | **手写 COM**（与 M5.3 的 CoreAudio 同一条路） | 零新依赖、不破坏单文件分发。代价是本批代码集中在 interop 层，且**槽位必须对头文件核** |
| ③ | **验收口径** | **本机按 2160×1440 用 Intel QSV 实测**；4K/8K 标注「待现场机型」 | 本机 MX250（GP108）**已实测 0 引擎、无 NVENC**；显示器只有 2160×1440 ⇒ **4K 在本机物理上抓不出来**。但 Intel UHD 620 **确有 QSV 的 H.264 + HEVC 硬编 MFT**（M5.0 第二批实测）⇒ 链路本身可以真机跑通 |
| ④ | **浏览器解码** | **WebCodecs + 保留 MJPEG 兜底**（下一批落地） | `isConfigSupported` 探测硬解，不支持（尤其超 4K 的 HEVC）就自动回落现有 MJPEG 链路。MSE 需额外做 fMP4 封装且缓冲模型加 200ms+ 延迟，**与 100ms 目标直接冲突** |

## 1. 本批做什么 / 不做什么

### 1.1 做

| 层 | 内容 |
|---|---|
| 抓屏 | **DXGI Desktop Duplication**（`IScreenCapturer.CaptureSurfaceAsync` 的**真实现**，GDI 那个保持不动） |
| 色彩转换 | `ID3D11VideoProcessor` **BGRA → NV12**，全程显存内 |
| 编码 | **MF 异步 MFT 硬编**（H.264 / HEVC），**纹理直喂**（真零拷贝） |
| 灰度 | 编码前色度置常量 128（决策 14），并**用抓包字节数**验证收益（§16.1 ⑥） |
| 验证 | 落文件 + **自编自解**（用 MF 解码器 MFT 解回来）+ 实测帧率/延迟/码率 |

### 1.2 不做（明确留给下一批）

- ❌ 接进推流链路（`RemoteStreamHost` 的那条循环、`EncodedStreamPayload` 的接线）
- ❌ 协议新增：**关键帧标记**、**解码器描述（avcC / hvcC）** —— 见 §4 那条"先记下来"
- ❌ 前端 `VideoDecoder`、`isConfigSupported`、降级 UI
- ❌ 中心端点 + `LicenseGate` 分类 + 归属校验（灰度开关的**下发**那一半）
- ❌ 码率/帧率自适应（§1.6 手段）
- ❌ 多屏

## 2. 关键设计：**共享 D3D11 设备是结构性要求，不是优化**

零拷贝的成立条件是**一条链上只有一个 D3D11 设备**：

```
DXGI Duplication ──BGRA 纹理──> ID3D11VideoProcessor ──NV12 纹理──> MF 硬编 MFT
        └──────────────── 必须同一个 ID3D11Device ────────────────┘
```

原因有两条，任一条不成立都会**静默降级成"拷回内存"或直接失败**：

1. `ID3D11VideoProcessorBlt` 的输入/输出视图必须与设备同源；
2. `MFCreateVideoSampleFromSurface` 造出的 `IMFSample` 只有在**编码器认得那个设备**时才走显存路径 ——
   编码器要认得设备，就得拿到同一个 `IMFDXGIDeviceManager`。

⇒ 因此本批**不把设备藏在抓屏器内部**，而是抽一个显式的
`D3D11GpuContext`（一个适配器上的 设备 + 立即上下文 + VideoDevice + VideoContext），
抓屏器与编码器**都从它取**。让"同一个设备"成为**结构上的事实**，而不是一句注释里的约定。

> ⚠️ 这条同时是本批**唯一一处会影响下一批做法**的设计：托盘的
> `Func<IScreenCapturer>` / `Func<int, IFrameEncoder>` 两个独立工厂
> **不足以表达这个约束**，下一批接线时要引入一个共享的 GPU 上下文工厂。**先记在这里，别到时候再想。**

### 2.1 适配器怎么选（本机是双显卡，方案 §5.1 第 1 条）

按**显示器设备名**匹配，而不是按"第一个适配器"或"独显优先"：

```
IDXGIFactory1.EnumAdapters1(i) → IDXGIAdapter1
IDXGIAdapter1.EnumOutputs(j)   → IDXGIOutput
IDXGIOutput.GetDesc().DeviceName  == 目标屏的 \\.\DISPLAYn
```

⚠️ 选错的症状是**全黑帧**（不是报错）。本机 Intel 核显在 DXGI 里暴露**多个适配器节点**
（M5.0 第二批实测：4 个节点、按型号归并成 2 块物理卡）—— 匹配必须按 output 反查，不能按节点序号。

## 3. 🔥 手写 COM 的做法：**只声明用到的槽位**

方案 §6.5 那张接口表是**语义**层面的；落到 C# 时如果照抄整个 vtable，`ID3D11DeviceContext`
有 **110+ 个槽**、`ID3D11Device` 有 **43 个**，而本批真正要调的不到 30 个。抄全了等于凭空引入
几十处"顺序写错也不报错"的风险。

⇒ **本批采用与仓内既有做法一致的形状**（`MediaFoundationEncoders` 里那条
`GetAllocatedString = 槽位 13` 就是先例）：**把用到的槽位做成具名常量，配一个共用调用助手。**

### 3.2 ⚠️ 两个**必须记住**的坑（都是从头文件里读出来的，不是猜的）

1. **`METransformNeedInput` 不是 GUID，是枚举值。**
   它属于 `MF_EVENT_TYPE`：`METransformNeedInput = 601` / `METransformHaveOutput = 602` /
   `METransformDrainComplete = 603` / `METransformMarker = 604`。
   异步 MFT **通过 `IMFMediaEventGenerator` 抛事件**（`IMFMediaEvent.GetType()`）来要输入 / 交输出，
   **不是** `ProcessOutput` 轮询。把它当 GUID 是个很自然的误写，而症状是"编码器一帧都不出"。
2. **`MFT_MESSAGE_NOTIFY_*` 的两个值与本能的写法相反**：
   `NOTIFY_START_OF_STREAM = 0x10000003`、`NOTIFY_END_OF_STREAM = 0x10000002`（**3 在前、2 在后**）。

### 3.3 🔥 真机实测踩出来的坑（**2026-10-16，写代码时又踩了一遍**）

> 下面每一条都是"编译通过、跑起来才发现"的。它们比 §3.1 那张表更值钱 ——
> 表是**查**出来的，这些是**撞**出来的。

1. 🔴 **槽位号是「接口内」的，跨接口不通用。** 从 `ID3D11Device` 上取"第 10 槽"得到的是
   `CreateInputLayout`，拿它当 `ID3D11Texture2D::GetDesc` 调，返回 `E_INVALIDARG`（`0x80070057`）。
   ⇒ `ComVtable.Bind` 必须传**你要调的那个接口的实例**。症状是"另一个函数被调了"，
   而这个错在只调一次、且返回值不看的地方（例如自检工具里）很容易溜过去。
2. 🔴 **`ID3D11DeviceContext` 有 115 个槽**（全库最长）。本批用到：
   `Map = 14` / `Unmap = 15` / `CopyResource = 47` / `Flush = 111`。
   交叉验证：`Begin = 27` / `End = 28` 与众所周知的顺序一致 ⇒ 解析没跑偏。
3. 🔴 **`AcquireNextFrame` 的第三参是 `IDXGIResource**`，不是纹理**；要 `QueryInterface` 成
   `ID3D11Texture2D`。**QI 出来的引用与 `IDXGIResource` 是两份**，两份都要放。
4. 🔴🔴🔴 **`AccumulatedFrames == 0` 的帧不能用 —— 这是「刚连上远控看见一片黑」的成因。**
   DDA 是**增量投递**的：只在你取帧的间隔里攒到过桌面更新时，才会把新的桌面图填进那块纹理。
   攒到 0 帧时它**仍然返回 `S_OK`**（因为**指针**可能有更新），但纹理内容**是未定义的**。
   本机实测（2160×1440 / Intel UHD 620）：

   | 帧 | AccumulatedFrames | 元数据 | 指针形状 | 读回来的像素 |
   |---|---|---|---|---|
   | 第 1 帧 | **0** | 0 B | 4096 B | **全 0（全黑）** |
   | 第 2 帧 | 13 | 16 B | 0 B | 99.98 % 非黑 |

   ⇒ **不变式：交出去的每一帧必须 `AccumulatedFrames > 0`。** 已写成用例
   `Every_frame_handed_out_came_from_a_populated_dda_frame` 钉死。
5. 🔴 **`TotalMetadataBufferSize` 不含指针形状** —— 实测首帧 `meta = 0 B` 而
   `pointerShape = 4096 B` 同时出现。所以"这一帧有没有脏区"只能看
   `TotalMetadataBufferSize`，不能看那个"总数"的名字想当然。
6. 🔴 **`GetFrameDirtyRects` 不要用「先传 0 字节问所需大小」的两段式。**
   本机实测：元数据明明是 16 B（正好一个矩形），那样问回来的"所需大小"却是 **0** ——
   于是恒判"没有脏区"，一个 16 字节就能装下的答案被问没了。
   ⇒ 一次给足缓冲（本批 64 个矩形），再看实际写入多少。
7. 🔴 **`ID3D11Texture2D` 的 `GetDesc` 是最可靠的"这个句柄到底是什么"的检查**：
   它回出来的宽/高/格式与另一套来源（`EnumDisplayMonitors`）必须一致。
   两者不一致就说明"枚举之后分辨率变了"，而这种事只给一个数时看不出来。
8. 🔴 **适配器按 output 反查是对的，而且本机上它是唯一可行的做法。** 实测 4 个 DXGI 节点：

   | 节点 | 名字 | 挂着的输出 |
   |---|---|---|
   | #0 | Intel(R) UHD Graphics 620 | **`\\.\DISPLAY1`（2160×1440, identity）** |
   | #1 | NVIDIA GeForce MX250 | 无 |
   | #2 | Intel(R) UHD Graphics 620（**另一个 LUID**） | 无 |
   | #3 | Microsoft Basic Render Driver | 无 |

   ⇒ 按序号挑，**四分之三的概率挑到没有输出的节点**。这也正是 M5.0 第一批里
   "一块物理卡暴露成多个节点"那条实测的来源。

### 3.4 🔥 GPU 色彩转换（BGRA→NV12）踩出来的（**2026-10-16，本批最贵的一节**）

1. 🔴🔴🔴 **驱动的「能力声明」、甚至「读回的状态」，都不等于它的「行为」。**
   本机（Intel UHD 620）视频处理器的**饱和度滤镜**：
   `FilterCaps` 声明支持（`0x7F` 含 `SATURATION` 位）、`GetVideoProcessorFilterRange`
   报得出量程 `0..1000 / 默认 100`、`SetStreamFilter` 设进去后 `GetStreamFilter` **读回正是我们设的值**
   （`enabled=True level=0`）—— **而输出与"完全关掉滤镜"逐字节相同**
   （彩色 / 灰度两版的 UV 平面一模一样：`128.0（36..229）标准差 4.9`）。
   把输入/输出颜色空间的 `Usage` 位、自动处理模式、设置先后顺序、量程上 8 个档位全试过，
   **8 个变体输出完全一致**。

   ⇒ 结论：**RGB 输入通路上根本不接滤镜块**（亮度/对比度/色相/饱和度在量纲上都是 YUV 域的东西）。
   **没有任何 API 能发现它，只能靠读回像素证伪。**

2. 🔴 **解法：灰度 = 两趟 Blt。** 第一趟 `BGRA→NV12` 照常（不管饱和度），
   第二趟把 **NV12 在 YUV 定义域上重处理一遍**并把饱和度压到最小 ⇒ 色度成为常量。
   实测通过：UV `128.0（128..128）标准差 0.0`，偏离 ±1 的字节 **0 / 1,555,200**。
   代价是多一次全显存 Blt（不过 PCIe），只在灰度开着时才有。
   ⇒ 由此还派生出**灰度自检**：第一次真要灰度时先读回像素自证一次，
   不合格就如实拒绝（见第 7 条）。

3. 🔴 **颜色空间位域必须按官方取值表写，不能按"二进制看起来对"写。**
   位序：`Usage:1`（0=Playback / 1=Video processing）、
   `RGB_Range:1`（**0 = Full 0–255** / 1 = Limited 16–235）、
   `YCbCr_Matrix:1`（0=BT.601 / 1=BT.709）、`YCbCr_xvYCC:1`、`Nominal_Range:2`（0=UNDEFINED / 1=16–235 / 2=0–255）。
   原代码 `RgbInput = 0b011` 的 `RGB_Range` 位是 **1＝有限范围**，而注释写的是"全范围" ——
   把"桌面 0–255"说成了"桌面 16–235"。症状是**整体发闷、深色发灰，一个错误都不报**。
   已改成 `RgbFullRangeInput => 0b000`，并把位序逐条写进注释。

4. 🔴 **vtable 槽位错一个的代价可以是进程级崩溃。**
   `VideoProcessorSetStreamAutoProcessingMode` 是 **37**，我一度写成 **31** ——
   31 是 `VideoProcessorSetStreamDestRect`（第 4 参是 `const RECT*`），
   把 `enable`（0/1）当指针传 ⇒ 解引用地址 1 ⇒ `AccessViolationException`，**测试宿主进程直接没了**。
   ⚠️ 这一组 `Set*` 是**连着的 14 个（27–39）**，名字长得像、位置全靠对着头文件数。

5. 🔴 **`Set` / `Get` 是成对交错的，按"Set 全在前、Get 全在后"去数会差 13 个槽。**
   已核实的全表：`SetOutputColorSpace = 15` / `SetStreamFrameFormat = 27` /
   `SetStreamColorSpace = 28` / `SetStreamAutoProcessingMode = 37` / `SetStreamFilter = 38` /
   `GetStreamFilter = 51` / `Blt = 53`；枚举器侧：`GetVideoProcessorContentDesc = 7` /
   `CheckVideoProcessorFormat = 8` / `GetVideoProcessorCaps = 9` /
   `GetVideoProcessorRateConversionCaps = 10` / **`GetVideoProcessorFilterRange = 12`**。

   这最后一条的**交叉验证**很巧：量程表是与官方文档一致的指纹（亮度 `-1000..1000/0/×0.1`、
   对比度 `0..1000/100/×0.01`、色相 `-1800..1800/0/×0.1`、饱和度 `0..1000/100/×0.01`、
   降噪 `0..64/0/×1`、边缘增强 `0..64/44/×1`、变形缩放 `0..1/0`、立体调整**读不到**）——
   而"唯一读不到量程的那一项"恰好就是 `FilterCaps` 里**唯一声明不支持**的那一位。

6. 🔴 **量程表里的 `Default` 不是"什么都不设"。**
   **边缘增强的默认值是 `44 / 64`（非零）**，也就是说"不显式关掉"≠"没开"；
   而它作用在**亮度**上（会改 Y）。已连同降噪一起显式关掉。

7. 🔴 **灰度必须自证（读回像素证伪），不能只看 API 说行。** 见第 1 条。
   自检做法：第一趟读 UV 得"彩色基准起伏"，第二趟读 UV 得"灰度起伏" ——
   `灰度起伏 == 0` ⇒ 通过；`彩色起伏 == 0` ⇒ **未判定**（下一个实例再试，最多 3 次，
   之后如实写成"结论未经证实"并标注按可用处理）；否则 ⇒ 失败 + 写明"驱动接受但未执行"。

8. 🔴 **灰度有真实但无害的亮度副作用，而且已量清来源。**
   三种像素分开统计（本机实测）：**平坦**（梯度 ≤4）**0.10**、**边缘**（梯度 ≥24）1.98、
   **彩色**（`|BT.709−BT.601| ≥ 3`）3.37。
   ⇒ 彩色上差得多、平坦上几乎不动，说明驱动是拿 **BT.601 亮度**做的去饱和
   （不是重采样 —— 那样平坦区也会变）。
   所以断言写成**按实测定界的组合**：`flatErr < 0.2`（核心不变式：平坦区不许被改动，
   它同时排掉了"重采样/锐化伤文字锐度"这唯一与灰度初衷相反的可能）+ `colorErr < 12` 上界。

9. 🔴 **对拍公式的「量纲错」与「色度平面错位」数字症状一模一样。**
   色度期望值最初写成 `Cb = 128 + 112 × (B − Y) / 1.8556`，而 `B/Y` 用的是 **0–255 原始值**
   ⇒ MAE **39.02 / 41.68**（阈值 6）。起因是
   **`112` 是"色度偏离中点的最大幅度"（224 的一半），不是缩放系数** ——
   拿它乘 0–255 量纲的差值，等于把真实色度放大 **255/2 = 127.5 倍**。
   正确式（与 `CompareLumaHypotheses` 同一套约定、与逆变换互为反函数）：
   `Cb = 128 + 224 × (B′ − Y′) / 1.8556`、`Cr = 128 + 224 × (R′ − Y′) / 1.5748`，
   `B′/R′/Y′` **归一化到 0–1**。改完 MAE = **0.06 / 0.04**，实现**一行没改**。
   ⇒ 所以用例里额外**把最偏的三个样本连原始 RGB 一起打出来**：
   量纲错 ⇒ 同向偏且正比于 `|B − Y|`；平面错位 ⇒ 乱跳。

10. 🔴 **NV12 在 D3D11 里是一张纹理**：色度平面紧跟亮度之后，
   起点是 `Data + RowPitch × Height`（**不是** `Data + Width × Height`），**必须逐行用 `RowPitch`**。
    另外 NV12 的 4:2:0 半平面要求**宽高都为偶数**（奇数直接拒绝，不静默裁边）。

11. 🔴 **视频处理器视图的纹理要求**：输入视图任何含 `DECODER`/`VIDEO_ENCODER`/`RENDER_TARGET`/`UNORDERED_ACCESS`
    的组合、或 `BindFlags = 0` 都可以；**输出视图必须 `D3D11_BIND_RENDER_TARGET`**，
    漏了会回一个不带解释的 `E_INVALIDARG`。
    `CheckVideoProcessorFormat` 的返回位是 `INPUT = 0x1` / `OUTPUT = 0x2`，**输入输出要分开判**
    （一个格式可以只支持其一）。

### 3.5 🔥 MF 硬编踩出来的（**2026-10-16，本批第二贵的一节**）

> 这一节里的每一条都满足同一个特征：**症状与真因隔着一层，且多数不报错。**
> 顺序按"踩到的先后"排，不是按重要性。

1. 🔴🔴🔴 **异步 MFT 的事件通路必须"按令牌门控"：令牌就是权限，没有令牌不许要输出。**
   这是**最贵的一条**。原写法是"一次 `TryEncode` 里连着 `ProcessOutput` 64 次、直到它说没有"，
   而那**必然在第一批帧喂进去之前先要一次**。
   Intel QSV H.264 编码器 MFT 对"没东西却来要"回的是
   **`E_UNEXPECTED`（`0x8000FFFF`）配 `MFT_OUTPUT_DATA_BUFFER_NO_SAMPLE`（`dwStatus = 0x300`）**，
   **不是**文档里那个 `MF_E_TRANSFORM_NEED_MORE_INPUT`。
   ⇒ 正确做法：**以 `METransformHaveOutput`(602) 令牌数为上限**，令牌内允许再追几次（B 帧/重排）。
   ⚠️ 原注释写的是"不按令牌个数定次数，因为一个令牌可能对应不止一帧" ——
   **后半句是对的，但它被当成了"可以无限次要"的理由**，而正确的结论是"**以令牌数封顶**"。

2. 🔴🔴🔴 **`GetEventType` 是 `IMFMediaEvent` 的方法，不是 `IMFMediaEventGenerator` 的。**
   `IMFMediaEventGenerator` 只有 **7 槽**，取第 33 槽会读到 vtable **之后 264 字节**的内存，
   把那块内存当地址 call ⇒ **`AccessViolationException`，整个测试宿主进程消失**。
   ⚠️ 报错位置（`PumpEvents`）看起来像"事件处理写错了"，与真因（**把接口 A 的槽位用在接口 B 上**）
   隔着一层。绑定要**在循环里对事件对象绑**，并按 vtable 指针做一次小缓存
   （事件是独立对象，不能像 `GetEvent` 那样提到循环外）。
   ⚠️ 顺带：`GetEventType` **刻意不叫 `GetType`** —— 那会隐藏 `object.GetType()`（`CS0108`），
   而更坏的是调用点会**静默解析成那个反射方法**，症状是"读到的事件类型永远不是 601/602"，
   编码器一帧不出、日志里毫无异常。

3. 🔴🔴 **`MF_E_TRANSFORM_STREAM_CHANGE`（`0xC00D6D61`）是硬件编码器出码流前的必经一步。**
   QSV 在第一次真正出码流前会**拒绝出帧、要求重谈输出类型**（把它实际用的 profile/level
   与 SPS/PPS 报出来）。处置：`GetOutputAvailableType(0, 0)` → 原样 `SetOutputType`
   → **必须在同一次调用里 `continue` 重试**。
   ⚠️ **它不会因为我们答应了换类型而补发一个 `HaveOutput` 事件** ——
   "记下来下次再说"是不够的。
   不处理它的症状是**"一帧都不出、且没有错误码"**。
   ⚠️ `GetOutputStreamInfo` 要挪进重试循环里：**换过输出类型之后它报的缓冲大小会变**。

4. 🔴🔴🔴 **`MFT_OUTPUT_DATA_BUFFER.dwStatus` 的四个取值是互斥枚举，不是位标志**（`mftransform.h:94`）：
   `INCOMPLETE = 0x01000000` / `FORMAT_CHANGE = 0x00000100` / `STREAM_END = 0x00000200` /
   **`NO_SAMPLE = 0x00000300`**。
   ⇒ **`0x300` 不是 `INCOMPLETE|FORMAT_CHANGE`，而是 `NO_SAMPLE` 一个值。**
   把它当位标志读会得出**完全相反**的结论（本项目就曾把"这次没有输出"误读成"编码器要求换格式"）。
   判它**一律用 `==`**。

5. 🔴 **异步 MFT 不保证"还没好就回 `MF_E_TRANSFORM_NEED_MORE_INPUT`"。**
   文档里那个位置本该是它，QSV 却用它自己的方式（第 1 条）表达"没有输出"。
   ⇒ **不能按文档的 HRESULT 去判，要按"有没有令牌"去判。**

6. 🔴🔴 **`MF_E_NOTACCEPTING`（`0xC00D36B5`）在解码器上是"先把我手上的输出取走再来"，不是错误。**
   把它当错误处理，**一段完全合法的码流会被判成"解不了"** ——
   而症状是"枚举到 1 个 H264 解码器，但每一个都没能把这段码流解出来"，
   把人往"码流有问题"方向带。
   ⇒ 喂样本的结果**必须是三态**（`Fed` / `NotAccepting` / `Failed`），
   **压成 `bool` 两种归法都是错的**（归"失败"会判死好码流；归"成功"会把那一帧**静默丢掉**，
   于是帧数对不上）。收到 `NotAccepting` 就**先把输出抽干、再重试喂**；
   抽干了还是 0 ⇒ 真卡住，**必须报错**（否则是一个静默死循环）。

7. 🔴 **`MFTEnumEx` 的输入/输出类型参数对编码器与解码器是相反的。**
   - 编码器：H.264 是**输出** ⇒ 填第 4 参 `pOutputType`。
   - 解码器：H.264 是**输入** ⇒ 必须填**第 3 参 `pInputType`**。
   填到第 4 参就等于在问"哪台解码器能**输出** H.264"，那是个没人能回答的问题
   ⇒ 拿到 **0 个**，报出来是"本机没有这个格式的解码器 MFT" ——
   **一个把人往"机器上没装解码器"方向带的假结论**。

8. 🔴🔴 **`MFIDXGIDeviceManager::ResetDevice` 的第一参：官方文档在同一条命令里自相矛盾。**
   - 参数表：`pUnkDevice` = "A pointer to the IUnknown interface of **the DXGI device**."
   - 备注：  "…call this method with a pointer to **the Direct3D device**."

   ⇒ **不能拿"文档明写要 DXGI 设备"当硬结论** —— 它同时明写了要 D3D 设备。
   把两者统一起来的机制是：管理器内部会拿这个 `IUnknown*` 去 **QI `IDXGIDevice`**，
   而 `ID3D11Device` **本来就能 QI 出 `IDXGIDevice`** ⇒ **两种传法都能 `S_OK`**。
   ⇒ 这也解释了为什么"传错"这件事**所有用例都发现不了**：返回值根本不区分。
   **它不构成"零拷贝名存实亡"的已证真因**，只是"按参数表那一句该给 DXGI 那一层"。
   ⚠️ 另有一条与排障有关的原文："If this method succeeds, **all open device handles become invalid**."
   ⇒ 每调一次 `ResetDevice`，之前 `OpenDeviceHandle` 拿到的句柄全部作废。

9. 🔥 **"零拷贝成立"不能用 `ResetDevice` 的 `S_OK` 代替 —— 要开一次句柄才算数。**
   本批新增 `D3D11GpuContext.DeviceHandleVerified`：建完设备管理器后**真的调一次
   `IMFDXGIDeviceManager::OpenDeviceHandle`**，开出来就立刻关掉（探针，不留）。
   它是**唯一**能把「`ResetDevice` 回了 `S_OK`」与「管理器手上真有一块能 QI 的设备」
   分开的动作。本机实测 **通过**。
   ⚠️ 因此 `Describe()` 里那两格**必须分开写**：`D3D 设备管理器 已挂上`（消息编进去了）
   ≠ `设备句柄自检 通过`（链路真的通）。合并成一句"零拷贝成立"，
   就等于把"消息发出去了"当成"链路通了"。

10. 🔴 **`IMFDXGIDeviceManager::OpenDeviceHandle` 的 `HANDLE` 在 x64 上是 8 字节**
    ⇒ 委托里是 `out IntPtr`，写成 `out int` 会把高 4 字节留给栈上的垃圾，
    拿到一个"看着像句柄、其实不是"的数。

11. 🔴🔴 **MF 官方文档对 D3D11 设备有两条 "should" 级要求**（`IMFDXGIDeviceManager::ResetDevice`
    的 Remarks 逐字核实）：
    ① 设备 **should** 带 `D3D11_CREATE_DEVICE_VIDEO_SUPPORT`（`0x800`）创建；
    ② **recommended** 在设备上下文上开多线程保护（`ID3D11Device` 上 QI `ID3D10Multithread`
    再 `SetMultithreadProtected(true)`）。
    ⇒ 本实现**两条都补上了**。**真机实测二者对本例的失败"逐字节无影响"** ——
    但都是文档明写的硬要求，属于"现在不加，换个驱动/机型就出问题"那一类。
    ⚠️ `D3D11_CREATE_DEVICE_VIDEO_SUPPORT` 有**不显眼的副作用**：驱动没实现到 WDDM 1.2 时
    它会强制"只允许 9.x 特性级别"，请求 10 以上**直接创建失败** ⇒ 必须**先带它试、失败退回**，
    并把"退回过"记下来。
    ⚠️ `ID3D10Multithread` 是 **D3D10 的接口**（`d3d10.h:5687`）—— 从 D3D11 设备上 QI 它
    **不是笔误，是官方文档的做法**；换成 `ID3D11Multithread`（`d3d11_4.h`）就要求 Windows 10 运行时。
    槽位 `Enter = 3` / `Leave = 4` / **`SetMultithreadProtected = 5`** / `GetMultithreadProtected = 6`；
    参数是 **4 字节 `BOOL` 不是 `bool`**，且该调用**没有返回值可查**。

12. 🔴 **`MF_TRANSFORM_ASYNC_UNLOCK` 有"两半"**：只在 `activate` 上设不够，
    **还要在 transform 自己的属性仓（`GetAttributes`）上再设一次**。
    漏了第二半的症状是 **`MF_E_TRANSFORM_ASYNC_LOCKED`（`0xC00D6D77`）**，
    而且它是在**后面某一次调用**才报出来，看起来像"那个函数不支持"。
    顺序硬要求：必须在 `ActivateObject` **之前**写在 activate 上；
    错了的报应就是 `ActivateObject` 回 `MF_E_TRANSFORM_ASYNC_LOCKED`，
    而那条错误信息**不会告诉你"要去设这个属性"**。

13. 🔴🔴 **测试驱动异步编码器必须给它真实的时间。**
    异步编码器只在"消化完上一帧"之后才补发下一个 `METransformNeedInput`。
    全速转的话 180 次调用在几十微秒内跑完，编码器连一帧都没编完
    ⇒ **实测只喂进去 5 帧（180 次机会里）**。
    生产的取帧循环本来就是 30 fps（帧间 33 ms）⇒ 必须把那份时间也给它，
    否则测的不是编码器，而是"我们的循环有多快"。
    ⇒ 本批改成**按帧数算时间预算**（每帧 200 ms，比生产宽 6 倍）+ `Thread.Sleep(1)`，
    断言信息里带出"给了多少毫秒"。

14. 🔴 **同步解码器的 `Drain` 必须"取到取不出为止"，且上限要给足。**
    `MFT_MESSAGE_COMMAND_DRAIN` 对**同步** MFT **允许返回 `E_NOTIMPL`**
    （它本来是为异步 MFT 设计的）⇒ **不看它的返回值**，真正把尾巴挤出来的是循环。
    早先写"8 轮 × 每轮最多 4 帧"看起来够，但**第一轮返回 0 就 `break` 了**
    ⇒ 尾巴一帧没挤出，**30 帧进、22 帧出**，差的 8 帧被静默吞掉。改成 64 轮后 **30 进 / 30 出**。
    ⇒ 那 8 帧**不是码流的问题，是验证代码没取干净** ——
    而"少几帧"会让"解出来多少帧"不再是"码流好不好"的证据。

15. 🔴 **`IMFMediaBuffer::SetCurrentLength` 是喂解码器时最容易漏的一格**：
    `Lock` 只给容量，不设长度 ⇒ `GetCurrentLength` 回 0 ⇒ 解码器收到「零字节样本」
    ⇒ **不报错、也不出帧**。

16. 🔴🔴🔴 **`MFSetAttributeSize` 的打包顺序：宽度在"高 32 位"，而不是低 32 位 —— 且形参名会骗人。**
    `mfapi.h` 逐字（`:799–803, 836`）：
    ```c
    inline UINT64 Pack2UINT32AsUINT64 (UINT32 uh, UINT32 ul) { return (((UINT64) uh) << 32) | ul; }
    inline UINT64 PackSize (UINT32 uw, UINT32 uh) { return Pack2UINT32AsUINT64 (uw, uh); }
    inline HRESULT MFSetAttributeSize (…, UINT32 uw, UINT32 uh) { … MFSetAttribute2UINT32asUINT64 (…, uw, uh); }
    ```
    ⇒ `MFSetAttributeSize` 把 **width 当第一个实参**传进 `Pack2UINT32AsUINT64`，
    而那个函数的第一个形参叫 **`uh`（高位）** ⇒ **width 落在高 32 位、height 落在低 32 位**。
    `PackRatio` / `MFSetAttributeRatio` 同理（**分子在高位**）。
    🔴 **这条踩过一次，代价是"码流大 4 万倍、且一个错都不报"**：
    某个测试文件**自己又写了一份** `Pack(uint low, uint high)`
    （**形参语序与平台层那个正好相反**），然后按"宽度、高度"的语序老实调用 ——
    编译通过、运行没有错误码，而 `MF_MT_FRAME_SIZE` 被设成了**转置的**尺寸
    （640×480 变成 480×640）、`MF_MT_FRAME_RATE` 被设成了 **1/30**。
    症状：喂进去的 NV12 是按 640 的跨度排的、编码器按 480 的跨度去读
    ⇒ 内容变成**跨行噪声** ⇒ 帧大得离谱。
    实测对照（同一个探针，只改打包）：

    | | 打包反了 | 修正后 |
    |---|---|---|
    | 640×480，5 帧合计 | **37,115,145 B** | **882 B** |
    | 首帧 | 87,305 B | **450 B** |
    | 样本缓冲容量 `Lock.max` | 16,666,000 B | **555,000 B** |

    ⇒ **约 41,000 倍的差距，而两边都没有任何错误码。**
    ⇒ 规矩：**打包只留一处实现，不许在别处再写一份**；而且**判"数字对不对"不能靠推理** ——
    那一节里的 `Lock.max` 一并打出来，正是它把"尺寸转置"当场坐实的
    （缓冲池是按帧尺寸分配的，转置之后容量直接差 30 倍）。

## 4. 🔸 本批**不实现但必须先记下来**的一条协议变更

MJPEG 是"每帧一张独立图"，所以现有帧头**没有任何 GOP 概念**。换成 H.264/HEVC 后，前端
WebCodecs 的 `VideoDecoder.configure()` 需要两样现在**没有**的东西：

| 缺什么 | 为什么需要 | 落在哪 |
|---|---|---|
| **关键帧标记**（`IsKeyframe`） | 丢帧 / 新观众加入后的**恢复起点**；解码器必须从关键帧开始 | `RemoteStreamFrameHeader` 加一个 bool |

是"没有它前端根本解不了"。写在这里，避免下一批又从头推一遍。

**关于"本机 QSV 到底能不能编"的孤立判据（探针）**

`MfMemoryModeEncodeProbeTests` 是**刻意保留**的诊断工具，不是临时文件。
它跑同一个 MFT 但**完全不走 D3D**（内存样本、不发 `SET_D3D_MANAGER`），
用来把「我们的 D3D 接线错了」与「这个 MFT 在这台机器上根本不出货」分开 ——
**生产路径里这两件事的症状逐字节一样**。本机实测 4 格全过
（640×480 与 2160×1440 各 2 个 MFT 实例）。
⚠️ 它的字节数**不要拿去和生产比**：它刻意不配码率控制，喂的也是"沿 y 恒定"的合成条带。

引擎数结论要按 §3.4/§16.1 的方法在目标机型上重标）。

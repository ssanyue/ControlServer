# M7.9 移除隐私屏 · 远程画面网页全屏（2026-10-19）

> 一句话：**把"遮住现场那块屏"的能力整体下线，换成"把画面放大到整块屏幕看"**。
> 前者改的是**别人机器上的可见状态**，后者改的是**你这台机器上的显示方式** ——
> 后者的风险面小一个量级，而它解决的痛点是同一个动作里更常见的那个。

---

## 1. 为什么移除隐私屏

不是"不好用"，是**它的成立条件太苛刻，而失败形态又无法被现场分辨**：

| 事实 | 后果 |
|------|------|
| 依赖 `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)`，**Windows 10 2004（19041）起才有** | 旧机器只能**拒绝**；降级（不排除抓屏）= 远方也黑 = 把远控一起关掉 |
| 遮挡层是"那台机器上的一个窗口"，会被显示器插拔 / 托盘重启 / 进程退出带走，**且不发通知** | 状态必须由被控端每秒上报；中心一旦拿"上次点了什么"当状态就会长期显示"已遮住"而现场看得见 |
| 它改变的是**那台机器上的人能看见什么** | 归进授权闸门（Gated）；越权语义比"看画面"重一档 |
| 现场判断"到底遮没遮"只能靠人眼看 | 自动化只能证到"被控端说它在遮 + 这条流没被遮"，最后一步永远验不了 |

⇒ 结论：**留着一个"看起来能用、失败时只能拒绝"的功能，比没有它更贵**。
产品侧的替代路径是"把画面看清楚"（全屏 + 1:1），那条路不碰别人的机器。

## 3. 新增：网页全屏

### 3.1 全屏的是"画面那一块"，不是整页

页面上还有工具栏、读数、剪贴板。全屏整页等于把一堆排障数字放大到投影上，
而用户要的是**看那台机器的屏幕** ⇒ `requestFullscreen` 打在 `.rd-viewport` 上。

### 3.2 三件容易做错的事（都在 `web/src/fullscreen.ts`，24 条单测钉住）

| 坑 | 表现 | 本仓的做法 |
|----|------|-----------|
| 全屏必须由**用户手势的同一个任务**发起 | 先 `await` 一次接口再请求 ⇒ Chrome 抛 `NotAllowedError`，页面看起来"点了没反应" | `toggleFullscreen()` 在**第一个 await 之前**就把请求发出去；这条写进了函数注释，改的人能看见 |
| 退出**不经过我们的按钮** | 用户按 Esc，浏览器自己退了，只补一个 `fullscreenchange` | 状态**只从 `document.fullscreenElement` 读**；本地布尔从不作为真源 |
| 老 WebKit 只有前缀属性 | 只读 `fullscreenElement` ⇒ 按钮永远显示「全屏显示」，点第二下还得再退一次 | `fullscreenElementOf` / `exitFullscreen` / `enterFullscreen` **两套都认** |

### 3.3 全屏之后必须重报视口（ROI）

🔥 这是本轮唯一"不重报就出 bug"的地方：`1:1 原始像素` 模式下被控端**只编当前视口那一块**。
全屏之后可视区变大 ⇒ 新露出来的那一大片**根本不在码流里**，表现是"上/下/左/右一条永远停在旧帧"，
而且不报错。所以 `fullscreenchange` 里第一件事就是 `scheduleViewportReport()`（走原来那个 300 ms 去抖）。

### 3.4 退出路径要收干净

| 时机 | 处理 | 理由 |
|------|------|------|
| 点「退出全屏」（提示条里） | `exitFullscreen(document)` | 提示条留在**被全屏的元素里面** —— 放外面的话一进全屏它就不见了 |
| 「停止观看」/ 切会话 / 换屏 | `teardownViewer()` 开头 `leaveFullscreen()` | 后面会把画布清成 `0×0`，留在全屏里就是"整块屏幕一片黑且退不出去" |
| 组件卸载（切页签） | `onUnmounted` 里 `leaveFullscreen()` + 摘监听 | 否则页签走了，屏幕还被一块没人画的 canvas 占着 |

### 3.5 不支持时说什么

`fullscreenSupported` 只在 `document.fullscreenEnabled === false` 时为 false
（WebKit 上它是 `undefined`，**不能**当不支持）。不支持时按钮画灰 + `title` 说明"换 Edge / Chrome"，
而不是"能点但没反应" —— 后者会让人反复点，并把账记到远控头上。

## 5. 现场要注意的一件事

🔴 托盘与中心**必须一起升**。原因不是协议不兼容（旧的 `privacy` 动作在新客户端上会落到
"不认识的远控动作"并如实回报），而是**旧页面 + 新中心**时那个按钮会 404 ——
所以页面产物也要跟着重发（`dotnet build Server` 会把 `wwwroot` 一起嵌进去）。

## 6. 打安装包时踩到的那个坑（已解决，留作处置手册）

第一次重打失败，报的是：

```
error MSB4018: "GenerateBundle" 任务意外失败
  System.UnauthorizedAccessException: Access to the path
  'D:\Project\zhongkong\dist\agent\ControlServer.Agent.Service.exe' is denied.
    at Microsoft.Win32.SafeHandles.SafeFileHandle.CreateFile(...)
    at Microsoft.NET.HostModel.MachOUtils.AdjustHeadersForBundle(String filePath)
```

### 6.1 它**不是**文件被占用，也**不是**目录不可写

两个反证：

- 同一目录里 `dotnet publish` **新建**这个 exe 是成功的（37 MB 完整落盘）；
- 只有紧接着那一步 —— `HostWriter.SetAsBundle` → `AdjustHeadersForBundle` ——
  用 `FileStream(..., FileMode.Open, FileAccess.ReadWrite)` / `MemoryMappedFile`
  把 exe **自己再打开一次**做原地回填时才被拒。

⇒ 这是"对**已存在的可执行文件**做原地写"被策略挡住，**不是**磁盘、不是占用、
也不是 `Remove-Item` 没删干净（目录确实被清空了，不然连新建都不会成功）。

### 6.2 判据（怎么一眼分清是"占用"还是"策略"）

| 现象 | 结论 |
|---|---|
| `Stop-Process` 报"拒绝访问"、进程树里能看见同名 exe | 文件**被占用**（先停进程） |
| 目录是空的、新建能成、只有收尾那一步失败 | **策略**（换输出目录，见下） |
| 报 `MSB3027 / MSB3021` | 占用（锁的是输出目录里的 dll） |
| 报 `MSB4018 + UnauthorizedAccessException + AdjustHeadersForBundle` | 策略（就是本例） |

### 6.3 修法：脚本新增 `-PayloadDir`

`build-agent-installer.ps1` 现在支持把"两个 exe 从哪来"指到别处（**默认值不变**，
还是 `dist\agent`）；`.iss` 里对应换成 `#define PayloadDir`，由 `/DPayloadDir` 覆盖。

```powershell
# ① 先发布到一个能原地写的目录
powershell -File deploy\windows\build-agent.ps1 -OutputDir D:\Project\zhongkong\.build\agent-payload

# ② 复用那份产物编译安装包（默认投放 %ProgramData%\ControlServer\downloads）
powershell -File deploy\windows\build-agent-installer.ps1 `
    -SkipPayloadBuild -PayloadDir D:\Project\zhongkong\.build\agent-payload
```

⚠️ `-PayloadDir` 只在**显式传**时才覆盖 `.iss` 的默认值 —— 默认路径仍由 `.iss`
自己按相对位置算，整个仓库挪盘也不会错。

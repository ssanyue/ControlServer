# M7.6 · 远控黑屏的真正成因：被控端息屏（2026-10-19）

> **一句话**：不是抓屏坏了、不是编码器坏了、不是链路坏了 —— 是**那台机器自己把屏幕关掉了**。
> 现场那一句「客户端电脑有画面变动时会恢复正常显示」，把前三轮的所有猜测一次性排除掉了。

---

## 0. 结论先行

| 现象 | 真因 | 决定性证据 |
|---|---|---|
| **画面全黑** | 被控端已**关闭显示器 / 进入黑屏屏保 / 睡眠** | 4K 的 IDR 只有 **2.4 KB**；同一套代码在本机同分辨率的 IDR 是 **101 KB** |
| **被控端一动就恢复** | 真实输入唤醒了显示 / 退出了屏保 | 用户现场观察 |
| 帧率掉到 **1 fps** | 静止退避（`RemoteStreamPacing`）＋ 屏幕上只剩极小变化 | 单帧 **3.4 KB**、累计 1.2 MB / 19 帧 |
| `被控端实测帧率` / `桌面静止` 显示 **—** | 被控端状态上报没到中心（旧客户端 / 上报通道断了） | 中心侧 `stats` 有数，`agentStats` 为 null |

**关键区分**：`3.4 KB` 的帧不是"没有画面"，而是"画面**有**，但内容是一整片纯色"——
DDA 在息屏时**并不失败**，它照样交付帧，交付的是黑。这就是为什么
**帧在流、码率正常、两端日志干干净净**，而人看到的是一块黑。

---

## 1. 为什么这一轮才定死（前两轮错在哪）

### 1.1 上一轮（M7.5 §0）的结论①是错的

M7.5 写的是"**被控端桌面本身就是一片纯黑且完全不动**"，并把三种成因
（锁屏 / 显示器关 / 全屏黑窗口）并列，说"远程无法再细分"。

**那个并列里有一条可以直接排除**：

> **锁屏解释不了"一动就好"。** 锁屏（安全桌面）不会因为你碰一下鼠标就解锁。

所以剩下的只有两种：显示器被关（DPMS）/ 黑屏屏保 / 全屏黑窗口。
而"黑屏屏保"与"关闭显示器"有一个共同点：**它们都由系统的空闲计时器触发**，
于是都会表现出"静置一段时间后变黑、有输入就恢复"。

⇒ 这一轮不需要任何新探测就能定性，**缺的只是用户那一句现象描述**。

### 1.2 上一轮已经拿到、但没被用上的那条硬数据

| | 分辨率 | IDR 字节 | 每像素字节 |
|---|---|---|---|
| 本机（正常桌面） | 2160×1440 | **101 341** | 0.0326 |
| 被控端（现场那片黑） | 3840×2160 | **2 457** | **0.0003** |

差 **100 倍**。H.264 的 IDR 是"整幅画面的独立编码"，只有**一整片纯色**
才可能用 0.0003 字节/像素编出来。这条数据当时被读成了"桌面本身是黑的"，
而正确的读法是：**"被控端交给我们的确实是一整片纯色"** —— 这两句话的后续动作完全不同：
前者是"没办法"，后者是"去找它为什么会变纯色"。

## 2. 修复

### 2.1 被控端：推流期间不让自己息屏（根治）

新增 `IDisplayWakeLock`（`Platform.Abstractions`）＋ `WindowsDisplayWakeLock`（`Platform.Windows`），
由托盘注入 `RemoteStreamHost`，**会话期间持有、结束即释放**。

用 `SetThreadExecutionState(ES_CONTINUOUS | ES_DISPLAY_REQUIRED | ES_SYSTEM_REQUIRED)`
同时挡住三件事：关显示器、屏保、睡眠。

**三个必须写进代码的坑**：

| 坑 | 后果 | 处置 |
|---|---|---|
| `ES_CONTINUOUS` 是**线程级**状态 | 随便找个池线程调一次，线程一退出锁就**静默消失**，而 `Acquire()` 早就返回了 true | 起一个**只为这件事活着**的线程，申请成功后阻塞在事件上不退出；`IsHeld` 判"线程还活着"，不判"我们申请过" |
| Session 0（服务）里调用**会假装成功** | 那条路上这条能力变成一句永远为真的谎话 | `IsSupported` 直接按 SessionId 拒绝并说明；托盘在用户会话里才有桌面（铁律 14） |
| 只预防不点亮 = 对着已经黑的屏做无用功 | 用户连上来第一眼还是黑 | `Acquire` 里先广播一次 `SC_MONITORPOWER(-1)` |

⚠️ **点亮对"屏保"无效**：屏保按设计不接受模拟输入，只认真实输入。
所以 `Acquire` 的说明里必须带上"点亮有没有成功"，不能一句"已阻止息屏"糊过去。

⚠️ **代价**：持有期间被控端显示器**不会自动关闭**。一台展厅机器被远程挂一整晚就是亮一整晚——
这是这个能力的固有成本，所以它必须能被关掉（`RemoteStreamHost` 的 `displayWakeLock` 可为 `null`），
而不是写死进推流循环。

### 2.2 页面：纯色必须被说出来

新增 `web/src/blankFrame.ts`：按**每像素字节数**判"这一帧几乎是纯色"。

- 为什么不是"小于多少 KB"：绝对字节数依赖分辨率，同一个纯色画面 1080p 约 1 KB、8K 能到 10 KB，
  写死阈值会在高分辨率上把正常画面判成纯色。
- 阈值 `0.002`：离实测的正常桌面（0.0326）有 **15 倍**余量，离那片黑（0.0003）有 **6 倍**余量。
- 只在**关键帧**上算（P 帧本来就小，拿它算会把每一帧都判成纯色），且只在**单块**时算。

🔴 **文案必须同时给出两种解释**：

> 这一帧几乎是纯色。如果现场那块屏是亮的，那它只是纯色壁纸 / 全屏单色窗口，不用管；
> 如果现场那块屏是黑的 —— 这台机器已经关闭显示器或正在跑黑屏屏保，在被控端动一下鼠标就会恢复。

只写"你一定息屏了"，会在"人家壁纸就是纯色"的机器上变成甩不掉的假告警；
而假告警的代价是真告警被忽略。

   必须有人过去动一下鼠标（或现场关掉屏保）。

## 4. 现场还需要做的事

1. **装新客户端**：`dist/agent-setup/ControlServer-Agent-Setup-0.1.0.exe`。
   旧版没有唤醒锁，装完之后**静置不会自己变黑**。
2. **第一次连上如果还是黑的** —— 在被控端动一下鼠标。那是屏保，不是我们没生效。
3. **建议顺手改电源计划**（展厅 / 无人值守机器本来就该这样）：
   ```powershell
   powercfg /change monitor-timeout-ac 0
   powercfg /change standby-timeout-ac 0
   ```
   屏保：`设置 → 个性化 → 锁屏界面 → 屏幕保护程序 → 无`。
4. **`被控端实测帧率` 与 `桌面静止` 显示 `—` 是另一个缺陷**：
   中心侧计数有数、被控端那份没有 ⇒ 状态上报没到。它让"桌面到底有没有变化"
   这个最关键的诊断指标在页面上完全看不见。见 §5。

## 5. 挂账

- **被控端状态上报断了**（`agentStats` 恒为 null）：在页面上表现为两格 `—`。
  需要按"旧客户端 vs 上报通道断了"分开查 —— 判据是客户端版本号与心跳。
- **息屏/锁屏状态应当主动上报**，而不是靠前端从码流大小反推
  （`OpenInputDesktop()` 失败 ⇒ 已锁屏；这比 bpp 启发式硬得多）。
- **`4K 吞吐`**（M7.5 §5）仍未拍板；本轮与它无关。
- 上一轮挂账的「唤醒显示器 `SC_MONITORPOWER`」**本轮已做进 `Acquire`**，
  但**只在会话开始时点一次**，没有做"持续重试"。

# M7.7 · 4K 只显示四分之一、多屏切换（2026-10-19）

> **现场反馈**：「部分客户机访问远程是无法正确显示 4K 画面（仅显示四分之一），
> 多屏状态下未提供屏幕切换功能」
>
> 上一份：`M7.5-远控黑屏与连不上.md`（黑屏／连不上）、`M7.6-息屏导致的远控黑屏.md`（一静止就黑）。

## §0 结论先行

| 报的现象 | 实际情况 | 处置 |
|---|---|---|
| **4K 只显示四分之一** | 「四分之一」在几何上只有一种含义：**宽高都只有该占的一半**。它既可能是**编码端**把整幅缩了一半再编，也可能是**解码端**只解出了左上那块 —— 两种的下一步动作相反，而原来的页面**两种都不说** | ① 绘制**恒按区域铺满**（拿掉"静静缩在左上角"这个默认行为）；② 面板新增**解码尺寸**一格 ＋ 对不上时一句话写明两个数；③ `VideoDecoder.configure()` **补上 `codedWidth/codedHeight`** |
| **多屏没有屏幕切换** | 代码里**早就有**（`GET /api/remote/screens/{id}` ＋ 面板上的「抓哪块屏」下拉 ＋ 建会话时传 `screenId`）。真正缺的是两件事：**它没进到你正在用的那个进程**（服务端内嵌 wwwroot，改前端必须重编 Server）；以及**会话运行中改屏不生效**（`screenId` 只在建会话那一刻下发） | ① 运行中给一个**显式的「切到这块屏」按钮**（＝停旧会话、按新屏重建）；② 提示"会中断几秒"，不做成"改下拉框就自动重连" |

## §1 「四分之一」到底是什么

### 1.1 先把几何说死

画布 3840×2160，画面只落在左上那块 1920×1080 的区域 —— 面积正好 1/4。
能产生这个结果的路径**只有一条**：**画出来的矩形比它该占的区域小一半（宽高各半）**。

产生"矩形小一半"的原因有两类，**表现完全相同、修法完全相反**：

| 哪一端缩了 | 帧内容的语义 | 正确处置 |
|---|---|---|
| **编码端**把整幅缩放成一半再编 | 内容仍然是**整屏**，只是分辨率低 | 铺满区域（糊，但看得到全部） |
| **解码端**只解出了左上那一块 | 内容**不是**整屏，剩下 3/4 根本不在码流里 | 铺满只会把"看得见的一角"放大 ⇒ **必须如实说出来** |

⇒ 所以这一轮**没有去猜是哪一端**，而是先让页面**必须把两个数摆出来**。

### 1.2 为什么"部分客户机"

这个限定本身是一条判据：**同一台被控端、同一份码流，换个观看端就好/坏** ⇒ 差异在观看端。
而观看端上唯一会因为机器不同而不同的环节是**解码器**：

- 软件解码（FFmpeg / OpenH264）：按 SPS 里的真实尺寸解，**不看**任何默认上限；
- 硬件解码（D3D11 / Media Foundation / VideoToolbox）：**会按自己的能力和默认值分配解码表面**。

`VideoDecoderConfig.codedWidth/codedHeight` 在 WebCodecs 里是**可选**的。不传时，
部分硬件解码路径会按一个默认上限（常见就是 1920×1080）分配表面 ——
4K 码流于是只解出左上那一块，**既不报错、也不掉帧、`decodeErrors` 还是 0**。

> ⚠️ **这是本文件里唯一一条「假设」，不是已证实的结论。**
> 它解释了"部分客户机"这个分布，且修法（把真实尺寸告诉解码器）在正常机器上**零副作用**，
> 所以先补上。真正定性要靠 §2.2 新加的那个读数 —— 下一张现场截图就能定案。

### 1.3 被排除掉的几种可能

| 怀疑 | 为什么排除 |
|---|---|
| DPI 缩放（200% 下拿到逻辑尺寸 1920×1080） | 托盘启动第一件事就是 `TryEnablePerMonitorV2()`（`Agent.Tray/Program.cs`），`GetMonitorInfo` 报的是物理尺寸 |
| 分块（M5.5）只画了第 0 块 | `EncodeRegionLayout.Tiles` 只按**宽度**切竖条，且 `_maxTileWidth` 默认 0（不切）；切成两条也只会"少右半边"，不是 1/4 |
| `fit` 模式的 CSS 把画布裁了一角 | `.rd-viewport.fit canvas` 是 `max-width/max-height + height:auto`，canvas 有固有宽高比 ⇒ 等比缩放，不裁切 |
| H.264 超过 4096 上限 | `TryValidateGeometry` 在**建管线之前**就拦下了 3840（上限 4096），不会走到"编了一半" |

## §2 改了什么

### 2.1 绘制：尺寸恒取**区域**，不取解码结果

`web/src/frameSize.ts`（新增，纯函数，13 条用例）

原来那一行是：

```ts
ctx.drawImage(source, geometry.x, geometry.y, size.width, size.height)
```

`size` 是**解码结果**。解码端一旦只出了半张，画面就静静缩在左上角 ——
而页面上没有任何一处会说话。现在：

```ts
const rect = pickDrawRect({ x, y, width: regionWidth, height: regionHeight }, size)
ctx.drawImage(source, rect.x, rect.y, rect.width, rect.height)
```

`regionWidth/regionHeight` 来自帧头（`header.width/height`，**这一块真正的编码尺寸**）。
单块时它等于整幅；旧被控端不带这两个字段时，兜底成"整幅 = 这一帧"，
于是**行为与从前完全等价**（不会把老客户端拉变形）。

### 2.2 让"对不上"这件事必须被说出来

面板新增一格 **解码尺寸**（对不上时标黄），并在画面上方给一句话，例如：

> 解码结果是 1920×1080，而整幅画面是 3840×2160 —— 只拿到 50%
> （宽高都只有该占的一半 ⇒ 看起来就是"只显示左上四分之一"）。
> 画面已按区域铺满，但内容本身只有这么多：要么被控端把整幅缩小后再编码，
> 要么这个浏览器只解出了左上那块。

**这句话的用法**（现场一分钟定性，不需要看日志）：

| 「画面分辨率」 | 「解码尺寸」 | 说明 |
|---|---|---|
| 3840 × 2160 | 3840 × 2160 | 正常，问题不在尺寸 |
| 3840 × 2160 | 1920 × 1080 | **解码端**缩了（浏览器/硬解） |
| 1920 × 1080 | 1920 × 1080 | **被控端**编码时就缩了（看它的屏是不是也报 1080p） |

⚠️ 比例取"更糟的那一维"，并且只缩一个方向时**不许**说成"宽高各少一半"——
那句话是现场去量尺寸的依据，编一个不存在的形变比不说更坏。

### 2.3 解码器：把真实编码尺寸告诉它

`web/src/webCodecsDecoder.ts`

```ts
const key: ConfigureKey = {
  codecString: header.codecString,
  description: header.description,
  codedWidth: header.width,     // ← 这一块，不是整幅
  codedHeight: header.height,
}
```

- 只有两个值都合法才写进 `VideoDecoderConfig`（只给一个会让某些实现按 0 处理）；
- `needsReconfigure` 把尺寸也纳入比较：换屏/换分块时 profile 与 level 可能一模一样，
  只有分辨率变了 —— 不重配的话解码器仍按旧尺寸解，画面被裁或拉伸且**不报错**。

### 2.4 多屏：运行中切屏

`web/src/components/RemoteDesktopPanel.vue`

- 新增 `screenSwitchPending`：**用户显式选了某块屏、且与当前这一路不同**时才为真。
  `screenId = null`（自动）**不算**——中心会把被控端实际挑中的那块回填进 DTO，
  拿 `null` 去比会永远显示"不同"，于是一进页面就挂着一个切换按钮。
- 新增按钮「切到这块屏」＋一句提示：**会重建会话，画面中断几秒**。
  不做成"改下拉框就自动重连"——那样用户会以为画面莫名断了。
- `startSession` 现在会**先收掉正在看的那一路**再建新的：

  ```
  先 teardownViewer()（退 Hub 组、释放输入、清视口）
  → 再 API 停旧会话（404 吞掉：它已经自己结束了）
  → 再建新会话
  ```

  不先停的话，M5.1「只允许一路」会让中心直接返 409，
  页面显示"那台机器正忙"——看起来就像"切换功能坏了"。

  ⚠️ 顺序不能反：先停旧的再退 Hub 组，会有一小段"中心已停、页面还在收"的空窗，
  那些帧会被当成异常全丢掉，而它们和"真的断流"长得一模一样。

### 2.5 顺手把一个会误导人的默认项说清楚

「抓哪块屏」的默认项原来写的是 `自动（多屏时取全部拼接）`。但**多屏时"自动"落到的是虚拟桌面**，
而 DXGI 一次只能抓一个 output ⇒ 硬件编码那条路会**安静回落 MJPEG**（`GpuPipelineStage.Screen`
那一级本来就是"安静回落"）。不写这句，现场会以为"多屏就该这么卡"。

现在写的是：`自动（多屏时取全部拼接 · 只能软编）`。

## §3 为什么你觉得"没有屏幕切换"

**代码里本来就有**：`GET /api/remote/screens/{agentId}`（中心，`RemoteController.Screens`）、
被控端的 `screens` 指令与 `ReportScreens` 上行、面板上的「抓哪块屏」下拉与「重读屏」按钮、
建会话时的 `screenId` —— 整条链 5 月份（M5.5）就通了。

你看到"没有"，最可能是这个：

> **服务端启动时优先读磁盘上的 `wwwroot`，磁盘上不存在才回退内嵌资源**
> （`Program.cs`：`Directory.Exists(physicalWebRoot) ? PhysicalFileProvider : ManifestEmbeddedFileProvider`）。
> `bin/Debug/net8.0` 下**从来没有 wwwroot 目录** ⇒ 一直在用**程序集里**那份页面。
> 所以**改了前端，页面上什么都不会变**。

上一轮已经踩过同一个坑（现场客户端不认识 `viewport` 指令，说明装的版本比源码旧）。

这一轮的产物已经放到 `src/ControlServer.Server/bin/Debug/net8.0/wwwroot/`
（`index-D5KvTgLC.js`）——**不用重编，重启服务端就会走磁盘那份**。
若要走内嵌（绿色版 / 单文件），才需要重编 `ControlServer.Server`。

## §4 现在要做的

1. **重启中心**（不用重编：产物已放进 `bin\Debug\net8.0\wwwroot`，启动日志会打印
   `静态资源来源：磁盘 …`）。⚠️ 正在跑的 `ControlServer.Server.exe`（11:03 启动）我没有替你停 ——
   它可能是你正在用来连现场的。
2. 打开有问题的那个客户机，看统计面板的**两格数**，按 §2.2 的表定性。
3. 多屏机器上试一次「切到这块屏」，确认画面能换过去（会有几秒黑，这是重建会话）。

  如果补了 `codedWidth` 之后「解码尺寸」仍然是 1920×1080，那问题在**被控端编码器**

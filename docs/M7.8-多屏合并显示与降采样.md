# M7.8 · 多屏合并显示画面不对（2026-10-19）

> **现场**：被控端 DESKTOP-2DFUKBT（三块 1920×1080 横排，虚拟桌面 5760×2160）
> **会话**：`123713-2fab8057`｜MJPEG｜**画面分辨率 5760×2160 / 解码尺寸 1920×720**
> **用户原话**：「多屏状态下合并显示画面不对」

## 0. 结论先行

| 你看到的 | 真因 | 证据 |
|---|---|---|
| **画面只占左上 1/9，其余全黑** | 帧头的"整幅尺寸"报了**屏幕**尺寸（5760×2160），而实际编出来只有 1920×720 ⇒ 前端画布 5760×2160、把 1920×720 画在 (0,0) | 截图两格数：5760/1920 = 2160/720 = **3** |
| **合并显示很糊** | MJPEG 主动把长边压到 1920（省 CPU）；三屏 5760 压过去后**每块屏只剩 640 像素** | `GdiJpegFrameEncoder.DefaultMaxLongEdge = 1920` |
| **页面说"尺寸也不是错的"** | 那句话本身是错的，本轮已改掉 | 见 §5 |

🔴 **它还顺带推翻了上一轮的结论。** 上一轮"部分客户机 4K 只显示四分之一"，我当时猜是"部分硬件解码器按 1080p 分配解码表面"，并加了 `codedWidth/codedHeight`。**那个猜测不是根因**（改动零副作用，保留，但不再当解释）。真正的原因是同一条：

```
3840×2160 压到 1920×1080  ⇒ 占画布的 1/4  ⇒ "只显示四分之一"
5760×2160 压到 1920×720   ⇒ 占画布的 1/9  ⇒ "合并显示画面不对"
```

**只有走 MJPEG 的机器会中招**（走 H.264 硬编是 1:1、不降采样），而"多屏拼接"和"硬编不可用的机器"**必然**走 MJPEG —— 这就解释了"部分客户机"这个分布。

| 解码尺寸 | **1920 × 720** | 实际解出来的像素 |

| 中心实测帧率 | 0 fps | 桌面静止（退避） |

画面占黑区的比例：宽 ≈ 1/3、高 ≈ 1/3 ⇒ 面积 **1/9**，贴左上角。这与 `1920/5760 = 1/3`、`720/2160 = 1/3` **完全吻合** —— 不是巧合。

## 2. 为什么"合并显示"必然走 MJPEG

顶部横幅这句话是对的（本轮只改了后半句）：

> GPU 硬编那条路**一次只抓一块屏**（DDA 只对单个 output 建 duplication），**拼接只能走 MJPEG**。

DXGI Desktop Duplication 的接口签名就是"针对一个 `IDXGIOutput` 建一个 duplication"，而"全部显示器"是 Windows 合成出来的**虚拟桌面**，它不对应任何 output。所以拼接只能回到 GDI：

- `BitBlt` 一次抓整块虚拟桌面（5760×2160）✅ 这是"画面是全的"的依据
- 然后软编 JPEG，而软编有**自己的预算**：长边 1920

**两条事实叠在一起就是这一轮的 bug**：抓的是全的，编出来是小的，而帧头说的是大的。

## 3. 根因：帧头的"整幅"该报哪个数

`RemoteStreamHost` 里原来这一句：

```csharp
var frameWidth = Width;      // 会话屏尺寸 = 5760
var frameHeight = Height;    // 2160
```

注释给的理由是：

> ⚠️ 内存路径（MJPEG）的 FrameSize 由会话自己按屏尺寸填

**这个假设在 MJPEG 引入降采样之后就不成立了。** 帧头里的三个尺寸必须是**同一个坐标系**：

| 字段 | 语义 |
|---|---|
| `frameWidth/frameHeight` | 整幅画面**在码流坐标系里**的尺寸（前端按它建画布） |
| `regionX/regionY` | 这一块在该坐标系里的左上角 |
| `width/height` | 这一块自己的像素尺寸（= 编码输出尺寸） |

一旦 `frameWidth` 用物理尺寸、`width` 用编码尺寸，前端就会把一小块画进一个大画布 —— **几何必然错，而且不报错**。

### 判据只能由"编码能力"决定

| 编码器 | 契约 | 整幅 = |
|---|---|---|
| **支持区域编码**（`IRegionSurfaceEncoder`，GPU） | `EncodeRegion` 明确 **1:1、不缩放** | 源纹理尺寸（`Width/Height`） |
| **不支持区域编码**（MJPEG 等内存路径） | 它**编的就是整幅**，但会主动降采样 | 实际编出来的尺寸（`payload.Width/Height`） |

## 4. 修法

判据抽成纯函数 `RemoteFrameExtent.Resolve`（`agents/ControlServer.Agent/Remote/RemoteFrameExtent.cs`），宿主只负责调用：

```csharp
var (frameWidth, frameHeight) = RemoteFrameExtent.Resolve(
    keepsNativeSize: surfaceEncoder is IRegionSurfaceEncoder,
    Width, Height,
    payload.Width, payload.Height);
```

退化规则（两个尺寸都可能拿不到）：**优先用另一个**。因为"声明得比内容大"会让画面缩在左上，"声明得比内容小"会把画面裁掉 —— 两个都不报错，都很难查。

配套改了四处：

1. **`RemoteSessionRegistry`**：中心会话的 `Width/Height` 跟着帧头走，注释改成"这是**码流坐标系**尺寸，不是物理桌面尺寸"，并指明要看物理尺寸请查屏清单。
2. **前端 `frameSize.ts` 新增 `describeEncodingScale`**：屏幕尺寸 vs 帧坐标系尺寸对不上时说出来（含两个数与百分比 + 出路）。用 `computed` 而非 `onFrame` 里算 —— 屏幕清单是异步到的，帧可能先到。
3. **统计格改标签**：降采样时"画面分辨率"变成"**编码分辨率**"并标黄。直说"画面分辨率 1920×720"而屏幕其实是 5760×2160，会让人以为"这台机器分辨率就这么低"。
4. **横幅文案**：删掉"尺寸也不是错的"，改成"长边会被压到 1920 再编码（省 CPU），所以合并显示是**缩略图清晰度** —— 要看 1:1 请切到单块屏"。

## 5. 那句错话为什么必须改

原文：

> 画面是**全的**（GDI 一次 BitBlt 抓整块虚拟桌面，不是半块画面、**尺寸也不是错的**）……

它想说的是"不是只抓了一块"，但写成了"尺寸没错"。而这一轮的全部问题就是**尺寸错了**。这种"页面主动给一个错结论"的代价最高：现场会照着它把排查方向整个反过来（去查显示方式、查缩放），而正确答案就在它旁边那两格数里。

## 6. 一个必须说清楚的取舍：合并 = 缩略图

修完几何之后，画面是**完整的**，但仍然是 **1920×720** —— 三块屏每块只分到 640 像素。

这不是 bug，是两条约束的交点：

- 拼接**只能**走 MJPEG（§2）
- MJPEG **必须**降采样（`DefaultMaxLongEdge = 1920`，注释写明"要看清细节的场景本就不该走 MJPEG"）

所以"多屏合并"这个功能的定位是**看全局布局**，不是看清内容。要看细节请**切到单块屏**（那一块走硬编 1:1）。

如果现场需要"合并也要能看清"，那条路是**放宽 MJPEG 长边**（例如每块屏保留 1280 ⇒ 三屏 3840 长边）。代价按像素量线性涨：1920×720 = 1.38 MPix ⇒ 3840×1440 = 5.53 MPix，**约 4 倍 CPU**。这是产品决策，本轮没动默认值。

## 0. 结论先行

| 用户说的 | 实际是什么 | 证据 | 处置 |
|---|---|---|---|
| **黑屏** | **被控端桌面本身就是一片黑**（抓屏链路完全正常） | 首帧 IDR 只有 **2.4 KB**（4K）；送 40 次鼠标移动后来了 34 帧、**1.4 KB/帧** | **现场处理**：解锁 / 开显示器 / 关掉那个全屏黑窗口 |
| **连不上 / 刚连就断** | 中心 09:18:22 把会话判死 → **没发 stop** → 被控端一直以为自己有一路在推 → **之后每次建会话都被自己拒绝** | 被控端「接收到的数据」里 4 条 `已有会话「091729-…」在推流` | **已修**（§4） |
| **帧率低（3.2 fps）** | 桌面静止 + 4K 软/硬编下限；**不是** 3.2 而是"静止退避 + 4K 吞吐" | 静止 5 秒 0 帧；持续变化下 14.6 fps | 静止退避是对的；4K 吞吐见 §5 |
| **反应特别慢** | 4K 下每帧 **68 ms**（2160×1440 基准 17.5 ms） | 10 秒实测 146 帧 | 待决策（§5） |

**页面上一句话误导了整场排查**：

> 「建会话后 20 秒内没有收到被控端的任何状态上报（最常见的原因：这台机器没人登录 / 托盘没在跑 / 客户端版本过旧不认识这条指令）。」

实测这三条**全都是错的**：机器在线、托盘在跑、指令也认得（同一分钟里音量与配置下发都执行成功了）。
真原因是"被控端坚定地拒绝了"。这句话已随 §4 的修复改掉。

### 1.1 时间线（中心日志 + 被控端回执对齐）

          中心收帧 47（用户截图那一刻）—— 平均 ≈1.2 fps
09:18:22  中心：超过 15 秒没有收到任何帧与状态 ⇒ 判死、本地关账   ← ⚠️ 没有发 stop
09:18:34  被控端：本机已有会话「091729-c6566be2」在推流 ⇒ 拒绝新会话
09:18:55  同上      09:19:18  同上      09:19:45  同上

### 1.2 决定性实验：把"抓屏坏了"与"桌面是黑的"分开

| 步骤 | 结果 |
|---|---|
| 开会话后**什么都不做**，看 5 秒 | 新增 **0 帧** |
| 主动送 **40 次鼠标移动**（4 秒） | 新增 **34 帧**、共 47 KB ⇒ **1.4 KB/帧** |
| 持续送移动 10 秒 | **146 帧（14.6 fps）**、1.8 KB/帧 |

`RemoteStreamHost` 主循环里 `surface is null`（DDA 没交付新画面）那一支是 **`continue`、一帧都不产**，
所以那 34 帧**必须是 DDA 真的交付了新表面**。抓屏链路是好的。

而 4K 的 H.264 关键帧只有 **2.4 KB** —— 这个尺寸**只可能是一片纯色**。
一块 3840×2160 的正常桌面（哪怕只有壁纸+任务栏），IDR 也在几十到几百 KB。

⇒ **被控端桌面是一片纯黑，而且完全不动。** 三个常见成因，远程无法再细分：

1. **锁屏**（DDA 对安全桌面按设计返回黑帧）；
2. **显示器被关掉 / 断了**（DPMS 或 HDMI 断开时 DDA 同样给黑）；
3. 一个**全屏黑窗口**盖在桌面上（例如业务程序崩在半黑画面上）。

## 2. 为什么"连不上"能持续十分钟（根因）

`RemoteSessionRegistry.Sweep` 判死一路会话时只做**本地关账**：

```csharp
foreach (var (sessionId, reason) in stale)
{
    Close(sessionId, reason, failed: true);   // ← 到此为止
}
return stale.Select(s => s.SessionId).ToArray();
```

而收尸人（`RemoteSessionSweeperHostedService`）**把返回值丢掉了**：

```csharp
_sessions.Sweep(BeijingTime.Now);   // ← 没有人去告诉那台机器
```

被控端那边呢？它的"只允许一路"是**拒绝新的那一路**：

```csharp
if (_active is not null)
{
    return Failed($"本机已有会话「{_active.SessionId}」在推流（M5.1 只允许一路）。");
}
```

于是形成闭环：**中心认为没有会话，被控端认为有一路**，两边都不算错，而那台机器彻底不可用。

它最后是被自己的**空闲超时**救回来的（约十分钟），这也是为什么"过一会儿又能连了"，
但那时用户早就放弃了。

> 🔥 这条故障的教训与 `REF-M5` 里的"MJPEG 回落"同源：
> **"我这边处理完了"不等于"对面知道了"**，跨进程/跨机做的每一件事都要问一句
> *对面怎么知道？* 不知道的话，它一定会以"僵尸状态"的形式回来。

## 3. 第二个坑：被控端明明回了话，中心却说"没人登录"

被控端在 09:18:34 就给出了明确结论（`已有会话在推流`），但那条结论只进了**客户端本地的
「接收到的数据」环形缓冲**，没有上报中心 —— `StartAsync` 那个分支 `return Failed(...)` 之前
**没有 `ReportAsync`**。

中心收不到任何状态，就在 20 秒后用自己的超时文案盖过去了。
一句话指错了三个方向（没人登录 / 托盘没跑 / 版本旧），现场按那句话去查，一个都查不到。

修正后的判据：**本机拒绝的每一条 start，都必须把"为什么拒绝"报给中心。**

## 4. 修复

| # | 位置 | 改了什么 | 为什么这样改 |
|---|---|---|---|
| 1 | `RemoteSessionRegistry.Sweep` | 返回值从 `string[]` 变成 `SweptSession[]`（**带 `AgentId` + `Reason`**） | 收尸人需要机器 Id 才发得出 stop |
| 2 | `RemoteSessionSweeperHostedService` | 判死后**逐条补发 stop**（`RemoteSessionService.StopOrphanedAsync`） | 从源头掐断"中心摘账、机器还在推" |
| 3 | `RemoteSessionService.StopOrphanedAsync`（新增） | 尽力而为、**绝不抛**；机器离线也只记一行 | 后台循环里不许因为一条 stop 让整轮巡检失败 |
| 4 | `RemoteSessionAdmission`（新增，纯判据） | 没在推 → `Start`；**同 id → `Duplicate`**；**不同 id → `SupersedeAndStart`** | 兜住"stop 又没送到"：以中心为准，停旧起新 |
| 5 | `RemoteSessionCoordinator.StartAsync` | 按上面判据：同 id 幂等；不同 id **先停旧的再起新的**；拒绝时**必须 `ReportAsync`** | 让这台机器永远不需要"重启托盘"才能恢复 |

**为什么"不同 id 就该接管"是安全的**：中心对每台机器**也只允许一路**
（`RemoteSessionRegistry` 的 `SessionBusy`），所以一个不同 id 的 start 能到达被控端，
唯一的解释就是**中心已经把旧那一路关账了**。接管不会让任何一路多跑 —— 旧的**先停**才起新的。

**为什么同 id 不许重建**：中心重连后可能重发同一条 start，重建会把刚建好的抓屏器 / 硬编 MFT
拆掉重来，用户看到的是"画面黑一下、再等首帧"。

新增用例：`RemoteSessionAdmissionTests`（5 条）、`RemoteSessionSweepTests.F_…`（1 条）。

## 5. 4K 的真实吞吐（待决策）

同一台机器、同一套代码：

| 分辨率 | 目标 | 实测 | 每帧 |
|---|---|---|---|
| 2160×1440（本机 i5-8265U / UHD 620） | 60 | **57.1 fps** | 17.5 ms |
| 3840×2160（被控端 Xeon ES / GTX 1060） | 60 | **14.6 fps** | **68 ms** |

像素只涨 2.67 倍，帧率掉到 1/4。三条路：

| 路 | 预期 | 代价 |
|---|---|---|
| `smooth` 档在超大屏上先缩到 2560 宽再编 | 每帧省 30–40 ms，够回到 30+ fps | 观看看不到原生 4K（**产品决策**） |
| 换 HEVC（被控端支持） | 码率省一半，编码耗时不省 | 浏览器要 WebCodecs HEVC，兼容性收窄 |
| 维持现状 | 4K / 15 fps | 只适合"看画面"，不适合操作 |

> ⚠️ 注意 `3.2 fps` 与 `14.6 fps` 不是一回事：前者是**桌面静止**时的退避节奏
> （软编路径 20 fps ÷ 6，硬编路径 60 ÷ 6），后者才是"画面真的在动"时的上限。

## 8. 顺带修掉的四处"假红"（测试口径）

查这件事的途中，全量里那几条 GPU 冒烟用例**连红四轮、而且每次红的用例还不一样**。
逐条查下来**没有一条是回归** —— 全是断言压在了不受控的输入上（铁律 9）。
它们的共同危害不是"红"，而是**红得有说服力**：报出来的都是"这条链子实际上没通"。

| # | 位置 | 原来的写法 | 为什么是假红 | 现在 |
|---|---|---|---|---|
| 1 | `WindowsGpuFrameEncoderSmokeTests.RunFrames` | **每轮重新抓一次**，抓不到就跳过 | DDA 是增量投递，单次等待 15 ms ⇒ 静止桌面上 40 轮 ≈ 0.6 s **必然 0 帧**，于是 `produced` 为空、报"没通"。而那一刻 `建/重建过 1 次`、设备也在 —— 链子是好的，只是没人给它画面 | 先等到第一张画面（≤2.5 s），之后**反复喂这一张**（"桌面静止"本来就是生产里最常见的一档输入）；并把"有没有画面"与"有没有码流"**分成两个字段**报（`FrameRun.Delivered` / `.Produced`） |
| 2 | `DxgiHardwareEncodeSmokeTests.CaptureOneFrame` | 试 **12 次**（≈180 ms） | 窗太窄 ⇒ 随"那一刻桌面上有没有人动鼠标"随机跳过；而且把结论硬写成 `NoDesktopUpdate`，实际多半是 `TimedOut` —— **日志在瞎猜** | 按**时间**等 2.5 s，并打印真实的 `LastAcquireOutcome` |
| 3 | `MfDecoderProbe.TryDecodeOnce` | `MF_E_NOTACCEPTING` ＋ `ProcessOutput` 取不出 ⇒ 当场判"卡住了" | 这两件事**可以同时成立**（解码器要攒够下一帧才吐第一帧），是**合法中间态**。实测同一天两次全量：一次解出 30 帧、一次报"卡住了"。而"卡住了"会把人往"码流坏了 / 编码有 bug"方向带 —— **方向是反的** | 给 **500 ms** 有界窗口，仍然没动静才判死 |
| 4 | `MfDecoderProbe.TryDecodeWith` / `TryDecode` | `frames >= 0` 当成功 | **0 帧被记成"解出 0 帧"并提前返回** —— 既不再试别的谈法，又把"解不出来"写成"解出来了，只是 0 帧" | `frames > 0` |

结果：GPU 两组 **10/10，连跑三轮都是 5 秒全绿**。

### 排错时踩到的、对现场同样成立的三条

1. **"喂 0 / 出 0" 要连"建/重建过 N 次"一起看。** 重建过、设备也在、参数集问过 ——
   说明它**没坏**，只是**没人给它画面**。只看"喂 0"就下结论等于把"没输入"当成"坏了"。
2. **同一台机器上"每次红的用例不同" ⇒ 先怀疑输入不受控 / 顺序相关**，别怀疑被测代码。
   真回归是**稳定**红的；飘忽的红几乎总是断言越界了。
3. **`After` 断言里嵌的 `Describe()`，要看它是在喂帧之前取的还是之后取的。**
   喂帧之前取的那一份计数全是 0（`喂 0 / 丢 0 / 出 0，事件 一个都没收到`）——
   拿它当"链路没通"的证据会得出**正好相反**的结论。本仓在这一点上踩过两次。

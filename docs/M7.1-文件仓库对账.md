# M7.1 文件仓库对账（库 ↔ 盘）

> 状态：**已交付**｜代码 `Core/Services/RepositoryGroomer.cs`｜验证 `deploy/drill/repo-reconcile.py`
> 前序：M6.5 运维收口（`--health` 是这次的落点）、M4.4 文件仓库

---

## 1. 一句话结论

`files/repo/` 与数据库会不同步，而**不同步时不报任何错**。这次补上了对账：
孤儿（盘有库无）由后台按宽限期回收，断链（库有盘无）只报警**绝不自动删记录**，
并且把它变成 `--health` 上的一行数字，让"文件悄悄丢了"这件事有人能看见。

---

## 2. 缺陷：注释承诺了一个从未存在的任务

`FileRepositoryService.DeleteAsync` 的原文（第 139-140 行）：

```csharp
// 元数据删掉了，磁盘文件删不掉也不该让请求失败 —— 否则运维会看到"删不掉"，
// 但库里其实已经没有它了（磁盘上那个孤儿文件由清理任务兜底）。
```

而全仓**没有**这个任务。本次改动之前，`FileTransferHostedService` 只做两件事：回收过期上传会话、
清理陈旧分发任务。（`grep -rn "孤儿" src/` 在改动前只命中注释，没有任何实现。）

**注释承诺了一件不存在的事，比"没有兜底"更坏**：它会让读代码的人以为那个目录有人管，
从此不再去看它。M6.5 的运维手册里已经把它记成"长期唯一失控项"，但当时只当作文档问题。

孤儿会从三条路产生：

| # | 路径 | 代码现状 |
|---|---|---|
| 1 | 删元数据成功、删磁盘文件失败（被占用 / 权限） | 只留一条 `Warn`，之后无人跟进 |
| 2 | 上传已 `Move` 进 repo、落库抛异常、回滚 `Move` 也失败 | `TryMoveBack` 只 `Warn` |
| 3 | 换机器 / 恢复备份时只带库不带 `files/`，或反过来 | 没有任何检测 |

---

## 3. 判据：三个不变量

### 3.1 🔴 宽限期 —— 它防的是一个具体竞态，不是"保守"

完成上传的顺序是：

```
File.Move(.part → repo)     ← 此刻：文件已在 repo 里
_store.AddAsync(item)        ← 此刻：库里才有记录
```

两步之间，文件**"盘上有、库里没有"** —— 与孤儿**长得一模一样**。
如果按"不在库里就删"去清理，就会删掉一个刚刚上传成功、正等着落库的文件，
用户看到的是**"上传成功但文件没了"**，而且没有任何报错。

所以判据是**文件年龄**（`mtime < now − 宽限期`），不是"这次扫描没对上"。
默认宽限期 **24 小时**（`Server:Files:OrphanGraceHours`），远大于那个毫秒级窗口。

> 用例 `Orphan_inside_grace_is_left_alone` 专门守这一条。少了它，
> 一个"看起来更激进"的实现（不在库里就删）能通过其他所有用例。

### 3.2 断链只报不删

库里有记录、盘上没有文件 ⇒ **用户的文件真的丢了**。

删掉那条记录能让 `files.lost` 变好看，代价是：
① 替用户决定"这个文件不要了"；② 让"文件丢了"这件事**从此看不见**（列表里没有、巡检也不报）。

正确动作只有一个：**报警 + 人去找备份**。所以 `LostItem` 只进报告，`Collect` 不碰它。

### 3.3 判龄一律走 UTC

`FileInfo.LastWriteTimeUtc` 与 `BeijingTime.Now.UtcDateTime` 比。
用本地时间（`LastWriteTime` / `BeijingTime.Now`）比，在**时区不是 +08:00** 的部署上会整体偏几小时：
偏早会误删、偏晚会让回收永远不触发 —— **两种都不报错**。

### 3.4 不递归、不猜

`repo/` 与 `uploads/` 本该是平铺的（`StoredName` 是服务端生成的单段名）。
出现子目录说明有人手工动过 —— 那种情况下"递归删"是最坏的选择。
对账只处理**顶层文件**，子目录记进 `UnexpectedDirectories` 只报不碰。

### 3.5 只有"无主"的 `.part` 才清

`uploads/*.part` 的判据不是"超龄"，而是**有没有会话**：

- 有会话（含仍然 open 的）⇒ 那是客户端的续传进度，**删了之后下一次续传从 0 开始且不报错**；
- 没有会话 ⇒ 恢复旧备份后的残留、或 Abort 半成功的残留，超龄后可删。

为此给 `IFileRepositoryStore` 加了 `ListSessionsAsync()`。**不能用 `ListZombieSessionsAsync`**：
它只返回"该回收的"，拿它判断"有没有主人"会得出**相反**的结论 ——
一个**活着**的会话恰好不在僵尸列表里，于是它的 `.part` 被判成无主文件删掉。

## 4. 接线

| 位置 | 动作 |
|---|---|
| `FileTransferHostedService` | 每 30 分钟一轮：先回收过期会话，**再对账**（顺序刻意：前者"删了记录但没删掉文件"的半成功，到这一步会变成无主 `.part` 从而被兜住），最后清陈旧分发任务；三者各自 try/catch |
| 日志 | 回收 → `Info`（数量 + 字节）；断链 → **`Warn`**（点名最多 5 条 + 总数）；子目录 → `Warn`；删不掉 → `Warn` 并下一轮重试 |
| `--health` | 见 §5 |
| 配置 | `Server:Files:OrphanGraceHours`（默认 24，`[Range(1, 8760)]`） |

> 断链用 `Warn` 而不是 `Info`：它意味着"仓库里列着、下载却会失败"，
> 是一件必须有人去看备份的事，不该淹没在 `Info` 里。

## 5. `--health` 的键

```
files.db.count=1       ← 库里几条记录（file_repo_items）
files.disk.count=1     ← repo/ 下几个文件
files.orphans=0        ← 盘有库无、且超龄（可回收）
files.orphan.bytes=0
files.lost=0           ← 库有盘无（要人管）
files.parts=0          ← uploads/ 下几个 .part（含正在传的）
files.stale.parts=0    ← 无主 .part（可回收）
files.grace.hours=24
```

**为什么要把它们拆出来**：原来 `--health` 只有一个 `files.count`，`--dbinfo` 也只有一个 `files.count`，
两者**其实算的是同一个数**（`DataMaintenanceCommand` 第 348 行递归枚举 `files/` 下所有文件）。
问题不在"同名不同义"，而在于**这个数回答不了"仓库健不健康"**：它把 `repo/` 与 `uploads/` 混在一起，
也不和库里的记录数对比 —— 一个 1 个文件 / 1 条记录的库，与一个 1 个文件 / 0 条记录的库，
看起来一模一样，而后者意味着有一个文件是孤儿（或者有一条记录断链）。

所以：

- `--dbinfo` 的 `files.count` / `files.bytes` **保持不变** —— `deploy/upgrade/upgrade.ps1:394`
  与 `upgrade.sh:327` 在消费它，改名会静默破坏升级验收（铁律：「配置项存在≠生效」，改键名同理）；
- `--health` 那边拆成 `files.db.count` / `files.disk.count` / `files.parts`，再加 `orphans` / `lost`。

`--health` 里对账走的是**只读 SQLite 直连**（`Mode=ReadOnly` + `Pooling=false`），不用 EF：
这条命令跑在 `WebApplication` 之前，拿不到 DI 容器；而为了它去把整条宿主编起来，
等于让"巡检"依赖"服务能被正常启动"—— 服务起不来时恰恰最需要巡检。

判据只有一份：CLI 把库里的行投影成 `RepoEntry`，调用 `RepositoryGroomer.Scan(...)`，
与后台任务是**同一个静态函数**。两套判据会各自演化，然后互相打脸。

## 7. 这份报告**不能**说明什么

1. 只验了 Windows 单文件 exe，**没验安装包 / 服务形态**（本机非管理员，`sc.exe` 被策略拦截）；
2. 只验了"启动后第一轮"，**没验连续 30 分钟一轮的节奏**（Tick 是常量，靠代码阅读保证）；
3. 宽限期的 24 小时是**判据参数**，没有等 24 小时去验证"真的不会提前删"—— 用例通过写 mtime 模拟历史；
4. 断链只在单机造出来（改文件名），**没有**验证"从备份恢复到另一台机器"的真实断链；
5. 一万条以上记录时的 `ListAsync` 全量取数**没有压测**（对账每 30 分钟一次，量级参照 M6.3 的 100 台）；
6. `repo/` 里出现**符号链接**时的行为没有验（`DirectoryInfo.GetFiles` 不跟随目录链接，但文件链接会被当普通文件）。

## 8. 挂账

- `files.lost` 目前只有"报警"这一条路，**没有**"从备份里自动找回"的辅助命令（人得自己对文件名）；
- 对账不做**内容校验**（不重算 SHA256）—— 文件大小对了但内容被改过，这一层看不出来；
- `images/`（按钮图片）**没有**做同样的对账：`ImageReferenceScanner` 只回答**正向**问题
  ——「这张图被谁引用」（用于删除前拦 409），**不能**回答「目录里哪些图已经没人引用」。
  要补就是"反向遍历目录、对每张图调一次 `FindReferrers`"。它比文件仓库好做的地方是
  没有"库↔盘"两套存储；难的地方是"没人引用"≠"可以删"（可能是刚上传、配置还没保存）。
  **同类缺口，未开工。**

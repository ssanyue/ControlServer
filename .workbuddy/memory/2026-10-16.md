## 第六批 ✅ **M5.3：声音回传 + 通道三态 + 网页安全上下文（https）**

> 承接上一批遗留的一条建议之后，用户授权口径仍是"按判断自行取默认值直接实现，
> 事后把取舍列出来复核"。本批**实际交付两件事**，第二件是被第一件逼出来的。

### ① 一条硬前提（方案文档里原本没写）

浏览器里 `AudioDecoder`（WebCodecs）与 `AudioWorklet` **只在安全上下文存在**：
局域网按 `http://192.168.x.x` 打开页面时，`window.AudioDecoder` **是 `undefined`，不是报错**
—— 整块功能**静默消失**。⚠️ **M5.4 的 `VideoDecoder` 同属 WebCodecs，受同一条约束**。

⇒ 中心**自带 https**（与 http 并存）：本地根 CA 签"本机名 + 本机 IP"的服务器证书；
`/trust/info` 给前端报端口与指纹；根证书 `GET /trust/controlserver-ca.crt`（DER）。
**两条已避开的坏做法**：① 根证书**不走 https 端口发**（还没信任时从 https 取会先撞"不安全"
警告，点多了大家就习惯性点继续，把整件事要教的东西抵消掉；根证书只有公钥，明文发无损）；
② **不放在 `/api` 之下**（可用性必须早于"已授权"，且避开 LicenseGate 分类表）。

### ② 端到端链路

托盘（Session 0 无音频端点，同 M4 结论）→ WASAPI loopback → Opus 20 ms/帧
→ **第二条管道**（托盘写、服务读）→ `PushRemoteAudio` → 中心 `AcceptAudio`
→ **独立转发队列** → Hub `Audio` → `AudioDecoder` → AudioWorklet → 扬声器。
画面侧同时从"收到就画"改成**抖动缓冲 + 按 60 ms 排期显示**（否则"现在显示的是哪一刻"没有定义）。

### ③ 八个取舍（已写进清单 §3.6，供复核）

音频**不配中心侧闸门**（与 M5.2 故意不对称）/ 新开第二条管道 / 转发队列分开（1 包 vs 50 帧）
/ 两流共用同一个目标延迟 60 ms / 音画偏差**测而不算** / 中心自带根 CA / 根证书明文匿名但不在 `/api`
/ **不做中心下发的音量**（静音只切本机）。

### ④ 顺手清掉的一处"同一个 bug 的根"

中心 `Entry.ApplyState` 两处）。抄 5 遍的规则第 6 处一定写错，而症状是
"**页面上有个看起来很合理的原因**"（如"通道就绪：本机已禁止远程输入"）——**没人会觉得那是 bug**。
⇒ 抽成唯一实现 `RemoteChannelStates.ReasonToKeep`（放 `Contracts`，被控端与中心共用），
5 处调用点全改，并补纯函数用例（当前 grep 确认 **0 处手抄**）。

### 🔥 本节最贵的三条（已写进方案 §3.4）

1. **驱动的「能力声明」和「读回的状态」都不等于「行为」。** 饱和度滤镜：`FilterCaps` 说支持、
   量程报得出 `0..1000/默认100`、`GetStreamFilter` 读回**正是我们设的值** —— 输出与"完全关掉"
   **逐字节相同**（8 个变体矩阵全试过）。⇒ **RGB 输入通路上根本不接滤镜块**。
   **没有任何 API 能发现它，只能靠读回像素证伪** ⇒ 解法＝**两趟 Blt**（第二趟在 YUV 域压饱和度）。
2. **`112` 是"色度偏离中点的最大幅度"，不是缩放系数。** 色度对拍写成
   `128 + 112×(B−Y)/1.8556` 而 `B/Y` 用 0–255 原始值 ⇒ MAE **39.02/41.68**（阈值 6）；
   改回 `128 + 224×(B′−Y′)/1.8556`（归一化 0–1）⇒ **0.06/0.04**，**实现一行没改**。
   ⚠️ 教训：**量纲错的数字症状与"色度平面错位"一模一样** ⇒ 用例额外把
   **最偏的三个样本连原始 RGB 打出来**（同向偏且正比于 `|B−Y|` ⇒ 量纲；乱跳 ⇒ 错位）。
3. **vtable 槽位错一个＝进程级崩溃。** `SetStreamAutoProcessingMode` 是 **37**，写成 **31**
   就成了 `SetStreamDestRect`（第 4 参 `const RECT*`）⇒ 把 `0/1` 当指针 ⇒ 解引用地址 1
   ⇒ `AccessViolationException` **把测试宿主进程干掉了**。这一组 `Set*` 是连着的 14 个（27–39）。

另：`RgbInput = 0b011` 把 `RGB_Range` 写成了"有限范围"而注释写"全范围"（**不报错，只是整体发闷**）；
**边缘增强默认值 44/64 非零**且作用在亮度上 ⇒ 必须显式关掉。

### 🔥 本批最贵的四条（已写进方案 §3.5）

1. **异步 MFT 的「令牌就是权限，没有令牌不许要输出」。** 原写法"一次 `TryEncode` 里连着
   `ProcessOutput` 64 次"必然在喂第一批帧**之前**先要一次；QSV 对"没东西却来要"回
   **`E_UNEXPECTED` + `NO_SAMPLE`（`dwStatus = 0x300`）**，**不是** `MF_E_TRANSFORM_NEED_MORE_INPUT`；
   更狠的是**那一次之后它再也不发 `NeedInput` 了** ⇒ 现场是"编码器建得好好的、喂 1 帧、
   然后一辈子不出货"，日志里只有一个没有任何信息量的 `0x8000FFFF`。
   ⚠️ 旧注释"不按令牌个数定次数，因为一个令牌可能对应不止一帧"——**后半句对，但它被当成了
   "可以无限次要"的理由**；正确结论是**以令牌数封顶**。
2. **`MF_E_TRANSFORM_STREAM_CHANGE` 是硬件编码器出码流前的必经一步**，
   且必须**在同一次调用里重谈并重试**（它不会因为我们答应换类型而补发 `HaveOutput`）。
3. **`GetEventType` 是 `IMFMediaEvent` 的方法，不是 `IMFMediaEventGenerator` 的** ——
   绑到发生器上（只有 **7 槽**）会读到 vtable 之后 264 字节的内存当地址 call
   ⇒ `AccessViolationException`，**整个测试宿主进程消失**。
4. **`dwStatus` 的四个值是互斥枚举不是位标志** ⇒ `0x300` 是 `NO_SAMPLE` **一个值**，
   不是 `INCOMPLETE|FORMAT_CHANGE`。判它一律用 `==`。

**定位手法本身也值一条**：把「我们的 D3D 接线错了」与「这个 MFT 在这台机器上根本不出货」
分开的唯一办法是**写个把 D3D 整个摘掉的探针**（内存样本、不发 `SET_D3D_MANAGER`）——
生产路径里这两件事的症状**逐字节一样**。没有那一步，会在 D3D 那一侧找一个不存在的错误。

⇒ 「贴 avcC 进去、码流还留 Annex-B」＝ configure 失败或花屏。两者是连体的。

### 🔴🔴 实测推翻了原来那条假设：**MF 在每个关键帧都重复 SPS**

原假设来自"30 帧里 SPS 只出现 1 次" —— 真因是那段码流**只有一个 IDR**（`GopSize = 60`），
**样本太小**。给 `DxgiHardwareEncodeSmokeTests` 加第二个强制关键帧后：

```
关键帧下标：0,15
  第 0 帧（198209 字节）：9,7,8,5     ← AUD,SPS,PPS,IDR
  第 15 帧（198209 字节）：9,7,8,5     ← SPS 也再带了一次
```

**为什么它重要**：注册写明 Annex-B 下**每个 `type:"key"` 的块必须自带全套参数集**；
而本批定的丢帧恢复是 `reset()` → 等下一个关键帧 → 重新 `configure()`。

（症状＝重连后一直花屏、两端日志正常）。⇒ 实测证明 MF 满足要求。

### 🔴 codec 串：两套规则

- **H.264**：`avc1.` / `avc3.` ＋ **SPS 载荷前 3 字节**的 6 位十六进制（字节对齐，抄就完了）。

## §8 第 5 步：指针合成（10-16 落地）

### 🔴 开工时发现方案有个没定过的分叉（§3.3.1）

§3.3 只写"**必须在 GPU 上**把指针画进 NV12"，但**没写怎么画**。核查后：
现有转换器是 `ID3D11VideoProcessor`、**固定功能**（明写"不引 HLSL / d3dcompiler"），
它**没有"在输出上再叠一层"的能力**，而**全仓没有任何 shader 基础设施** ⇒ 当时**没有可用的执行体**。
三个候选里 **C（VideoProcessor 多流）是"做不到"而不是"精度不够"**（混合单元只会 `src α over dst`，
做不了逐位 AND/XOR）⇒ 只剩 A（HLSL 渲染管线，要引本仓第一份 `d3dcompiler`）
vs B（CPU 小块合成，零新依赖、静止零代价）。**出方案 → 用户拍板 B**。

### 🔴 实施**偏离**了 §3.3.1 里 B 的描述（重要，别说成"跑了题"）

方案 B 写的是"CPU 合成 → **CPU 转 NV12** → `CopySubresourceRegion` 写回"。**实际没让 CPU 转 NV12**：

```
CPU 合成（只碰指针那一小块 BGRA，~4 KB）
  → UpdateSubresource 上传到一张 BGRA 小纹理
    → 交给**同一个** ID3D11VideoProcessor 局部 Blt（SourceRect + DestRect）→ 它就是 NV12
```

两个理由，都是"不这么写就**静默出错**"级：
1. 🔴 **CPU 自己转 NV12 = 可见贴片**：整屏那趟是 VideoProcessor 用 BT.601 有限范围系数转的
   （M5.4-a 实测 MAE 0.06）。CPU 再实现一套 ⇒ 两套系数**不可能逐位一致**，指针周围颜色肉眼可见地偏，**不报错**。
2. 🔴 **NV12 的色度平面在 D3D11 纹理里没有独立地址空间**（`Desc.Height` 只有图像高度）
   ⇒ `UpdateSubresource` + `D3D11_BOX` **写不进 NV12**（这正是 `ContextSlots.UpdateSubresource=48` 那句注释的由来）。

⇒ 与 §3.3 (a) 那句"必须在 GPU 上画进 NV12"**不矛盾**：CPU 只碰 4 KB 的 BGRA（**没有** 4K 一帧 33 MB，
不放弃零拷贝），**色彩转换与 NV12 写入仍在 GPU 上、且是同一条通路**。§3.3.1 的 B 里"CPU 转 NV12"半句作废。

1. 🔴🔴 **桌面副本是"纯指针帧"的硬前提**：DDA 只在桌面真变时才填纹理，`AccumulatedFrames==0`

2. 🔴 **`PointerUpdated` 与 `DesktopUpdated` 刻意分开**：合并后"帧率很高"与"画面一直没动"就分不开了（处置相反）。

### 🔴🔴 修掉一处**既有缺陷**：异步 MFT 输出**晚一次调用**才到

- **实测**：喂 17 帧 / 出 16 帧 ⇒ `TryEncodeSurface(surface_N)` 拿到的是**第 N−1 帧**的字节。
- **旧写法两个后果**：① 把这份字节贴上 `surface_N` 的时间戳 ⇒ **AV 整体差一帧**
  （30 fps 下 33 ms，唇音看得出）；② 把"本轮没出帧"记成一次丢帧 ⇒
  **页面报"掉了很多帧"而实际一帧没丢**。
- **修法**：门面自己 `EnqueuePendingFrame` ↔ `DequeuePendingFrame` **FIFO 配对元数据**，
  抓屏时刻由 `EncodedStreamPayload.CapturedMonoTicks` **带出来**（不让调用方在编完之后自己取）。
- 🔸 与 §3.6"把一次丢帧升级成一次掉线"**同族**：**计数错了，排查方向就反了**。

### 三分类：判据是"**喂进去没有**"，不是读失败文案

`accepted = encoder.FramesFed > fedBefore`：
`accepted && 没吐` ⇒ **正常延迟**（不计丢帧、**不要求关键帧** —— 那帧没丢，参考链上没洞；
而 4K 的 IDR 本来就贴着管道上限）；`!accepted` ⇒ 忙丢或真失败，按丢帧。
⇒ 宿主侧**调用前后各读一次 `DiscardedFrames`，增量 > 0 才算丢帧**。

### 🔥 "抓屏没有新帧"不是失败、不是丢帧、也不该收场

DDA 是**增量投递**（`CaptureSurfaceAsync` 返回 `null` ＝ 桌面与指针都没变，按约定如此）。
当成失败会同时得到两个错误结论：① `Dropped` 虚高；② **启动预算按"从没出过帧"判定
⇒ 定格在一张图上的展厅机器 30 秒后被收场**，而它完全正常。
⇒ 处置：不计失败 / 不计丢帧 / 不喂编码器 / **重置启动预算时钟**
（预算只统计"**有东西可发却发不出去**"的那段时间）。

### 🔴 挑屏的唯一出处：**门面挑，宿主搬**

内存路径（GDI）**优先虚拟桌面**（能拼）、GPU 门面**优先主屏**（DDA 一次只能抓一个 output）
—— 规则**刻意不同** ⇒ 宿主若也挑一次，多屏机上**必然挑到另一块屏**：两边都"挑对了"、
**无处报错**，症状是 **看着 A 的屏幕、实际操作 B**。
修法：`ScreenId` / `ScreenName` / `FrameSize` 上抬到 `ISurfaceFrameEncoder`；
`Prepare` 分两半（GPU 那条**不接受 `screenId` 参数**）；左上角偏移按屏号回查**无状态**的
`WindowsScreenEnumerator.Enumerate`（⚠️ 禁止拿 `CaptureSurfaceAsync` 去"试抓一帧量尺寸"
—— 门面对"不是它选的屏"会**重建整条 duplication**）；虚拟桌面请求以
`GpuPipelineStage.Screen`（环境问题）**带原因拒绝**（不拦的话 7680×4320 会先在 4096 上限上失败，
报出来是"尺寸超格式上限"，**理由给错、排查方向就反了**）。

1. **封装三件套必须自洽**：`avc3`/`hev1`＝带内（码流一字节不动、`Description=null`）；

2. **打包必须在尺寸闸门之前**（带外把 3/4 字节起始码换成**固定 4 字节**前缀，**长度会变**）。
3. **参数集从"这一帧自己的码流"里解**，`MF_MT_MPEG_SEQUENCE_HEADER`（36 B）**只做兜底**；
   解的时候**一律用带外的采样入口名**（`avc1`/`hvc1`），带内那份用 `ToInBand` 换前缀。
4. **不认得的打包方式：回落 ＋ 留痕，缺一不可**（只回落不留痕 ⇒ 中心写错 `out-of-band`

### 根因：**"空桶跳过"只做了一半**

`Bucketize` 一直"空桶跳过、不补 0"（怕画出假的"掉到底"曲线），但它**只保证没有点，不保证折线断开** ——
前后两个点被折线**直接连起来**，"被控端关机两小时"于是画成一条"这段时间一直很稳"的直线。
它比补 0 **更隐蔽**：补 0 至少看得出掉下去了。

### 判据与落点

- 判据 `max(离线判定阈值 75 s, 2 × 分桶粒度)`：前半**与在线表的灰点同源**，后半防粗粒度窗口"少一格"就断；
  ⚠️ 不能"少一格就算" —— 断线重连期间样本会攒进下一批，丢一两格是网络抖动。
- 服务端插**全 null 的断点标记**（`IsGap`），前端那套「null 必须断开折线」自然断开；
  契约新增两个**带默认值**的字段（`IsGap` / `GapThresholdSeconds`）⇒ 老夹具零改动。
- 纯函数四处：`GapThreshold` / `GapMarker` / `MarkGaps`（**幂等**、**只标两段真数据之间**、无空白**零分配**）/ `MergeLayers`。
- 前端：断点**浅底衬** + 悬停"（这段没有数据）" + 空白段说明（几段 / 起止 / 多久）——
  **光断开是沉默的**，不说用户会以为图表坏了。

### 两处最容易漏的

1. **接缝不是离线**：长窗口是"老一段日聚合 + 最近一段明细"，接缝天然隔了将近一天；
   跨接缝判会**每次查询**都在同一位置插假断点（一条随"现在几点"左右滑动的豁口）⇒ `MergeLayers` 各判各的。
2. **实时帧那条路**：详情页是"拉一段历史 + 每来一帧往前挪一格"，被控端离线十分钟后回来的第一帧
   会被直线接过去；**更糟的是点一下「刷新」它就变回空白** ⇒ 同一段时间两种画法。挪格时用同一个判据。

### ⚠️ 附带发现（**未修，挂账**）：`daily+raw` 是一条**跑不到的路**

写"接缝不判空白"的用例时发现 `rawFrom` 的三元表达式取的是 `min` 而不是 `max`：

```csharp
var rawFrom = to - span > to - rawSpan ? to - rawSpan : from;   // 恒等于 from ⇒ 日聚合是死代码
```

- **证据**：18.6 天窗口（`2026-09-28 ~ 2026-10-16`）返回 `source="raw"`、`bucketSeconds=3600`。
- **影响**：`rawSpan = 200 000 行 × 5 秒 = 11.57 天` ⇒ 7 天窗不受影响；**30 天窗被截成"最老的" 11.57 天**，
  最近 18 天在图上没有点。
- **为什么不在本轮改**：改一行会让 30 天窗取数整个变样（日聚合第一次真正上线），
  而它撞上另一个既有设计（接缝那天 `00:00 → rawFrom` **按设计就是空的**）⇒ **先定行为，再改那一行**。

### 🔴🔴 实施中撞到的三条"错了不会报错"的真问题（**这一次最值钱的部分**）

1. **vitest 在受限环境（沙箱 / 受管构建机）会「假绿」** —— 它把转换后的模块写进**系统 temp** 再 import，

   而汇总行照样写 `Test Files 3 passed` / `Tests 48 passed` / `Errors 1`。一次**假绿**。
   ⇒ **假绿比没有测试更坏**（让你以为有回归网）。修法：`pool: 'forks'` ＋ `singleFork: true`，
   `cacheDir` 放项目内。判据是"**连跑三次都 4/4 文件、58/58 用例**"。

   ⚠️ 断言**一条没动** —— 单进程是**正确性**要求，不是性能调优。
2. **`RemoteStreamOversizeTests` 里那条红是「测试自带的竞态」，不是产品缺陷** ——
   `ReadFramesAsync` 自己 `await using` 客户端、**读完 want 帧就把管道关了**，
   而后面几条断言（`IsStreaming` 仍为真 / 日志无"接收端已断开"）是在**断开之后**才读的
   ⇒ 服务端下一次写失败、**如实**记了一句断链。表现：**单独跑绿、整个程序集一起跑红**（xunit 并行改时序）。
   ⇒ 修法不是放宽断言，而是**别在断言之前把管子拔掉**：客户端提到用例里建、用例里释放
   （**两个用例都要改**：`:64` 与 `:156`）。⚠️ **本步一行 C# 生产代码都没改。**
3. **切会话必须重建 `RemoteVideoBuffer`，不能只 `clear()`** —— 缓冲里住着**按上一路格式造的解码器**，
   只 `clear()` 之后会"拿 MJPEG 的解码器去解 H.264"，而症状只是**花屏**。
   原来那条注释给的理由（"让 rAF 循环留着跑、省一帧启动延迟"）**其实不存在**：重建同样在第一帧上、
   同样立刻排期。⇒ `videoBuffer?.stop(); videoBuffer = null`。

### 四条不可回退的设计决定

1. **`maxInFlight` 由解码器回答，H.264 是不设限** —— WebCodecs 的 `VideoDecoder` 内部要缓存若干帧
   才有第一帧输出，**限深会在第一帧死锁**。
2. **`feed` 不许是 `Promise<DecodedFrame>`** —— "喂了 N 帧只出 1 帧"是**常态**不是异常。
3. **`DecodedFrame.release()` 是合同、必须幂等** —— `VideoFrame` 不会被 GC；MJPEG 那个是空操作
   但**仍然要实现**（排期层不许知道"哪种解码结果要释放"）。面板里"一帧配不上队列项就反过来释放
   `decoded`"那处是**显存泄漏点**（漏 GPU 内存，GC 不收也不报错）。
4. **`codecString` 前缀与 `description` 的有无必须自洽**（`avc3`/`hev1` 带内**不许**带；
   `avc1`/`hvc1` 带外**必须**带）⇒ 在**进解码器之前**挡掉；且**无 `codecString` 时不许手写默认串**
   （串错 ⇒ `NotSupportedError`，看起来像"浏览器不支持 H.264"）。

### 与方案预览的三处差异

### ① 速率：为什么不能直接用"相邻两次事件"

- 服务端**不推速率**（`TransferProgress` 只有 `receivedBytes` / `totalBytes` / `progressPct`）⇒ 纯前端派生。
- 🔥 **进度事件约每 8 MB 一条**（服务端 `ChunkSizeBytes`）⇒ **两点间隔本身在剧烈变化**：
  大文件在慢链路上两条事件能隔几十秒。拿"相邻两点"当瞬时速率会一会儿几百 MB/s、一会儿 0。
  ⇒ 窗口取 **20 秒**。
- 取数顺序：**滑窗**（≥2 点、跨度 ≥400 ms、有正增量）→ 否则**均值兜底** `已收字节 / (完成时刻 − 开始时刻)`。
  均值那条在小文件（只来一两条事件）时是唯一能算的；大文件在传时它也常有值，因为 `startedAt` 是服务端写的、早于第一条事件。
- 🔴 **两个真坑**：
  1. **时区**：时间戳是带 `+08:00` 的 ISO。两个 ISO 相减时偏移是常量、会**抵消** ⇒ "时长算错"**不会**出现在那条路径上；
     它只在**拿它跟 `Date.now()` 相减**时暴露（`completedAt` 缺失、用"此刻"当终点的那条路）。
     不带偏移的串按契约**补 `+08:00`**（本机 UTC+8 ⇒ 这条钉不出差别，已经在测试注释里写明白）。
  2. **数字会自己往下掉**：`completedAt` 缺失时用 `now` 当终点 —— 所以它**只在事件到达那一刻求值一次**，
     结果被 `last` **冻结**。否则传完之后分母还在涨、分子不动，速率会慢慢往下爬。
- 显示口径：`running` 强调色、`completed` 弱化成均值；`pending` / `failed` 显示 `—`；
  采不到一律 `—`，**绝不显示 `0 B/s`**（那会被读成"网络完全空闲"，而实际是"还没开始"）。

### ② 回传成功 → 刷仓库

- 只在 `state === completed && task.direction === collect` 时 `emit('collected')`（下发方向不往仓库写东西）。
- `FilesPanel` 侧 **250 ms debounce** 合并："一次回传给 N 台"会是 N 条终态事件，不该变成 N 次请求。
- 断线期间传完的漏网情形，由**两条既有**路径兜（重连时 App 调 `refresh()`、重新挂载时 `onMounted`）——**不另加机制**。

## #41 · 修掉「页面『被控端实测帧率』恒 `—`」（承接 #40 ④，10-16 深夜）

**起因**：`#40` 只定位、未修，并把它记成挂账 #59。这一轮把它修掉 + 钉回归网。

**根因（比"改一个字"深一层）**：整路会话里**只有终态那条**上报带计数。
🔥 **只把 `withCounters` 翻成 `true` 是不够的** —— 宣布"我开始推了"那一刻
`Record` 还没跑（它在这一帧送出去之后才跑）⇒ 计数**必然是 0** ⇒ 页面只是从 `—`
变成 `0 fps`，**一样是错的**。缺的不是一个数字，是**周期性**。
**它为什么不能算小事**：那格与"中心收了多少帧"是**并排看**才有意义的一对 ——
被控端发 500 / 中心收 12 ⇒ 链路上在掉（治网络）；被控端发 3 / 中心收 3 ⇒ 是被控端
编不动（治编码）。**只给一个数时这两种故障长得一模一样，而处置相反。**

**修法**（`RemoteSessionCoordinator.PumpAsync`）：起一条**推流期间每秒一次**的计数上报，
**复用** `ReportChannelStatesAsync`（与两条通道状态共用同一套字段拼装 —— 那十几个位置参数
少传一个就整体错位而编译器不报）；`RunAsync` 包进 `try/finally`，
**先取消、`await` 干净，再报终态**。
⚠️ 顺序反了 ⇒ 迟到的 `streaming` 盖在 `stopped` 之后 ⇒ 页面钉在"还在推流"且**不会自己好**。
⚠️ 中心侧另有一道**独立免疫**：`ApplyState` 里 `if (State == Requested) State = Streaming;`
（状态**只许往前**）⇒ 迟到的 streaming 复活不了已停的会话。两道都成立才是"不会发生"。
⚠️ `withCounters` 的 XML 注释一并更正（原文写"计数由终态上报给全"，与新设计不符）。
帧回调**一行未改**（新任务与它并行，不动热路径）。

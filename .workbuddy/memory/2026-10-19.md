# 2026-10-19 · M7.5 远控黑屏 / 连不上

## 现场四类症状的结论（见 `docs/M7.5-远控黑屏与连不上.md`）

1. **黑屏不是抓屏坏了** —— 被抓端桌面本身就是一片纯黑且完全不动。
   决定性实验：开会话后静止 5 秒 = 0 帧；主动送 40 次鼠标移动 = 34 帧 / 47 KB（1.4 KB/帧）。
   `surface is null` 那条路不产帧，所以那 34 帧必是 DDA 真实交付；加上 4K 的 IDR 只有 **2.4 KB**
   （正常桌面 IDR 几十~几百 KB）⇒ 桌面本身是黑的。三种成因（锁屏 / 显示器关 / 全屏黑窗口）远程无法再细分。
2. **"连不上"的真因是僵尸会话** —— `Sweep` 只本地关账、没发 stop；收尸人还把返回值丢了
   ⇒ 被控端以为仍在推 ⇒ 拒绝一切新会话，靠自己的空闲超时才恢复（实测隔了 **9 分 50 秒**）。
3. **第二个坑**：被控端回了「已有会话在推流」，但那个分支没有 `ReportAsync`，
   中心收不到状态 ⇒ 20 秒后用"没人登录 / 托盘没在跑 / 版本旧"盖过去，**三条全错**。
4. `3.2 fps` 不是性能问题，是**桌面静止的退避节奏**（20 ÷ 6）；4K 真实吞吐是 **14.6 fps / 68 ms 每帧**。

- `RemoteSessionRegistry.Sweep` → 返回 `SweptSession[]`（带 `AgentId` + `Reason`）

## 三条可迁移的排错纪律（已写进文档 §8）

1. "喂 0 / 出 0" 要连 **"建/重建过 N 次"** 一起看 —— 重建过、设备在 ⇒ 是没人给它画面，不是它坏了。
2. 同一台机器上**每次红的用例不同** ⇒ 先怀疑输入不受控 / 顺序相关，不要怀疑被测代码。
3. `After` 断言里嵌的 `Describe()`，要看它是**喂帧之前**还是之后取的 —— 之前取的全是 0，拿它当证据会得出相反的结论（已踩两次）。

# 2026-10-19（续）· M7.6 推翻上一条结论：黑屏是**被控端息屏**

## 🔴 结论修正（用户补了一句现象，前两轮全白查）

> 「客户端电脑**有画面变动时会恢复正常显示**」

这句话把 M7.5 的"三种成因并列"砍成一种，因为**锁屏解释不了"一动就好"**（安全桌面不会碰一下就解锁）。

⇒ **真因：被控端静置后按电源计划关掉了显示器（或起了黑屏屏保）**。
DDA 在息屏时**并不失败** —— 它照样交付帧，交付的是一整片黑。
所以「帧在流、码率正常、两端日志干干净净，画面全黑」。

**最硬的那条证据上一轮就有，却被读反了**：

| | 分辨率 | IDR | 每像素字节 |
|---|---|---|---|
| 本机正常桌面 | 2160×1440 | 101 341 | 0.0326 |
| 现场那片黑 | 3840×2160 | **2 457** | **0.0003** |

差 100 倍 ⇒ 只有一整片纯色才编得出 0.0003 bpp。
上一轮读成"桌面本身就是黑的"，正确读法是"**被控端交给我们的是一整片纯色**"——后续动作完全不同。

## 三个坑（已写进代码注释）

1. **`ES_CONTINUOUS` 是线程级状态** ⇒ 必须由**一个只为这件事活着的线程**持有；
   `IsHeld` 判"线程还活着"，不判"我们申请过"（池线程一退出锁就静默消失）。
2. **Session 0（服务）里调用会假装成功** ⇒ `IsSupported` 按 SessionId 直接拒绝。
3. **点亮对屏保无效** ⇒ `note` 里必须带"点亮有没有成功"，不许一句"已阻止息屏"糊过去。

## M7.7 · 4K 只显示四分之一、多屏切换（第二轮现场反馈）

- **症状**：「部分客户机看不全 4K（只显示四分之一）」＋「多屏没有屏幕切换」。
- **「四分之一」的几何含义只有一种**：宽高都只有该占的一半。成因两类、修法相反 ——
  ① 编码端把整幅缩一半再编（内容仍是整屏）；② 解码端只解出左上那块（3/4 不在码流里）。
- **原来为什么没法判**：`ctx.drawImage(source, x, y, size.width, size.height)` 用的是**解码结果**
  的尺寸 ⇒ 解码端一缩，画面就静静落在左上角，而页面上**没有任何一处会说话**。
- 新增 `web/src/frameSize.ts`：`pickDrawRect`（**尺寸恒取区域**）＋ `describeSizeMismatch`
  （一句话同时给出两个数，且只缩一维时不许说"宽高各半"）。
- 面板新增「解码尺寸」一格；对不上时标黄 + 上方提示。
  **定性表**：画面分辨率 4K / 解码 1080p ⇒ 解码端；两者都 1080p ⇒ 编码端。
- `webCodecsDecoder.ts`：`ConfigureKey` 加 `codedWidth/codedHeight` 并写进 `VideoDecoderConfig`。
  **假设**（未证实）：不传时部分**硬解**按默认 1080p 分配表面 ⇒ 4K 只解 1/4，不报错不掉帧 ——
  这是"部分客户机"的唯一合理解释。`needsReconfigure` 也把尺寸纳入比较。
- **多屏不是没做**（M5.5 五端就通了）：`GET /api/remote/screens/{id}`、`screens` 指令、
  `ReportScreens` 上行、面板下拉、建会话传 `screenId` 全在。缺的是
  ① **运行时改屏不生效**（`screenId` 只在建会话时下发）→ 新增「切到这块屏」按钮
  （`startSession` 先 `teardownViewer()` 再停旧会话再建新的，避 409）；
  ② **页面没更新**：`Program.cs` 是 `Directory.Exists(contentRoot/wwwroot)` **优先读磁盘**、
  不存在才用 `ManifestEmbeddedFileProvider`。`bin/Debug/net8.0` 下从来没有 wwwroot ⇒ 一直在用内嵌。
  **本轮产物已拷进 `bin/Debug/net8.0/wwwroot` ⇒ 重启即生效，不必重编。**

  ⇒ 硬编安静回落 MJPEG。不写这句，现场会以为"多屏就该这么卡"。
- 验证：`frameSize.test.ts` 13、`webCodecsDecoder.test.ts` 33（+5）、前端全量 **127/127**、

## M7.8 多屏合并显示画面不对（真因 = 帧头整幅取错 + MJPEG 降采样）

- 现场：三屏拼接 5760×2160，帧头报 5760×2160、实际编出来 **1920×720**（2160/720=5760/1920=3）
  ⇒ 前端画布 5760×2160、把 1920×720 画在 (0,0) ⇒ **画面只占左上 1/9**。
- 🔴 **这同时是上一轮"4K 只显示四分之一"的真根因**：3840×2160→1920×1080 占 1/4。
  上一轮猜的"部分硬解按 1080p 分配表面"**不是根因**（`codedWidth/codedHeight` 零副作用保留，但不再当解释）。
  **只有走 MJPEG 的机器中招**（硬编 1:1）⇒ 解释"部分客户机"这个分布。
- 根因代码：`RemoteStreamHost` 单块分支 `frameWidth = Width`（屏幕尺寸），
  假设"MJPEG 按屏尺寸填"—— 那个假设在 MJPEG 引入降采样后就不成立了。
  帧头三件必须同坐标系：`frameWidth/Height`（整幅）+ `regionX/Y` + `width/height`（这一块）。
- 修法：判据抽成纯函数 `RemoteFrameExtent.Resolve(keepsNativeSize, 屏W/H, payloadW/H)`：
  - 支持区域编码（`IRegionSurfaceEncoder`，契约 1:1 不缩放）⇒ 整幅 = 屏尺寸
  - 不支持（MJPEG）⇒ 整幅 = payload 尺寸（它编的就是整幅，只是缩了）
- 前端：`describeEncodingScale`（屏 vs 帧坐标系，<95% 才说）+ 统计格降采样时改标签为
  「**编码分辨率**」+ 横幅删掉"尺寸也不是错的"（那句是假的，代价最高的一类错）。
- 取舍：**合并 = 缩略图**（拼接只能 MJPEG、MJPEG 必然降采样，每块屏只剩 640px）。
  要 1:1 → 切单块屏（走硬编）。**"合并也看清"需产品拍板放宽长边**（3840 ⇒ 约 4 倍 CPU），本轮没动默认值。
- 验证：`RemoteFrameExtentTests` 9、Agent **366/366**、`frameSize.test.ts` 18、前端 **132/132**、
  Core **933/933**、`vue-tsc` 干净、两端编译 0 警告 0 错误。
- 文档：`docs/M7.8-多屏合并显示与降采样.md`。

## M7.10 合并显示（全部屏幕）的全屏清晰度

- 需求：`全部显示屏幕状态下的全屏效果，未达到单屏幕状态下的全屏那样的效果`。
- 根因：`GdiJpegFrameEncoder.DefaultMaxLongEdge = 1920` **与屏数无关**。
  三屏 5760×2160 压到 1920×720 ⇒ **每块屏只剩 640 宽**；缩略图看不出来，一点全屏

## M4.3b AMD CPU 温度读不到（✅ 已落地）

**现场**：AMD 机器温度栏 `CPU —`、GPU/硬盘有值；`thermalState=ok`、`thermalNote=null` ⇒ **页面一个字都不解释**。

**四条独立根因**（都不报错）：
1. **老 AMD（K10/K15、FM2/AM3）的 CPU 温度在主板 SuperIO**，挂在 `Motherboard → SubHardware`；
   旧实现只遍历顶层 `HardwareType.Cpu` ⇒ 永远 null。
2. **AMD 命名不止 `Core (Tctl/Tdie)`**：`CCD1 (Tdie)` / `CCDs Max` / `CCDs Average` 都含 Tdie，
   旧逻辑"含 Tdie 就取"⇒ 把**单个 CCD 裸片温度**当成整颗 CPU。
3. **`ok` 判据太宽**（任一项有值即 ok）⇒ CPU 缺失时 `Note=null`，只剩 `CPU —`。
4. **首次枚举只刷 2 次**；AMD 的 SMN 比 Intel MSR 慢 ⇒ 失败即永久 `failed`。

**修法**：抽 `Platform.Abstractions/ThermalSensorPicker.cs`（拍平→分级）；
`WindowsThermalSource` 递归 `Flatten`（子硬件继承父分类）+ 连刷 3 次（80ms）+
**仅"枚举到 CPU 但没读到温度"才允许重试**（≤3 次 / 间隔 30s；驱动加载失败仍只试一次）+
`ok` 且 CPU 缺失时把三句话写进 `Note`（没枚举到 CPU / 这颗 U 没传感器 / 读数无效）。
启动日志本就会打印 `ThermalNote`，现场直接可见。前端在 `cpuTempMissing` 时加一行提示 + 曲线区整句诊断
（⚠️ 提示必须放在 `v-if/v-else` 链**之后**，插中间会打断配对）。

**🔥 0 ℃ 的坑**：文档 §22.2 明确"0 ℃ 合法、不许净化"（冷库）。初版照 Linux 判据把 0 丢了，**已回退**：
Windows 只挡 `NaN/±Inf/<-40/>150`，与 `AgentMetricsAggregator.Temperature` 同界。
Linux 仍把 0 当占位（sysfs 驱动没填就写 0）—— **两边故意不同**，已在 §22.2 与 picker 注释写清。

**为什么抽类**：旧策略**一条测试都没有**（测试工程不引 Platform.Windows）——
AMD 命名差异与"温度在主板"正是因此一直没人发现。现在 20 条用例跨平台可跑。

**验证**：Core **933** / Agent **394**（+20）/ Integration **620** 全绿，基线已 `--update`；
`vue-tsc` 干净、vitest **163**、vite build 已写 `Server/wwwroot`；
Server 用 `-p:BaseOutputPath=.build/altbin/` 旁路编译（`bin\Debug` 被运行中的 Server 锁）**0 警告 0 错误**。

**未做**：无 AMD 真机（本机 i5-8265U、非管理员）⇒ 真机度数未实测；
**LHM 不升**（0.9.3/0.9.4 CPU 实现类相同，0.9.4 只带来 `System.Management 9` 的 NU1605 冲突；

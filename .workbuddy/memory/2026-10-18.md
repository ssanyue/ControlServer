## M7.1 文件仓库对账（M6 收官后的第一块）

### 为什么先做这个

M6 五块收官后，总方案的路线图（M1–M6）**已经走完**，"下一步"只能从挂账里挑。
先把**做不了**的排除掉：当前进程不是管理员（`IsAdmin=False`），且 `sc.exe` 被安全策略拦死
⇒ 安装包 / 服务形态 / `-HardenDataDir` / ACL 真机验证**这一轮全部做不了**，不是不努力。
Linux、8K、Session0 GPU 同理（无环境）。

剩下的里面，`docs/运维手册.md` §6 自己点名的"长期唯一失控项"就是文件仓库。
而核对代码后发现它比文档写的更严重：**`FileRepositoryService.DeleteAsync` 第 140 行的注释
承诺"磁盘上那个孤儿文件由清理任务兜底"，而全仓没有这个任务**
（`FileTransferHostedService` 只回收过期会话与陈旧分发任务）。

**注释承诺了一件不存在的事，比"没有兜底"更坏** —— 它让读代码的人以为那个目录有人管。

### 三条会产出孤儿的路径（都真实存在）

1. 删元数据成功、删磁盘文件失败（被占用 / 权限）⇒ 只留一条 `Warn`；
2. 上传已 `Move` 进 repo、落库抛异常、回滚 `Move` 也失败 ⇒ `TryMoveBack` 只 `Warn`；
3. 换机器 / 恢复备份时只带库不带 `files/`，或反过来 ⇒ 无任何检测。

### 判据：三个不变量（这是本轮唯一真正要设计的东西）

1. 🔴 **宽限期防的是竞态，不是"保守"**。完成上传是 `File.Move(.part→repo)` 然后 `AddAsync`。
   两步之间文件"盘上有、库里没有"，**与孤儿长得一模一样**。按"不在库里就删"去清理，
   会删掉一个刚刚上传成功的文件，用户看到"上传成功但文件没了"，**且不报错**。
   ⇒ 判据只能是**文件年龄**（mtime 早于 now − 24h），不是"这次扫描没对上"。
2. **断链（库有盘无）只能报警**。删记录能让 `files.lost` 变好看，代价是替用户决定丢文件，
   并让"文件丢了"从此看不见。⇒ `Collect` 不碰 `Lost`。
3. **判龄一律走 UTC**（`LastWriteTimeUtc` vs `BeijingTime.Now.UtcDateTime`）。用本地时间比，
   在时区不是 +08:00 的部署上整体偏几小时：偏早误删、偏晚永不触发，**两种都不报错**。

外加两条边界：`repo/` 出现子目录**不递归、只报**；`.part` 的判据是**有没有会话**而非年龄
（有主的 `.part` 是客户端的续传进度，删了之后续传从 0 开始且不报错）。

**🔥 CodecAPI 槽位（这一条差点写错）**：SDK `icodecapi.h` 的实际顺序是
`IsSupported(3) → IsModifiable(4) → GetParameterRange(5) → GetParameterValues(6) → GetDefaultValue(7) → GetValue(8) → SetValue(9) → RegisterForEvent(10)`。
`IsModifiable` 是**后来插进去的**，所以按老资料（没有它）数出来会**整体错一位** —— 错位的表现是
"值写进了 RegisterForEvent：**返回 S_OK、读回来还是旧值**"，于是每个调优项都显示"已设"、实际一个都没设。

**为什么 4（tile）和 5（ROI）没做完**：两者要的是**同一个底座** ——「编码器只编抓回来那张纹理的一个子矩形」
（`D3D11Nv12Converter` 已有 `SetStreamSourceRect` 可用，但 `WindowsGpuFrameEncoder.Prepare` 的尺寸判定、
指针合成的坐标平移、`RemoteSessionDto` 的帧尺寸与源区域两个概念、以及前端输入映射全要跟着改）。
- 只做一半的 ROI 会得到"全屏固定视口能用、一滚动就错位"的半成品 —— 用户明确拒接临时补丁。
- ROI 还有一个**要用户拍板**的策略问题：视口每滚一次就要重建编码器（MF 码率/尺寸硬编码，≈0.3 s 空窗、首帧必关键帧），
  是"滚动停止 300 ms 后再切"，还是"只允许固定 1:1 视口、拖动时沿用旧帧"。

  整帧基准＝不设矩形；单块基准＝源取 region、目标写满输出。改错的表现是"指针叠加之后整幅被压进一个小输出"（不报错）。
- `WindowsGpuFrameEncoder`：`_regions` ＋ 每块一条 `TileLane { Converter, Encoder, Pending, ProducedAnyFrame, … }`。
  **一块一路独立码流**（H.264 P 帧只参考同路，两块塞进同一编码器会互相污染参考链）；
  **配对队列逐块**（异步 MFT 延迟是逐编码器的，共用一支会让每块时戳来自别的块）。
- 判"要不要重建管线"用**清单相等**，不用尺寸相等：ROI 只换位置（宽高不变）时拿尺寸判会认为"没变"⇒ 视口永远不生效。
- `FrameSize` 报**源纹理**尺寸（不是某一块）：报成小块会让画布缩成一角且不报错。
- 码率**按块均分**（`MinLaneBitrateBps=500_000` 兜底）：每块拿满额会让 2 块变 2 倍码率。
- 分块时**一律带内**：`_codecDescription` 是第 0 块的参数集，各块 SPS/PPS 可能不同（宽度不同）。

**契约 / 中心 / 授权**
- 帧头加 `FrameWidth/FrameHeight/RegionX/RegionY/TileIndex/TileCount`（`TileCount` 默认 **1**）；
  `RemoteSessionActions.Viewport`、`RemoteSessionCommandDto`/`Dto` 加四个视口字段与 `TileCount`。
- 新增 `POST api/remote/sessions/{id}/viewport` → `SetViewportAsync` → 注册表 `ApplyViewport`（只记账＋广播）。
  **已进 `LicenseGate` 分类表**（视口改的是被控端编码区域，与质量档同类）。

**Agent / 托盘**

  `maxTileWidth = H264MaxDimension / HevcMaxDimension`；MJPEG 挪到集合最后一格（3 块 4K 硬编好过整幅软编）。

**前端（`RemoteDesktopPanel.vue`）**

## 补三个前端入口（多屏 / 质量档 / 剪贴板）—— 10-18 中午

**契约对齐（三个容易写错的点）**
- `RemoteScreenDto.Id` 是**抓屏器认的 Id**，不是显示器序号 —— 传序号下去被控端只会回"指定屏幕不存在"。
- `ClipboardChanged` 的载荷**没有 sessionId**（服务端只发到该会话分组，因为文本可达 60 KB）⇒
  前端能做的最强判断是"**换路即清**"：让上一路迟到的推送变成一个可见的空，而不是变成"别人的剪贴板"。
- `auto` **不是第四套数字**：`Resolve()` 把它解析成 `balanced` 的数，区别只在"编不动会不会自己降"。
  UI 上不写这句，用户切到"自动"发现码率没变，会以为档位坏了。
- 屏清单**三态不许合并**：`pending=true`（还在问）/ `pending=false` 且空（**真的没有可抓的显示器**，
  通常=没人登录）/ 有列表。把①画成②，现场会去拆显示器。
- 剪贴板**三态不许合并**：`text=null` 且无 `note` = 那台机器剪贴板里**没有文本**（图片/空/被占用，
  不是故障）；`text=null` 且有 `note` = 读失败（`note` 是原因）。

**做了什么**
- `types.ts`：`REMOTE_QUALITY_PROFILES`、`REMOTE_HUB_METHODS.clipboardChanged`、

  `RemoteSessionDto.quality?: string | null` —— **可选**，因为"读不到"不许画成"它是 auto"。
- `api.ts`：`remoteScreens(agentId, refresh)` / `setRemoteQuality` / `readRemoteClipboard` /
  `getRemoteClipboard` / `writeRemoteClipboard`。
- 面板：工具栏加「抓哪块屏」下拉（默认项是**自动=多屏拼接**，不是主屏）+「重读屏」按钮；

  会话内加「剪贴板」块（**读/写两个按钮分开** + 草稿框 Ctrl+Enter + 读到内容的只读视图 + 复制到本机）。
- `loadScreens` 自己约 1 秒重问一次（上限 4 次）—— 那个端点永远先返回，不重问页面会永远停在"读取中"。

## 三个前端入口的浏览器实证：两处真缺陷（10-18 傍晚）

挂账清零后剩下唯一一条"我自己能验、但一直没验"的：**多屏 / 质量档 / 剪贴板只在浏览器里活**。
`vue-tsc` 与 `vitest` 都碰不到模板 ⇒ 给它补了一节 `--panels`（复用整套起中心/客户机/托盘/登录/建会话的架子）。

加完先跑一遍，**第一条就红了**：`[FAIL] 解码器有产出 :: 实得 None` ——
看起来像"被控端不推流"，可客户机日志、协商、`framesSent` 全正常；控制台里 135 条
`Cannot read properties of undefined (reading 'text')` 才是真因。

### 缺陷①：`Ok(null)` ⇒ 204 ⇒ `undefined` ⇒ 整个渲染函数崩

- 服务端 `GET /api/remote/sessions/{id}/clipboard` 是 `return Ok(TryGetClipboard(...))`；
  ASP.NET Core 默认的 **`HttpNoContentOutputFormatter` 把 null 值改成 204**；
- 前端 `unwrap()` 对 204 返回 `undefined`；面板把它塞进 `clipboard`，模板接着读 `clipboard.text`
  ⇒ **render 抛异常 ⇒ 面板一片空白**（连画面都不出，因为统计卡片在同一个 render 里）。
- 修三处（每处都留了注释）：`api.ts` 的 `getRemoteClipboard` 收口 `.then(dto => dto ?? null)`；
  `loadClipboard` / `onClipboardChanged` 都 `?? null`；模板判"还没读过"用 **`!clipboard`** 而不是 `=== null`。
- 修完 `解码器有产出` 立刻回来（4 → 18 → …），三入口 31/31 全过。

### 缺陷②：冒烟跑的是「内嵌的旧包」—— 改完前端怎么都不生效

修完上一处重跑，报错**一模一样**，连 bundle 文件名都没变（`index-D5r0XzDw.js`，而磁盘上早就是 `index-CxGcD-xT.js`）。
真因：`Program.cs` 是"**cwd 下有 `wwwroot` 目录就读磁盘，否则回退 `ManifestEmbeddedFileProvider`**"，
而冒烟的 cwd = 仓库根（没有 `wwwroot`）⇒ 发的是编译期嵌进 dll 的那份。
**改完前端必须再 `dotnet build src/ControlServer.Server`**，否则整轮验的是上一个版本，而构建/产物/源码全绿。

为此给冒烟加了前置判据 **「服务端发的前端产物 = 磁盘上刚构建的那一份」**（比 `index-*.js` 文件名），
把"改完没反应"从"怀疑自己改错了"变成一句直接可读的红。

### 判据（31 项，落在页面文字 / 后端返回值 / 宿主剪贴板三处交叉）

- 多屏：第一项必须是「自动」且默认选中（写成主屏 ⇒ 用户以为拼接坏了）；除自动外每项带 `N×M`；
  点「重读屏」25 s 内回到可点且项数不变。
- 质量档：四档顺序对；badge「当前：X」**等于后端 `quality`**；点「低」⇒ 后端 `quality=low`，再切回 ⇒ 后端回原值；

## M7.4 · 远控 60 帧（实施 ＋ 实测，详见 `docs/M7.4-远控60帧.md`）

**改了什么**：契约新增档位 `smooth`（60fps/25Mbps，既有三档一个数没动）；`RemoteStreamPacing`

**实测（本机 i5-8265U ＋ UHD620/MX250，2160×1440）**：
- JPEG q70 单帧：1280×720 12.4ms｜1920×1280 **27.4ms（36fps 上限、60fps 要 213Mbps）**｜4K 88.7ms
- **GDI 抓屏是 MJPEG 路径的真上限**：空闲 47ms（21fps）→ 负载下 58ms（17fps），比编码还贵
- **GPU 路径有落点**：DXGI 抓屏 3.15ms（317fps）＋ H.264 硬编 106fps（2160×1440）
- 真会话实测：**目标 12 与目标 60 都跑 18.2 fps** ⇒ 当前上限与目标帧率无关

**结论：60 不能宣称达成。** 结构性瓶颈是推流循环**逐帧 `await` 中心回执**
（`SendOneAsync`→SignalR InvokeAsync），上限 = 1/(抓屏+编码+往返)。三条路（不动／单槽丢旧帧／多槽队列）
待拍板，推荐单槽丢旧帧（B），并给"没送出去的帧"单独计数。

**这轮现场数据不可用的原因**：本机可用内存只剩 700MB；用来制造画面变化的 Edge 窗口没出现在桌面截图里，
`0.1KB/帧` 说明画面基本没动 ⇒ 18.2fps 是"静止去重＋抓屏负载"的混合，不能据此判 60。
下一轮要在干净机器上、用 smoke 那套自带播放器页面、**按收帧计数增量**测三档。

### 补记（同日晚）：18.2 fps 那组数据**判定为无效**，别拿去当结论

复核改档链路后否决了之前的解释：`RemoteSessionService.SetQualityAsync` 确实把
`MaxFps = min(请求, 档位)` **下发给被控端**（失败会 `_log.Warn` 而不是静默）。
那么 **target=12 却测出 18.2 fps 在逻辑上不可能**（周期 83ms ⇒ 上限 12）。
⇒ 18.2 是测量口径/环境问题（旧构建托盘、无观看端接入、内存 700MB），
**不是**"上限与目标帧率无关"。

更关键的一条算术：抓屏 3.15ms ＋ 编码 ~8ms ≈ **11ms**，而 18.2 fps 对应 **55ms/帧**
⇒ **44ms 没有归属**。所以"逐帧 `await` 回执"这条理论**不足以**解释它 ——
若照 B 方案直接改推流循环，很可能**改错层**（正是本仓 §9 那条纪律要防的）。

⇒ 定下来的下一步（未动手）：先加**只读探针**（抓屏 / 编码 / 写管道三段 Stopwatch，
只打日志、不改行为），并让被控端把**实际生效的 targetFps** 回带进统计
（"改档到底有没有到托盘"从此不用猜）。测完拿到真实分解，再决定 B 改在哪一层。
⚠️ 前置：验证必须重启 `ControlServerAgent`（管理员），否则托盘还是旧构建。
⚠️ 探针的坑：`WaitForNextFrame` 的**等待时间不等于抓屏耗时**，两项要分开计。

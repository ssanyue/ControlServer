### 2. 写冒烟时踩到的四个坑（**全是断言写错，不是产品缺陷**）

1. **「删除已不存在但仍被引用的图片」返回 409，不是 404** —— `DELETE /api/config/images/{f}`
   的**引用检查先于存在性检查**。所以 `?force=true` 删掉文件后，配置仍引用着它，再删还是 409。
   要测 404 得用**从未存在**的合法文件名（`img` + 32 个 `0` + `.png`）。
2. **发 TCP 到没人监听的端口 = 0 字节 + 失败**（约 2s 后被拒）。用它测"指令按名解析"
   会把「目标不可达」和「指令解析失败」混在一起 ⇒ **测内容解析一律用 UDP**。
3. **幂等闸门断言必须同时确认两面**（第 1 次 200 **且** 第 2 次 409）。
   只断言"出现过 409"会**假通过**：上一对的第 2 次与下一对的第 1 次常落在同一秒 ⇒ 连续两组 `409/409`。
   修法：配对失败后 `time.sleep(0.25)` 让开一秒再试，最多 8 对。
4. **非 ASCII 路径段必须 URL 编码**：`http.client` 要求 request target 是 ASCII，
   直接写 `/api/commands/不存在的-id` 会抛 `UnicodeEncodeError`（不是服务端拒绝）。

走完整流程（含 `npm run build`）时 rollup 会把 `/*#__PURE__*/` 提示写到 **stderr**。
若调用方写成 `powershell -File build-portable-exe.ps1 2>&1 | Select-Object -Last 40`，

### 1. ⚠️ 需求(3) 的关键判断：前端**不走 `actionId`**，后端**两条路都留**

这是本轮**最容易做错**的地方。单条执行有两条通道，用途严格不同：

| 通道 | 谁用 | 语义 |
|---|---|---|
| 请求带 `actions:[...]`（**内联**） | **编辑页的「执行」按钮** | 执行**当前草稿**里的那一条 |
| 请求带 `buttonId/subButtonId` + `actionId` | 脚本 / 运维 / 将来定时联调 | 按**已保存配置**精确触发某一条 |

**为什么编辑页必须走内联**：编辑页改的是 **draft（未保存）**。若用 `actionId`，
服务端会按**已保存的旧配置**去执行 —— 用户刚把目标 IP 改成 `10.0.0.9` 再点「执行」，
发出去的却是旧 IP。这正是点这个按钮最不想看到的结果。
所以后端**两种都实现且都有测试**，但前端只走内联。

### 2. ⚠️ 后端：两种「空」绝不能合并（`SelectActions`）

```csharp
private static IReadOnlyList<ButtonAction>? SelectActions(
    IReadOnlyList<ButtonAction> all, string? actionId)
{
    if (string.IsNullOrWhiteSpace(actionId)) return all;   // 没限定 → 整组
    var hit = all.FirstOrDefault(a => a.Id == actionId);
    return hit is null ? null : new[] { hit };             // 找不到 → null
}
```

- 指定了 `actionId` 但**该按钮下没有它** → **404**（明确告知"你点的这条不在了"）
- **没指定 `actionId`、而整组本来就有 0 条** → **200 + 0 steps**（合法的空执行）

若把两者都返回"空列表"，"我以为只发一条、其实发了一整组"与"按钮被清空了却以为成功"都会变成**静默降级事故**。
`Action_id_runs_only_that_one_action` 与 `Executing_an_action_from_a_button_that_has_none_still_returns_an_empty_run` 分别守门。

孤立 `actionId`（既没 `buttonId` 也没 `subButtonId`）→ **400**（动作 Id 只在按钮内唯一，无法定位）。

### 3. `ActionExecuteRequest` 字段位置（`record` 位置参数）

`ActionId` 插在 **`SubButtonId` 之后、`Label` 之前**。这是 `record` 的**位置参数**，
改动会波及所有按位置构造的调用点 ⇒ 新增字段时**必须**放在末尾或先确认无位置调用；
本轮所有调用点都用命名参数，`-c Release` 构建 **0 错误**佐证。

### 4. 需求(1)：权限**不降级**

全局字段（程序名 / 自由排布 / 默认按钮图片 / 背景图 / 监听端口）从编辑页搬到设置页时，
`SettingsPanel` 用 **`CanOperate`（Admin + Operator）** 收口，而**不是** `isAdmin`。
理由：这几个字段本就是**操作员日常要动**的东西，借"搬家"顺手收紧成 AdminOnly 属于**权限倒退**。

### 5. 需求(1)：保存必须**整份替换**

`PUT /api/config` 是**全量语义**。所以 `saveGlobal()` 先**深拷贝** `props.config.settings`
再改那 5 个字段，否则"只保存全局"会把整站的按钮**全清空**。冲突仍是 409 + 回显 `current`；
`globalConflict` 类型是 `ControlSettings | null`（取 `body?.current?.settings`，不是 `body?.current`）。

### 6. `globalDirty` 必须是 `computed`，不能是函数

写成函数时 `v-if="globalDirty"` **永远为真**（函数对象本身 truthy）→ "未保存"提示常驻。
同理 `watch(props.config)` 要**跳过有脏改动的场景**，否则别人一改配置就把正在编辑的全局草稿冲掉。

### 7. 需求(3)：单条执行时**本条 `delayMs` 不生效**

`delayMs` 的语义是"**上一条**发完后等这么久再发本动作"（第 0 条不等待）。
单条执行时它自己成了第 0 条 ⇒ 延迟**必然**不生效。
前端**显式提示**（`（单条执行时本条 {{ delayMs }}ms 延迟不生效）`）而不是静默 —— 否则用户会以为"延迟坏了"。

### 8. 需求(3)：子按钮 override 的透传链

子按钮的目标 IP/端口由**所属集合**提供，不在动作自己身上。所以"执行"按钮要么能拿到集合目标、要么会发错地址。透传链：

```
SubSetForm(set.targetIp/Port) → SubButtonEditor(setTargetIp/Port, 必填)
  → ActionListEditor(shared-target + overrideIp/Port) → ActionEditor(ownerLabel/overrideIp/overridePort)
```

`runSingle()` 里 `sharedTarget && !overrideIp` → 直接**报错拒发**（"所属集合的目标 IP 为空"），
不允许退化成用动作自身的 IP 发出去。实测：动作写 `10.0.0.1:1`，实发 `127.0.0.1:18149`（集合目标）。

### 9. 需求(4)：高度用 `max()` 而不是单一 `calc()`

```css
.table-wrap.tall { max-height: max(560px, calc(100vh - 260px)); }
```

单一 `calc(100vh - 260px)` 在 600px 高的小窗口下只剩 340px —— **比原来更矮**，与"加大显示高度"的诉求相反。
`max(560px, …)` 保证**下限 560px**、大屏再随窗口长高。

## 追加需求 —— 「关闭 CMD 窗口不能停止服务」✅（同日，托盘之后）

> 需求原文：「关闭CMD窗口不能直接关闭服务，这个功能未实现」

**这是上一轮托盘的漏网之鱼**：上一轮只解决了"双击启动（无控制台）"这条路，
但 `run.cmd` 那条 —— 从 cmd 里启动 → 服务**继承那个控制台** → 关窗照样把它带走。
`run.cmd` 自己第 8 行还写着「关闭窗口 = 停止服务」，等于把缺陷写在了脸上。

### 先复现，再动手（避免"以为修好了"）

写了个真机脚本：起一个 cmd 窗口跑服务 → `AttachConsole(cmd_pid)` 精确拿到**那扇窗**
（不按类名找，防止误伤用户自己那个实例的窗口）→ `PostMessage(WM_CLOSE)` → 看服务是否还活着。

| | 服务进程挂在控制台上 | 关窗后 |
|---|---|---|
| 修复前 | **True** | **1 秒内消失** |
| 修复后 | **False** | 12 秒仍存活 |

### 根因与唯一解

Win32 里关闭控制台窗口**不是可拦截的信号**，是一次**必然生效的处决**：系统向所有客户端
进程投递 `CTRL_CLOSE_EVENT`，**应用无法否决**（处理器返回 TRUE 也只能把死期从 0 秒拖到约 5 秒）。
⇒ "让服务扛住关窗"在**拥有控制台**的前提下**做不到** ⇒ 只能**先离开**：
`kernel32!FreeConsole()`。这是唯一的实现路径，没有第二种写法。

⚠️ **"已经改成 WinExe 了"不等于解决**：双击时确实没有控制台，但"从 cmd 启动"时
进程**会继承**那个控制台。"GUI 子系统"与"不受控制台生命周期管辖"是两件事。

### 改了什么

- `WindowsInteractiveHost.ConfigureConsoleOutput(bool)`：决策表 = 输出被重定向 → **什么都不做**；
  非交互会话 → 不折腾；`AttachConsole=true` → 保留终端（开发模式）；**默认 → `FreeConsole()` 脱离**。
- `Program.cs §0.1`：`ReadAttachConsoleFlag(args)`（手写扫 argv，不用 `AddCommandLine` ——
  它对 `--key value` 这种空格写法会抛 `FormatException`，而这段代码在最早期，异常 = 连错误都发不出）
  → 用返回的 `consoleOutputUsable` 决定 **Serilog 要不要挂 Console sink**（脱离后挂它只会白写）。
- `run.cmd` 整篇改写：顶部说明与结尾提示全改成「**关闭本窗口不会停止服务**」；
  启动方式从 `dotnet run`（占着终端）改为 **build + `start` 启动产物 exe**；
  并**轮询端口真的进入监听**才报「已启动」，不再凭空断言。
- `ControlServerFactory` 加 `Server__Startup__AttachConsole=true`（原因见下第 3 条）。

### 四个关键判断

1. **重定向场景一个字都不能动**：`FreeConsole` 只关闭**指向控制台**的句柄，**不碰**文件/管道句柄。
   所以"输出已被抓走"时既不附着也不脱离 —— 直接返回。这一条同时保住了**集成测试宿主**
   （stdout 是 xunit 的管道）与**冒烟脚本**的零副作用。
2. **`AttachConsole` 的返回值不等于"控制台可用"**：从 cmd 启动时进程**已经**继承了控制台，
   此时 `AttachConsole(ATTACH_PARENT_PROCESS)` 会因"已有控制台"而失败（ACCESS_DENIED），
   但控制台分明可用 ⇒ 判定要用 `GetConsoleWindow() != 0`。**这个坑把我的验证脚本骗过一次**。
3. **测试宿主会被这种"进程级副作用"误伤（第二次了）**：集成测试是在**测试进程内**跑 `Program`，
   用户在**自己终端**里跑 `dotnet test`（输出没重定向）时，宿主会去 `FreeConsole` 掉测试进程
   自己的控制台 → xunit 输出丢失。加 `AttachConsole=true` 走"保留"分支解决。
   上一轮的单实例互斥体是同一个教训 —— **新增进程级副作用必须回头检查测试宿主**。
4. **开一个开发模式的口子**：`--Server:Startup:AttachConsole=true` 保留终端与实时日志，
   代价是关终端会停服务。**默认永远站在安全的那一侧**（关窗不停服务），要看日志得显式开口。

- 全量测试 **Core 357 + 集成 180 = 537，0 失败**（新增逻辑对测试零副作用）
- 冒烟 **4/4**（跑的是重新打包后的 WinExe）
- **`run.cmd` 端到端**：跑 `run.cmd` → 拿到那扇窗的真实 HWND → WM_CLOSE → 12 秒后服务仍在

### 坑（验证手段本身）

- **`FindWindow("ConsoleWindowClass", 标题)` 绝不能用**：Win11 可能被 Windows Terminal
  接管（类名不同），而且桌面上**同时存在用户自己那个实例的控制台窗口** —— 第一次按类名找，
  找到的**正是用户的窗口**（标题「中控服务 ControlServer — http://localhost:8080」），
  并且**真的向它发了 `WM_CLOSE`**；用户跑的是修复前的版本（附着控制台），
  于是**把用户当时正在运行的那个服务关掉了**。⚠️ **这不是"差点误伤"，是"确实误伤了"**
  （事后 `tasklist` 复查：`ControlServer.Server.exe` 已不存在、8080 无人监听）。
  ⇒ 教训：**在用户机器上做破坏性实验前，必须先用 PID 精确认领目标**，
  绝不能用类名/标题这类可能撞车的特征定位。改用
  `FreeConsole → AttachConsole(PID) → GetConsoleWindow`，**只认 PID**；
  并且破坏性动作前要先断言"这个窗口确实属于我起的进程"，否则宁可不做。
  同一次实验还因为窗口没找对而得出"需求已满足"的假结论 —— **目标错 + 什么都没做**，双重失效。

  随后 `AttachConsole` 不可靠（err=5）。要拿真控制台窗口就**一个 std 句柄都不传**

- **判据要选"因果上更强"的那个**：与其"关窗后看存活"（依赖真的关到了窗），不如直接看
  **进程是否还挂在控制台上** —— 挂着 ⇒ 关窗必然带走（已因果证实），不会假阳性。

## 追加需求 1 条 ✅ —— WoL 编辑项瘦身：只留 MAC（16:1x）

### 这三个控件在 WoL 下**确实**没用

- 目标：`NormalizeWolHost` 把空 / `0.0.0.0` 视为 `255.255.255.255` ⇒ 留空即广播
- 端口：`TargetPort > 0 ? TargetPort : DefaultWolPort(9)` ⇒ 0 即 9
- 数据类型：**发送路径一次都没读过**（走 `TryParseMac` + `BuildMagicPacket`）

⇒ **后端零改动**。新界面写进去的就是后端本来就读得懂的默认值（`""` + `0`）。

### 关键判断：不能"只隐藏"

从 UDP 切到 WoL 时，`targetIp` / `targetPort` 还留着原来那台机器的值 ——
界面不显示但后端照样用，那就成了"界面没说、实际这么做"，比多两个控件更误导。
所以切入 WoL 时**就地归位**（`targetIp=''`、`targetPort=0`）：

- 数据类型**不动**（WoL 不读，留着切回 UDP 能恢复）
- 「指令库」例外要清掉（指令库不含 WoL，永远解析不出来）
- 切回 UDP **不补值**：目标框重新可见、显示为空，由用户填 —— 可见的空值不算误导

### 顺带修掉一个隐藏数据类型带来的隐患

⇒ WoL 改走**纯前端**魔术包计算（102 字节，口径与 `BuildMagicPacket` 逐字对齐，

### 旧配置 / 外部导入的非默认目标：告警 + 一键归位

否则「固定发往广播」那句说明本身就是假话。沿用 §28 的原则：**只提示、不静默改写**。

### 落库安全性核对

## 追加：第二轮复测 —— 退出码 1，重装的「删/建」竞态 ⚠️→✅

用户装了上轮的新包，弹窗**已能自报原因**：「装配脚本中途报错（**退出码 1**）」。

**根因链**：
1. `PrepareToInstall` 调 `uninstall-service.ps1` 停+删旧服务；
2. 但该脚本是**估算式等待**：`sc stop` → 睡 2s → `sc delete` → **立刻返回**；
3. `sc delete` 只是**标记删除**（1072 `ERROR_SERVICE_MARKED_FOR_DELETE`），真正清除**异步**，要等句柄全关；
4. 紧接着 `sc create` 撞 1072 ⇒ 创建失败；

6. 抛出的信息还指向"权限不足"，**把排查方向整个带偏**。

> 教训：上轮加的保护逻辑本身没错，错在**它依赖的前置状态没被正确建立**。

- `install-service.ps1`：**`catch` 块补上诊断收集** —— 先前弹窗让人去看 `install-diagnostics.log`，

## 追加：Windows 安装包第三轮实测 —— 定位真根因（`sc.exe` argv 被拆烂，1639）

**用户在本机（`DESKTOP-9VFHRMA`）重装，依旧失败** ⇒ 这次日志可直接读，证据是硬的。

**现场证据**（`C:\ProgramData\ControlServer\logs\install-service.log`）：
```
==> 3/6 注册服务并配置恢复策略（进程自愈）
    <sc create 的帮助文本全文>              ← 打印帮助 = 参数解析失败
警告:   sc create 未生效（退出码 1639），第 1/2/3 次尝试
[!!] 安装失败：服务注册失败：sc create 连续 3 次未生效（退出码 1639）…
```
`install-diagnostics.log` 同时排除两个方向：`管理员：True`（**不是权限问题**，正是上轮我写进错误提示的猜测）、
`服务未注册` + `8080 无任何监听`（不是端口冲突）。

**1639 = `ERROR_INVALID_COMMAND_LINE`**；"原生工具打印自己的帮助文本"就是这个判据。

**根因**：PowerShell 5.1 往原生程序传参时**吞掉参数里的内层引号**，只在**空格处**断成新的 argv。
用 `.py` 探针（`import sys; print(sys.argv[1:])`，同走原生 argv 通路）实测：

| 写法 | 探针抓到的真实 argv |
|---|---|
| `sc.exe create X binPath= "C:\Program Files\A\S.exe" --flag` | `[…,'binPath=','C:\Program','Files\A\S.exe --flag',…]` |
| 路径**无空格**时 | `['binPath=','D:\A\S.exe --flag']` ✅ 侥幸能过 |
| 内层引号转义成 `\"` | 更糟 ❌ |

⇒ `binPath=` 只拿到 `C:\Program` ⇒ 帮助 + 1639。**只在装到含空格路径时现形**（默认恰好就是 `Program Files`）。

**解法**：改用 `New-Service`（cmdlet，走 .NET 参数绑定 → 直通 `CreateService` API）。
对照实证：同一台机器、同一个 96 字符含空格字符串 —— cmdlet 绑定**完整到达** ✅ ／ 原生 argv **被拆开** ❌。
**仍保留 `sc.exe`** 的调用点（参数都**不含引号**）：`failure reset= 86400 actions= restart/5000/…`、
`sdshow / sdset <SDDL>`、`stop / delete / start / query`。
新增兜底：注册后回读 `HKLM\…\Services\<名>\ImagePath`，不以引号开头就自动改写（防 unquoted service path）。
同源顺手修：`Start-Process -ArgumentList` 是「数组拼空格、**不自动加引号**」⇒ 给 `--data-dir` 补引号。
顺手改：`.iss` 里"装配脚本"措辞 → "部署脚本"。

**上一轮结论被推翻**：所谓「删/建竞态（1072）」**不成立** —— 服务**从未**成功注册过，不存在残留。
**更正上轮"先重启电脑"的建议：这次不需要重启。**
但上轮那两项**可观测性**改动（`sc create` 不再 `| Out-Null`、`catch` 里补诊断收集）
**正是本轮定案的关键** —— 不先让失败可观测，就只能在假设之间反复横跳。

**教训**：① **"静态检查全过 + 编译零警告"替代不了"真机上跑一次"**；② **先让失败可观测，再猜根因**。

**本机实测边界**：工具会话 `IsInRole(Administrator) = False` ⇒ 仍**无法端到端安装**
（且 `sc.exe` 在沙箱硬黑名单）。能验的都验了：6 个 `.ps1` AST 全过、BOM 齐全、ISCC 重编**零警告**、
argv 拆分与 cmdlet 绑定**两条通路均有对照实测**。

**参照对象的核心机制**（已写进 `docs/M3-授权方案.md` §1）：
1. `license.dat` = `JSON → +sig(HMAC-SHA256) → Base64`；字段 `v/mc/lt/id/ed/et/md/sn/vi/hn/ub/ud/bt/ivt/sig`
2. **`ivt` 联网校对时间是整个防线的关键** —— 正式/试用授权只能由"联网导入/联网生成"产生，
   两条路径都写 `ivt`；手工编辑的授权文件即使签名合法也因缺 `ivt` 被拒。
3. 通用授权（`ub=1`）：`mc` 留空，**首次联网导入时自动绑定本机**，`ud` 为最迟可导入绑定时刻。
4. `time_record.dat`：`{v:2, floor, records[≤50]}`，`floor`=最早一次联网校准（**只前移不后移**）。
5. 门控分级：`0` 无文件 / `2+trial` 试用过期 → **完整门控**（可生成试用）；`2+full` 正式过期 / `3` 异常 → **仅导入**；`1`/`4` → 正常。
6. ⚠️ **参照对象翻过的车**：`_completeImport` 曾写 `ri >= 1`，把"已过期(2)/异常(3)"也当成功
   ⇒ 导入过期授权后门控关闭、直接进主界面且无提示。**服务版一律用白名单枚举判成功。**
7. 时间存储约定：**把北京墙钟当 UTC 存**（规避本机时区差异）—— 与服务版铁律 #4 `BeijingTime` 语义一致，可直译。

**服务版必须改的三处**（形态不同）：
| # | 参照对象 | 服务版 | 原因 |
|---|---|---|---|
| ① | HMAC 对称密钥硬编码在客户端 | **ECDSA P-256 非对称**，私钥只在签发 CLI | 服务端 exe 交付到客户机房，对称密钥内嵌 = 拿到 exe 即可伪造授权 |
| ② | 授权文件放 exe 同目录 | 放 `{DataDir}\license.lic` | exe 在 Program Files（写不进），数据在 ProgramData |
| ③ | 超级密码（授权文件存 hash 当万能钥匙） | **取消**，交由 RBAC 三角色 | 已有角色体系，再塞绕过 RBAC 的密码 = 安全反模式 |

**方案文档**：`docs/M3-授权方案.md`（16 节：结论先行 / 参照拆解 / 差异适配 / 数据模型 / 密钥模型 / **闸门矩阵** /

**两个我认为最关键的设计判断**（都在文档里给了权衡表，待用户拍板）：
- **闸门要卡在"价值点"上**：未授权时**放行**登录/只读/授权导入/用户管理（授权导入是唯一自救通道，必须通），

### 几个不显然的决策

1. **规则放 Core，不放工具里** —— 与 `LicenseImportRules` / `LicenseEvaluator` 是一套东西的两面，
   共用同一个评估器才不可能出现"签发说没问题、导入说有毛病"。
2. **自检公钥从私钥现推**，不让调用方传公钥文件；否则可能拿的是磁盘上那份已过期的 `vendor-public.pem`，
   把"公钥私钥不配对"伪装成"签发失败"。
3. **`new-key` 默认拒绝覆盖私钥** —— 覆盖不会"更新"什么，只会让此前签发的全部授权失效。
4. **`--days 0` 在 CLI 层拦下** —— 下游把"未指定有效期"理解为**永久**。
5. **`gen` 先校验参数、再联网取时**（引入 `GenerateOptions` 中间形态）—— 否则"网络不通 + 参数也写错"时
   用户会先折腾网络，修好重跑才发现错在参数上。
6. **本机钟慢于网络时间 ⇒ 用网络时间当签发时刻**（与服务器"应用内校正"同口径）。
7. **`ivt` 必填**，`--offline` / `--anchor` 是**显式降级**，不给默认值 ——
   随手用本机钟填 `ivt` 会让它从"可信锚点"退化成"又一个能被改的数"。
8. **输出只用 ASCII 标记**（`[ok]/[warn]/[fail]/[error]`）；标签列宽按**显示宽度**补空格（CJK 算 2 列）——
   第一版用 `PadRight`，中文标签明显对不齐。
9. **`NormalizePem`**：`ExportSubjectPublicKeyInfoPem()` 不带结尾换行，而项目里 `VendorPublicKey.Pem`
   带换行 ⇒ "直接替换"的片段会在最后一行多一个 diff，必须规范成恰好一个换行。

### ⚠️ 顺手揪出并修掉一个真 Bug（跨用例环境变量泄漏）

全量跑出现 2 个失败：`TimersApiTests.Firing_a_timer_manually_executes_it` 期望 200 实得 403、
`Firing_an_unknown_refid_returns_404` 期望 404 实得 403 —— 都是授权闸门拦的。

根因：`ControlServerFactory` 用**进程级环境变量**注入配置，而它对
`Server__License__Enforcement` 是"**传 null 就跳过赋值**"。闸门矩阵用例把它设成 `Enforce` 之后，
这个值**永久留在进程环境里**，此后每个宿主都被判成"Enforce + 无授权" ⇒ 所有要求动作执行的用例集体 403。
症状是"换一次运行顺序就换一批红的"，与授权本身毫无关系。

修法：该键**无条件赋值**（传 null = 删除变量）。并加守门用例
`Enforcement_setting_does_not_leak_from_one_host_to_the_next`（直接断言新宿主的
`LicenseService.ConfiguredEnforcement == Warn`）。同类前科：本文件里对 NTP 服务器列表的注释已记过一次。

## 二、本轮修掉的**真问题**（都补了守门用例 / 脚本）

1. **🔥 `SQLite does not support expressions of type 'DateTimeOffset' in ORDER BY clauses`**
   —— 遥测表最初用 `DateTimeOffset` 落库，EF 的 SQLite 提供程序**拒绝翻译** `OrderBy`，运行时抛。
   首次出现在 `QueryPowerEventsAsync`：**开关机记录一打开就 500**；客户端侧表现为
   "上报被拒（error）"每分钟刷屏 24 行。
   → 新增 `Persistence/TelemetryTime.cs`（Unix 毫秒），实体 `At` → `long AtMs`，Store 全部改写，
   `migrations remove` + `add` 重建迁移。`agent_inventories` 例外（一机一行、无排序）。
   **代价**：亚毫秒被裁掉（已用一条集成测试钉住）。
2. **上报失败日志刷屏**：三条上报循环共用一个 `_ingestFailureStreak`，指标的成功会**清掉**开关机的失败计数
   ⇒ 每轮都重记一行。→ 拆成三个独立计数器，`LogIngestFailure(..., ref int streak)`。
3. **`TelemetryStateStore` 属性名 `Path` 遮掉 `System.IO.Path`** ⇒ `CS1061: "string" 未包含 "Combine"`。
   → 改名 `FilePath` + `System.IO.Path.Combine`。
4. **开关机「详情」列是噪音**（前端验证时当场发现）：`property.Value.ToString()` 无差别转换 ⇒
   `byte[]` 变成字面量 `System.Byte[]`，Kernel-Power 41 的载荷变成一串裸数字
   （实测 19 条记录里一半以上不可读），而这一列的**唯一用途**就是与事件查看器逐条核对。
   → 改为**优先取 `FormatDescription()` 正文原文**（与事件查看器逐字一致），退路才是**纯文本型**插入字符串。
   ⚠️ 与"不解析正文"**不矛盾**：不解析 = 不从正文抠断电时刻当 `At`；这里是**原样呈现**。
   修后实测 19/19 条可读，例如 `上一次系统的 17:09:49 在 ‎2026/‎10/‎8 上的关闭是意外的。`
   —— **真正的断电时刻**就在这一列。
5. **遥测三端点漏进授权闸门分类表** ⇒ fail-closed 会把它们当"不可用"拦掉。
   失败形态极隐蔽：**有授权时一切正常，没授权时详情页一片空白**。
   → 归入 `Allowed`（只读查询与在线表同一条判据），并由 `LicenseGateTests` 的反射守门用例钉住。
6. **前端图表横轴少 8 小时**：`new Date(t).toISOString()` 产出 `...Z`，被 `fmtDateTime`（截 ISO 字符串）显示。
   → 新增 `format.ts` 的 `beijingIso(ms)`；服务端 `QuerySeriesAsync` 也把窗口归一化回 `+08:00` 再回显。
7. **`在 <script setup>` 里 `export interface` 不合法** → `ChartSeries` 移到 `types.ts`。
8. **`AgentsPanel.vue` 里 `sortBy` 重复声明** → `TS2451`。`vue-tsc` 抓到的。

## 四、本轮最后调掉的三个"看着像 bug 其实不是"

- **Core 单测 `Power_stats_on_the_realistic_machine_shape_yields_five_unexpected` 期望 5 得 4**：
  夹具写成 `{5,6,7,7,8}` 有两个重复日期 ⇒ 相邻两组事故落在 10 分钟合并窗口内被算成一次。
  **是夹具不真实，不是聚合器错**。改用明确的天偏移 `{0,1,2,3,4}`。
- **冒烟 `至少一个点带 CPU 值 0/1`**：CPU / 磁盘 / 网络都是**差分计数器**，第一帧没有"上一帧"可比 ⇒ 必然为 null。
  就绪判据却只等 1 条原始样本。→ 门槛提到 **4 条**（脚本里写明了"别调回去"）。
- **集成测试 `AverageUptimeSeconds` 期望 8h 得 2s**：夹具把两条 unexpected 插在 boot 与 shutdown **之间**，
  配对被提前关掉。这是 `SummarizePower` 的**既定语义**（意外关机确实终止了那一段在线），不是缺陷。

## 六、本轮新增的操作陷阱（会重复踩）

1. **`rm` 清理被活动进程占用的文件会"挂住"而不是报错**：本机 `rm` 被一层 safe-delete 包装
   （转调 `genie-trash` → 回收站），碰上被句柄占用的文件它**不返回失败、也不停下**——
   实测 `rm -f cs-m42-*.log` 在后台跑到 5 分钟仍在跑，`SAFE_DELETE_FAIL_CLOSED` 刷出来之后继续等。
   **对策**：删临时产物前先确认没有进程持有它；卡住就直接 `TaskStop`，
   再改用 Python `os.remove` / `shutil.rmtree` 直删（**能拿到明确的 `WinError 32`**，比静默挂起好定位）。
2. **`taskkill /PID n /F` 在 Git Bash 里必然失败**：`/PID` 被 MSYS 路径转换吃掉
   （变成 `C:/…/PortableGit/PID`），加 `//PID` 又被原样传过去。**唯一可靠写法**是走
   `python -c "subprocess.run(['taskkill','/PID','..','/F'])"`，或用 `PowerShell` 工具的 `Stop-Process`。
3. **后台常驻的 python 启动器会"扣住"子进程的重定向日志句柄**：`cs-m42-final-boot.py` 里
   `while True: time.sleep(3600)` 是**故意**的（否则子进程随包装进程被回收），
   但副作用是它持有 `*.log` 的写句柄 ⇒ 服务端/Agent 进程都杀了、日志仍删不掉。
   **收摊顺序**：先杀启动器 → 再杀 exe → 最后删文件。
4. **`agent-browser` 会话不跨 Bash 调用保持**：脚本跑完（或进程退出）后页面回到 `about:blank`，
   紧接着单独发一条 `eval` 只会得到 `[]`/`NO_TABLE`。**凡是需要页面状态的断言，
   必须写在同一个脚本里**（open → 登录 → 点页签 → 点详情 → 抽取，一气呵成）。

## 七、口径与落地范围

**用户拍板的岔路**：「**做 M4.3 温度，按推荐：驱动可选、默认不装**」。
即引入 `LibreHardwareMonitorLib`（MPL-2.0，内含 **WinRing0** 内核驱动），**默认关闭**，
**只有安装客户端时勾选才加载**；拿不到就显示"未启用"，**绝不显示 0**。

**验收标准**（`docs/M4-客户端Agent与局域网管控方案.md` §14）：
"勾选时拿到 CPU/GPU/硬盘温度；未勾选/驱动失败时显示'未启用'且**不报错不刷日志**"。

**三态语义**（贯穿契约/聚合/前端）：

| 状态 | 含义 | 触发 |
|---|---|---|
| `ok` | 已启用，且**拿到了至少一项**读数 | 勾选 + 能读到任意一项 |
| `disabled` | 未启用（**默认、正常态**） | 未勾选 / 配置没开 |
| `failed` | 一项都没拿到 | 勾选但驱动被拦，原因进 `ThermalNote` |

**落地清单**：

| 层 | 内容 |
|---|---|
| 契约 | `AgentTelemetryDtos.cs`：`AgentMetricsSummaryDto`/`AgentMetricsPointDto` 加 `cpuTempC`/`gpuTempC`/`storageTempC`（`double?`）；`AgentInventoryDto` 加 `thermalState`/`thermalNote`；新增 `AgentThermalStates`（`Ok`/`Disabled`/`Failed` + `IsValid`） |
| Core | 无新模型；新增**公共**净化函数 `AgentMetricsAggregator.Temperature(double?)`（唯一实现）；`Summarize`/`ToPoint` 都改调它 |
| Platform | `IThermalSource` 端口 + `BasicThermalSource`（Linux/降级：返回 `disabled`）；`WindowsThermalSource`（LHM，钉 **0.9.3**） |
| Agent | `TelemetryCollector.ReadThermal()`（**一次采样只读一次**）；`AgentRuntime` 接线；配置项 `Agent:Telemetry:ThermalEnabled`（默认 `false`） |
| Infra | 迁移 `20261011183719_M4_3_AgentThermal`（`agent_metrics` 加 3 列 + `agent_metrics_daily` 加均值/峰值共 6 列 + `agent_inventories` 加 2 列）；`EFAgentTelemetryStore` 落库净化 |

**「默认不装」的实现位置（关键）**：**不是**打包排除 —— 排除方案迟早被"顺手引用"破坏，且排掉后连勾选也装不上。
LHM 把 `WinRing0x64.sys` 以 **gzip 资源**内嵌在 DLL（`LibreHardwareMonitor.Resources.WinRing0x64.gz`），
**只有真的 `Computer.Open()` 才解出来落盘并加载**。所以实现就是 `Read()`/`EnsureInitialized()` 第一行
`if (!_enabled) return` —— **连 `new Computer` 都不构造**。

**`ThermalEnabled` 刻意不进服务端下发的设置 DTO**：用不用内核驱动是**现场决定**，
**不给中心端"远程给所有客户机装驱动"的能力**。

## 八、本轮修掉的**真问题**（都补了守门用例 / 脚本）

1. **🔥 温度净化只做了一半 ⇒ 在线表混进 NaN ⇒ `GET /api/agents` 整个 500**
   —— `EfAgentTelemetryStore`（存储路径）已净化，而 **`AgentMetricsAggregator.Summarize`（在线表摘要路径）原样透传**。
   `System.Text.Json` 严格模式（只开了 `AllowReadingFromString`，**没开** `AllowNamedFloatingPointLiterals`）
   **拒绝** NaN/Infinity ⇒ **一个 NaN 就使整张列表 500，一台坏客户端让所有机器从页面上消失**。
   → 把 `Temperature(double?)` 提为 Core **公共 static**，**两条路径共用同一份规则**。
   ⚠️ 这类 bug 的形态是"库里是 null、在线表是 NaN"——两条路径若规则不同就会**分裂**。
2. **`AgentThermalStates.IsValid` 写了却没人调用**：摄入侧不校验 `thermalState`，
   客户端可以塞任意字符串进库。→ `AcceptInventoryAsync` 加白名单：不合法**连 `ThermalNote` 一起清空**（`with { ... }`）。
3. **`ok` 的契约注释写错了**：原注释暗示"驱动装上了"。实测证明 `ok` = "**拿到至少一项**读数"，
   **显卡走用户态 NVAPI/ADL**（非管理员下也会 `ok` + `gpuTempC` 有值，而 `cpuTempC`/`storageTempC` 为 null）。
   → 契约（`AgentThermalStates.Ok`）与前端（`THERMAL_STATES.ok`）注释都改写为"**≠ 驱动装上**"。

## 十、本轮最重要的**实测发现**

> **`ok` ≠ "驱动装上了"。** `ok` 的真实语义是"**拿到了至少一项**读数"。

## 十四、这一刀里几个"错了就静默"的设计点（都已写进代码注释）

1. **已收字节的唯一事实来源是 `.part` / `.cs-part` 文件长度**，不是数据库计数器 ——
   两者分开维护迟早不同步，而不同步的表现是"从错误位置继续写"⇒ 长度对、内容坏。
2. **偏移不匹配回 409 + 真实 `receivedBytes`**（不是错误，是"你该从这儿接着传"）；
   客户端据此重新对齐。服务端 `AppendChunk` 若允许任意偏移写，并发重试会拼出一段怪物。
3. **摘要一律"谁落盘谁自算"**：上传完成由**服务端**算（客户端给的只当期望值），
   下载落地由**客户端**算（服务端给的只当期望值）。
4. **原子落地**：写 `.cs-part` → 校验 → `File.Move`。同卷 Move 是元数据操作，
   不存在"目标目录里躺着一个下了半截的文件"的窗口。
5. **`AgentTransferTaskDto` 里的 `TargetDir` 是"白名单里的哪一项"，不是任意路径** ——
   服务端不知道对方磁盘长什么样，**白名单的唯一执行者是客户机**。
   三种写法都认：空 ⇒ 默认目录、绝对路径 ⇒ 逐项比对、目录名 ⇒ 按末段名比对；其余一律拒。
6. **传输工作线程跑在"进程生命周期"上，不随 SignalR 长连接生灭** ——
   搬字节走普通 HTTP，与 SignalR 是两条通路；一次心跳抖动不该把正在传的 2GB 掐掉。
7. **两个 HttpClient**：控制面（补领/进度/完成/建会话）短超时；字节面**无总超时**
   （2GB 慢链路跑十几分钟正常，只能靠取消令牌中止）。塞进一个客户端就只能二选一。
8. **入队按 `ItemId` 去重**：上线补领与 SignalR 推送可能对同一条各说一次，
   两个工作线程同时传会写出两个互相踩的 `.cs-part`。
9. **回传时"客户机不能自称 kind"**（服务端强制 `collected`）；**客户机只能动自己那一行明细**。
10. **MVC 路由不带前导斜杠**：闸门按模板 `StartsWith("api/")` 判，`[Route("/api/x")]`
    会**静默判不中**⇒闸门形同虚设（详见 `AgentHubMethods` 注释）。

1. **上传必须用 `XMLHttpRequest` 而不是 `fetch`** —— `fetch` 没有上传进度事件，

2. **200 与 409 都是"成功"**：偏移不符时服务端回 409 + 真实 `receivedBytes`，

3. **必须有"偏移不前进就抛错"的守卫** —— 否则服务端若持续回同一偏移就是**死循环**

4. **上传不报 SHA256**：浏览器算 2GB 摘要要把整个文件读进内存；服务端反正会自算一份当权威值。
5. **回传的"总大小"未知时显示"已收 X"而不是百分比** —— `0%` 会被读成"一点没动"。
6. **`TransferProgress` 不带任务级状态** ⇒ 前端自己按明细重算汇总（镜像

### 六个关键取舍（都写进了代码注释）

1. **`GET config` 的 404 一律当"暂无配置"（返回 null），不翻译成"一份空配置去覆盖本机"** ——
   否则"服务端一次瞬时 404"会变成"客户机上的任务全被清掉"，代价完全不对称。
   真要清空任务就在页面上保存一次（版本号会 +1），那是一条走得通的正路。
2. **缓存的语义是"已经应用成功的那一版"，不是"拿到手的最后一版"** ——
   拉回来但应用失败的配置不该留下痕迹，否则降级运行会按一份从没生效过的配置跑。
3. 🔥 **`SemaphoreSlim(1,1).WaitAsync(0)` 把四条同步路径串起来**（Welcome / ConfigChanged / 心跳 / 手动刷新）。
   没有它，四路同时拉取会产生四个"新版本"、各自重启一遍任务 ——
   表现是"改一次配置，循环发送被启动了四次（四个循环同时往同一个目标发）"。抢不到锁的那次直接返回：
   反正真正那次拉到之后版本就对齐了。
4. 🔥 **`RefreshConfig` 指令必须 `force: true`**（刻意不看版本号）。这条指令就是为
   "版本没变但机器看起来没按配置动"准备的；看版本再决定拉不拉，等于把它废掉。
5. 🔥 **"已应用版本"与"已回报版本"分开记**。应用成功 ≠ 回报成功：回报那一刻连接刚好断了的话，
   没有"心跳里补报"这一步，页面会**永远**停在"已下发 v5 / 已应用 v4"，运维会以为机器没生效。
6. **任务执行 = "整代重启"**：换一份配置就取消上一代全部执行体、按新配置重起。
   只有一个取消源，不需要维护 `Id → 执行体` 映射（配置里的 Id 是前端生成的，复制粘贴会产生重复）。

### 三个"看起来能跑、其实会出错"的实现细节

- 🔥 **取消后不能立刻 `Dispose` 取消源**：还在 `Task.Delay` 上的任务没摘掉自己的注册，
  这时候 Dispose 会让它抛 `ObjectDisposedException` —— 一个**只在"改配置的瞬间恰好到点"时**
  才出现的偶发异常，"重试一次就好了"最容易骗过验证。收尾走 `TrackAsync`（等这一代真正退出再 Dispose）。
- 🔥 **定时发送不用每秒轮询**：算出"下一个触发点"再睡过去，且**等待切成 ≤30 秒的小段**
  （长 `Task.Delay` 在系统休眠 / 时钟被改之后会整体偏移；切段则每段重新按当前时间算，
  跨午夜的日期翻转也自然处理）。触发后**跳过 61 秒** —— `Task.Delay` 可能因定时器粒度
  在"还差几毫秒到点"时返回，于是下一次循环算出的触发点还是同一分钟，**同一时刻发两遍**。
- 🔥 **循环任务只在第 1 次打成功日志**、失败按 **1 / 每 20 次**节流。5 秒一次的成功日志
  会在一夜之间把客户机日志刷到几十 MB（M4.2 已踩过同一个坑）。
- **`HttpRequestMessage.Headers` 没有索引器**（是 `HttpRequestHeaders` 不是字典）⇒
  必须 `TryAddWithoutValidation`；写 `headers[name] = value` 直接 `CS0021`。
  （`HubConnectionOptions.Headers` 才是字典，那边可以索引赋值。）

### 会话侧的那一块**明确留白，而不是假装能用**

`ISessionCommandChannel` 当前注册的是 `UnavailableSessionCommandChannel`（带一句可读原因，
会进启动自述日志）。「延时启动程序 / 音量」会被**明确跳过并说明原因**，
而不是静默什么都不做 —— 静默失败是这类"Session 0 看不到"的功能最难查的形态。

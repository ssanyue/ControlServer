## #42 · 修掉「会话活性判据把**静止画面**判成断线」（M5.1 遗留缺陷）

**起因**：M5.4-b 已收官，按例做"下一批（M5.4-c）开工前核查"。
核查**不是复现出来的，是读出来的** —— 读 `RemoteSessionRegistry.Sweep` 的**判据来源**时发现：
**三处说明写着同一句话，而代码没有实现它。**

| 说明（三处，措辞一致） | 代码实际做的 |
|---|---|
| `IdleTimeout`：「不再收到帧、**也没有状态上报**时，多久判成断了」 | `last = LastFrameAt ?? StartedAt ?? RequestedAt` |
| `RequestedTimeout`：「多久还没等到**任何**状态上报就判没起来」 | `now - RequestedAt > 20 秒` |
| `Sweep` 自己的文档：「清掉已断的（**帧停了、状态也不再上报**）」 | 同上 |

**触发路径（产品主线、必现）**：DDA 是**增量投递**的 ⇒ 桌面没变、指针没动就不给新帧
（被控端日志自己写着「这是正常现象，**没有丢帧**」）⇒ 中心 `LastFrameAt` 停住
⇒ **15 秒后被判死** ⇒ `Close` 之后被控端下次推帧收 `Rejected` ⇒ **整路会话结束**；
观众重开，15 秒后再死一次。
🔥 **"展厅里定格在一张图上的机器"就是这一台** —— 而它恰好是这套系统最典型的场景。

🔥 **为什么它从来没被发现**：M5.1 起的每一次真机冒烟，屏幕上**都有东西在动**
（编辑器光标在闪 / 鼠标在动 / 任务栏时钟在跳）⇒ 总有帧 ⇒ 判据永不触发。
**"没有东西在动"这个前提，冒烟脚本一次都没造出来过。**

**修法**：判据收成**一个字段** `Entry.LastAgentAt`（= 最近一次收到这个被控端的**任何上行**），
`Observe`（帧）与 `ApplyState`（状态上报）各刷新一处；`Sweep` 的两个分支都改用它
（`requested` 那支的计时起点从 `RequestedAt` 改成"最后一次回话"）。
🔥 **为什么不是"各处补一个 if"**：这条链路上还有**第三条上行 = 音频**，而它**刻意不算**
（没声卡的机器照样在正常推画面；反过来"只有声音在走"也不该让一路死会话赖着不走）
⇒ 做成一个字段、并**要求每处新上行都明确表态**：下一个加上行的人会**看见**它，
而不会只看见自己要改的那个方法。音频那处因此写了一整段"为什么不算"，并有用例 `E` 钉住。

⚠️ **取舍（必须写明）**：修完之后，**"服务活着在回话、但托盘那条流真的卡住"**不再被自动清掉。
**这是故意换的** —— 协议层上**「桌面静止」与「托盘卡住」长得一模一样**（都是"没帧、状态照报"），
而前者每 15 秒毁一次会话、后者只是画面冻住（页面读数会明说 0 fps，用户还能自己点「结束会话」）。
真要分开，得让被控端**上报「本机桌面静止中」**（它已经知道 —— `idleTicks`）⇒ 记入 `M5.0-实施清单.md` §6。

⚠️ **顺带记一条不一致**（只记录、不改）：中心 `RequestedTimeout`（20 秒）vs
被控端 `StartupFrameBudget`（30 秒）—— 中心可能在被控端自认"还在预算内"时先把它清掉，
而现场看到的是"这台机器连不上"。要动就得先统一"多慢算太慢"的口径。

**回归网**：新增 `tests/ControlServer.Server.IntegrationTests/RemoteSessionSweepTests.cs`（**5 条**）。
**修前 5 条里 2 条红**（正是那两条"说明写着帧或状态、代码只看帧"的）；**修后 5/5 绿**。

### 分片的设计结论（三条候选，只留一条）

- ❌ **甲 · 端到端**（被控端分 → 浏览器合）：中心 `Fanout` 的丢弃单位是**"一条消息"**
  ⇒ 它会丢掉**同一帧的中间一片** ⇒ 前端拼出**长度对、内容错**的码流 ⇒ **花屏，且中心与前端都不报错**。
  要救就得把队列的丢弃单位改成"帧" —— 而那**等于中心已经在重组了**（只是换了个位置）。
- ❌ **丙 · 只抬上限**（`MaximumReceiveMessageSize` → 64 MiB）：那是**整条连接**的上限，
  一帧畸形就让连接吃 64 MB。**分片的全部意义就是把压力摊平成多条小消息。**
- ✅ **乙 · 终止在中心**：跳 4/5/6 **零改动**、前端**零改动**、`Latest` 语义不变。
  且🔥 **只有"装不下"的帧才分片** ⇒ **2160×1440 与 4K 的行为一个字都不变**（**惰性**改动）。
  🔥 **单槽重组，不需要定时器/超时/后台清扫** —— 因为可以**论证**：
  第 3 跳是单条顺序连接上的顺序流（`await sink(frame)` 之后才读下一帧；分片同帧内也顺序 await）
  ⇒ **下一个帧 id 出现时，上一帧要么已齐、要么已永久丢**。
  ⚠️ 拼字节**离开 `_gate`**（十几 MB 的拷贝压在全局账本锁里 = 让所有会话的所有帧去等它）。

### 立了一条"不改代码也要先记下"的纪律

**「降阈值跑通」≠「8K 跑通」**：本机屏只有 2160×1440 ⇒ 8K 真机端到端**物理不可得**。
冒烟可以加个临时参数把分片阈值降到 64 KB，让**正常帧也走分片路径** —— 那证的是
**"分片机制没有 bug"**；而**"8K 会不会撞"是算术**（`ceil(帧字节 / 片上限)`），由单测覆盖。
**把这两件事说成一件，就是编数字。**

### 🔥 本轮的核心是一条纪律：**「用例造的数据，必须由生产那一份代码造出来」**

分片这条路有两端（**被控端切** / **中心拼**）。如果用例自己再写一份切片，
那么"3 片拼回来逐字节相等"证明的是**「用例切的片能被拼回来」** ——
而生产切片器把最后一片多切一个字节时，**用例全绿**，故障在现场表现为"画面从某个位置开始花"。

⇒ 新文件 `src/ControlServer.Contracts/RemoteFrameChunker.cs`（`CountFor` / `NeedsChunking` / `Slice`）
是**这条链路上唯一的切片实现**，**被控端真正切片时用它，用例造片时也用它**
（`RemoteFrameReassemblyTests` 里原先那个私有 `Slice` 已删）。
它**不写任何字面量尺寸**（三个尺寸数仍然只有 `SignalRMessageBytes` 一个根）。

⚠️ **但这条纪律有边界**：有五种片**生产代码永远造不出来**（片数荒唐 / 下标越界 / 片数为 1 /
同序号片数不一致 / 累计超单帧上限）—— 那正是它们要防的东西 ⇒ **必须在用例里手搓**。
判据是「**生产代码造得出这种形状吗**」，不是"能不能偷懒用现成的切片器"。

### 被控端接线：为什么把 `PushRemoteFrameAsync` 拆成两层

`PushRemoteFrameAsync`（生产唯一入口）→ `internal static PushFrameAsync(invoke, frame, ct)`（**全部逻辑**）。
**收一个"发射器"委托**的理由：这段逻辑里三条判据都只能靠"看着到底发出去了几条什么消息"来验
（① 惰性：2160×1440 / 4K 仍是一整帧一条消息；② 片数 = `ceil(len/片上限)`；③ 中心说停就停），
而 `HubConnection` 是**具体类、方法不可替** ⇒ 不抽这一刀，`AgentFrameChunkingTests` 就无从下手。
这与 `RemoteSessionCoordinator` 的 `FrameSink`/`AudioSink` 是同一套路：**接缝开在"谁真正动手"那一步**。

## 步 5：把「请补关键帧」接上（四跳链路 ＋ 节流）

### 链路（一条反向信号，横跨两个进程）

```
中心 RemoteFrameReassembler 拼不起来
  └─ ack.NeedKeyframe = true（步 2 就发了）
       └─ PushFrameAsync 读它（按帧累积，循环外只问一次）   ← 发帧路径上
            └─ Coordinator.RequestKeyframe（1 秒节流）
                 └─ 指令管道 action=keyframe
                      └─ Host.RequestKeyframe → Session.RequestKeyframe（Interlocked 标志）
                           └─ 泵下一轮 wantKeyframe = true ⇒ 编码器出 IDR
```

### 三个设计判断（都不是"顺手"）

1. **节流放在服务侧（收到的那一侧）**：中心只知道"我这帧拼不起来了"，它**不知道对面多久能补上一个** ——
   让它去重＝让它猜。1 秒 ≈ 12 帧一个 IDR：既是"恢复得快"与"不把码率打爆"之间的一格，
   也是中心持续丢帧时能长期承受的上限。
2. **按「帧」去重，不按「片」**：一帧十几片，中心在同一故障下**每片都回**这个标志。
   每片各要一次 ⇒ 把一次丢帧放大成**一路 IDR**（8K 的 IDR 正是最贵的东西）。
3. **两条纪律的例外必须写出来**：`Active._lastKeyframeRequestTicks` 用 `Interlocked`+CAS
   **不进 `_gate`**（调用点在发帧路径，每帧一次）；`RequestKeyframe` 是**同步 `void` +
   fire-and-forget**，被调方法**全包 try**、异常落 Warn（`void asyncFn()` 那条纪律的显式兑现）。

### 🔥 顺带修掉一个静默洞

泵里原来是 `wantKeyframe = false;`（**无条件**清）。而 `forceKeyframe: true` 只是**请求**不是**命令** ——
编码器可能这一帧给不出 IDR（忙 / GPU 重建 / 参数集没就绪）。无条件清 ⇒ 请求**永久消失**，
而两边日志都写着"请求已送出、帧也发出去了"。改成 `if (payload.IsKeyframe)`，
与同段代码里 `_oversizeKeyframeStreak` 只在关键帧上清零是同一条纪律。

## M5.4-c② · 静止降帧 ＋ 上报（10-17 中午）

### 步 7：`DesktopIdleMs` 的**七跳**（本方案原稿漏写的一段，见 §4.4）

抓屏器 `null` → 托盘 `_lastNewFrameAt`（QPC）→ `Session.DesktopIdleMs` → 托盘 `Handle` 的
`desktop-idle` → **服务每秒问一次**（1 秒超时）→ `Active.DesktopIdleMs` → `NewState` →
`AgentRemoteSessionStateDto` → 中心 `_desktopIdleMs` → `RemoteSessionDto` → 页面。

三条**必须钉死的细节**：

1. **`null` / `0` / `12000` 三态绝不合并**：`null`＝这台机器不提这件事（旧客户端）⇒ 页面画 `—`；

3. **静止时长必须由抓屏器说，不由服务自己数"多久没收到帧"**：没新帧有三种成因
   （桌面真没变 / 编不出来 / 链路丢了），计数上一模一样、处置相反。

### 🔴 第一轮 3 条红 —— 红得非常有说服力

### 一次**错误的根因假设**（写下来因为它很像真的）

第一反应："DWM 在无脑 present，只要任何被遮挡的程序在自绘，`AccumulatedFrames != 0`"。
写了个临时探针（已删）直读 `WindowsDxgiScreenCapturer.Diagnostics` —— **假设当场被推翻**：

```
accum=0 meta=0 shape=4096 → 23/24 次（DWM 没在乱 present）
PointerUpdated            → 22/24 次   ← 真凶
```

### 真因：**盖布自己没有光标**

`WNDCLASSW.hCursor = NULL` ⇒ 光标到了这块窗上"没人负责它" ⇒ 系统反复重设
⇒ DDA 每帧报一次指针更新（`PointerShapeBufferSize` 每帧 4096，整个形状重发）
⇒ `pointerMoved = true` ⇒ `changed = true` ⇒ **静止计时永远归零**。

一行修掉：`wc.hCursor = LoadCursorW(NULL, IDC_ARROW)`。同一探针立刻变
`shape=0`、`PointerUpdated = 0`、`TimedOut/NoDesktopUpdate = 23/24`。

🔴 **教训（已升级成铁律 15）**：`DesktopIdleMs` 的判据是「抓屏器没报新帧」，而
"抓屏器报新帧"里有一条**与画面无关**的来源 —— **指针**。任何"让桌面静止"的工具
都必须先把自己那只手指安顿好；而**像素连拍对这条完全瞎**，它看到 0 变化，
会把人引向"产品没退避"（这次被带偏半个多小时）。

### 绿了（26/26）

```
· 退避：… 桌面已静止 2.1 秒，抓屏轮询从 12 fps 退避到 2 fps（这只是省 CPU，**不是停止**：…）
· 恢复：… 桌面恢复变化，抓屏轮询立刻回到目标帧率 12 fps（此前退避了 7.9 秒）。
· 全程 streaming；撤布后 framesReceived 107 → 116
合计 26 项：通过 26，失败 0
```

顺带修掉一处**输出指向错**：两条 check 的 detail 在 PASS 时也印着"没等到…"的失败说明
（铁律 9 ②「有说明还要问指向对不对」），已改成按结果分支。

## M5.4-c③ 前置实验：**运行中改码率这件事，被实测否掉了**（10-17 14:0x）

> 方案 §5.2 原本写的是「新增 `tune` 下行指令，带 `MaxFps` / `BitrateBps`」。
> 文档自己也留了 ⚠️：「码率运行时可改需先实测，不许当成已知可用」。
> 这一步就是去做那个实测 —— **结果是：不行**。

### 怎么测的（临时探针，已删）

真机上建 MF 硬编码器 → 喂**逐帧全帧噪声**（不可压缩 ⇒ 字节数完全由码控决定）→
运行中直接调 `ICodecAPI::SetValue`，同时 `GetValue` 回读 ＋ 用**字节/墙上时间**交叉验证。
环境：Intel® Quick Sync Video H.264 Encoder MFT｜1280×720@30。

### 结果（同一台机器，两轮）

| 码控 | 旋钮 | `SetValue` | 回读 | 实测码率 | 判读 |
|---|---|---|---|---|---|
| Quality（**生产用的就是它**） | Quality 70→20 | **S_FALSE** | **仍 70** | 85.48→85.24 Mbps | 没接受 |
| Quality | Quality 20→70 | S_OK | 70 | 85.47 | 只在"设成当前值"时 S_OK |
| CBR | MeanBitRate 8M→2M | **S_FALSE** | **仍 8e6** | 8.63→8.40 Mbps | 没接受 |
| CBR | MeanBitRate 2M→8M | S_OK | 8e6 | 8.34 | 同上 |

三条必须一起读：

1. **运行中改不动**（回 S_FALSE、回读不变、字节不变）。**S_OK 只出现在"设成它已经是的那个值"时**
   ⇒ 只看返回值的人会以为成功了。
2. 🔴 **生产是 `Quality` 码控**（`MediaFoundationEncoderOptions.Default` 默认），
   而在 Quality 下 `MeanBitRate` **连"上界"都不是**：8 Mbps 的提示喂噪声跑出 **85 Mbps**（差 10 倍）。
   ⇒ **这条路上根本没有"码率"这个量可调**；要限码率必须换码控模式。
3. 两种改法都**没有换关键帧**（计数 0）—— 因为没生效，"会不会打断 GOP"轮不到发生。

### 那就只能重建，重建的价（720p 实测 ×3 轮）

`TryCreate` **137 / 141 / 212 ms**；建好后到"第一帧真的出来" **147–166 ms** ⇒
**观众看到的空窗 ≈ 0.3 秒**；重建后首帧**必为关键帧**（噪声内容 691 KB，真实桌面小得多）。

### 于是 ③ 的范围要缩

| 项 | 原设计 | 实测后 |
|---|---|---|
| 帧率 | `tune` 改 `MaxFps` | ✅ **成立**（本机 pacing，不碰编码器，零代价；② 已有退避，只差"从中心改"） |
| 码率/质量 | `tune` 改 `BitrateBps` | 🔴 **不成立**（只能重建，≈0.3s 空窗；必须有冷却＋迟滞，否则来回重建＝一直黑） |
| 分辨率 | 不做 | 不变 |
| 中心侧反馈源 | 前端 overflow / 解码重建次数 | **现在没有**；没有它，码率无从判起 |

### 一条**度量口径**的错（第一版探针）

第一版按「出帧数 ÷ 30」算时间跨度 ⇒ 一半帧被异步编码器忙丢，跨度被算短一半，
Mbps 直接虚高 2 倍（171 vs 真值 85）。**忙丢的帧也是时间** ⇒ 只能按墙上时间算。
这与铁律 9 ③ 同一类：**数字对不上时先怀疑自己量的东西**。

### 诚实边界

- 这只是一台机器上的**一个** MFT（Intel QSV H.264）。NVENC / AMF 未必一样
  ⇒ 不许写成"MF 硬编一律不支持运行时改码率"；它证明的是**不能假设它行**。
- 720p 的重建价 ≠ 4K 的重建价（4K 本机不可得）。

### 🔴 一处原设计被改正：**证书不进备份**

改正后的口径：`https/` 里**只带 `controlserver-ca.crt`（公钥）**；私钥与口令、`downloads/`、
`logs/`（默认）、`-wal/-shm` 一律跳过，并且**逐项写进 manifest 的 `skipped`**（带理由）。

## M6.2 安全审计（收官）

### 结论：41 项判定 —— 通过 21 / 已修 7（=4 个必修项）/ 已知风险 13

**必修 4 项（全部已修＋有用例）**

1. **口令是单轮 SHA-256**（`Sha256PasswordHasher`，注释写"待迁移"却从未迁）⇒ 新增 `Pbkdf2PasswordHasher`
   - `pbkdf2-sha256$210000$<salt>$<key>`，**迭代数写进值里**（否则调高默认值＝全员登不进来）；
   - 旧值**先能验**、成功登录后**就地重算**（rehash-on-login）—— 放在失败分支＝任何人可锁死账号；
   - 登录路径原本**不校验长度** ⇒ 超长口令直接喂哈希（免费 CPU 放大），现超长按"口令错误"且不进入派生。
2. **登录端点无限速** ⇒ 按 IP 固定窗口（默认 20 次 / 5 分钟，可配可关）。
   - 账号锁定挡不住：①换用户名扫（每个名字试 4 次）；②**故意锁死管理员**（5 次错密码锁 15 分钟，循环＝永久 DoS）。
3. **`Server:Security:AllowedCidrs` 是死配置**（M1 就写在 `SecurityOptions` 里，**全仓 0 处消费**）⇒ 接线
   - 空＝不限制；非空＝只放白名单＋**回环永远放行**；**解析失败拒绝启动 + 退出码 1**（fail-closed）；
   - `FromConfiguration` 同时认 JSON 数组与逗号分隔单行（环境变量**绑不出数组**，只认数组＝现场那行被静默当空）。
4. **无基线安全响应头** ⇒ `nosniff` / `X-Frame-Options: DENY` / `Referrer-Policy: no-referrer`。
   - **CSP 没加**：Vue 产物有内联样式，瞎写＝白屏（挂账）。

**顺带修的**：换 PBKDF2 后"账号不存在"与"存在"的耗时差从微秒变几十毫秒 ⇒ 用户名可枚举。已补**时序对齐**（不存在也跑一次 dummy Verify）。

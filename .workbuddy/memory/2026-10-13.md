### 四道关卡（任何一关不过就丢弃，且**绝不回包**）

1. **本机开关** —— `Agent:Tasks:Enabled=false` 时**根本不绑定端口**（不是"绑定了再丢弃"：
   不开的端口在 `netstat` 里看不见，那才是"关"该有的样子）；
2. **来源 IP 白名单** —— 名单为空则放行（白名单只是纵深防御，真正判"合法"的是签名）；
3. **HMAC-SHA256 验签** —— 密钥由本机 `agentKey` 经 HKDF 派生；
4. **防重放** —— 同一 `nonce` 窗口内只生效一次。

### 五个关键取舍（都写进了代码注释）

1. 🔥 **丢弃日志必须按时间节流**（第 1 条立刻记，之后每 5 秒一条 + 附带被压掉的总数）。
   一次灌包可以是每秒上万条，逐条记录会把客户机日志写爆、日志滚动还会把有用的历史挤掉 ——
   **"防重放"的实现反过来变成一种 DoS**，这是最讽刺也最容易漏的一处。
2. 🔥 **防重放表做成进程级字段，不是"每次监听一份"**。换个端口就重置的话，
   攻击者只要等到一次配置变更就能重放旧报文。
3. 🔥 **`TryVerify` 把 `nonce` 显式交出来**，而不是让监听器自己再切一遍报文。
   切分规则是"线路格式"的一部分，只能有一处实现。
4. 🔥 **Windows 上取消挂起的 UDP 接收，抛的常常是 `SocketException(995, WSA_OPERATION_ABORTED)`
   而不是 `OperationCanceledException`**。少了这条 `catch ... when (ct.IsCancellationRequested)`，
   每次停监听都会多打一行"网卡抖动"的假警告 —— 而假警告会让真警告变得不可信。
5. **关机 / 重启用 `shutdown.exe` 而不是 P/Invoke `ExitWindowsEx`**：后者只"通知系统准备关机"
   （不会真的断电，还得自己调 `SetSystemPowerState`），而 `shutdown.exe` 一把做对；
   更要紧的是 `/t 5` 那个延时期内可以用 `shutdown /a` **撤销** —— 误发指令后有救回来的机会。

### 防火墙：**打破了"客户端不开任何入站端口"这条旧承诺**

`deploy/windows/install-agent.ps1` 与 M4 方案 §5.5 原来都写着"客户端不开任何入站端口、
安装时不建任何防火墙规则"。M4.5 的 UDP 指令通道是这个承诺的**唯一例外**，
而 Windows 防火墙默认丢入站 ⇒ 规则不建的话，通道**能绑定成功但一个包都收不到** ——
失败形态正是本项目最讨厌的静默失败。

**用户拍板：安装时按「程序」放行**（不是按端口、也不是运行时动态加规则）：

- **为什么不按端口**：通道端口由中心下发、可随时改（默认 8080，允许范围 1024~65535），
  端口级规则没法预先写死 —— 改一次端口就得重写一次规则，改漏了就是"指令发出去机器没反应"。
- **程序级规则**：`-Program` 指向 Agent 服务 exe，一次装好、之后换端口不用再动。
  作用域确实比端口级略宽（该程序可监听任意 UDP 端口），但**鉴权在程序内部**
  （验签 + 白名单），防火墙这层只解决"包收得到收不到"。
- 规则显示名固定 `ControlServer Agent UDP`，重装先删后建（幂等）；
  **无条件创建**（通道启不启用是中心下发的，装的时候还不知道；通道关着时这条规则无副作用）。
- 新增 `-SkipFirewallRule` 供"现场有统一防火墙策略 / 本机不用该通道"跳过（跳过会**警告**，不静默）。
- **卸载侧刻意与安装侧相反处理失败**：安装侧吞掉异常（不让服务装不上），
  卸载侧**不吞**（要明说"请手工删规则"）—— 吞掉就留下一条谁也看不见、谁也想不起来的悬空规则，
  下次有别的程序恰好装到同一路径时会莫名"白得"一次入站放行。

### 六个关键设计取舍

1. **协议 = 一次连接 = 一条指令**（一行紧凑 JSON 进、一行出来）。不搞长连接 + 请求 Id 配对：
   这里送的是"按一下音量 / 拉起一个程序"这类低频动作，本地管道上一次连接的开销远低于一百微秒，
   而配对协议要额外维护"谁在等哪个 Id"、处理半截响应、处理并发写。
2. 🔥 **管道名按会话编号区分**（`ControlServer.Agent.Session.<n>`）：托盘的单实例互斥量是 `Local\`
   作用域（每会话一个）⇒ 多用户同时登录时会有**多个托盘**；共用一个名字的话只有先到的能建起管道，
   服务此后固定敲到"先登录那个人的桌面"，音量改在别人账户里而日志毫无异常。
3. 🔥 **权限不设自定义 ACL，用命名管道的默认 DACL**：`CreateNamedPipe` 在 `lpSecurityAttributes = NULL`
   时给的是「SYSTEM 全控 + 管理员全控 + 创建者全控」—— 创建者是当前用户（托盘），要连的只有 SYSTEM（服务），
   三方恰好都在。刻意不引 `System.IO.Pipes.AccessControl`：多一个包、多一份要跟着权限模型维护的东西，
   而安全性并没有变强。（默认 DACL 顺带带来一条有用的后果：**同机其他普通用户连不上**。）
4. **`IsSupported` 与 `IsAvailable` 必须分开**：前者 = "有朝一日能不能用"（平台 + 是否接线），
   后者 = "此刻能不能用"（有没有人登录、托盘在不在）。只给一个布尔值，这两种情形会被迫同样处理，必然错一边。
5. 🔥 **延时启动程序从"不可用就跳过"改成"先等用户会话再计时"** —— 服务在开机时就起来，
   而托盘要等用户登录 ⇒ 服务启动后的头几十秒里"会话侧不可用"是**常态而不是故障**。
   原来那句"已跳过 + 一条 WARN"等价于"开机自启的程序永远不启动"。等待不设上限（换配置/停机/被吊销会取消它），
   每 30 分钟提醒一次，并把"若本机没装托盘就不会执行"一起说出来。
6. **音量只报"从系统读回来的真实状态"**：`HostAudioResult.State` 是操作**之后**重新 `GetMute` /
   `GetMasterVolumeLevelScalar` 的结果，服务侧日志因此能写"音量已调高：50%（未静音）"，
   而不是"指令已发出"。两个字段都可空 —— 读不到就是 null，**不用 `false` 冒充"没静音"**。

### 实测抓出来的两个坑（都是"看起来能跑、其实会错"那一类）

- 🔥 **Windows 上连一条不存在的命名管道不会立刻报错，而是一直等到超时**。
  第一版 `RoundTripAsync` 用 5 秒的请求超时当连接超时，于是"托盘不在"时一条音量指令要 5 秒才回话
  （重试一次 = 10 秒）。新测试 `Missing_Tray_Fails_The_Send_Without_Throwing` 跑了 5 秒才失败，直接暴露。
  修法：**连接超时独立且短**（400ms），与请求超时（5s）分开。
- 🔥 **`ConnectAsync(ct)` 取消时抛的也是 `OperationCanceledException`**，与"调用方取消"同一个类型。
  原来的 `catch (OperationCanceledException) { throw; }` 会把"托盘不在"伪装成"任务被取消"往上冒
  ⇒ 整条任务链静默中断，日志里只留一句没头没尾的取消。
  判据只能是 `when (cancellationToken.IsCancellationRequested)`。

### 另外三处"刻意这么做"

- **探测连接必须静默**：服务每几十秒探一次可用性；若托盘每次都记一行"连上没说话"，
  托盘日志会被刷爆，而真正超时的那条反而被埋掉。约定：读到 `null`（连上就断）= 探测 ⇒ 不记；
  **读超时** = 卡住的客户端 ⇒ 记一行。
- **管道对象建一次、反复用**（连接之间 `Disconnect`）：改成"每处理完就 Dispose 再重建"
  会在两次之间留一段"管道不存在"的空窗，撞上的服务端会拿到一次连接失败 ⇒ "偶发一条指令没反应"。
- **`ProgramLauncher` 显式设工作目录**为程序所在目录：不设时 ShellExecute 出来的进程工作目录可能是
  `C:\Windows\System32` ⇒ "程序找不到自己旁边的配置文件"，而现象是"程序起来了但行为不对"。
  另外失败时把 Win32 错误码一起带出来（`2` = 路径不存在 / `5` = 拒绝访问）。

## 三条设计约定

- 🔥 **前端不复制校验规则**：判据只有一份，在 Core 的 `AgentConfigRules`（服务端保存前与客户端应用前共用）。
  前端把用户填的原样送上去，再把服务端返回的问题清单**原样**显示。`PUT` 不过回 400，
  `message` 是**全部**问题用「；」连接。已验证页面显示的那串字与 400 响应**逐字相同**。
- 🔥 **保存后一律用服务端返回的配置重渲染**：服务端会静默归一化
  （`9:5` / 全角冒号 → `09:05`、去空白、协议名大写、时刻去重排序）。不重渲染就永远看不出
  "我填了两个时刻、列表里只剩一个"。
- 🔥 **版本条是四态**，不能压成"相等 / 不等"：`never`（`appliedConfigVersion === null`，**从没回报过**）/
  `synced` 已生效 / `pending` 尚未应用 / `ahead` 版本异常。**`null` 绝不显示成 `v0`** ——
  那与"已应用 v0"是两回事。三种"不一致"的解释文案各不相同（合成就丢掉了"该不该去处理"）。

## 本轮抓出并修掉的三个缺陷（两个服务端 + 一个前端）

都是"不报错、就是一直不对"的类型：

| # | 缺陷 | 根因 | 修法 |
|---|---|---|---|
| ① | `AppliedConfigVersion` 在**所有** API 响应里恒为 `null` | `AgentHostRegistry.ToDto` 构造 DTO 时漏传该字段；它是**可空**的，漏传不报错。三处调用点都只 `with { ConfigVersion = … }`，谁也没补 | 修在 `ToDto` 里带上 |
| ② | 内存快照"同步刷新"是**静默空操作** | `AcceptAppliedAsync` 用 `ApplyChange(host with {...})`，而 `ApplyChange` **只读 `IsRevoked` / `LastSeenAt`**；且 `_hosts` 是**整体换代的不可变数组**，改 record 也反映不进去 | 新增 `SetAppliedConfigVersion(id, v)`：`Clone()` 数组、只替换那一个元素、只增不减 |

# 现场故障：「服务端不能发现装了客户端的电脑」——根因定位（未改产品代码）

## 结论先行

**发现（UDP 广播）没坏，坏的是注册被拒；而且服务端对"被拒"一个字都不记。**

现场（`192.168.101.177` 装了客户端）的真实服务端 `log-2026-10-13.ndjson`：

```
每 60 秒一轮（10:57:42 → 11:36:48，共 40 轮）：
  [Discovery] 已应答客户端发现请求：0CF7-B685-5178-81AC（Agent 0.1.0，来自 192.168.101.177:xxxxx）
  [Enrollment] ← 无
  HTTP POST /api/agents/register → 400
```

服务端**一直在应答**，客户端也**一直拿到** `CS-HERE` ⇒ 发现链路完好。
但注册**永远 400**，于是机器永远进不了在线表。

## 根因（两条，都有硬证据）

1. **客户端没有任何注册凭据。** 用户实例的真实数据库（只读复制后查询）：

   | 表 | 行数 |
   |---|---|
   | `agent_hosts` | **0** —— 从来没有客户端注册成功过 |
   | `enrollment_tokens` | **0** —— **从未生成过任何令牌/加入码** |

   而 `AgentEnrollmentService.ResolveCredentialAsync` 要求"安装包令牌 / 加入码"二选一，
   两者都空 ⇒ `("missing", "缺少注册凭据：…")` ⇒ `AgentsController.Register` 映射成 **400**。

2. **节奏证明它是 400 而不是 401**：401（凭据错）走 `RevokedRetry = 5 分钟`，
   400（缺凭据）走 `IterationOutcome.Retry`（退避 1→2→4…→**60 秒**饱和）。
   现场日志**恰好 60 秒一轮** ⇒ 确认是"没带凭据"，不是"凭据不对"。

## 复现（`.tools/discovery-diag/run.sh`，新建，1 分 23 秒）

真服务端 + 真客户端，只改**有没有凭据**这一个变量：

| | 阶段 A（无凭据） | 阶段 B（带加入码） |
|---|---|---|
| 客户端发现 | ✅ `发现中心服务端：http://…` | ✅ 同左 |
| 服务端应答 | ✅ 每轮 `已应答客户端发现请求` | ✅ 同左 |
| 注册 | ❌ **4 次全 400** | ✅ `register → 200` |
| 服务端日志里的原因 | **完全没有** | `[Enrollment] 客户端注册成功` |
| 在线表 | 0 台 | **1 台，状态 online** |
| 客户端自己的日志 | `注册失败（missing）：缺少注册凭据…` | `注册成功：Id=1` |

与现场日志的签名**逐字一致**（轮询间隔、状态码、服务端可见性）。

## 三个缺陷（产品侧）

1. 🔥 **服务端对"被拒绝的注册"零可见性**（最要命）。
   `AgentEnrollmentService` 的 `Fail(...)` 路径**一条日志都不写**；
   Serilog 请求日志只有 `HTTP POST /api/agents/register → 400`，**不带原因**。
   ⇒ 运维在服务端只能看到"有请求进来、400 了"，看不错在哪。
   客户端那边的日志（在另一台机器上）反而写得很清楚。
2. 🔥 **三处文案把"发现"说成了"出现"**，且互相印证，把人锁死在错误方向上：
   - `Server/HostedServices/AgentPresenceHostedService.cs:83`
     `"客户端在线表：暂无注册记录（安装客户端后会在 1 分钟内自动出现）。"`
   - `web/src/components/AgentsPanel.vue:448`
     `"用下面的「客户端安装包」…安装后，它会自动出现（通常 1 分钟内）。"`
   - `deploy/windows/ControlServer.Agent.iss:170/174`
     向导副标题 `"这两项都可以留空 —— 留空时客户端会自动发现同一局域网内的中心服务端。"`
     + 标签 `"注册令牌（可留空，之后用「加入码」补配）"`
   **事实**：留空 ⇒ 发现一定成功，注册一定失败，机器**永远不会出现**。
3. **安装向导弹不出"加入码"**：只有 `/TOKEN=`（且写死进 `-Token`，见 `.iss` 的
   `GetTokenValue`），没有 `/JOINCODE=`，也没有对应输入框 ⇒ 想用加入码必须装完再手工改
   `appsettings.json` 并重启服务（`install-agent.ps1 -JoinCode` 支持，但向导不暴露）。

## 脚本里踩到的四个坑（都是**我自己的**，不是产品缺陷）

1. 🔥 **代理会吞掉注册请求**。本机 Git Bash 配了 HTTP 代理，而 .NET `HttpClient`
   默认读 `HTTP_PROXY`/`http_proxy`（`HttpClient.DefaultProxy`）⇒ 客户端的 POST 被送到代理，
   **服务端一条注册请求都收不到**，客户端报
   `'u' is an invalid start of a value. Path: $ | LineNumber: 0`（那是代理回的纯文本）。
   广播走 UDP 不经代理 ⇒ **发现照常成功**，所以症状是"发现好了、注册没反应"，
   极容易被误判成产品缺陷。修法：起客户端时 `env -u HTTP_PROXY -u http_proxy …`。
   ⚠️ 现实世界同样适用：客户机上装了全局代理软件会出现一样的效果。
2. 🔥 **NDJSON 里没有中文**。`LogService` 用 System.Text.Json 写，默认把非 ASCII
   转义成 `\uXXXX`（`"Message":"\u6CE8\u518C\u6210\u529F…"`）⇒ 直接 `grep 注册成功` **永不命中**，
   而按 JSON 解析的查看器却正常显示。表现为"日志里明明有、判定却说没有"。
   判定要 python 解析后匹配。
3. **Agent 的自述日志不落 stdout**，只落 `LogService` 的 NDJSON
   （stdout 只有 Host 那两三行）⇒ 盯 stdout 会一路等到超时，误判成"客户端什么都没干"。
4. `AgentListDto` 的字段是 **`items`**，不是 `hosts`。

## 现场立刻可用的补救（不需要改代码）

1. 网页「客户端」页 → **生成加入码**（2 小时、一次性）或**生成安装包令牌**。
2. 在客户机上把凭据写进 `C:\Program Files\ControlServer Agent\appsettings.json`
   的 `Agent:JoinCode`（或 `Agent:EnrollmentToken`）。
3. 重启服务：`Restart-Service ControlServerAgent`（或在 `%ProgramData%\ControlServer.Agent\logs\`
   看到 `注册成功`）。

## 🔥 超出拍板范围的一处改动（**复现脚本当场撞出来的**，已如实标注）

`DiscoveryListenerHostedService` 的收包 `catch (Exception)` 里，**UDP 复位从 Error 降到 Debug**：

```
Error [Discovery] 接收发现广播失败（监听继续） | SocketException: 远程主机强迫关闭了一个现有的连接。
```

- **机制**：Windows 上 UDP 的伪错误。服务端把 CS-HERE 回给客户端**那一轮的临时端口**，
  而客户端**每轮发现都新开一个 socket**（关闭后）⇒ 对端 ICMP「端口不可达」被记在这个 socket 上，
  下一次 `ReceiveAsync` 时以 `SocketException(10054 / ConnectionReset)` 抛出。**自愈**。
- **为什么必须改**：它**每台机器每次重启都来一条**。挂在 Error 级上，百来台机器就足以把
  真正要看的日志（我们刚加的 `Enrollment` 告警）淹掉 —— **正是本次修复要解决的问题本身**。
- 只认 `ConnectionReset`；**刻意排除 `NetworkReset`(10052)**（它也可能是链路真断，该留 Error）。
- ⚠️ 这条**没有单元测试**（`TestServer` 没有真 socket，造不出真实 ICMP），只由复现脚本覆盖。

## 本轮新踩的坑（详情见 REF-M4 §20.4）

1. 🔥 **按文案数日志必须同时按级别过滤**：去重把重复项降到 `Debug`，而 **Debug 行的文案与 Warning 一模一样**

2. **`LogService` NDJSON 的属性名是 PascalCase**（`Category`/`Level`/`Message`/`LevelText`，默认无 naming policy），

3. ⚠️ **`LogService.FlushAsync()` 可能什么都不做**：抢锁用 `WaitAsync(0)`，后台刷盘定时器

4. **`TestServer` 下 `RemoteIpAddress` 不带真 socket** ⇒ "来源"列的断言只能按机器码 + 状态筛。
5. `JsonElement` 是结构体，`FirstOrDefault` 拿到的是 `Undefined` 而不是 null

6. 注册失败的状态码**不是一种**：缺凭据 = **400**、凭据不对 = **401**。
   我第一版测试把两者都断言成 400，当场变红 —— 这个差别本身就是现场的判断线索。

## J. M4.8 收口：三个**只有真机 / 真浏览器**才暴露的缺陷（同日补）

> §I 那句"全绿已落地"当时是基于**测试**写的。随后的真机 + 真浏览器验证推翻了其中三处。
> 三个缺陷**全部通过了编译、单测与桩测试**，且症状都伪装成"这台机器没采到数据"（完全正常的一种形态）。
> 详见 `REF-M4-Agent.md` §26.7 / `docs/M4-…方案.md` §28.8。

### J.1 缺陷与修法

| # | 缺陷 | 为什么测试抓不到 | 修法 |
|---|---|---|---|
| 1 | `PdhGetFormattedCounterArray` 缺 `CharSet.Unicode` ⇒ 绑到 `…ArrayA`，实例名是 ANSI 乱码 ⇒ 上层静默跳过 ⇒ **磁盘与 CPU 一条都不剩** | 结构体布局与 W 版**一样**，**值全对**、只有名字坏了；不抛异常、不给错误码 | 加 `CharSet.Unicode` + 真机守门用例 |
| 2 | 把 `Processor Information(*)` 的 `组号,处理器号` 当成**插槽** ⇒ 1 插槽 / 4 核 / 8 线程被报成 **8 颗物理 CPU** | 编译期与桩测试都看不出"8"是错的；它是**在页面上说假话**，不是精度问题 | `GetLogicalProcessorInformationEx(RelationProcessorPackage)` 建映射再聚合（⚠️ 该枚举 **Package = 3 不是 0**） |
| 3 | `AgentMetricsSummaryDto` 不带逐设备读数 ⇒ 前端实时帧写死 `devices: null` ⇒ 硬件「当前值」与硬件曲线**永远停在打开页面那一刻** | 单看前端是"这段没数据"的合法形态；而它**正好违反契约里明令禁止的那种漂移** | 摘要加 `Devices`（末位可选，既有调用点不动），`Summarize` 透传，前端 `devices: m.devices ?? null` |

**取舍留档（缺陷 3）**：否掉了"详情页每 N 秒重拉整个窗口"这条路 —— 那是一次**真的扫库查询**
（窗口最长 30 天），而这份数据客户端**本来就采到了**，只是没推。代价是广播载荷每台约 +1 KB
（300 台 × 每 2 秒 ⇒ 约 0.2 MB/s，内网可忽略）。

### J.2 🔥 两条**假通过**的断言（这才是上面溜过去的原因）

| 断言 | 假在哪里 | 改成 |
|---|---|---|
| `Disk_and_cpu_devices_are_actually_reported` | 只断言磁盘**存在**，没断言 `ReadBps` **有值** | 冒烟/UI 侧补"至少一项有数" |
| UI 验证「当前值不是空的」用 `value !== '—'` | 磁盘那格显示的是 **`读 — / 写 —`**，整串确实不等于 `—` ⇒ 通过，屏幕上一个数都没有 | 判据改为**串里出现数字**（`/\d/`） |

> **通用教训**：写"这个字段不为空"的断言时，先问清楚**本项目里"空"长什么样**。
> `—`、`null`、`0`、`读 — / 写 —` 四种形态各出现过一次，每一个都曾让断言在功能坏掉时照样变绿。

### J.3 排查方法论（值得复用）

- **`.tools/device-probe/`**（本地、已 gitignore）：直接 `new WindowsHostMetricsSource()` 采 3 帧，
  把逐设备读数**原文**打出来。真机采集类缺陷**只有把原文打出来才看得见** ——
  它不抛异常、不给错误码，在结构上只表现为"某个字段是 null"或"少了几条"。
- **`.tools/m48-ui-check` 里新增传输层探针**：`Page.addScriptToEvaluateOnNewDocument`
  在页面脚本之前替换 `WebSocket` / `EventSource`，把 SignalR 收到的帧原文留在 `window.__live`。
  🔥 **两个坑**：① 必须在**页面脚本之前**安装，加载后再替换已经来不及（SignalR 抓走了原始构造函数）；
  ② SignalR 的 JSON 协议**每条消息尾部有一个 `\u001e`(RS) 分隔符** —— 不剥掉它 `JSON.parse` 必抛，
  表现是"帧明明收到了、却一条都解析不出来"（第一版就是这么误判成"推送不带逐设备"的）。
- **验证"实时帧有没有被用上"的正确姿势**：**故意在数据长出来之前打开页面**。
  那一刻历史是**合法但全空**的（速率类计数器要两次采样），于是格子上的数**只可能**来自实时帧 ——
  把实时帧丢掉（`devices: null`）的实现在这里必然超时。数据等齐了再开页面，两条路径就分不开了。

### J.4 缺陷 4：**修缺陷 3 时自己引入的**（NaN 会拖垮整张在线表）

把 `Devices` 放进摘要 = 把逐设备读数从"只存在于库和时序端点"搬进了 **`GET /api/agents` 的 JSON**。
而入站的 `SanitizeDevices` 当时**只清洗 Kind/Key/Name，没碰数值** ⇒ 风险等级变了：
一个 `NaN` 原本只毁它自己那条曲线，现在能让**整个在线表序列化失败**（严格模式默认拒绝 NaN/Infinity）——
**一台坏客户端拖垮所有人的列表页**。与当年温度那次同形态。

修法两道（幂等）：`SanitizeDevices` 六个数值字段过 `Finite()` → null（⚠️ 只丢非有限，
**不套物理区间**：速率没有有意义的上下界，套区间只会误伤真实数据 —— 这一点与 `Temperature()` 刻意不同）；

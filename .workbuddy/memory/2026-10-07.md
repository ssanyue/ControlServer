## 追加：抛开复用性的「最佳效果」选型（文档附录 B）

用户追问"不考虑代码复用，哪种语言/框架能达到最佳效果"。

**结论**：
- 前提澄清——浏览器端只能是 TS（Blazor WASM 不划算），真正选的是**后端语言**。
- **最佳效果 = Go + TypeScript(React/Vue)**。关键论据：`Pion`(纯 Go WebRTC) + `ffmpeg`(ddagrab/x11grab) 拿 H.264 硬编，最省力拿高画质低延迟；静态单文件跨平台 daemon 部署最简；goroutine 适合 UDP 监听 + 高并发；net/http 原生 Range 断点续传。
- **并列次选 = .NET 8 ASP.NET Core**（SignalR 开箱即用、Windows 深度集成最顺、开发效率最高）；偏 Windows 交付求快 → .NET，偏 Linux 求稳求简 → Go。
- **Rust** 仅极端性能诉求（4K60 远程桌面）且团队有能力时才值得；**Python 不推荐**（部署+GIL）；**Node 全栈** CPU 密集需外挂原生进程，不如直接 Go/.NET。
- 加权评分（10 分制）：Go 9.0 / .NET 8.6 / Rust 8.3 / Node 7.6 / Python 6.2。
- 推荐规格：Go 1.22+ / net/http+chi / gorilla-websocket / Pion / ffmpeg / SendInput-XTest / SQLite(modernc 纯 Go) / React+TS。

## 追加：绿色版单文件 exe（双击即运行）· 已实现并实测

用户需求：「做一个 exe，双击打开即可自动运行启动」。

**产物**：`dist/win-x64/ControlServer.Server.exe` —— **单文件、48.7MB、自包含**（无需系统 .NET），双击即启动服务并**自动打开浏览器**。

**一键脚本**：`deploy/windows/build-portable-exe.ps1`（构建前端 → 发布单文件 → 校验"发布目录只有 1 个文件"）。

**关键实现**：

**🐛🐛 修掉一个「定时器整体静默失效」级真 Bug（靠真实宿主 + 真实时钟才暴露）**

`TickAsync` 的逐秒回补循环原来直接拿带亚秒的 `DateTimeOffset` 累加：
```csharp
for (var t = from.AddSeconds(1); t <= now; t = t.AddSeconds(1))
```
`PeriodicTimer(1s)` 的**实际节拍通常略小于 1 秒**（实测 ≈0.995s），于是每拍 `now − from ≈ 0.995s`，
而 `from + 1s` 永远大于 `now` ⇒ **循环体一次都不执行**，`_lastDetect` 每拍只前进 0.995s，
**永久卡死**：不报错、不写日志、`timer_fires` 里连一行记录都没有。

**修法**：循环边界**截断到整秒**再推进（新增 `TruncateToSecond`）。截断后各拍区间
`(floor(from), floor(now)]` 首尾相接，并集恰好是 `(floor(起), floor(止)]` ⇒ 每个整秒被求值且仅被求值一次。

**顺带修的第二个 Bug**：亚秒级时钟回退（NTP 周期重校几乎总会带来几十~几百毫秒的**负**修正）
被 `now <= from` 误判为"时钟回退"⇒ 每 30 分钟刷一条无意义警告，且把锚点往前挪会漏掉中间的整秒。
改为：仅当回退幅度 ≥ 1s（`RollbackTolerance`）才告警 + 重新锚定；亚秒抖动直接吸收、锚点不动。

**守门测试有效性已反向验证**：把修复临时还原成旧实现后
`Sub_second_tick_intervals_still_evaluate_every_second` **确实失败**，改回后通过。

**⭐ 单元测试为什么抓不到**：假时钟按**整秒**精确推进，`from + 1s` 恰好等于 `now`，循环正常执行。
这类"真实节拍与假设不符"的缺陷**必须靠真实宿主验证**，写再多单元测试也照不出来。

### 三个设计决策（写下来免得回头改坏）

1. **业务失败用「结果对象」，不用异常**。重名 / 找不到 / 入参非法都是正常分支，
   异常表达会让 HTTP 层 catch 一堆，也容易把"校验失败"和"存储炸了"混在一起。
   `CommandMutationStatus` = `Ok / NotFound / DuplicateName / Invalid / StorageCorrupt` → HTTP `200 / 404 / 400 / 400 / 500`。
2. **失败也必须带回服务端当前全量列表**（`Commands`）—— 前端可立即刷新，不必再发一次 GET。
3. **损坏文档：读退化、写拒绝**。读路径解析失败退化为空库继续服务；
   写路径必须返回 `StorageCorrupt` 并停手 —— 否则用户点一次「新增」就把还没抢救的原始内容永久覆盖。
   有守门用例 `Mutation_refuses_to_overwrite_a_corrupt_document`（断言原文一字不动）。

### 其它要点

- **`Id` 一律以路由为准**：`UpdateAsync` 里把 `item.Id = id` 强制写回，避免前端 body 里 Id 写错导致"改一条留一条"。
- **新增时 Id 撞车 → 换新 Id**，不让"新增"变成"悄悄覆盖"。
- **重名校验必须排除自身**（`FindByName(..., exceptId)`），否则"只改协议不改名"会被拒。
- 协议 / 数据类型**归一化大小写**（`utf-8` → `UTF-8`），但**不认识的取值一律拒绝**，不静默改写。
- `DataTypes.CommandLibrary`（「指令库」）必须挡在写入口 —— 否则指令库里的指令指向指令库会无限套娃。
- `SaveAsync`（整份替换，带 `expectedVersion`）**保留**，用于批量 / 导入场景；
  逐条增删改**不开放** `expectedVersion`（局部意图天然可合并，两人分别加不同指令不该冲突）。

## M2-E5 监听端口热重启（408/408 绿）

### ⚠️ 方案 §4.4 的既定路径是**错的**，已实测证伪

方案原写：「通过 `IServerAddressesFeature.Addresses` 改监听地址；先 `await server.StopAsync()`
再 `StartAsync()`（`IServer` 实例可复用）」。**两个前提都不成立**：

1. `KestrelServerImpl.StartAsync` 有一个 `_hasStarted` 标志，停止时**不复位**，
   二次启动直接抛 `InvalidOperationException("The server has already started.")`。
   （反射确认：`KestrelServerImpl` 是 internal 类型。）
2. 想绕开它自己 new 一个 Kestrel 也不行 —— `StartAsync` 需要
   `IHttpApplication<HostingApplication.Context>`，那是 internal 类型。

### 实际做法：Kestrel 不动，只换底下的监听 socket

`SwitchableConnectionListener`（新文件）实现 `IConnectionListener`，
`AcceptAsync` 从"当前"内层 listener 转取；换端口时**先在新端口绑定，成功了才关旧的**
（顺序不可颠倒，反过来就会留下"两个端口都没在听"的空档）。

**由此得到的好处**（比"重启 Kestrel"强得多）：
- 切换可以在**处理请求的过程中同步完成** —— 不需要方案里那套"先返回已受理、延迟 N 秒再切"，
  用户点一下当场就知道"成没成、端口腔没占住"；
- **天然没有"旧端口已停、新端口没起"的窗口**：绑失败时旧 listener 一动没动，
  连回滚都不需要（回滚逻辑本身才是最容易出错的地方）；
- 已建立的连接（包括正在发这个响应的那条）不受影响，响应一定能送达。

### 🐛🐛🐛 三个真 Bug（全部是「静默失效」级，全部靠真机验证才暴露）

**① Kestrel 会**反转** DI 工厂列表**

`IConnectionListenerFactory` 必须同时实现 `IConnectionListenerFactorySelector`（`CanBind`），
否则会被静默跳过。但**实现了还不够**：Kestrel 把 DI 里的工厂列表**反转**后装进 `TransportManager`。
实测（反射 dump）：

```
DI 顺序          = [Switchable, SocketTransportFactory, NamedPipeTransportFactory]
TransportManager = [NamedPipeTransportFactory, SocketTransportFactory, Switchable]   ← 反转
```

于是"插到最前"（`Insert(0, …)`）反而让自己排到最后，`SocketTransportFactory` 一路抢先，
本工厂**连 `CanBind` 都不会被调用**。
修法：改用 `AddSingleton`（**追加**），反转后正好排到第一位。
已在 `ApplicationStarted` 加自检：接管失败会打「【功能降级】监听地址热切换未启用」，
避免将来 .NET 改了顺序行为后只能靠用户"点了没反应"才发现。

**② 内层 listener 返回 `null` 时不能透传给 Kestrel**

Kestrel 用 `null` 表示"这个监听结束了"，收到就**永久退出接受循环**。
症状极具迷惑性：新旧端口都能看到 `LISTENING`、TCP 也能 `ESTABLISHED`
（内核完成了三次握手，连接躺在 backlog 里），但**没有任何请求得到响应**。
修法：`AcceptAsync` 里先判断"是换了 listener 还是真的停止"，只有后者才把 `null` 交上去；
另加"代（generation）CTS"主动打断正在等待的 Accept —— 不把正确性押在
"旧 listener 被 Unbind 后会自己结束"这个实现细节上。

**③ `old.DisposeAsync()` 会中止"正在回写切换结果的那个连接"**

Kestrel 的 `SocketConnectionListener` 在 Dispose 时中止它已接受、仍在服务的连接。
实测症状：切换本身完全成功（新端口 LISTEN、旧端口停了），但客户端收到 **HTTP 000**，
服务端日志里是 `Pipe.AllocateWriteHeadSynchronized` 的异常栈。
对一个"点了改端口却拿不到结果"的功能来说，这跟失败没区别。
修法：旧监听器只 `UnbindAsync`（停止接受新连接），**延迟 2 分钟再 Dispose**（与 Kestrel
默认 keep-alive 超时同量级，足够前端跳走）。

**④（顺带，旧账）`ConfigurationManager.Sources.Insert(...)` 不会触发 provider 重建**

插进去的源**本次进程读不到任何值**。这个坑极其安静：没有异常、没有日志，只是"配置不生效"。
连原本那段"exe 同目录 appsettings.json"（便携部署）也因此**从未生效过**。
受支持且会触发重建的是 `Add` / `Remove`（都来自 `ICollection<T>`），
所以 `InsertConfigSourceBeforeEnvironmentVariables` 改成"先 `Add` 到末尾、
再把环境变量源整体挪到它后面"。

### 端口持久化：可写来源

`ServerAddressOverrideStore` → 数据目录下 `server-overrides.json`（与数据库、日志同级）。
**不写 appsettings.json 的三个理由**：部署目录常常只读 / 单文件发布时可能来自内嵌资源 /
会重排用户手写的注释与格式。

优先级（实测）：


### 🐛 本次复验新发现的两个缺陷（E5 遗留，需拍板）

#### 缺陷 A：`NoChange` 分支跳过持久化 ⇒ 用户无法收敛多地址配置
- **复现**：overrides 内为 `["…:8080","…:9188"]` 时，POST `{"urls":["…:8080"]}`
  → `IsSame(oldUrls, newUrls)` 为 true（两者都是 8080）→ **提前返回 `NoChange`，不调 `TryPersist`**
  → 文件里 9188 永久残留，界面上怎么改都删不掉
- **根因**：`IsSame` 比较的是 **`CurrentUrls`（实际监听器）** 与请求值；
  而持久化文件代表的是**期望配置**。两者在「多地址 → 单地址」收敛场景下天然不一致。
- **影响**：功能可见性缺陷（用户改不动配置）

#### 缺陷 B：持久化写入**全量 `newUrls`**，但实际只切了主地址 ⇒ 运行期与重启后行为不同
- 请求 `{"urls":[":8080",":9188"]}` → `RetargetAsync` **只切主地址**（9188 没被绑）
  → 但 `TryPersist(newUrls)` **把两个地址都写进文件**
- **后果**：重启后 9188 会**真的**被绑上 —— 运行期与重启后行为不一致
  （运行期消息里那句「其余地址按原配置继续监听」在小地址场景下还能自洽，但一旦 newUrls 引入了**新**地址就不成立了）
- **需拍板**（三选一）：
  - **A** `RetargetAsync` 真的把所有新地址都绑上（多监听器管理，实现最重）

## M2-E5 缺陷修复（任务 #40，方案定稿「只接受单地址」）

### 决策：C 方案 —— `POST /api/system/address` 一次只接受一个地址

理由链：
1. 热切换**只作用主监听地址**（`RetargetAsync` 只换一个 listener）—— 这是实现事实，不是选择。
2. 若放行多地址，就会出现「只切了第一个、却把全部写进持久化文件」的**假成功** —— 重启后多出来的地址会真的被绑上，运行期与重启后行为不一致。
3. `HttpOptions.Urls` 是 **`string`**（分号分隔），多地址是配置文件层面的能力，不是 Web UI 的职责。
4. 既然做不到，就不假装能做到。→ 多地址一律 `Invalid`（400），文案指路配置文件。

### 实施（4 处）

| 文件 | 改动 |
|---|---|
| `src/ControlServer.Contracts/SystemDtos.cs` | **删 `SwitchDelaySeconds`**；重写 `ServerAddressChangeRequest` / `ResultDto` 的文档（原文说"必须等响应回到浏览器之后才执行"、"默认 3 秒"，与实现矛盾）；`SecondsUntilSwitch` 注释改为"恒为 0，保留仅为兼容" |
| `src/ControlServer.Server/Services/ServerAddressOverrideStore.cs` | `Save` **一律写字符串**（`string.Join(';', urls)`）—— 原来多地址写 JSON 数组，而数组展开成 `Urls:0`/`Urls:1` 子键、父节点值为 null ⇒ **写进去自己读不回来**；新增 `TryReadUrls()`（兼容历史数组格式） |
| `src/ControlServer.Server/Services/ServerAddressService.cs` | `TryBuildTarget`：**去重后 > 1 个 → Invalid**（判据是"去重后"，不是"数组长度"，所以 `["a","a"]` 放行）；`NoChange` 分支**收敛持久化** |
| `web/src/api.ts` | 删 `switchDelaySeconds` 参数 + 加注释说明"一次只能一个地址" |

   配了**反向守门**用例把契约钉死。
2. **扩展名之外加魔数嗅探**：扩展名是客户端自称的，只信它等于允许把任意字节
   （HTML/压缩包/可执行文件）存进图片目录并以 `image/png` 服务出去。
3. **`DELETE` 默认拒绝删除"仍被引用"的图**（409 + 引用方清单，`?force=true` 放行）。
   否则删一张被多处引用的图会让那些按钮**静默**退化成纯色（前端对 404 本就回退、不报错）。
4. `FormOptions.MultipartBodyLengthLimit` 收窄到「上限 + 1 MB」（默认 128 MB 太宽松）。

### ⚠️ 框架事实：MVC 在**调用 action 之前**就读取表单

`multipart/form-data` 请求会先被 MVC 的值提供器读一遍，因此"请求体超过
`MultipartBodyLengthLimit`"这次失败**轮不到端点的 try/catch**。实测（真机与 TestServer 一致）
拿到的是框架默认 **400** + ProblemDetails，文案 `Multipart body length limit 5242880 exceeded`
（英文、含内部数字），而 **413** 才是负载过大的正确状态码。
⇒ 组合根用 `ApiBehaviorOptions.InvalidModelStateResponseFactory` **只针对这一种失败**改写响应。
识别只能靠框架文案（无错误码、拿不到强类型异常）⇒ 集成测试
`Upload_rejects_a_body_larger_than_the_multipart_buffer_limit` 是这条依赖的**哨兵**。

### 一个被测试打回的自我纠正

`Path.GetExtension` 在 **.NET 8** 里：`".png"` → `".png"`（**不是**空串）、
`".gitignore"` → `".gitignore"`、`"a.png.exe"` → `".exe"`。
我原先按"点开头会被判成空串"写了注释，被用例打红后实测确认并改正。
（放行 `.png` 这个名字是安全的：客户端文件名只用来取扩展名，最终文件名由服务端生成。）

### 另一处易误判

`Program.cs` 在组合根之前就调了 `IDataDirectory.EnsureCreated()`（日志路径依赖它），
**图片目录启动即存在**。所以"被拒的上传没留下东西"要断言**目录为空**，不能断言"目录不存在"。

### 关键决策

1. **不等 G2 的细粒度端点**，编辑页直接走 `PUT /api/config` 整体提交 + 乐观锁。
   理由：动作列表增删改互相牵连（顺序、Id），整体提交才能保证服务端收到的是自洽配置；
   单管理员场景并发代价可接受。G2 降级为后续优化项。
2. **draft 深拷贝 + 就地修改**：子表单绝不重建对象，只改具体字段 ——
   服务端多出来而前端类型里没声明的字段（如旧的 `timerTime`）才不会被抹掉。
3. **脏检测用序列化对比**（`JSON.stringify(draft) !== baseline`），
   而不是"动过就永远是脏的" —— 改回原样会重新变干净。
4. **正在编辑时绝不覆盖 draft**：`props.config` 变化仅在 `!dirty` 时同步；
   脏时只置 `remoteDirty` 提示，由用户决定"载入服务端最新"还是"用我的覆盖"。

### ⚠️ 两个必须记住的坑

1. **`crypto.randomUUID()` 在局域网 HTTP 下是 `undefined`**（非安全上下文）。
   服务是 `http://192.168.x.x:8080` 访问的，直接调用会让「新建按钮」整个失效。
   `factory.ts` 里改为优先 `crypto.getRandomValues` + 手拼 UUID v4。
2. **`const props = defineProps(...)` 时模板里不能写 `action.xxx`**。
   props 的键不是顶层绑定，模板会把它当 `_ctx.action` → `undefined` → 运行时报错。
   全部统一写成 `props.xxx`（已重写 ImagePicker / ActionEditor / ActionListEditor 三处）。

### 语义确认（写编辑器前查证）

- **WoL**：数据内容存的是 **MAC 地址**；端口 0 回退 9；目标空或 `0.0.0.0` 回退广播。
- **`DataType = "指令库"`**：`dataContent` 存**指令名**，发送前经 `ICommandLibrary` 解析成真实协议/类型/数据。
- **月度计划**：`months` + `days` 是**旧格式**（交叉匹配），服务端迁移为 `monthDays`（每月独立日期）；
  前端只写 `times` + `monthDays`，旧字段由服务端补齐。
- **子按钮集里 WoL 被强制降级为 UDP**，所以 `SubButtonEditor` 干脆不给选（前端提示 + 服务端兜底，双保险）。

### 两个真发现

1. **手动触发的时刻语义**（重要）：`TimerSchedulerService.FireNowAsync` 把记录写在
   **你点的那一刻**（`now.ToString("HH:mm:ss")`），而 `firedToday` 查的是**触发点定义的时刻**
   ⇒ **手动触发后 `firedToday` 仍为 false**（实测：触发点 `08:00:00` vs 记录 `21:40:59`）。
   **这是有意设计，不要"修"**：若按触发点时刻落记录，手动调试一次就会吞掉当天的正式定时。
   → 前端加本地留痕（`manualFired`，在「今天」列显示"手动触发过 21:40:59"）+ 说明文案讲清原因。
2. **`input[type=time]` 的秒陷阱**：配置里的时刻是 `HH:mm:ss`（服务端补秒，**必需** ——
   定时器按 `HH:mm:ss` 精确字符串匹配，写 `08:00` 会永远匹配不上、**静默不触发**）；
   而 `type="time"` 默认 `step=60`，遇到**秒非 0** 的值会**显示空白并把空串写回 v-model**
   ⇒ 时间点被静默清空。→ `TimeListEditor.vue` 加边界转换（读入截 `HH:mm`，写回补 `:00`）。

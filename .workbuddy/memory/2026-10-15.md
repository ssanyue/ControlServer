四个语义决策（`AskUserQuestion`）：① **只通知、不阻塞保存**；② **拒绝连接＋客户端保留身份重试**（「移除」保留）；
③ **全部网卡 MAC＋两个广播地址**；⑤ **第三类瓦片＋支持对接码**。

### 1.1 需求④：这是本轮唯一的**真 BUG**，且根因很干净

**一句话**：清单排期由客户端**本地持久化的"上次上报时刻"**（`TelemetryStateStore.InventoryReportedAt`）决定，
周期 **6 小时**；而"服务端这边还有没有这份清单"**客户端根本不知道** ——
记录被移除 / 重新注册换了新 Id 之后服务端是一张白纸，客户端却以为"6 小时前刚报过"。

⇒ 现场表现就是"这台客户机不上报硬件清单"，而且**只在重新注册之后出现**（与用户描述吻合）。

**修法（服务端说、客户端听）**：`AgentWelcomeDto` 新增 `bool NeedsInventory = false`（带默认值 ⇒
老服务端行为完全不变），服务端在 Welcome 里如实告诉它；客户端收到即**忽略 6 小时排期立刻补报**，
只有成功才清零。

⚠️ 为什么不改成"每次注册都重报一遍"：那会让每一次服务重启 / 网络抖动的重连都去跑一遍 WMI（1～2 秒 CPU）。

### 1.2 需求②：拉黑与旧吊销的三处差别（这就是"真围栏"的全部内容）

| | 旧「吊销」 | 新「拉黑」 |
|---|---|---|
| agentKey | **清成 null** | **保留**（认证时按标记拒） |
| 重新注册 | **会复活** | **直接被拒**（`status=blocked`） |
| 客户端收到后 | 清身份/配置/停任务 + 5 分钟退避 | **什么都不清** + **15 秒**轮询 |
| 取消之后 | 要重新注册 | **下一次重试就连上** |

- 服务端：`IsRevoked → IsBlocked`（迁移 `M4_12_AgentBlock` **只做列重命名**）、
  `/revoke`·`/unrevoke` → `/block`·`/unblock`、`SetBlockedAsync` **刻意不动 agentKey**、
  `RegisterAsync` 在**注册入口**就拒（按 machineKey 兜底）。
- 客户端：连接被拒（401）之后**不再无脑清身份**，改成"**去注册一次、按结果分流**"
  （成功＝记录被移除过；`blocked`＝被拉黑，什么都不清）；
  `OnBlocked` 不再清配置/停任务（一旦清掉，重连时版本号对齐到 0 ⇒ **配置不会再被应用** ⇒ 任务再也起不来）。
- ⚠️ **拉黑不影响 UDP 指令通道**（按"未连接"处理，照旧监听）—— 与吊销同一口径，已在文档里写明。

### 1.3 需求③：唤醒只能在服务端做（因为它要唤醒的是**关着的**机器）

- 去掉列表里的**版本列**与「重启服务」按钮（服务端 `POST …/reboot` **保留**，只是没 UI 入口了）。
- 新增 `唤醒` / `关机` / `重启`；关机·重启走**早就存在**的 `POST …/power`（SignalR，要求在线），
  且**不可撤销** ⇒ 与「移除」共用同一道两段式确认（`confirmDeleteId` 泛化成 `armed`）。
- **唤醒**是全新的 `POST …/wake` + `AgentWakeService`：对**每一块上报过的网卡 MAC** 各发一遍魔术包，
  每块发往 `255.255.255.255` 与该机最后来源 IP 的**定向广播**，端口 **9 与 7** 都发。
  ⚠️ WoL **无应答** ⇒ 返回 `ok` 只代表"包发出去了"（这句话写在响应 message 里）。
  ⚠️ MAC 来自**注册时上报的主机信息**，不在 6 小时一次的清单里（清单 DTO 里没有网卡字段）。

### 1.4 需求①：本机页可改中心地址

- 新增 `AgentServerOverride`（状态目录 `server-override.json`）：**优先级最高**
  （本机覆盖 > `Agent:ServerUrl` > 凭据里的地址 > 广播发现）。
  为什么不回写 `appsettings.json`：程序目录通常**不可写**；而且升级覆盖安装会丢。
- 页面新增一行输入框 + 「保存并切换」，走独立端点 `PUT /api/server`（同样带本机令牌）。
- 生效路径：落盘 + 置信号 → **心跳循环窥见信号立刻断开**（否则要等长连接自然断，可能几小时）→
  主循环**先尽力上报旧中心** → 作废本地身份 → 按新地址重新注册。
- 上报端点 `POST /api/agents/{id}/server-change`（新策略 `AgentSelfReport`，只能报自己名下）；
  ⚠️ 它**只写日志、不改任何状态**，失败也**不阻塞保存**（旧中心不可达时正是最需要改地址的时刻）。

### 1.6 本轮踩到的坑（都可复用）

1. 🔥 **批量重命名误伤了另一个实体**：`RevokedAt` 同时存在于在线表与**已废弃的令牌表**
   （`EnrollmentTokenEntity`），我的 `replace_all` 把它也改了；而我顺手加给在线表的
   `row.BlockedAt` 更是**在线表根本没有那一列**（靠 CS1061 才发现）。
   ⇒ 教训：**批量重命名前先数命中，并确认命中的是哪个类型**。
2. **迁移文件被误改**：排除模式写的是 `'Migrations/'`，Windows 路径是 `src\…\Migrations\…`
   ⇒ 25 个**历史迁移**被改。历史迁移必须原样（它是已应用的记录）；全部还原，只让 EF 重新生成快照。
3. **`register` 对一条业务拒绝返回 500**：状态码映射表里没有 `blocked` ⇒ 落到默认 500。
   现场看到"服务端坏了"，而原因就写在响应体里 ⇒ 已改成 **409**。
4. **测试辅助方法内部自带断言**：`RegisterAsync` 里断言"必须 200"，
   于是"预期被拒"的用例必红 —— 是**用例写法**问题，不是产品的。补了 `RegisterRawAsync`。
5. **属性名遮蔽 `System.IO.Path`**：`AgentServerOverride.Path` 让类里所有 `Path.Combine` 编译不过（CS1061）
   ⇒ 改名 `FilePath`。
6. **`run-all.py` 默认打 `dist/` 产物**（旧代码）：开发期要显式把被测服务端指到 `.artifacts-check`
   （同源解析会自动挑同一批构建的客户机），一次 agent 冒烟 1.5 分钟 vs 3 分钟。

### 2.1 延迟语义（最容易被理解错，所以写进了类型注释）

`DelayMs` ＝ **「执行完本步之后、下一步之前」等多久**。⇒ 第一步恒 0；**最后一步永远不生效**
（清洗器归零 ＋ 解析时归零 ＋ **界面不显示这个框**）；与成员自己动作的前置延迟**各算各的**。
上限 **60 秒**（组合跑在"有人在场"的链路上，填 10 分钟会让人以为点了没反应）。

### 2.2 对接码：与主按钮**同级**、按 Order 合并扫描

**不是**"先扫完所有按钮再扫组合"——两者合并成一个按 `Order` 排序的序列再比对，
界面上谁靠前谁先命中。因此 `PairingMatchKind` 的**枚举数值不再等于优先级**，旧注释已改写。

### 2.4 🔥 本轮顺带逮到一个真缺陷

`ConfigBackupService.KnownSettingsFields` 是**手写的配置字段清单**；加了 `comboButtons` 之后
没人想起同步它 ⇒ 导入一份含组合按钮的配置时，界面会报「**已忽略字段：comboButtons**」——
数据其实没丢（反序列化走模型），但那句话会让人以为**组合按钮全丢了**，
而且真正该提醒的单机版字段（`windowWidth` / `autoStart` 之类）会被这句话淹掉。

**修法不是"补一个名字"，而是把那份清单改成从 `ControlSettings` 反射生成** ——
"加了字段却忘了登记"这一类 bug 从根上消失。另有既有用例 `Parse_reports_no_ignored_fields_for_a_clean_service_backup`
**先红后绿**地逮住了它（它跑的是"真导出→再解析"，所以新字段一出现就暴露）。

> 教训：**手写的"已知字段清单"就是一份平行的真相，它一定会漂。**

### 2.5 本轮踩到的坑（4 条，都被记进 REF §31.6）

1. C# 字符串里嵌 ASCII 双引号（中文说明里写 `"一串按钮"`）⇒ 编译错误，**连续踩三次**；中文注释里的引号一律用 `「」`；
2. `LogService` 是 `IAsyncDisposable` ⇒ 测试里必须 `await using`（不是 `using`）；
3. **断言前先问"这条链路上谁先动手"**：派发测试的配置是原始 JSON 写入、读取时会跑清洗 ⇒ 悬空成员在**载入时**就没了，"执行期跳过悬空成员"那条断言永远看不到跳过记录 ⇒ 改由纯逻辑用例覆盖；
4. 断言写成了自相矛盾（"三类瓦片的 Order 都是 0"＋"它们共用同一条编号空间"不可能同时成立）——是测试自己的错。

## 三、M4.14：本机页「服务端」明细默认收起（同日）

### 3.0 改法（一处文件，零 C# 改动）

`agents/ControlServer.Agent/Config/local-ui.html`：

| | 内容 |
|---|---|
| 摘要行（**常显**） | 徽标（已连接/未连接中心）＋ **地址** ＋ 展开/收起开关 |

### 3.1 三条纪律（本轮真正容易写错的地方）

1. 🔥 **收起状态只由 `serverOpen` 一个变量说了算，`renderServer` 全程不碰 `hidden`** ——
   页面每几秒重拉一次状态，渲染去写 hidden ⇒ 用户刚展开的明细被刷回去；
2. 🔥 **收起不能把故障一起收进去**：连不上时 `statusText`（被拉黑 / 在线表满 / 正在广播找）
   留在摘要行；连上时它是"已连接 地址"（与徽标＋地址重复）⇒ 收起态不留；
3. 没连上时退而显示目标地址 ⇒ **必须带「（目标）」后缀**，不能冒充"已连的"。

### 3.2 验证（实测）

- `--only agent`：**172 PASS / 0 FAIL**；全量 `run-all.py`：**9/9**；
- 交付产物重建：`dist/agent`（Service 36.3 MiB ＋ Tray 35.9 MiB）＋
  `dist/agent-setup`（61.0 MiB，SHA256 `60F08AEE…FF27`），已补投 `%ProgramData%\ControlServer\downloads\`。
  `dist/installer` / `dist/win-x64*` 未重建（payload 是服务端程序，不含本机页）。

### 3.3 本轮踩到的坑（4 条）

1. 🔥 **别用二进制 grep 验单文件 exe 里的内嵌页面**：`EnableCompressionInSingleFile=true` 会压掉
   ⇒ 命中 0 是**假 FAIL**（要验就验未压缩的中间程序集，或让冒烟从跑着的客户端取页面）；
2. 🔥 **`check()` 在 PASS 时也照印 `detail`** ⇒ detail 必须写中性证据（属性列表 / 名单），
   写成"没有 hidden"就会在日志里读成一条假 FAIL；
3. 🔥 **"不在明细里"对"元素不存在"也会通过**（`parents` 缺失 = 空列表）⇒ 存在性必须单独断言

4. 变异测试第一版**全绿却什么都没跑**：终点标记 `# ── ③` 在文件里出现三次，`index()` 拿到前面那个
   ⇒ 切片为空 ⇒ 加"抽出来是空就退出"的守卫。**抽代码做测试的工具自己也要能被证伪。**

## 四、M4.15 修复：中心页面的「关机 / 重启」毫无效果（同日）

> 详情见 `REF-M4-Agent.md` §33；方案侧见 `docs/M4-…方案.md` §35。

### 4.0 根因（一句话）

`AgentCommandNames.Power` **契约写了、实现没写**：常量注释写着「服务侧执行」，
但中心的 `power` 指令到了客户端**没有任何人处理** ——
实现只长在 `UdpCommandListener`（UDP 通道）里，SignalR 那条路是空的
（`AgentServiceHost` 的 switch 没有它 ⇒ 落 default ⇒「收到未知指令（已忽略）」）。

⇒ "UDP 明文指令有效、页面按钮无效"，用户描述的两半同时对上。
同一个洞还覆盖 `volume`（音量按钮同样无效果，用户还没碰上）。

### 4.1 修法

抽一层**共享执行器** `AgentCommandExecutor`（新文件），UDP 与中心指令**共用同一份实现**：

- 电源 → 服务侧 `IHostPowerController`；音量 → 会话侧 `ISessionCommandChannel`；
- 返回结论（不抛），由调用方写进「接收到的数据」；
- `AgentRuntime.OnCommand`：`Power`/`Volume` 就地执行并写**真实结论**，不再写"已转交本机指令处理"
  （那句话正是把这次故障掩盖掉的元凶）；`Restart` 仍转交宿主。

⚠️ **不采取**"在宿主 switch 里补 case"：两条通道两份实现必然漂，执行的真相只能有一份。

### 4.2 三处语义决策（用户确认）

1. **演练模式是全局闸**：中心的关机指令**也**被它拦下（安全闸不留漏勺；键名沿用历史）；
2. 留痕写**结论**，不写"已转交"；
3. 服务端文案补"是否真的执行，请看那台机器的「接收到的数据」"＋演练模式提示 —— **下发 ≠ 执行**。

### 4.3 验证（实测）

- `AgentCommandExecutorTests` **12 条**；集成 `AgentsApiTests` +2（400 / 409）；
- 🔥 **冒烟先红后绿**：旧产物跑出 `[FAIL] …['收到未知指令：power（已忽略）']`，
  重建产物后 `[PASS] 指令真的走到了本机执行器… []`；客户端跑在演练模式 ⇒ **全程没真关机**；
- 全量 `run-all.py` **9/9**（**576 PASS / 0 FAIL**）；
- 单元/集成 **1315 通过、0 失败**（Core 808 / Agent 116 / 集成 391）；
- 交付产物**五套全部重建**（服务端与客户端本轮都改了）。

### 4.4 坑与教训

1. 🔥 **断言顺序会造成假 PASS**："演练模式已开启"这句话 UDP 那条路**也会记**，
   新断言必须排在"真发 UDP 报文"之前，否则分不出是谁的功劳；
2. `CancellationToken` 没给默认值 ⇒ 测试每个调用都得补参数（已改 `= default`）；

## 五、历史曲线「同一硬件多个条目」根因定位（需求：本机页服务端信息收起之后）

### 5.1 现象
`多gpu2.png`：「历史曲线」的硬件选择器里，显卡 `NVIDIA GeForce GTX 1060 6GB` **6 条同名**、
网卡 `Hyper-V Virtual Ethernet Adapter (vEthern...)` **6 条同名**。

### 5.2 根因（已用真实库一锤定音）

拿 `C:\ProgramData\ControlServer\control.db` 里 `DESKTOP-1UKRNGI`（AgentId=11）的
962 条遥测样本反查 —— **这台机器只有 1 块 GTX 1060**，但窗口内出现过 **6 个 LUID**：

| LUID | 区间 | 帧数 |
|---|---|---|
| `0x0001245E` | 10:11:17→10:13:09 | 22 |
| `0x00012360` | 10:14:09→10:15:02 | 9 |
| `0x000123B4` | 10:15:52→10:16:12 | 4 |
| `0x000122FF` | 10:17:09→10:19:39 | 28 |
| `0x01B697A3` | 11:10:42→11:14:38 | 45 |
| `0x000123CA` | 11:16:48→12:32:17 | 845 |

- **两两零重叠**；每次 LUID 变化都**紧跟一次重启**（uptime 归零 ×4 已捕获）。
- 网卡同理：5 个不同的 `Id(GUID)`，名字**全都是** `Hyper-V Virtual Ethernet Adapter（vEthernet (Default Switch)）`。

🔥 **结论**：`LUID`（GPU）与 `Id`（Hyper-V 虚拟网卡）都是**运行时标识符，系统每次启动重新分配**。
而前端 `windowDevices` 取的是**窗口内出现过的所有实例 Key 的并集** ⇒ 同一块硬件在窗口里留下的
**多个历史身份**被当成多块硬件列出来。**不是多卡，也不是采集错。**

### 5.3 顺带确认的事实

- 磁盘（`disk0/1/2`）、CPU（`cpu0`）的 Key **重启后稳定** ⇒ 截图里这两组是对的，只有 GPU / 网卡中招。
- 服务端 `AgentTelemetryService` / `EfAgentTelemetryStore` **原样透传** devices（只清洗 + 截断 64 条），
  不做按 Key 聚合 ⇒ **改动落点在前端展示层**，不必动契约 / 数据库 / 客户端。
- 显示侧还有第二个缺陷：`.device-chip-name { max-width:240px; ellipsis }` 把网卡名里的
  **区分信息（别名 `vEthernet (…)`）正好截掉** —— 于是"同名"更无从分辨。

### 5.4 实施（用户口径：各占一条 + 序号；已消失的不单列）

新模块 **`web/src/deviceIdentity.ts`**（纯函数，可单独喂数据验证）：

| 判据 | 规则 |
|---|---|
| 归并身份 | `kind` + **展示名**（名字为空时退回 Key） |
| 真的并存 | **同一帧内**同名 ≥2 条才加 `#1/#2`；跨帧各一条＝同一块硬件换了身份，直接归并 |
| 列表来源 | **每个种类取它最后一次出现的那一帧**（至多回看 **3** 帧） |
| 取值 | 按时刻挑"当时还活着的那一个 Key"，**绝不把同组的键相加**（重启前后不会同时有值） |

- 交互：单选 chip → **勾选多选**；同种类勾中多块 → 一张图对比；
  **颜色认硬件、线型认通道**（磁盘读写 / 网卡上下行＝同色实线 + 虚线）。
- 配套：`ChartSeries.key` 放宽为 `string` ＋ 新增 `dash`；`MetricsChart` 内部加 `raw()` 宽化取值。
- 改到的文件：`web/src/deviceIdentity.ts`（新）、`web/src/components/AgentDetailPanel.vue`、
  `web/src/components/MetricsChart.vue`、`web/src/types.ts`。

### 5.5 验证（实测）

- 🔥 **`web/tools/check-device-identity.mjs` 19 PASS / 0 FAIL**，样本是**真实数据**
  （`device-identity-real-frames.json`：从上面那台机器的 962 条里挑出覆盖全部身份漂移的 **9 帧**）。
  **修复前后条数 17 → 7**（显卡 6→1、网卡 7→2，磁盘 / CPU 不变）；
- 🔥 **变异测试 3/3 被逮住**：把身份退回 Key ⇒ **6 条断言变红**（核心被钉住）；
  关掉并存编号 ⇒ 4 条；关掉回看 ⇒ 16 条；
- `npm run typecheck` + `npm run build` 通过。

### 5.6 两条 FAIL 是**断言写错**，不是实现错（值得记）

第一版断言里我写了：

- ❌ "占位名不含身份信息 ⇒ 退回用键 ⇒ 列出 2 条" —— 实际是 **1 条**。因为 `lastFrameOf`
  只取最后一帧，另一个 LUID 早就不在了。**把"不归并"和"列表只反映当前"混为一谈了。**
- ❌ "改名 ⇒ 认作 2 条" —— 实际是 **1 条**，而且**改名前的数据仍然取得到**（取值走 Key）。

⇒ 顺着这两条把实现里一处**过度特判**也去掉了（原先给 `GPU 适配器 N` 开小灶、不参与归并）：
那个编号来自计数器出现顺序，多少带点身份信息；而不归并就等于**回到"每次重启多一条"的病**。
现在只有**名字为空**才退回用键。两条 FAIL 换来一处简化 ＋ 两条更准确的断言。

## 八、M4.17 修复：「明明在线却提示离线」＋「离线仍尽力下发」（同日）

### 8.1 症状与根因

用户：「客户端在线，但用关机 / 重启时提示客户端不在线离线、无法下发指令；
**另外即便客户端离线，仍需要向该客户端发送相关指令，但提示离线**」。

🔥 **根因 = "在线"与"能不能下发"是两套判据**，必然打架：

| 用途 | 判据 | 位置 |
|---|---|---|
| 页面显示"在线" | 只看**最后心跳距今多久**（10/30/75 s） | `AgentPresence.Classify` ← `AgentHostRegistry.ToDto` |
| 下发闸门 | 只看**内存里有没有 SignalR 连接 Id** | `ConnectionIdOf` ← `AgentsController.SendCommandAsync` |

矛盾窗口（能长达几十秒，因为客户机重连退避 1→…→60 秒）：
① `MarkDisconnected` 把"最后心跳"钉成**断开那一刻** ⇒ 断开后 30 秒页面照旧是绿的；
② **中心一重启**内存连接表清空，而库里 `LastSeenAt` 只落后几秒 ⇒ 页面绿、下发必 409。

### 8.2 改动（用户拍板：判据纳入长连接事实 + 离线走"尽力而为"）

**后端**
- `AgentPresence.Classify(…, bool? longConnection = null)`：`false`＝已知连接断 ⇒ **不可能判成 Online**，最多 Unstable；
  `true`＝照旧按时间；`null`＝不知道（防御）。
- `AgentHostRegistry`：`ToDto` 传 `live is null ? null : live.ConnectionId is not null`（**不能**写 `live?...`，那会把"不知道"算成 false）；
  **`RefreshAsync` 给装载进来的每台主机 `GetOrAdd` 一条内存记录**（绝不覆盖已有连接 Id），堵住"中心刚重启"那半边。
- `UdpCommandProtocol.TryFormat(name, argument, out token)`：规范指令 → 线路 token（`DOWN`/`RESTART`/`+`/`-`/`0`/`1`），
  与 `TryResolveCommand` **成对**。
- `AgentsController`：`SendCommandAsync` 在无长连接（或发送瞬间失败）时改走 **`SendWhileUnreachableAsync`**
  → 判定顺序 **能力 → 地址 → 端口 → 发出**；成功回 **200 + `status:"udp"`**，消息里**明写"当前离线"**；
  只有"连 UDP 也够不着"才 409。`Reboot` 改为复用同一方法（**无 UDP 兜底**，UDP 只支持关机/重启整机/音量）；
  `RedeliverConfig` 文案改成"离线…配置不会丢，按版本号自愈"（**保留"离线"二字**，有用例钉着）。

**顺手补的三个洞**：拉黑机器**一律拒发**（409 `blocked`，否则 UDP 兜底成了拉黑后门）；
`/reboot` 提示语指向"只能经长连接下发"；`/config/redeliver` 不兜底。

**前端**：`AgentsPanel.vue` 关机/重启按钮 `:disabled` 从 `state!=='online'` 改成 **`host.isBlocked`**，
title 三态；`api.ts` 的 `powerAgent` 文档改写（`ok:true` ≠ "机器马上会关"）。

### 8.3 验证

`npm run typecheck` ✅；Core **124 PASS / 0 FAIL**（新增 17 条）；集成全量 **396 PASS / 0 FAIL**（新增 4 条：
真发到回环 socket 收到 `DOWN`、连接断掉不再显示在线、新注册表装载的主机不显示在线、拉黑拒发）；
`npm run build` ✅（产物进 `wwwroot`，交付包 `dist/` **未重发**）。

### 8.4 挂账

断连瞬间会一闪而过黄点（诚实但可能被当成网络抖）；**排队补发未做**（用户选"尽力而为"）；
UDP 兜底无应答，"到底关没关"仍要去看机器。详见 `docs/M4-…方案.md` §37 与 `REF-M4-Agent.md` §35。

### 9.4 🔥 顺带挖出一件事：**客户端的命名口径换过一代**

同一份窗口按三种口径数条目：

| 口径 | 条数 | 构成 |
|---|---|---|
| 旧：窗口内 `(kind,key)` 并集 | **16** | 显卡 6 + 网卡 6 + 磁盘 3 + CPU 1 |
| 中：`kind` + 名 归并，**无回看** | 11 | 磁盘 6 + CPU 2 + 网卡 2 + 显卡 1 |
| 新：`kind` + 名 归并 + **回看 3 帧** | **7** | 显卡 1 + 网卡 2 + 磁盘 3 + CPU 1 |

中间那一行说明：这台机器在 `10:11:22–10:13:09` 的 **21 帧**里报的是**型号名**
（`ST1000DM003-1ER162（D:）` / `12th Gen Intel(R) Core(TM) i7-12700KF`），
之后改回 `物理磁盘 0（D:）` / `物理 CPU 0`。

**这不是"重命名"，是客户端换了上报口径**（磁盘 / CPU 也一起变了，不像人工改名）。
"回看 3 帧"顺手把它也收掉了 —— 否则磁盘 / CPU 同样会冒出重复条目。
代价是**换代发生在最近 3 帧内**时会有约 15 秒的双条目窗口（已写进 REF §34.4）。

## 十一、M5 方案 v2：13 条决策已拍板，按 **4K60 @ ≤100ms** 重写（同日 18:37）

> 用户逐条回了 v1 §13 的 13 条决策。产出去向：`docs/M5-局域网远程桌面实时方案.md`（**整份重写为 v2**）。

### 11.1 决策取值（已定）

1 局域网内｜2 **不允许** Agent 开入站端口｜3 🔥 **4K 60fps / <100ms（下限）**｜4 不接受第三方 VNC、工期充裕｜

### 11.2 🔥 4K60 推翻 v1 的三个结论（这是本轮的核心）

| v1 | v2 |
|---|---|
| MJPEG 先行、H.264 二期 | **4K60 下 MJPEG 物理不可能**（4K JPEG 软编 40–80ms/帧 ⇒ 12–25fps）。降为「仅联调脚手架，不进验收」 |
| H.264 硬编是二期可选项 | **唯一可行路径**（必须硬编） |
| FFmpeg 外部进程是低工作量首选 | **4K60 下不可集成**：raw 帧 **1.99 GB/s**，无法过管道。**FFmpeg 降级为「能力标定工具」，集成直接投 MF** |

**新增硬约束**：4K60 必须**零拷贝 GPU 管线** —— BGRA 1.99 GB/s 只能在显存内，
**BGRA→NV12 的色彩转换必须在 GPU 上做**（CPU 转换 = 3 GB/s 读写，必然掉帧）。
唯一过 CPU 的是编码后的码流 **3–6 MB/s**。

### 11.3 本机实测（🔸 重要反例，写进方案 §3.2）

| 项 | 实测 |
|---|---|
| 显卡 | Intel UHD 620 ＋ **NVIDIA GeForce MX250（GP108）** |
| 屏幕 | 2160×1440@60（连 4K 都不是） |
| ffmpeg | 未安装 |

- **MX250（GP108）通常不含 NVENC**（该最低端核心被阉割硬件编码器）；
- UHD 620 有 QSV，但 4K 编码上限约 **30 fps**，达不到 4K60。
- ⇒ **开发机不能作为 4K60 标定环境；spike 必须在目标展厅机上做**；
- ⇒ 更强地证明了**降级链**（§1.5）的必要性：现场大概率存在编不动 4K60 的机型。

### 11.4 其它关键新增结论

- 🔥 **队列深度 = 1 比编码速度更重要**：抓屏/编码/发送三阶段各自独立、容量 1 的通道、忙就**丢帧**。
  4K60 的延迟杀手不是单环节慢，而是**流水线排队**（与前端「只渲染最新帧」是同一原则的两端）。
- ⚠️ **「整屏」必须限定为单屏**：双 4K 拼接 = 7680×2160，**超单块 NVENC/QSV 的 4096 上限**。多屏必须分屏编码。
- ⚠️ **4:2:0 让文字发虚**：4:4:4 浏览器不解 ⇒ 只能靠码率(40–60M) + preset 补偿，**要提前告知使用方**。
- **8.5 已写死的能力边界**：Ctrl+Alt+Del / UAC 安全桌面 / 锁屏注入 / 中文输入法 —— 都做不到。
- `IVideoEncoder` 签名**传 D3D11 纹理而非 `byte[]`** ⇒ v1 的 `CapturedFrame.Buffer`(`byte[]`) 在 4K60 下是**错误设计**，需 `CapturedSurface` 变体。
- 4 路并发（决策 8）量化：服务端收发 **160+160 = 320 Mbps**（千兆余量约 3×）；**一块 GPU 只能跑 1 路 4K60**，故「4 路」指 4 台不同被控机。
- 音频（决策 6）独立成章：**必须会话侧** WASAPI loopback（Session 0 无音频端点）→ Opus 20ms 帧 → 同会话传输 → AV 同步 <40ms；
  时间戳用**会话内单调时钟**（不用 `BeijingTime`，避免墙钟跳变；`BeijingTime` 只用于审计留痕）。

### 11.5 里程碑重排

M5.0 接口+分类+**能力探测** → M5.1 链路打通（占位 MJPEG，**不设指标**） → M5.2 输入控制（1080p60 ≤100ms）

## 十二、M5 方案 v3：分辨率阶梯 + HEVC 关键路径（同日 18:46）

> 用户澄清两条：① **4K60 只是保底基准，被控端分辨率可能远大于 4K**（"不能局限于本机的配置"）；
> ② 观看端需支持 **1:1 原图 + 上下左右滚动条**。产出：`docs/M5-…方案.md` **整份重写为 v3**。

### 12.1 🔥 最有价值的发现（联网核实，非记忆）

**NVIDIA 官方 Video Codec SDK 支持矩阵**：

| 编码 | 硬编最大分辨率 | 覆盖代际 |
|---|---|---|
| **H.264** | **4096×4096** | **所有架构**（Maxwell→Ada 都是） |
| **HEVC** | **8192×8192** | Pascal 起（含 Turing/Ampere/Ada；Maxwell 仅 4096） |

⇒ **推翻 v2 的「整屏必须限定单屏」**：双 4K 拼接（7680×2160）**用 HEVC 单路整编是可行的**，
「多屏必须分屏编码」不再是硬要求。**≤8192 走 HEVC 整编；>8192 才需分块/降采样**。

⇒ **反转 v2 的「H.264 主路」**：**超 4096 宽时 H.264 硬编直接不可用**（硬件限制，非驱动问题）
⇒ **HEVC 成为超 4K 的唯一硬编路径** ⇒ **HEVC 浏览器解码升级为关键路径风险**。

**旁证（Citrix 文档）**：H.264 硬件编码不支持 >4096×4096，**多数远程工具在此会静默回退软编** ⇒ 延迟指标直接崩。
我们必须主动识别并切 HEVC，否则掉进同一个坑。

**顺带证实**：官方矩阵脚注 "Except GM108 and GP108 (not supported)" ⇒ **MX250 确无 NVENC**，不必再实测。

### 12.2 新增：分辨率阶梯（方案 §1.1）

| 分辨率 | BGRA 吞吐 | 可用硬编 | 码率 | 单路占千兆 |
|---|---|---|---|---|
| 1080p60 | 0.50 GB/s | H.264/HEVC | 8–15 Mbps | 3% |
| 4K60 | 2.0 GB/s | H.264/HEVC | 25–50 Mbps | 10% |
| 5K60 / **双 4K 拼接 7680×2160** | 3.5–4.0 GB/s | ⚠️ **仅 HEVC** | 40–80 Mbps | 14–16% |
| **8K60** | 8.0 GB/s | ⚠️ **仅 HEVC** | 60–120 Mbps | 24% |
| >8192 宽（3×4K） | — | ❌ 超上限 | 分块 | — |

⇒ **8K60 时 4 路并发 = 960 Mbps，千兆饱和** ⇒ **决策 8 的「4」改为带宽配额制**：
`MaxConcurrentSessions=4` + `MaxTotalBitrateMbps=500`，两者都满足才准入。
（另修正：v2 说「一块 GPU 只能 1 路 4K60」→ 准确说法是**取决于 NVENC 引擎数量**，主流 GeForce 1 个，高端 2 个；
GeForce 并发 session 上限官方为 **8**。）

### 12.3 新增：显示模式（方案 §10，用户要求）

| 模式 | 行为 |
|---|---|
| **适应窗口 fit** | 默认，整帧等比缩放 |
| **1:1 原图 + 滚动条** | 按原始像素显示，超出出滚动条（Ctrl+滚轮缩放、双击切换） |

三个技术约束：① canvas 有尺寸上限（Chrome ~16384²，8K 在限内，3×4K 接近边界）；
② 1:1 时**只 `drawImage` 可视区域源矩形**（ROI 渲染）避免全量重绘；③ **带宽不减少**（仍传全帧），ROI 编码列 M5.5+。
⇒ **坐标映射必须加滚动偏移**（§8.4）：`画面像素 = (视口内坐标 + scrollLeft/Top) ÷ 缩放`，**漏掉就会「点哪儿都偏」**。

### 12.4 验收口径已收敛（原 §0.4 待澄清项）

## 十一、M4.18 修复：「从客户机回传到仓库失败」（同日）

用户原话：**「文件传输优化：从客户机回传到仓库失败，需要修复」**。

### 11.1 根因（有现场日志，不是猜）

**「浏览」能看到的范围（整盘）与「回传」能读取的范围（一个私有目录）是两个集合。**

- `TransferBrowseService` 在 M4.7 已放开为**整盘**（顶层 = `DriveInfo.GetDrives()`）；
- 而 `TransferPaths.ReadWhitelist` 的兜底**没跟着改**（仍是 `{状态目录}\outbox`，M4.4 的默认值）。

两条路径各自维护"本机能碰哪些路径"，只改了其中一处。**证据**取自
`C:/ProgramData/ControlServer/logs/log-2026-10-15.ndjson`：任务 #5–#9 同一条路径连撞 5 次，
每次都是 `源路径不在本机白名单目录内：D:/BaiduNetdiskDownload/unity项目测试.zip（允许：…/outbox）`；
用户随后改用「下发」，#10 立即完成。**只要源文件不在 outbox 里，回传就 100% 失败**，
而网页上「浏览」能一路点进 D 盘并选中那个文件 —— 没有任何一处提示"这两个范围不一样"。

### 11.2 修法（用户从三个方案里选了 A）

| 方向 | 默认范围（改后） | 收窄开关 |
|---|---|---|
| **写**（下发落地） | `{状态目录}\inbox`（**不变**） | `Agent:Transfer:InboxDirectories` / `DefaultInboxDirectory` |
| **读**（回传读取） | **整盘**（所有盘符根 = 浏览的可见范围） | **只认 `Agent:Transfer:OutboxDirectories`** |

- 🔥 **不拿 `InboxDirectories` 当收窄开关**：那是**写**的设置，让"写"顺带把"读"掐掉
  是一条没人猜得到的隐式耦合 —— 而本次事故的根子恰恰是"两处语义悄悄分叉"。
- 盘符枚举收进 **唯一实现 `TransferPaths.DriveRoots()`**，`TransferBrowseService` 改为调用它：
  **「浏览看得见」与「回传读得到」从此是同一集合、同一份代码**。
- **顺带修掉一个潜伏的致命缺陷**：`FileTransferMath.IsInside` 旧实现**无条件补一个尾分隔符**，
  而 `Path.TrimEndingDirectorySeparator` **刻意不裁根**（`C:/` 原样留下）⇒ 前缀变成 `C://` ⇒
  **任何把盘根写进白名单的配置都整盘失效**（"写了等于没写，且比没写更糟"）。
  `{状态目录}\inbox` 落在盘内所以一直没暴露，本次"可读 = 盘符根"才把它逼出来。

- `dotnet test`：**Core 845 + Agent 122 + 集成 396 = 1363，0 失败**；

## 十二、M4.19 修复：「下发到客户机的路径保存不了」（同日，第二轮）

用户原话：**「文件下发到客户机的路径无法保存的问题，保存后需要能看到具体路径」**。

### 12.1 根因（日志钉死，不是猜）

**点「记为此机默认目录」确实存进库了，但紧接着的那一次建单又把它抹掉了；
而"存进去了"在屏幕上毫无表现。** 两条链路各自都对，合起来是"保存成功、然后马上被删除"：

1. **前端 `DistributionPanel.onPathRemembered`**：只更新了 `remembered`（供**下次物化**用的覆盖层），
   没动**已经物化好的那一格** `targetDirs[id]` —— 而物化**只发生一次**
   （`watch(selectedIds)` 里的 `if (id in targetDirs) continue`）。勾选时这台机器还没记过 ⇒
   填的是空串 ⇒ **点完按钮屏幕上什么都不变**。
2. **后端 `DistributionsController.RememberPathsAsync`**：`EffectiveTargetDir ?? string.Empty`
   —— 一次**"存放路径留空"的建单把记忆写成空串**，等于**删掉运维刚存下的目录**。

**证据**（`C:/ProgramData/ControlServer/logs/log-2026-10-15.ndjson`）：
```
16:47:08 / 16:47:18 / 16:47:43  客户端默认目录已记忆（Id=11）      ← 连点三次（点了没反应）
16:47:49                        新建下发任务 #10 … 落地目录 (默认)   ← 输入框空 + 顺带把记忆写成 ""
18:28                           GET /api/agents ⇒ lastTargetDir = "" ← 记住的目录不见了
```

### 12.2 改法

- 前端：记住之后**把这一台那一格也填上**。⚠️ 不能无条件覆盖 ——
  只在该格为空、或它正好等于"记住之前那个记忆值"（= 没人动过）时才填。
- 后端：`?? string.Empty` → **`IsNullOrWhiteSpace(dir) ⇒ continue`**。
  🔥 **留空只是"这一次不定目录"，不该有删掉记忆的副作用。**

### 12.3 验证

1. **`Start-Process` 起的服务端会在工具调用结束时被回收**：我为了整体编译停掉了你原来的实例

## 十四、M5 方案 v3.1：**8K 是在役上限**，不是边缘情形（同日 18:51）

用户原话：**「v3 §0.4 需要注意，被控端的分辨率最高会达到 8K」**。
产出：`docs/M5-…方案.md` **就地升级为 v3.1**（新增 §0.5，改 §0.2/0.3/0.4/1.x/6.x/7.3/13/14/16）。

### 14.1 🔥 本轮最重要的发现（联网核实，官方数据）

**v3 把 8K 写成「贴 8192 上限 ⇒ 仅 HEVC ⇒ 可用」，漏了一个致命区别：**

> **8192×8192 是「分辨率上限」，不是「吞吐上限」。**

- **NVIDIA 官方 FFmpeg 文档**原文：`8K60 … **may require multiple NVENC engines with split encoding** for real-time performance`；
  还给了 8K60 直播示例（`-preset p3 -tune hq -rc cbr -b:v 100M -split_encode_mode forced`）、**显存 ≥ 8 GB**、码率 **80–150 Mbps**。
- **实测（arXiv 论文）**：单引擎 Pascal **27 fps** @8K P1；双引擎 GTX 1070/1080Ti 单流 30–32 fps，**开 2-way SFE 才 62 fps**；
  Blackwell RTX PRO 6000 + SFE **125 fps**。
- ⇒ **消费级唯一明确路径 = Ada 双 NVENC（AD104-400 / AD103 / AD102，即 4070 Ti Super 及以上）**。
  **4060 / 4070 是单引擎（AD107/AD106/AD104-250）⇒ 8K60 不成立。**
  **Ampere（含 3090）虽是双引擎，但 SFE 仅 Ada 支持 ⇒ 单流仍不超单引擎能力。**
- 🔸 **反直觉坑**：NVIDIA 新 **UHQ 调优模式会让 8K 吞吐崩**（8K P1：48→55 fps），因为把帧交给 SM 做 RD 优化、**串行化饿死 NVENC** ⇒ **8K 路径必须固定 p1–p3 + SFE**。

### 14.2 🔥 第二处升级：Chromium **没有 HEVC 软解**（v3 只说「需实测」）

- **Chromium 出于专利原因，FFmpeg 解码白名单里只有 H.264**；HEVC 走 `enable_platform_hevc`，注释写「实际解码由平台提供」。
- ⇒ `isConfigSupported({codec:'hvc1…', hardware_preference:'prefer-software'})` **对 HEVC 返回 false**；
  **硬件不支持＝没有兜底＝彻底不可用**（与 VP9/AV1 有软解可退不同）。
- Edge 在 Windows 走 MF，**解 H.265 需装「HEVC 视频扩展」**，且有输出帧尺寸错误的 bug。
- 第三方实测支持率（`hev1.2.4.H180.B0` = Main10 **L6/8K 档**）：**Chrome/Win ≈84%、Edge/Win ≈56%、Firefox ≈0%**。
- ⇒ 我们前端主路径是 Chrome/Edge（决策 13）⇒ **Firefox 可直接不管**，但要在帮助文档写明。

| §0.4 验收 | 一句话「原生分辨率 @60fps」 | **拆两条**：保底 = **4K60 ≤100 ms**；上限 = **8K 覆盖但帧率由硬件定** |

**① 拍板**：§1.3 的 **路径 B**（托盘抓屏+编码 → 新流式管道 → 服务 → 复用已有 SignalR）。
两条推论都来自"命名管道默认 DACL"这一条事实：

  码流是持续几十秒到几小时的长连接 —— 塞进去会让"超时"的语义彻底变味。

**② 写代码时踩到/修掉的四个真 BUG（都不是编译错误）**
| 症状 | 根因 | 修法 |
|---|---|---|
| 客户端常量 `PushRemoteFrame`/`ReportRemoteSession` **声明了、服务端却没实现** | 常量加在 `AgentHubClientMethods`，`AgentHub` 上没写方法 ⇒ **编译能过，只有真跑才炸**（帧全丢） | 补上两个方法；`HubContractArityTests` 钉住 |
| 会话卡在 `requested` ⇒ **该机器再也建不了新会话** | `Sweep` **刻意跳过 requested**（"那时没帧正常"）⇒ 一次失败变永久故障 | 加 `RequestedTimeout = 20s`；超时按"指令可能压根没到"收场 |
| **中心已收掉的会话在被控端一直空转** | 抓屏失败策略是"永远重试"（为锁屏/UAC/热插拔）；但"屏不存在"**永远不会好**；中心收会话时**不下发停止**（账本不碰网络）⇒ 循环没人叫停 | 加 `StartupFrameBudget = 30s`：**一帧都没产出过**就收场（判据是"从没出过帧"而非"连续失败次数"，后者会误杀"跑一小时中途锁屏"） |
| `LastFrameBytes` 是 `int`、字段写成 `long` | CS1503 | 字段改 `int`（单帧封在 512 KB 内） |

**③ 三个"顺序"是被刻意定死的（反了就是难查的故障）**
- 🔥 **建会话：先登记账本、再下发指令** —— 反过来，被控端可能**快过**中心登记，
  第一帧与 `streaming` 一起被判成"会话不存在"丢掉 ⇒ **画面永远不出来、两边日志都正常**。
- 🔥 **停会话：先下发停止、再关账本**（与建相反）—— 反过来那最后一帧/`stopped` 会撞上"会话不存在"。
- 🔥 **`Entry.StartFanout` 在登记那一刻就挂**，不是"第一帧到了再挂" ——
  晚挂的窗口里写进容量 1 队列的帧会一直躺着没人读（第一帧永远出不去，直到被第二帧顶掉）。

**④ 真机自检数字（`GdiCaptureSmokeTests`，本机 UHD620+MX250，单屏 2160×1440）**
```
抓帧 BGRA 12150 KB（跨距 8640）→ 编码 1920×1280 / JPEG 189 KB → base64 253 KB / 上限 512 KB
12 fps ⇒ 约 17 Mbps
```
⇒ 把两条设计约束从"推断"变成"实测"：**原始帧绝不可能过管道**（12 MB×12fps≈145 MB/s）；
**MJPEG 只能在 1080p 级**（已用掉上限 49%；4K 约 675 KB base64 ⇒ **直接超 512 KB**，
超限后果不是"糊一点"而是**整条消息被丢弃 ⇒ 画面彻底停住**）。
**另一个实测**：虚拟桌面**只在多屏时**才枚举（单屏请求 `virtual-desktop` 抛"找不到屏"——
刻意如此），我第一版用例就断言错了，被真机自检抓出来。

**⑤ 前端**：新增 `RemoteDesktopPanel.vue`（canvas 渲染，`Image` 解码→`drawImage`，**为 M5.4 换 `VideoDecoder` 留位**）；

## 第四批 ✅ M5.2 输入回传全链路（本轮：浏览器 → 中心 → 客户机服务 → 托盘 → SendInput）

> 与 M5.1 那条**完全对称、方向相反**，而且是**第二条独立管道**。
> 交付口径：**两道独立闸门**（中心会话级开关 **默认关** ＋ 被控机本机否决，中心无法覆盖）。
> 用户授权："按 5 点自行取默认值直接实现并跑全量验证，事后把取舍列出来复核"。

**① 五个取舍（已写进清单 §5.4.1，供复核）**

| # | 取舍 | 定为 | 代价 / 何时反过来 |
|---|---|---|---|
| ① | 管道复用 or 新开 | **新开第二条反向管道**（服务写、托盘读） | 同流双向写会读到**另一方向的半句话**（垃圾/卡死，两边日志都正常）。多一条管道，离瓶颈极远 |
| ② | 被控端能否本地否决 | **能**：标记文件 `remote-input.deny`（**存在＝禁止**，空文件即可） | 现场要手建一个文件。要界面就落在**本机配置页**（服务写、托盘读**同一个文件**，零新协议） |
| ③ | 中心开关默认值 | **默认关**，且**会话级** | 每开一路都要点一次 —— 这正是要的（决策 11 只管"谁能看画面"） |
| ④ | 坐标怎么传 | **归一化 0–65535，分母＝尺寸−1**，托盘换像素 | 多一层数学，且**错了在开发机上看不出来** ⇒ 必须靠用例，见下 |
| ⑤ | 合批与合并 | 移动 **16 ms 合批＋相邻只留后一条**；**其余三类一条不丢** | 前后端两套缓存 ⇒ 规则必须**逐字一致**；极端拥塞时轨迹略糙 |

**② 六条"写错了也不会报错"的坑（全部落在注释里）**
- **`INPUT` 必须 `LayoutKind.Explicit` 联合体**：否则 `cbSize` 校验失败、`SendInput` **静默返回 0**；
- **`MOUSEEVENTF_ABSOLUTE` 必须配 `VIRTUALDESK`**：缺它时 0–65535 只映射到主显示器，而**单屏机上两者完全一致** ⇒ 开发机测不出；
- **归一化分母是 `尺寸−1`**：用"尺寸"时**最右/最下一列永远点不到** —— 1080p 下差不到 1 像素（没人发现），**8K 下是 30+ 像素宽的一整条边**；
- **`SendInput` 返回值必须看**：0 = 被 UAC 安全桌面 / 完整性级别拦住；不看就等于把"被系统拦住"当"点下去了"；
- **屏幕 `Left`/`Top` 偏移**：单屏机恒为 0 ⇒ 忘了加在开发机上永远是对的，**多屏机整体错位**；
- **`ReleasePressedKeys` 必须有**：中心可能在"按下 Ctrl"与"抬起 Ctrl"之间断掉 ⇒ 那个键在被控机**永久按着**，而**在被控机画面上看不出来**。前端同样有一套（修饰键跟踪 + `blur`/切会话/关闸门时强制松开）。

**③ 前端坐标换算的坑（本轮自查发现并修掉）**
`toNormalized` 一开始想直接用 canvas 元素框 —— **不行**：`object-fit: contain` 会在元素框里居中留边，
`fit` 模式下元素框比画面大 ⇒ 坐标原点对不上（"鼠标整体偏一点"）。
改成**按 `contain` 的语义手动算**（`naturalAspect` vs `boxAspect` → 求实际绘制矩形 → 去 letterbox），
`fit` 与 `1:1+滚动条` 两种情况都自然正确。

**④ 顺手清掉的两处"拿别的码顶包"**
`RemoteErrorCodes.NotImplemented` 曾被"请求体为空"借用（看起来像"功能没做"），
新的 `input/enabled` 端点初稿又把同一句话归成 `InputNotEnabled`（看起来像"闸门没开"）。
两句都把人引向**完全错误的方向**。⇒ 新增 `RemoteErrorCodes.BadRequest` 并改掉这两处；
`NotImplemented` **保留**（M5.3–M5.5 还会有骨架期），只是不再有调用点。

**⑤ 本轮改掉的一条旧用例（必须改，它断言的东西已经不存在了）**
`RemoteDesktopApiTests.Input_relay_is_honestly_not_implemented` 断言 **501** —— M5.2 已接入，501 没有了。

必须比**响应体里的机器可读码**。⇒ 这就是"判端点别看状态码"那条纪律的由来。

> **"你正在看这一路"是唯一的资格条件，判据里不许出现"别人"**。

**① 改掉的语义（一句话）**
在"能看 / 能控"之外多了第三个条件：**你此刻正在看这一路**。
在此之前，一个**已经刷新过**的页面（不再收这一路的画面，却还揣着一条有效的 Cookie 连接）
也能把别人正在看的那一路打开控制。

**② 判断点被刻意收进一处**：`RemoteHub/RemoteWatchScope.IsWatching(watched, sessionId)`
—— 抽出来是为了能被**纯函数用例钉住**，以及将来做"一格看多路"时只有这一处要改
（`WatchedSessionKey` 的注释里早就预告了那个变更点）。

**③ 顺手清掉两处"一个码说两件事"**
- `SendInput` 原来拿 `SessionNotFound` 说"你不在看这一路" ⇒ 新增 `RemoteErrorCodes.NotWatching`；
  前端 `describeInputFailure` 里那两句文案也拆开了（它们曾共用一句）。
- `SetInputEnabled` 原来返回 `RemoteSessionDto?`，那个 `null` 同样说不清两种拒绝 ⇒ 改为**回执**。

**④ 又一处"写错了也不会报错"**
前端 `invoke<T>` 的 `T` 是**断言式**的：服务端换了返回类型，TypeScript **不报错**。
症状是每次翻开关都弹一句"被拒"（字段对不上 ⇒ `ack.ok` 读成 `undefined`），而服务端日志一切正常。
⇒ `HubContractArityTests` 补了**返回类型**断言。

**⑤ 两处"靠客户端自觉"改成"服务端强制"**
- `Join` 现在**先把上一路退干净**（退组 ＋ 摘登记）。原来指望客户端先调 `Leave`，
  而客户端会忘（刷新 / 切标签 / 那次调用在路上丢了）—— 忘了是**双向**代价：
  一直收着上一路的高频帧，**且**还能往上一路送输入。
- `Leave` 现在只在"退的正好是当前那一路"时摘登记。原来无条件摘，
  而重发 / 重复调用会让它带着一个**已经不是当前那一路**的 Id 到 —— 会把**新**的登记误摘掉，
  症状是"刚切过去，点第一下就被拒"。

**⑥ 明确不做的（理由见清单 §3.5 ①）**
**不做"当前 N 人在看"**：那要中心维护一张"谁在看哪一路"的表，而有表就有漏水路径；
漏掉的后果是**计数漂高** —— 页面上永远显示"还有别人在看"，于是**没人敢操作**，比没有计数更坏。
⇒ 会话级语义 ＋ 页面上一句"这个开关是会话级的，多人同看请先约定谁上手"。
真要做排队，得先有**独占控制权**（谁抢到 / 超时归还 / 被抢占怎么提示），那是一次语义变更。

**⑦ 验收**
`RemoteWatchScopeTests` **新增 12 条**（正常路径 ＋ 空/null/大小写/前缀/前后空格十行 ＋
用反射钉住**"判据只有两个入参"**，即"多人同看都合格"）；`HubContractArityTests` 补返回类型断言。
编译 **0 警告 0 错误**；**全量 1442 用例 0 失败**（相关三组 38/38）；`npm run typecheck` 0 错误；前端产物已重发。

**⑧ ⚠️ 没做到**
"多人同时看一路"**没有自动化验证** —— 需要一个真 Hub ＋ 两条真连接，
而现有用例里**没有 SignalR 测试基建**（`HubContractArityTests` 走反射，不连 Hub）。
本批只把**判据**钉死了；`Join` 清上一路、`Leave` 不误摘新登记这两条**只在代码里**（有注释与理由）。
⇒ 要补的话是"引入 SignalR 测试基建"，比这一批大。

# 压测工具（M6.3）

> **一句话：起 N 台协议级假 Agent，把中心压到「100 台在线」的形态，出一份曲线报告。**

---

## 1. 它测什么、不测什么

| | 说明 |
|---|---|
| ✅ 测 | **中心**：100 路长连接、心跳/遥测落库、命令下发、1–2 路推流转发、CPU / 内存 / 延迟曲线 |
| ❌ 不测 | **被控端**：抓屏、硬编、真实码流。假 Agent 不抓屏也不编码 |
| ❌ 不测 | 浏览器解码开销（假观看端只数帧，不画） |
| ❌ 不测 | GC 次数 / GC 暂停（要 `dotnet-counters`，本工具不带） |

🔴 **不能拿这份报告承诺「100 台 4K 远控」。** 它只回答一件事：**中心这一侧会不会先垮。**

---

## 2. 怎么跑

```powershell
# Windows：20 台 1 分钟（冒烟）
.\run-loadtest.ps1 -Agents 20 -Minutes 1 -Tag smoke

# 带 L2 命令 + L3 一路推流
.\run-loadtest.ps1 -Agents 20 -Minutes 1 -CommandsPerMin 120 -Streams 1 -Tag smoke

# 100 台 30 分钟（M6.3 的验收口径）
.\run-loadtest.ps1 -Agents 100 -Minutes 30 -Ramp 10 -CommandsPerMin 600 -Streams 1 -Tag 100
```

```bash
# Linux / WSL
./run-loadtest.sh 20 1
AGENTS=100 MINUTES=30 RAMP=10 COMMANDS_PER_MIN=600 STREAMS=1 TAG=100 ./run-loadtest.sh
```

脚本自己会做四件事：**挑空闲端口 → 用临时数据目录起服务 → 等 `/healthz` → 压完停服删目录**。
报告固定落在 `deploy/loadtest/reports/`，**与你在哪个目录敲命令无关**（早先默认是相对 cwd 的 `reports`，
从仓库根跑一次就把报告撒到了仓库根 —— 已改成按程序集位置上溯定位）。

> ⚠️ 跑之前先 `dotnet build src/ControlServer.Server`（脚本不会替你编译中心）。

---

## 3. 为什么必须用「临时数据目录」

假 Agent 是**真的注册进库里**的。对现场库跑一轮，在线表里就会多出 N 台不存在的机器，
而且它们会一直显示"离线"——运维分不清哪台是真的。

脚本用 `%TEMP%\controlserver-loadtest-<时间戳>` 当数据目录，退出时删掉。
**别绕过脚本直接对着现场实例跑。**

---

## 4. 三档标准口径（M6.3 用同一套参数做对比）

| 档 | 台数 | 时长 | 爬坡 | L2 命令 | L3 推流 |
|---|---:|---:|---:|---:|---:|
| 小 | 20 | 3 min | 5 s | 120 条/分 | 1 路 32 KB × 30 fps |
| 中 | 50 | 3 min | 8 s | 300 条/分 | 同上 |
| 大 | 100 | 30 min | 10 s | 600 条/分 | 同上 |

命令速率按 **6 条/分钟·台** 递增 —— 每台的命令率恒定，规模线性放大，
这样三档之间的差异才只反映"台数"，而不是"命令给多了/给少了"。

## 5. 输出怎么读

每次跑出两个文件：

- `loadtest-<tag>-<时间>.md` —— 报告（结论表 + 分位 + 10 秒窗口序列 + 边界声明）
- `loadtest-<tag>-<时间>.csv` —— **逐秒**原始数据（可丢进 Excel / pandas 自己画）

几个容易读错的点：

| 现象 | 怎么读 |
|---|---|
| 心跳 P95 在几毫秒 | 正常。局域网 + 内存态应答，本来就该是个位数毫秒 |
| 内存先涨后落 | 正常。.NET 的 GC 会回收，看**末段是否持续上涨**而不是看峰值 |
| 推流"收到 < 发出" | 正常。中心转发队列是**容量 1 + 丢最旧**，看**到达率** |
| L2 "差 N 条" | 中心回了 200 但假机器没收到。`Command` 是**单向推送、无回执**，这是唯一的度量方式 |

### 三个会骗人的读数（都踩过）

1. **短轮次的"内存涨了 X%"**：本机光预热就要 60–90 秒，前 20% 的热身段不够长 ⇒
   3 分钟那轮报过 `+12.1%`，而同配置跑满 30 分钟是 `−5.8%`。**短于 5 分钟的轮次别看这一行。**
2. **"峰值在线"是假机器自报的**，不是中心侧连接表。中心被强杀时 TCP 不会立刻断，
   客户端要连败 3 次心跳（约 30 s）才判定断线 —— 那段时间报告仍显示"满员"，而中心其实已经空了。
3. **CPU/内存按启动时那个 PID 采**：中心中途重启后，后面几段是 `—`（采不到），不是"占用 0"。

### 跑完想量库体积

```bash
python _dbsize.py <临时数据目录>/control.db
```

只读打开，按表/索引分摊（`dbstat`），输出行数与 MB —— 用来算"100 台跑满 30 天库会多大"。
⚠️ **想量准就等停服之后再读**（本报告的数字都是停服后量的）：服务在跑时读到的是"那一刻的快照"，
而 `-wal` 里还没 checkpoint 的部分算不算进去，取决于连接参数 —— 同一个库能读出两个不一样的数。

## 6. 断线恢复专项（手工，一次约 4 分钟）

这是 **M6.4 升级回滚的前置验证**：中心停一停再起来，100 台能不能自己回来。
脚本没有开关（中途杀进程这件事脚本不好编排），手工做：

1. 起 100 台，**只测 L1**：`--commands-per-min 0 --streams 0`
   （重启后管理员 Cookie 会话会失效 ⇒ L2 会全 401，数据就脏了）；
2. 进度行跑到"在线 100/100"后，**直接杀掉中心进程**，等 **25–30 秒**；
3. 用**同端口、同数据目录**重启（模拟升级后启动）；
4. 看报告的**重连累计数**与在线数时间序列。

参考读数（i5-8265U 实测）：

- 停服 26 秒 ⇒ 每台攒够 **3 次心跳失败**才判定断线 ⇒ 累计 `fail = 台数 × 3`（100 台 = 300，正好对上）；
- 中心起来后 **约 20 秒内 100 台全部回位**（退避 1→2→4→8→10 s，同时重连不挤爆）；
- ⇒ **升级窗口内"指令不可达"最坏 ≈ 停服时长 + 30 s（察觉）+ 20 s（回位）**。

## 7. 已知限制

1. **假帧是随机字节**：中心不解码只转发，对中心压力真实，但测不到解码；
2. **L3 起流由工具直接触发**，不等假 Agent 收到 start 命令（真 Agent 还有挑屏 + 建编码器的延迟，那段是被控端的成本）；
3. **不自动模拟断网重连**：`--agents` 那一轮不会主动踢连接，所以"重连 0 次"是**没测**、不是**稳**。
   要测就按 §6 手工做（已有一轮证据：100/100 全部恢复）；
4. **客户端不需要配接收上限**：`MaximumReceiveMessageSize` 只存在于服务端（SignalR 8.0.10 客户端程序集里没有这个符号）；
5. **`run-loadtest.ps1` 未在能跑 PowerShell 原生 exe 的机器上端到端验过**（`.sh` 与分步命令都验过）；
6. Linux / Docker 未在本轮覆盖。
